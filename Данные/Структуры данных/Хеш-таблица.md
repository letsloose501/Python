# Хеш-таблица

**Хеш-таблица** — структура данных, обеспечивающая поиск, вставку и удаление за $O(1)$ в среднем, независимо от числа элементов.

> **Аналогия:** гардероб с номерками. Называешь номер — получаешь пальто мгновенно, без перебора вешалок.

В Python хеш-таблица — это `dict` и `set`. АТД поверх неё — [Словарь](../../Данные/АТД/Словарь.md), [Множество](../../Данные/АТД/Множество%20и%20кортеж.md).

---

## Как работает

### Хеш-функция

Ключ → **хеш-функция** → целое число → индекс в массиве.

```
hash("name") = 8923476
8923476 % 8 = 4   →   массив[4] = "Иван"

поиск d["name"]:
  hash("name") % 8 = 4   →   массив[4]   →   "Иван"
```

Доступ — это два вычисления и одно обращение к массиву, а не перебор. Поэтому $O(1)$.

### Требования к хеш-функции

- **Детерминированность** — одинаковый ключ → всегда одинаковый хеш
- **Равномерность** — хеши распределены по всему диапазону
- **Скорость** — быстро вычисляется

### Хешируемость

Хешировать можно только **неизменяемые** объекты. Если объект изменится после вставки — его хеш изменится, и он потеряется в таблице.

```python
hash(42)           # → 42
hash("hello")      # → число (меняется между запусками Python для строк)
hash((1, 2, 3))    # → число
hash([1, 2])       # TypeError: unhashable type: 'list'
hash({"a": 1})     # TypeError
```

Хешируемы: `int`, `float`, `str`, `bool`, `tuple` (если элементы хешируемы), `frozenset`. Нехешируемы: `list`, `dict`, `set`.

## Коллизии

Два разных ключа дали один индекс — **коллизия**. При достаточном числе элементов неизбежна (принцип Дирихле).

### Цепочки (Separate Chaining)

В каждой ячейке — **связный список** всех пар с этим индексом.

```
индекс 4: → ("name", "Иван") → ("nickname", "ваня") → None
```

### Открытая адресация (Open Addressing)

Отдельных списков нет — всё лежит в самом массиве. При коллизии ищем следующую свободную ячейку по фиксированному правилу (**зондирование**).

- **Линейное зондирование**: `i+1`, `i+2`, `i+3`… — просто, но занятые ячейки слипаются в длинные кластеры;
- **Квадратичное зондирование**: `i+1`, `i+4`, `i+9`… — кластеризации меньше.

**Удаление здесь — отдельная проблема.** Просто очистить ячейку нельзя: она стоит посреди чужой цепочки проб, и поиск, наткнувшись на пустоту, решит, что дальше искать нечего, и не найдёт лежащий за ней ключ.

```
кладём A (индекс 4), B тоже метит в 4 → уезжает в 5

[_][_][_][_][A][B][_]
удалили A, просто обнулив ячейку:
[_][_][_][_][_][B][_]
ищем B: идём в 4 → пусто → «B в таблице нет» 💀
```

Поэтому удалённую ячейку помечают **надгробием** (tombstone) — «здесь было занято, иди дальше». Поиск через них проходит, вставка может их переиспользовать. Накопившиеся надгробия захламляют таблицу и убираются при следующем расширении.

> **Как это сделано в Python.** `dict` — открытая адресация с таблицей размера $2^i$, где начальный индекс берётся как младшие `i` бит хеша. Дальше идёт не линейная проба, а рекуррента `j = 5*j + 1 + perturb`, где `perturb` — сдвигаемый на 5 бит остаток хеша. Смысл в комментариях CPython объяснён прямо: линейное зондирование «смертельно», потому что порядок проб совпадает с порядком, в котором обычно приходят подряд идущие ключи; а `perturb` постепенно подмешивает в пробу **старшие** биты хеша, которые иначе просто отбрасывались бы.

### Что выбрать

| | Цепочки | Открытая адресация |
|---|---|---|
| Где лежат данные | во внешних списках | в самом массиве |
| Заполнение > 1 | переживает (цепочки растут) | невозможно физически |
| Cache locality | плохая — прыжки по памяти | отличная — соседние ячейки |
| Удаление | тривиальное | надгробия |
| Память | +указатели на каждый узел | компактно, но нужен запас |

Цепочки проще и терпимее к плохой хеш-функции; открытая адресация быстрее на практике из-за попадания в кэш процессора, но требует держать заполнение низким и аккуратно удалять. Промышленные реализации (`dict` в Python, `HashMap` в Java) выбирают второй путь.

## Размер таблицы: простое число или степень двойки

Индекс получают как `hash(key) % N`, и от выбора `N` напрямую зависит, насколько ровно лягут ключи.

**Почему советуют простое число.** Если `N` делит общий множитель с закономерностью в ключах, часть корзин выпадает из игры. Крайний случай — `N = 2`:

```
все чётные ключи  → корзина 0
все нечётные      → корзина 1
```

Половина таблицы пустует, вторая вырождается в один длинный список — то есть в $O(n)$. При `N = 10` тот же эффект дадут ключи, кратные десяти. Простое число не делит такие закономерности и «размазывает» даже неудачные ключи — поэтому классические реализации с цепочками берут `N` простым (997, 1021 и т.п.).

**Почему на практике берут степень двойки.** Взятие остатка — деление, одна из самых дорогих операций процессора. Если `N = 2^i`, то `hash % N` заменяется на `hash & (N - 1)` — просто отбрасывание старших бит, на порядок дешевле. Расплата: индекс определяется **только младшими битами** хеша, и любая закономерность в них бьёт напрямую.

> Обе стратегии рабочие, потому что решают одну задачу с разных концов: **простое число компенсирует слабую хеш-функцию, степень двойки требует сильной**. Отсюда и выбор: Python и Java берут степень двойки, но не полагаются на голые младшие биты — Python подмешивает старшие через `perturb` в пробу, Java перед маскированием делает `hash ^ (hash >>> 16)`. Если хеш-функция хорошая, размер таблицы на распределение уже не влияет.

Для учебной реализации на цепочках проще взять простое число: оно прощает наивную хеш-функцию вроде `key % N`.

## Коэффициент заполнения

`занятые / всего`. При превышении ~⅔ — таблица **расширяется вдвое**, все элементы перехешируются.

```
[_][A][_][B][_][C][_][_]   → 3/8 = 0.375  норма
добавляем до 6/8 = 0.75    → расширение:
[_][A][_][B][_][_][C][_][_][_][_][_][_][_][_][_]   (16 ячеек)
```

Расширение — $O(n)$, но случается редко. Амортизированная стоимость операций — $O(1)$.

---

## Сложность

|Операция|Средний случай|Худший случай|
|---|---|---|
|Поиск|$O(1)$|$O(n)$|
|Вставка|$O(1)$|$O(n)$|
|Удаление|$O(1)$|$O(n)$|

Худший случай — все ключи в одной ячейке (плохая хеш-функция или атака). На практике при хорошей функции не встречается.

## Реализация

```python
class HashTable:
    def __init__(self, capacity=8):
        self._capacity = capacity
        self._size = 0
        self._buckets = [[] for _ in range(capacity)]   # цепочки

    def _index(self, key):
        return hash(key) % self._capacity

    def _load_factor(self):
        return self._size / self._capacity

    def _resize(self):
        старые = self._buckets
        self._capacity *= 2
        self._size = 0
        self._buckets = [[] for _ in range(self._capacity)]
        for цепочка in старые:
            for k, v in цепочка:
                self.set(k, v)

    def set(self, key, value):
        if self._load_factor() > 0.7:
            self._resize()
        i = self._index(key)
        for j, (k, v) in enumerate(self._buckets[i]):
            if k == key:
                self._buckets[i][j] = (key, value)   # обновить
                return
        self._buckets[i].append((key, value))
        self._size += 1

    def get(self, key, default=None):
        i = self._index(key)
        for k, v in self._buckets[i]:
            if k == key:
                return v
        return default

    def delete(self, key):
        i = self._index(key)
        for j, (k, v) in enumerate(self._buckets[i]):
            if k == key:
                self._buckets[i].pop(j)
                self._size -= 1
                return
        raise KeyError(key)

    def __setitem__(self, key, value):   # d[key] = value
        self.set(key, value)

    def __getitem__(self, key):          # d[key]
        i = self._index(key)
        for k, v in self._buckets[i]:
            if k == key:
                return v
        raise KeyError(key)

    def __delitem__(self, key):          # del d[key]
        self.delete(key)

    def __contains__(self, key):         # key in d
        return self.get(key, _M := object()) is not _M

    def __len__(self):
        return self._size

    def __iter__(self):                  # for k in d
        for цепочка in self._buckets:
            for k, _ in цепочка:
                yield k

    def __repr__(self):
        return f"HashTable({{{', '.join(f'{k!r}: {self[k]!r}' for k in self)}}})"


ht = HashTable()
ht["name"] = "Иван"
ht["age"] = 25
print(ht)              # → HashTable({'name': 'Иван', 'age': 25})
print(ht["name"])      # → Иван
print("age" in ht)     # → True
del ht["age"]
print(len(ht))         # → 1
```

## Хешируемый объект

Чтобы использовать объект как ключ — реализовать `__hash__` и `__eq__`. Правило: `a == b` → `hash(a) == hash(b)`.

```python
class Точка:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __eq__(self, other):
        return self.x == other.x and self.y == other.y

    def __hash__(self):
        return hash((self.x, self.y))   # делегируем хешу кортежа


карта = {Точка(0, 0): "старт", Точка(1, 0): "вправо"}
карта[Точка(0, 0)]   # → "старт"
```

> Если определяешь `__eq__` без `__hash__` — Python автоматически убирает `__hash__`, объект становится нехешируемым.

## set — хеш-таблица без значений

`set` устроен как `dict`, только хранит ключи без значений. Операция `x in set` — $O(1)$ vs $O(n)$ у `list`.

```python
s = {1, 2, 3}
3 in s          # O(1)
3 in [1, 2, 3]  # O(n)
```

Подробнее как АТД — [Множество](../../Данные/АТД/Множество%20и%20кортеж.md).

## Хеш-таблица vs Дерево поиска

| |Хеш-таблица|[BST (сбалансированный)](../../Данные/Структуры%20данных/Дерево.md)|
|---|---|---|
|Поиск|$O(1)$ средн.|$O(\log n)$|
|Худший случай|$O(n)$|$O(\log n)$|
|Порядок ключей|Нет|Отсортирован|
|Диапазонные запросы|Нет|Да|
|Требование к ключу|Хешируемый|Сравнимый|

Хеш-таблица — по умолчанию. Дерево — когда нужен порядок или диапазонные запросы.

## Комбинация с другими структурами

Слабость хеш-таблицы — **она не хранит никакого порядка**. Лечится не заменой структуры, а сложением: в словаре по ключу держат **указатель на узел** другой структуры, которая порядок как раз хранит.

- **Словарь + [двусвязный список](../../Данные/Структуры%20данных/Связный%20и%20двусвязный%20список.md#двусвязный-список)** → [LRU-кэш](../../Алгоритмы/Задачки/LRU-кэш.md): поиск за $O(1)$ от словаря, порядок использования и вытеснение за $O(1)$ от списка. Так устроены `OrderedDict`, `functools.lru_cache` и кэши в СУБД.
- **Словарь + [куча](../../Алгоритмы/Иные/Двоичная%20куча%20и%20очередь%20с%20приоритетом.md)** → очередь с приоритетом, где элемент можно найти и обновить, а не только снять минимум.

> Общий приём проектирования: если одна структура закрывает половину требований, а вторая — другую половину, их **соединяют указателями**, а не выбирают между ними. Стоимость — лишняя память на связи, выигрыш — обе операции за константу.
