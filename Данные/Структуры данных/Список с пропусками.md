# Список с пропусками

> _Отсортированный связный список с «экспресс-этажами» — те же $O(\log n)$, что у дерева, но без единого поворота_

---

**Список с пропусками** (skip list) — вероятностная структура данных: отсортированный [связный список](../../Данные/Структуры%20данных/Связный%20и%20двусвязный%20список.md), над которым надстроены дополнительные уровни-«экспрессы», пропускающие часть элементов. Высота, на которую поднимается каждый элемент, выбирается **случайно**. Придумал Уильям Пью в 1990 году как более простую замену сбалансированным деревьям.

---

## Проблема: список хранит порядок, но ищет линейно

Отсортированный связный список хорош тем, что порядок в нём поддерживается сам собой, а вставка в известное место стоит $O(1)$. Но чтобы **найти** это место, приходится идти от начала — $O(n)$.

```
1 → 2 → 5 → 7 → 8 → 10 → 11 → 12
                    ↑ чтобы дойти сюда, прошли всё
```

[Двоичное дерево поиска](../../Данные/Структуры%20данных/Дерево.md#двоичное-дерево-поиска-bst) решает это за $O(\log n)$, но платит сложностью: чтобы дерево не выродилось в список, нужны повороты и перекраска (АВЛ, красно-чёрное). Реализовать это правильно, а тем более сделать потокобезопасным — трудно.

---

## Идея: этажи-экспрессы

Над базовым списком надстраиваются уровни. На нижнем этаже — все элементы, выше — только часть, ещё выше — часть от части. Верхние этажи работают как экспресс-линии метро: проехал полпути одним прыжком, спустился, доехал по местной.

```
этаж 3:  1 ─────────────────────▶ 7 ────────────────▶
этаж 2:  1 ──────▶ 5 ───────────▶ 7 ──────▶ 10 ─────▶
этаж 1:  1 ─▶ 2 ─▶ 5 ─▶ 6 ──────▶ 7 ─▶ 8 ─▶ 10 ─▶ 12
```

**Поиск 9:** начинаем с верхнего этажа. `9 > 7` — идём вправо к 7; дальше на этом этаже конец, спускаемся. На втором этаже следующий — 10, а `9 < 10`, значит, нужное место левее: спускаемся. На первом этаже находим позицию между 8 и 10.

Логика ровно как у двоичного поиска: на каждом шаге отсекаем половину оставшегося.

**Вставка:** находим место, вставляем в нижний список, а затем **бросаем монетку** — с вероятностью ½ поднимаем элемент на этаж выше, и так пока выпадает «орёл». Никакой балансировки: высота регулируется случайностью.

Именно поэтому структура вероятностная: $O(\log n)$ здесь — **в среднем**, а не в худшем случае. Теоретически все монетки могут лечь неудачно и получится обычный список, но вероятность этого падает экспоненциально с ростом $n$.

## Реализация на Python

```python
import random

class Узел:
    def __init__(self, ключ, значение, высота):
        self.ключ = ключ
        self.значение = значение
        self.next = [None] * высота        # ссылка вперёд на каждом этаже

class СписокСПропусками:
    МАКС_ВЫСОТА = 16
    P = 0.5

    def __init__(self):
        self.head = Узел(None, None, self.МАКС_ВЫСОТА)   # фиктивная голова
        self.высота = 1

    def _бросить_монетку(self) -> int:
        # 1. высота нового узла: пока выпадает «орёл» — растём
        h = 1
        while random.random() < self.P and h < self.МАКС_ВЫСОТА:
            h += 1
        return h

    def _спуск(self, ключ) -> list:
        # 2. на каждом этаже запоминаем последний узел перед искомым местом
        путь = [self.head] * self.МАКС_ВЫСОТА
        узел = self.head
        for этаж in range(self.высота - 1, -1, -1):
            while узел.next[этаж] and узел.next[этаж].ключ < ключ:
                узел = узел.next[этаж]
            путь[этаж] = узел
        return путь

    def найти(self, ключ):
        кандидат = self._спуск(ключ)[0].next[0]
        return кандидат.значение if кандидат and кандидат.ключ == ключ else None

    def вставить(self, ключ, значение) -> None:
        путь = self._спуск(ключ)
        сущ = путь[0].next[0]
        if сущ and сущ.ключ == ключ:            # 3. ключ уже есть — обновляем
            сущ.значение = значение
            return

        h = self._бросить_монетку()
        self.высота = max(self.высота, h)
        новый = Узел(ключ, значение, h)
        for этаж in range(h):                    # 4. вшиваем на каждом своём этаже
            новый.next[этаж] = путь[этаж].next[этаж]
            путь[этаж].next[этаж] = новый
```

Как это читать: вся структура держится на `_спуск` — он собирает «путь», то есть последний узел перед нужным местом на каждом этаже. Поиск использует только нижний элемент пути, вставка — все, потому что новый узел нужно вшить в каждый этаж, до которого он дорос. Ни поворотов, ни перекраски, ни проверок баланса — в этом и смысл.

## Сравнение со сбалансированным деревом

| | **Список с пропусками** | **[АВЛ / красно-чёрное](../../Данные/Структуры%20данных/Дерево.md#самобалансирующиеся-деревья)** |
|---|---|---|
| Поиск, вставка | $O(\log n)$ **в среднем** | $O(\log n)$ **гарантированно** |
| Балансировка | случайная высота, ничего не перестраивается | повороты и перекраска |
| Сложность кода | десятки строк | сотни строк, легко ошибиться |
| Конкурентный доступ | простой: правки локальны | трудный: поворот трогает целое поддерево |
| Диапазонный запрос | пройти по нижнему этажу | обход in-order |

Главная строка здесь — **конкурентный доступ**. При повороте дерева меняется структура целого поддерева, и его надо блокировать; вставка в skip list трогает только соседние ссылки на нескольких этажах. Поэтому там, где нужны параллельные записи, скип-лист часто выигрывает не асимптотикой, а простотой синхронизации.

## Где применяется

- **RocksDB** — memtable по умолчанию именно скип-лист, и это **единственная** его реализация memtable, поддерживающая конкурентную вставку. Нужны и упорядоченность (чтобы сброшенный SSTable уже был отсортирован), и параллельная запись — скип-лист даёт то и другое.
- **[Redis](../../Библиотеки/Сторонние/Redis.md)** — Sorted Set (`ZADD`, `ZRANGE`) реализован парой «хеш-таблица + скип-лист»: хеш даёт доступ к элементу по значению, скип-лист держит порядок по score и обслуживает диапазонные запросы.
- **LevelDB, Apache Lucene** — те же задачи упорядоченного хранения в памяти.

## Ловушки

- **Ждать гарантий худшего случая.** Их нет: структура вероятностная. Для систем реального времени с жёстким дедлайном это может быть неприемлемо.
- **Забыть про генератор случайных чисел.** Плохой или предсказуемый источник случайности ломает распределение высот, а с ним и асимптотику.
- **Экономить память на маленьких данных.** У скип-листа накладные расходы на указатели (в RocksDB — около 1,33 указателя на элемент). На сотне элементов проще отсортированный [массив](../../Данные/Структуры%20данных/Массив.md).
