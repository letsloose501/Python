# datetime

> _Дата — не строка и не число: у неё своя арифметика, и `datetime` знает про високосные годы и переносы месяцев._

---

**datetime** — модуль для работы с датами и временем: получить текущий момент, вычислить разницу, прибавить дни, разобрать и отформатировать. Считать даты «руками» (через дни и остатки) — источник ошибок; `datetime` берёт на себя високосные годы, разную длину месяцев и границы суток.

Зачем на бэкенде: метки времени в БД и логах, вычисление сроков (TTL, дедлайны), разбор дат из запросов. На контесте встречаются задачи «сколько дней между датами», «какой день недели».

## Четыре типа

| Тип | Что хранит | Пример |
|---|---|---|
| `date` | год, месяц, день | `2026-07-06` |
| `time` | часы, минуты, секунды | `14:30:00` |
| `datetime` | дата + время вместе | `2026-07-06 14:30` |
| `timedelta` | **промежуток** времени | `5 days, 2:00:00` |

## Получить «сейчас»

```python
from datetime import date, datetime

date.today()        # → 2026-07-06         только дата
datetime.now()      # → 2026-07-06 14:30:05.123   дата и время
```

Собрать конкретную дату: `date(2026, 7, 6)`, `datetime(2026, 7, 6, 14, 30)`.

## Арифметика через timedelta

Разность двух дат даёт **`timedelta`**; прибавление `timedelta` сдвигает дату. Границы месяцев и високосность — автоматически.

```python
from datetime import date, timedelta

d1 = date(2026, 7, 6)
d2 = date(2026, 12, 31)

(d2 - d1).days              # → 178   сколько дней между датами
d1 + timedelta(days=30)     # → 2026-08-05   (перескок через июль корректный)
d1 + timedelta(weeks=2)     # → 2026-07-20
```

## День недели

```python
date(2026, 7, 6).weekday()      # → 0   понедельник=0 … воскресенье=6
date(2026, 7, 6).isoweekday()   # → 1   понедельник=1 … воскресенье=7
```

> На отборах любят условие «неделя начинается с понедельника» — это ровно `weekday()`, где 0 = понедельник.

## Строка ↔ дата: strftime и strptime

**`strftime`** (date → строка) и **`strptime`** (строка → date) работают по кодам формата.

```python
from datetime import datetime

dt = datetime(2026, 7, 6, 14, 30)
dt.strftime("%d.%m.%Y %H:%M")             # → '06.07.2026 14:30'   (formaT → строка)
datetime.strptime("06.07.2026", "%d.%m.%Y")   # → datetime(2026,7,6)  (Parse ← строка)

dt.isoformat()                            # → '2026-07-06T14:30:00'  стандарт ISO 8601
```

Коды: `%Y` год (4 цифры), `%m` месяц, `%d` день, `%H` часы, `%M` минуты, `%S` секунды. Мнемоника: str**f**time — **f**ormat (наружу), str**p**time — **p**arse (внутрь).

## Ловушка: наивное и осознанное время

По умолчанию `datetime` **наивный** — не знает свой часовой пояс. Для серверов и хранения в БД используют **осознанное** время в UTC:

```python
from datetime import datetime, timezone
datetime.now(timezone.utc)      # осознанное время в UTC
```

> Смешивать наивное и осознанное время нельзя — вычитание бросит `TypeError`. На бэкенде правило: хранить и считать в UTC, показывать в локальном.

## Именованные часовые пояса: zoneinfo и pytz

`timezone.utc` — только фиксированное смещение. Для настоящих поясов («Москва», «Нью-Йорк») нужна **база IANA** (tz database) — она знает и смещение, и правила перехода на летнее время. Доступ к ней дают два инструмента:

| | **`zoneinfo`** (stdlib, 3.9+) | **`pytz`** (сторонний, legacy) |
|---|---|---|
| Откуда | встроен ([PEP 615](https://peps.python.org/pep-0615/)) | `pip install pytz` |
| Привязка пояса | `datetime(..., tzinfo=ZoneInfo("..."))` | **только** через `tz.localize(...)` |
| Статус | рекомендуемый в новом коде | устаревает, но ещё всюду в старом |

### zoneinfo — современный способ

```python
from datetime import datetime
from zoneinfo import ZoneInfo

# осознанное время сразу в нужном поясе
dt = datetime(2026, 7, 6, 15, 0, tzinfo=ZoneInfo("Europe/Moscow"))
dt                                   # → 2026-07-06 15:00:00+03:00

# конвертация в другой пояс — astimezone
dt.astimezone(ZoneInfo("America/New_York"))   # → 2026-07-06 08:00:00-04:00

# текущее время в поясе
datetime.now(ZoneInfo("Europe/Moscow"))
```

> На Windows базы tz в системе может не быть — поставь пакет `tzdata` (`pip install tzdata`), `zoneinfo` подхватит его автоматически.

### pytz — почему нельзя через tzinfo=

У `pytz` **другой контракт**: передавать его пояс прямо в `datetime(tzinfo=...)` **нельзя** — вернётся историческое смещение (LMT, для Москвы «+2:30»), а не текущее. Правильно — метод `localize` для наивного времени и `astimezone` для конвертации:

```python
import pytz
from datetime import datetime

tz = pytz.timezone("Europe/Moscow")

# ПРАВИЛЬНО — привязать пояс к наивному времени
dt = tz.localize(datetime(2026, 7, 6, 15, 0))     # → 2026-07-06 15:00:00+03:00

# НЕПРАВИЛЬНО — даёт LMT-смещение +02:30
dt_bad = datetime(2026, 7, 6, 15, 0, tzinfo=tz)   # ловушка pytz

# конвертация
dt.astimezone(pytz.timezone("America/New_York"))
```

Именно из-за этой ловушки `localize` `zoneinfo` и вытеснил `pytz` в стандартной библиотеке — со `zoneinfo` привязка работает очевидным `tzinfo=`.

> **Правило бэкенда:** хранить и считать в **UTC** (`datetime.now(timezone.utc)`), а в пояс пользователя переводить только на выводе — одним `astimezone`. Так летнее время и разница поясов не путаются в расчётах.
