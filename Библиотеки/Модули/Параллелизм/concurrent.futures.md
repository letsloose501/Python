# concurrent.futures

> _Один интерфейс на потоки и процессы: написал код раз — а чем его крутить, потоками или процессами, решаешь сменой одного класса._

---

**concurrent.futures** — высокоуровневая обёртка над [потоками](../../../Библиотеки/Модули/Параллелизм/threading.md) и [процессами](../../../Библиотеки/Модули/Параллелизм/multiprocessing.md). Вместо того чтобы вручную создавать `Thread`/`Process`, звать `start`/`join` и собирать результаты через очереди, ты отдаёшь функции **пулу рабочих** и получаешь на каждую **Future** — обещание результата. Один и тот же код работает и на потоках, и на процессах — меняется лишь класс исполнителя.

Зачем: запускать пачку задач конкурентно **малой кровью** — без ручной оркестровки потоков/процессов, с готовым сбором результатов и прозрачным пробросом исключений.

## Проблема: сырые Thread и Process — это много ручной работы

С голым [threading](../../../Библиотеки/Модули/Параллелизм/threading.md) приходится самому создавать потоки, дожидаться их, а результат складывать в общую структуру под замком или в [очередь](../../../Библиотеки/Модули/Параллелизм/queue.md):

```python
from threading import Thread

результаты = []
def работа(x):
    результаты.append(x * x)          # общий список — нужна синхронизация, легко словить гонку

потоки = [Thread(target=работа, args=(i,)) for i in range(10)]
for t in потоки: t.start()
for t in потоки: t.join()             # руками стартуем и ждём каждый
```

`concurrent.futures` прячет всю эту рутину: пул сам управляет рабочими, а результат возвращается напрямую — никаких общих списков и ручного `join`.

## Два исполнителя (Executor)

**Executor** — пул рабочих с единым API. Реализаций две, интерфейс у них **одинаковый** — в этом вся идея:

| Исполнитель | Рабочие | Для чего |
|---|---|---|
| **`ThreadPoolExecutor`** | потоки (общий GIL) | I/O-bound: сеть, диск, БД |
| **`ProcessPoolExecutor`** | процессы (свой GIL у каждого) | CPU-bound: вычисления на всех ядрах |

Переключение между ними — это замена **одного слова**:

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

# для ожидания сети — потоки:
with ThreadPoolExecutor() as ex:  ...
# для тяжёлых вычислений — процессы (тот же код ниже):
with ProcessPoolExecutor() as ex: ...
```

Почему так: потоки и процессы решают разные задачи (см. GIL), но управляются одинаково — поэтому и API общий.

> **Число рабочих по умолчанию.** `ThreadPoolExecutor` → `min(32, cpu + 4)` (потоки дешёвые, их можно много). `ProcessPoolExecutor` → число ядер (на Windows не больше 61). Явно задаётся параметром `max_workers`.

## submit + Future — запустить задачу и получить обещание

**`submit(fn, *args)`** ставит вызов `fn(*args)` в очередь пула и **сразу** возвращает объект **`Future`** — «результата ещё нет, но он будет здесь».

```python
from concurrent.futures import ThreadPoolExecutor

def загрузить(url):
    ...                                   # операция с ожиданием (сеть)
    return len(url)

with ThreadPoolExecutor(max_workers=4) as ex:
    future = ex.submit(загрузить, "https://ya.ru")   # ушло в пул, не блокирует
    print(future.done())                             # → False (ещё считается)
    print(future.result())                           # → 12  (.result() ЖДЁТ готовности)
```

**`Future`** — «обещание» результата. Основные методы:

| Метод | Что делает |
|---|---|
| `.result(timeout=None)` | вернуть результат; **блокирует**, пока не готов; **перебрасывает** исключение задачи |
| `.done()` | завершена ли (успех, ошибка или отмена) |
| `.exception()` | вернуть исключение задачи (или `None`) |
| `.cancelled()` | была ли отменена |
| `.add_done_callback(fn)` | вызвать `fn(future)`, когда задача завершится |

## map — параллельный map, результаты по порядку

Когда нужно применить функцию к списку — **`map`** короче, чем `submit` в цикле. Он раздаёт элементы по рабочим и возвращает результаты **в порядке аргументов** (не в порядке готовности):

```python
with ThreadPoolExecutor() as ex:
    for длина in ex.map(загрузить, urls):     # запускает все, отдаёт по порядку
        print(длина)
```

Отличие от `submit`: `map` проще, но отдаёт результаты строго по порядку — первый медленный элемент задержит выдачу остальных.

## as_completed — обрабатывать по мере готовности

**`as_completed(futures)`** отдаёт Future **в порядке завершения**, а не запуска. Нужно, когда хочешь реагировать на каждый результат сразу, как только он готов:

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor() as ex:
    futures = [ex.submit(загрузить, u) for u in urls]
    for future in as_completed(futures):      # кто первым закончил — того и обрабатываем
        print(future.result())
```

## wait — дождаться по условию

**`wait(futures, return_when=...)`** блокирует до наступления условия и возвращает пару множеств `(done, not_done)`:

```python
from concurrent.futures import wait, FIRST_COMPLETED

done, not_done = wait(futures, return_when=FIRST_COMPLETED)   # проснуться на первом готовом
```

- `ALL_COMPLETED` (по умолчанию) — ждать все;
- `FIRST_COMPLETED` — вернуться, как только готов **любой**;
- `FIRST_EXCEPTION` — вернуться на первой ошибке.

## Ловушки

**Исключение всплывает только на `.result()`.** Если задача упала, пул это не покажет, пока ты не запросишь результат — там оно и перебрасывается:

```python
future = ex.submit(делить, 1, 0)
# ... тишина, ошибки будто нет ...
future.result()        # ← ZeroDivisionError вылетает ЗДЕСЬ
```

**`ProcessPoolExecutor`: аргументы и результат должны быть picklable.** Процессы не делят память — данные пересылаются через [сериализацию](../../../Библиотеки/Модули/Форматы%20данных/pickle.md). Поэтому lambda и функции из REPL не пройдут — нужна функция уровня модуля.

**`ProcessPoolExecutor` на Windows** — запуск оборачивай в `if __name__ == "__main__":` (как и в [multiprocessing](../../../Библиотеки/Модули/Параллелизм/multiprocessing.md#process--запустить-функцию-в-отдельном-процессе)), иначе дочерние процессы заново импортируют модуль и уйдут в рекурсию.

> **Всегда используй `with`.** Выход из блока вызывает `shutdown(wait=True)` — дожидается задач и освобождает рабочих. Без `with` легко оставить висящие потоки/процессы.

## Executor vs сырые модули

| | `concurrent.futures` | `threading` / `multiprocessing` |
|---|---|---|
| **Уровень** | высокий (пул + Future) | низкий (сам создаёшь и ждёшь) |
| **Сбор результатов** | автоматически (Future) | вручную (очереди, общие структуры) |
| **Потоки ↔ процессы** | смена одного класса | разные API |
| **Контроль** | меньше, но проще | полный, но многословный |

> Практическое правило: для «раздать задачи по пулу и собрать результаты» бери **`concurrent.futures`**. К сырым `Thread`/`Process` спускайся, когда нужен тонкий контроль (демоны, свои примитивы синхронизации, долгоживущие потоки).

> **Python 3.14+:** добавлен **`InterpreterPoolExecutor`** — пул на суб-интерпретаторах. У каждого свой GIL (как у процессов → настоящий параллелизм CPU-bound), но они легче процессов. Промежуточный вариант между потоками и процессами.
