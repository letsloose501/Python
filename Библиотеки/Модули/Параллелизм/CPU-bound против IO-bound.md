# CPU-bound против I/O-bound

> _Сначала определи, чем задача занята — считает или ждёт. От этого зависит весь выбор инструмента._

---

Любая медленная задача упирается в одно из двух: в **процессор** (она *считает*) или в **ожидание** (она *ждёт* сеть, диск, базу). Это деление — фундамент, с которого начинается выбор между потоками, процессами и async: неправильно определил тип — выбрал не тот инструмент и не получил ускорения. Механика самих потоков/процессов/корутин — в Асинхронность и многопоточность; здесь — **как различать эти два типа и почему для них нужны разные инструменты**.

## Два типа нагрузки

- **CPU-bound** (ограничена процессором) — узкое место в **скорости вычислений**. Процессор загружен на ~100%, работа кончится быстрее только если дать больше ядер или более быстрый CPU.
  _Хеширование паролей, сжатие и обработка изображений/видео, рендеринг, парсинг больших объёмов, матричные вычисления, ML-инференс, перемножение чисел в цикле._

- **I/O-bound** (ограничена вводом-выводом) — узкое место во **внешнем ресурсе**. Процессор почти простаивает — просто ждёт ответа от сети, диска или БД. Более быстрый CPU не поможет: сеть от этого быстрее не станет.
  _HTTP-запрос к API, запрос к базе данных, чтение/запись файла, ожидание сокета, `time.sleep`._

**I/O** — input/output, ввод-вывод: любой обмен данными с миром за пределами процессора и памяти.

```
CPU-bound:  ████████████████████  проц занят всё время — считает
I/O-bound:  ▓──ждём сеть──▓──ждём диск──▓   проц почти простаивает
```

## Как различить

Главный критерий — один мысленный тест:

> **«Если дать в 10 раз более быстрый процессор — задача ускорится кратно?»**
> Да → **CPU-bound** (она реально считала). Почти нет → **I/O-bound** (она ждала сеть/диск, а они быстрее не стали).

| Признак | CPU-bound | I/O-bound |
|---|---|---|
| Узкое место | Процессор | Сеть, диск, БД |
| Загрузка CPU | ~100%, ядро «горит» | Низкая, проц ждёт |
| Что делает | Считает | Ждёт |
| Ускорит бóльший CPU / ядра | Да | Нет |
| Ускорит быстрее сеть / SSD | Нет | Да |
| Примеры | шифрование, картинки, ML | HTTP, БД, файлы |

**Практическая проверка — посмотреть на загрузку.** Запусти задачу и открой диспетчер задач / `htop`:

- ядро загружено на 100%, программа «жрёт» CPU → **CPU-bound**;
- программа висит, а процессор почти свободен → **I/O-bound** (ждёт).

Для точной картины — [профилировщик](../../../Библиотеки/Модули/Отладка%20и%20утилиты/Профилирование%20и%20отладка.md): если время уходит в вычислительные функции — CPU-bound; если в вызовы `recv`/`read`/`sleep`/запросы к БД — I/O-bound.

## Почему для них нужны разные инструменты

Всё упирается в **GIL** (Global Interpreter Lock) — замок CPython, который пускает выполнять Python-байткод **только одному потоку за раз**. Как GIL ведёт себя, зависит ровно от типа нагрузки.

**I/O-bound — потоки и async ускоряют.** Когда поток начинает ждать ввод-вывод (сеть, диск), он **отпускает GIL** — другой поток в это время работает. Ожидания накладываются друг на друга, и 100 запросов идут почти за время одного.

```
I/O-bound на потоках/async — ожидания параллельны:
Задача1  ▓ждём──────────▓
Задача2    ▓ждём──────────▓     ← пока один ждёт, GIL свободен,
Задача3      ▓ждём──────────▓      другие шлют свои запросы
```

**CPU-bound — потоки НЕ ускоряют.** Считающий код GIL не отпускает: пока один поток крутит цикл, остальные стоят в очереди. 4 потока на 4 ядрах дадут скорость примерно как 1 поток (и даже медленнее — из-за переключений контекста).

```
CPU-bound на потоках — только по очереди:
Задача1  ▓считает▓
Задача2           ▓считает▓     ← GIL занят одним,
Задача3                    ▓считает▓  параллелизма нет
```

**CPU-bound — процессы ускоряют.** У каждого процесса свой интерпретатор и **свой GIL**, поэтому процессы реально бегут на разных ядрах одновременно. Цена — они дороже потоков и данные между ними передаются через `pickle` (см. [multiprocessing](../../../Библиотеки/Модули/Параллелизм/multiprocessing.md)).

### Правило выбора

| Нагрузка | Инструмент | Почему |
|---|---|---|
| **Массовый I/O** (тысячи соединений) | `asyncio` / `aiohttp` ([Asyncio Event Loop и aiohttp](../../../Библиотеки/Модули/Параллелизм/Asyncio%20Event%20Loop%20и%20aiohttp.md)) | Один поток, переключается на ожиданиях — дёшево |
| **Умеренный I/O** | потоки: [threading](../../../Библиотеки/Модули/Параллелизм/threading.md) / `ThreadPoolExecutor` | Потоки отпускают GIL на ожидании |
| **CPU-bound** | процессы: [multiprocessing](../../../Библиотеки/Модули/Параллелизм/multiprocessing.md) / `ProcessPoolExecutor` | Обходят GIL — настоящий параллелизм |

> Мнемоника: **считаешь → процессы, ждёшь немного → потоки, ждёшь массово → async.** Переключение между `ThreadPoolExecutor` и `ProcessPoolExecutor` в [concurrent.futures](../../../Библиотеки/Модули/Параллелизм/concurrent.futures.md) — это смена **одного класса**, поэтому главное — правильно определить тип, а замена инструмента дешёвая.

Отсюда же и **размер пула**: для I/O-bound — больше числа ядер (потоки почти всё время ждут), для CPU-bound — по числу ядер (больше смысла нет, ядра всё равно заняты счётом).

```python
# CPU-bound → процессы (обходят GIL):
from concurrent.futures import ProcessPoolExecutor
with ProcessPoolExecutor() as pool:
    results = list(pool.map(тяжёлый_расчёт, данные))

# I/O-bound → потоки (GIL свободен на ожидании):
from concurrent.futures import ThreadPoolExecutor
with ThreadPoolExecutor(max_workers=20) as pool:
    results = list(pool.map(скачать_url, urls))

# массовый I/O → async:
import asyncio
results = await asyncio.gather(*(скачать_async(u) for u in urls))
```

## Ловушки и нюансы

- **Смешанная нагрузка — самый частый случай.** Реальная задача бывает и той и другой: *скачать* файл (I/O) → *обработать* его (CPU). Тогда разбивай: I/O-часть на async/потоках, CPU-часть выноси в процессы. В вебе ([FastAPI](../../../Фреймворки/FastAPI.md)) — то же: `async def` + `await` на I/O, а тяжёлый счёт через `run_in_executor` с процессами или в [Celery](../../../Библиотеки/Сторонние/Celery.md).

- **C-расширения часто отпускают GIL.** NumPy, `hashlib`, криптобиблиотеки на C внутри тяжёлых операций **освобождают GIL** — тогда даже потоки дают параллелизм на CPU. Но чистый Python-цикл — нет. Поэтому «потоки бесполезны для CPU» — правда именно для *питоновского* кода.

- **CPU-задача блокирует и event loop, и поток.** В `async def` тяжёлый счёт останавливает весь loop (нет `await` — нет переключения); в потоке — держит GIL. Ни async, ни потоки CPU-задачу не спасают — только процессы. Подробно про выбор «поток или процесс» и порог, с которого пора выносить, — [Блокирующий код в event loop](../../../Библиотеки/Модули/Параллелизм/Блокирующий%20код%20в%20event%20loop.md).

- **Файлы — I/O особого рода.** Формально чтение с диска I/O-bound, но настоящей асинхронности у файлов в ОС нет: `aiofiles` под асинхронным синтаксисом уносит работу в поток. Внешне неотличимо от честного `await`, под нагрузкой ведёт себя иначе — см. [Асинхронная работа с файлами](../../../Библиотеки/Модули/Параллелизм/Асинхронная%20работа%20с%20файлами.md).

- **Закон Амдала ограничивает выигрыш.** Даже вынеся CPU-задачу на процессы, ускоришь только *параллелизуемую* часть; последовательный кусок остаётся узким местом (см. Закон Амдала).

- **Free-threading (Python 3.13+).** Экспериментальная сборка без GIL (PEP 703) позволяет потокам параллелить и CPU-код. Пока не мейнстрим — по умолчанию GIL на месте.

## Как определить и выбрать — по шагам

```
1. Замерь, где уходит время (профиль / htop).
        │
        ├─ ядро на 100%, время в вычислениях ──► CPU-bound
        │        └─► процессы: ProcessPoolExecutor / multiprocessing / Celery
        │
        └─ проц простаивает, время в ожидании ──► I/O-bound
                 ├─ соединений тысячи ──► asyncio / aiohttp
                 └─ немного, нужен простой код ──► потоки / ThreadPoolExecutor
```

> Не угадывай тип по интуиции — **сначала замерь**. Часто «медленный» код оказывается I/O-bound, и вместо распараллеливания вычислений достаточно async-запросов; и наоборот — async не ускорит перемножение матриц.
