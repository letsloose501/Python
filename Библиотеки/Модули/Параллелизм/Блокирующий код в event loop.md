# Блокирующий код в event loop

> _Вопрос не «есть ли в коде блокировка» — она есть всегда. Вопрос «насколько долго»._

---

[Event loop](../../../Библиотеки/Модули/Параллелизм/Asyncio%20Event%20Loop%20и%20aiohttp.md#event-loop--сердце-asyncio) — один поток. Пока корутина не дошла до `await`, она держит его целиком: остальные задачи стоят, сколько бы их ни было. Отсюда главное правило async-разработки — **не занимать loop надолго**. Эта заметка о том, что считать «надолго», как такой код находить и куда его выносить.

## Блокирует всё, вопрос только — насколько

Частое заблуждение новичка: «в асинхронном приложении блокирующего кода быть не должно». На деле **любой** ваш код блокирует loop, потому что выполняется в том же единственном потоке:

```python
async def handler(request):
    total = 3 + 5                      # блокирует loop — наносекунды
    data = json.loads(request.body)    # блокирует loop — микросекунды
    if not check_auth(request.headers): # блокирует loop — микросекунды
        raise Unauthorized
```

Сложение, разбор JSON, проверка заголовков, `if`, логирование, сериализация ответа — всё это вычисления, всё это [CPU-нагрузка](../../../Библиотеки/Модули/Параллелизм/CPU-bound%20против%20IO-bound.md), и всё это не отпускает loop. Приложения, состоящего только из внешних запросов, не бывает.

> Поэтому цель — не «убрать блокировки», а **держать их короткими**. Плохо не то, что код блокирует, а то, что он блокирует на миллисекунды и дольше.

### Шкала: где проходит граница

| Длительность | Примеры | Вердикт |
|---|---|---|
| нано- и микросекунды | арифметика, `if`, разбор небольшого JSON, форматирование лога | норма, так работает любое приложение |
| единицы миллисекунд | цикл по десяткам тысяч элементов, крупная сериализация | терпимо, но замерить |
| десятки — сотни миллисекунд | `requests.get`, синхронный запрос к БД, `time.sleep`, хеширование пароля | **авария**, выносить |
| секунды | чтение большого файла, тяжёлый расчёт, ожидание внешней API | **авария**, выносить обязательно |

Почему 200 мс — это авария, хотя «по человеческим меркам мгновенно»: считать надо не в масштабе одного запроса, а в масштабе сервиса.

```
1000 RPS, один запрос блокирует loop на 200 мс
   → за эти 200 мс приходит ещё ~200 запросов
   → все они ждут в очереди, ничего не выполняется
   → очередь растёт быстрее, чем разбирается → сервис ложится
```

Один клиент разницы не заметит. Под нагрузкой падает всё — и по метрикам это выглядит не как «медленный эндпоинт», а как «весь сервис перестал отвечать».

## Худший случай: `async def` без единого `await`

Функция, объявленная `async def`, но не содержащая настоящих точек приостановки, **хуже обычной синхронной функции**: она выглядит асинхронной, читается как асинхронная, а loop не отпускает.

```python
# НЕПРАВИЛЬНО — async-обёртка вокруг блокирующей библиотеки
async def get_profile(user_id: int):
    return requests.get(f"https://api.example.com/users/{user_id}").json()
#   requests синхронный: 200 мс весь сервис стоит, ни одна другая корутина не выполнится

# ПРАВИЛЬНО — асинхронный клиент, на ожидании loop свободен
async def get_profile(session, user_id: int):
    async with session.get(f"https://api.example.com/users/{user_id}") as r:
        return await r.json()
```

Обманчиво здесь именно `async def`: синтаксис обещает конкурентность, которой нет. Синхронная функция хотя бы честна — по ней видно, что её надо звать из потока.

## Три способа вынести блокировку

Порядок именно такой: сначала пытаются заменить библиотеку, и только если нельзя — уносят в поток.

### 1. Заменить на асинхронный аналог — лучший путь

Корутина остаётся в том же потоке, поток не создаётся, накладных расходов нет.

| Синхронное | Асинхронная замена | Особенность замены |
|---|---|---|
| [requests](../../../Библиотеки/Сторонние/Работа%20с%20WEB/requests.md) | **httpx** | API почти совпадает с `requests` — миграция самая дешёвая; только клиент |
| [requests](../../../Библиотеки/Сторонние/Работа%20с%20WEB/requests.md) | **aiohttp** ([см.](../../../Библиотеки/Модули/Параллелизм/Asyncio%20Event%20Loop%20и%20aiohttp.md#aiohttp--асинхронный-http)) | клиент **и** сервер: на нём можно писать сам сервис |
| [psycopg2](../../../Библиотеки/Сторонние/Работа%20с%20БД/psycopg2.md) | **asyncpg** / `psycopg` 3 в async-режиме | нужен и async-движок [SQLAlchemy](../../../Библиотеки/Сторонние/ORM/SQLAlchemy.md#асинхронный-режим-и-параллельные-запросы) |
| `time.sleep` | `asyncio.sleep` | `time.sleep` останавливает loop целиком — классическая ошибка |
| `open()` | `aiofiles` | ⚠️ под капотом всё равно поток — см. [Асинхронная работа с файлами](../../../Библиотеки/Модули/Параллелизм/Асинхронная%20работа%20с%20файлами.md) |

> `httpx` и `aiohttp` решают одну задачу. Практическая разница: `httpx` ближе по API к `requests` (проще переписать legacy), `aiohttp` умеет ещё и серверную часть, поэтому на нём пишут сами сервисы, а не только клиентов к чужим.

### 2. Вынести в поток — когда заменить нельзя

Legacy-библиотека, внутренний корпоративный пакет, синхронный SDK — переписать нельзя, но вы знаете, что внутри **ожидание сети**, а не счёт. Такое уносят в отдельный поток: поток на ожидании отпускает GIL, loop продолжает крутиться.

```python
import asyncio

def fetch_legacy(user_id: int) -> dict:      # синхронная, переписать нельзя
    return legacy_client.get_user(user_id)   # внутри — сетевой запрос

async def get_profile(user_id: int):
    return await asyncio.to_thread(fetch_legacy, user_id)   # → в отдельный поток
```

**`asyncio.to_thread(func, *args)`** (Python 3.9+) — выполнить синхронную функцию в потоке из пула и дождаться результата, не блокируя loop. Старая форма того же — `loop.run_in_executor(None, func, arg)`; `to_thread` короче и предпочтительнее.

### 3. Вынести в процесс — когда это счёт

Поток CPU-задачу не спасает: [GIL пускает в интерпретатор одного](../../../Библиотеки/Модули/Параллелизм/CPU-bound%20против%20IO-bound.md#почему-для-них-нужны-разные-инструменты). Документация `asyncio` говорит об этом прямо: `to_thread` годится, чтобы сделать неблокирующими **I/O-функции**, а для CPU-задач — только если расширение отпускает GIL.

```python
from concurrent.futures import ProcessPoolExecutor

pool = ProcessPoolExecutor()

async def register(password: str):
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(pool, hash_password, password)  # другой процесс
```

Совсем тяжёлое (минуты, ретраи, расписание) выносят не в процесс, а в очередь задач — [Celery](../../../Библиотеки/Сторонние/Celery.md) или TaskIQ.

## Потоки не бесплатны

`to_thread` кажется универсальным лекарством, но у него есть потолок. По умолчанию `asyncio` использует общий `ThreadPoolExecutor`, у которого с Python 3.8 `max_workers = min(32, os.cpu_count() + 4)`.

Следствия, о которых узнают поздно:

- **Пул конечен.** Больше `max_workers` одновременных `to_thread` — остальные ждут в очереди пула. Ваш «неблокирующий» вызов снова начинает ждать, просто в другом месте.
- **Поток — сущность ОС, а не Python.** Его создание и переключение стоят времени; на короткой операции эта цена может съесть весь выигрыш.
- **Общий пул на всё приложение.** Один жадный участок кода, забивший пул, тормозит все остальные `to_thread` в сервисе. Лечится своим `ThreadPoolExecutor` под конкретную задачу.

```python
from concurrent.futures import ThreadPoolExecutor

report_pool = ThreadPoolExecutor(max_workers=4)      # свой пул — не мешает остальным

async def build_report(data):
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(report_pool, render_pdf, data)
```

## Ловушка: рефакторить не всё подряд

Обратная крайность — увидеть в `async def` любой синхронный код и броситься его выносить.

```python
async def merge_items(items: list[dict]) -> list[dict]:
    return [{**item, "ok": True} for item in items]   # чистый Python, без I/O
```

Здесь нет ни одного `await`, и формально функция «блокирует loop». Но если в списке сотня элементов, блокировка измеряется микросекундами — заметить её нельзя ничем. Выносить такое в поток бессмысленно: **передача в поток обойдётся дороже самой работы**.

> Правило приоритета: сначала чинят то, что блокирует на **миллисекунды и дольше** (сеть, диск, БД, криптография), и только потом — косметику. Такую функцию правильнее просто сделать обычным `def`, а не `async def`, но в очереди задач рефакторинга она стоит последней.

## Как это находят

**На собеседовании.** Классическая секция: дают кусок async-кода и просят найти плохое. Ищут в первую очередь `requests` / `time.sleep` / синхронный драйвер БД внутри `async def` и `async def` без единого `await`. → [Вопросы с собеседований](../../../Вопросы%20с%20собеседований.md#асинхронность)

**В проде.** Симптом характерный: латентность растёт **у всех** эндпоинтов сразу, включая те, что ничего тяжёлого не делают, — потому что стоит общий loop, а не конкретный обработчик. Ищут через [метрики и трейсы](../../../DevOps/Наблюдаемость%20—%20метрики,%20логи,%20трейсы.md) и [профилировщик](../../../Библиотеки/Модули/Отладка%20и%20утилиты/Профилирование%20и%20отладка.md); помогает `asyncio` в режиме отладки (`PYTHONASYNCIODEBUG=1`) — он логирует колбэки, выполнявшиеся дольше 100 мс.
