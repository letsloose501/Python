# Асинхронная работа с файлами

> _`await` здесь не переключает loop, а создаёт поток. Синтаксис асинхронный, механика — нет._

---

С сетью асинхронность работает честно: корутина уходит в ожидание, а loop занимается другими. С **файлами это не так**. Библиотека `aiofiles` даёт асинхронный синтаксис, но под ним нет асинхронного ввода-вывода — работа уносится в отдельный поток. Знать это нужно не из любопытства: на файловой нагрузке приложение начинает плодить потоки и деградировать там, где вы этого не ожидаете.

## Почему у файлов нет настоящей асинхронности

Сетевой запрос устроен удобно для event loop. Сокет умеет сказать ядру: «данных пока нет — разбуди меня, когда придут». Пока ядро ждёт, [loop](../../../Библиотеки/Модули/Параллелизм/Asyncio%20Event%20Loop%20и%20aiohttp.md#event-loop--сердце-asyncio) крутит другие задачи. На этом построен весь `asyncio`.

Файл так не умеет. Обычное чтение с диска — операция, которая либо мгновенно берёт данные из страничного кэша, либо блокирует поток до ответа диска. Промежуточного состояния «я подожду и позову» у него нет.

```
Сокет:  read() → «данных нет» → loop уходит к другим → ядро будит  ✅ настоящий async
Файл:   read() → поток стоит, пока диск не ответит                 ❌ разбудить некого
```

Асинхронные интерфейсы для файлов в ОС существуют, но каждый со своей бедой:

- **POSIX AIO** — реализован слабо и медленно, местами поверх тех же потоков;
- **Linux native AIO** — работает только с `O_DIRECT` (мимо страничного кэша), а это ограничение убивает большинство сценариев; запрос всё равно может заблокироваться, если ядру нужно дочитать метаданные;
- **io_uring** — современный и действительно быстрый, но появился недавно, спецификация активно менялась, и он есть только в Linux.

Поэтому в стандартной библиотеке Python асинхронной работы с файлами **нет вообще** — ни `async open`, ни аналога. Разработчики языка не стали привязываться к интерфейсу, который в каждой ОС свой и продолжает меняться.

## Что на самом деле делает aiofiles

**`aiofiles`** — самая популярная библиотека для «асинхронных» файлов (~3,3 тыс. звёзд на GitHub против пары десятков у альтернатив). Её собственная документация формулирует честно: она вводит асинхронные версии файлов, **делегируя операции отдельному пулу потоков**.

```python
import aiofiles

async def read_report(path: str) -> str:
    async with aiofiles.open(path, mode="r") as f:   # ← здесь берётся поток из пула
        return await f.read()                        # ← чтение идёт в том потоке
```

То есть `await` в этом коде **не отдаёт управление loop'у на время ввода-вывода**, как при сетевом запросе. Он ждёт, пока другой поток закончит обычное синхронное чтение. Ровно то же самое можно написать руками:

```python
# aiofiles.open(...) ≈ то же, что явный вынос в поток
data = await asyncio.to_thread(pathlib.Path(path).read_text)
```

Разница только в удобстве синтаксиса — механика одна: [блокирующая операция вынесена в поток](../../../Библиотеки/Модули/Параллелизм/Блокирующий%20код%20в%20event%20loop.md#2-вынести-в-поток--когда-заменить-нельзя).

## Два следствия, из-за которых это важно

### 1. Много файлов — много потоков

Пока файлов единицы, разницы нет никакой. Но если приложение обрабатывает загрузки от клиентов и файлы идут сотнями одновременно, каждый вызов занимает поток. Поток — сущность операционной системы, а не Python: у него есть цена создания, цена переключения контекста и стек в памяти.

```
100 одновременных aiofiles.open()
   → 100 задач в пул потоков (а он по умолчанию min(32, cpu+4))
   → часть работает, остальные стоят в очереди пула
   → плюс постоянные переключения контекста между потоками
   → латентность растёт, система деградирует
```

Симптом коварный: код выглядит асинхронным, метрики loop'а чистые, а сервис всё равно тормозит — потому что затык не в loop, а в пуле потоков под ним.

### 2. На маленьком файле синхронное чтение быстрее

Передача работы в поток стоит времени: взять поток из пула, передать аргументы, переключить контекст, вернуть результат. Если сам файл маленький (условные сотни килобайт) и лежит в страничном кэше ОС, чтение занимает микросекунды — **дешевле, чем накладные расходы на поток**.

```python
# Конфиг на старте приложения — 4 КБ, читается один раз
settings = json.loads(pathlib.Path("config.json").read_text())   # ✅ обычный open

# Не так: цена потока больше самой работы
settings = json.loads(await (await aiofiles.open("config.json")).read())   # ❌
```

## Что делать на практике

| Ситуация | Решение |
|---|---|
| Мелкий файл, читается один раз на старте (конфиг, шаблон, ключ) | обычный `open()` — асинхронность не нужна |
| Мелкий файл в обработчике запроса, файлов немного | обычный `open()`, но замерить; вынести, если попадает в миллисекунды |
| Большой файл или их много одновременно | `aiofiles` / `asyncio.to_thread`, обязательно с ограничением одновременности |
| Действительно высокая файловая нагрузка на Linux | `aiofile` / `caio` поверх io_uring — настоящий async, а не потоки |

Ограничение одновременности — главный практический приём: пул потоков всё равно конечен, лучше явно контролировать очередь, чем упереться в неё случайно.

```python
import asyncio, aiofiles

sem = asyncio.Semaphore(10)          # не больше 10 файлов одновременно

async def load(path: str) -> str:
    async with sem:                  # остальные ждут здесь, не забивая пул потоков
        async with aiofiles.open(path) as f:
            return await f.read()

async def main(paths: list[str]):
    return await asyncio.gather(*(load(p) for p in paths))
```

> Общее правило шире файлов: **знай, что из твоих `await` — настоящая асинхронность, а что — поток под капотом.** Внешне они неразличимы, а ведут себя под нагрузкой совершенно по-разному. Тот же вопрос стоит задавать любой библиотеке с приставкой `aio-`.
