# venv

> _Отдельная песочница с пакетами под каждый проект — чтобы зависимости одного не ломали другой._

---

**venv** — модуль создания **виртуальных окружений**: изолированных копий Python со своим набором установленных пакетов. Каждый проект получает собственную песочницу, и его зависимости не пересекаются с другими проектами и с системным Python.

**Зачем:** проект A требует Django 4, проект B — Django 5. Если ставить пакеты глобально, они конфликтуют. Виртуальное окружение даёт каждому проекту свою версию.

## Проблема: один глобальный Python

Без окружений `pip install` кладёт пакеты в общесистемный Python. Тогда:

- две программы не могут требовать разные версии одной библиотеки;
- обновление пакета для одного проекта ломает другой;
- список установленного превращается в свалку, и непонятно, что нужно конкретному проекту.

Виртуальное окружение решает это изоляцией.

## Создать и активировать

```bash
python -m venv .venv          # создать окружение в папке .venv

# активировать:
source .venv/bin/activate     # Linux / macOS
.venv\Scripts\activate        # Windows

# внутри окружения:
pip install requests          # ставится ТОЛЬКО в это окружение
deactivate                    # выйти обратно в системный Python
```

После активации `python` и `pip` указывают на окружение — установленные пакеты видит только этот проект. В приглашении терминала появляется префикс `(.venv)`.

## Фиксация зависимостей — requirements.txt

Чтобы окружение можно было воспроизвести на другой машине, список пакетов сохраняют в файл:

```bash
pip freeze > requirements.txt        # выгрузить точные версии в файл
pip install -r requirements.txt      # восстановить окружение из файла
```

Это то, что делают на сервере при развёртывании и коллеги при клонировании проекта.

## Что коммитить, что нет

> Папку `.venv/` **не** кладут в репозиторий (она большая и зависит от ОS) — её добавляют в `.gitignore`. В репозиторий идёт **`requirements.txt`**: по нему окружение пересоздаётся одной командой.
