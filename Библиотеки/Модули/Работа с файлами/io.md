# io

> _Файл в оперативной памяти: то, что ведёт себя как файл, но не касается диска._

---

**io** — модуль потокового ввода-вывода. Его главная практическая ценность — **`StringIO`** и **`BytesIO`**: объекты, которые ведут себя как открытый файл (`.read()`, `.write()`), но данные держат **в памяти**, а не на диске. Заодно `io` — фундамент, на котором построена встроенная функция `open()`.

Зачем: собрать текст «как в файл» без создания файла, подсунуть функции «файл» в тестах, работать с данными из сети как с файлом.

## Проблема, которую решает StringIO

Иногда функция или библиотека ожидает **файловый объект**, а у тебя данные в памяти (или наоборот — нужно собрать вывод в строку). Создавать реальный файл ради этого — лишнее. `StringIO` притворяется файлом.

```python
from io import StringIO

buf = StringIO()
buf.write("первая строка\n")
buf.write("вторая строка\n")

buf.getvalue()      # → 'первая строка\nвторая строка\n'  весь накопленный текст
```

Можно и читать, как из файла:

```python
buf = StringIO("строка 1\nстрока 2\n")
buf.readline()      # → 'строка 1\n'
for line in buf:    # итерируется построчно, как файл
    ...
```

## BytesIO — то же для байтов

`BytesIO` — файл в памяти для **двоичных** данных: картинок, архивов, ответов сети.

```python
from io import BytesIO

buf = BytesIO()
buf.write(b"\x89PNG...")     # например, сгенерированное изображение
данные = buf.getvalue()      # bytes, готовые к отправке/сохранению
```

Типичный бэкенд-сценарий: библиотека формирует PDF/картинку в `BytesIO`, и результат сразу уходит в HTTP-ответ, минуя диск.

## io под капотом open()

Встроенный `open()` возвращает именно io-объекты. Тип зависит от режима:

```
open("f.txt")         → io.TextIOWrapper    текст (str), с кодировкой
open("f.bin", "rb")   → io.BufferedReader    байты (bytes)
```

Поэтому `sys.stdin`, `sys.stdout` ([sys](../../../Библиотеки/Модули/Система%20и%20окружение/sys.md)) и `StringIO` взаимозаменяемы — все они текстовые потоки с одним интерфейсом.

### Три слоя текстового потока

`TextIOWrapper` — не монолит, а верхушка стопки. Под ней буфер, под ним сырой дескриптор:

```
_io.TextIOWrapper      str → bytes: кодировка, перевод строк
  └─ _io.BufferedWriter    буфер io.DEFAULT_BUFFER_SIZE = 8192 байта
       └─ _io.FileIO       системный вызов write() в дескриптор
```

Спуститься на уровень ниже — атрибут `.buffer`, ещё ниже — `.raw`:

```python
sys.stdout.buffer.write(b"\x89PNG")   # байты минуя кодировку
```

Средний слой и объясняет, почему вывод не появляется сразу: он копится в буфере — см. [Стандартные потоки — stdin, stdout, stderr](../../../Ядро%20языка/Стандартные%20потоки%20—%20stdin,%20stdout,%20stderr.md#буферизация--главная-практическая-ловушка).

> ⚠️ У `StringIO` атрибута `.buffer` **нет**. Поэтому библиотека, слепо дергающая `sys.stdout.buffer`, ломается в тестах, где поток подменён на `StringIO`.

## Где применяют

- **Тесты** — подменить файл на `StringIO`, чтобы не трогать диск;
- **Захват вывода** — перенаправить `print` в `StringIO` и проверить, что вывелось;
- **Генерация файлов в памяти** — собрать CSV/картинку/архив в `BytesIO` и отдать в ответ;
- **Данные из сети** — обернуть загруженные байты в `BytesIO` и читать как файл.
