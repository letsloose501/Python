# Профилирование и отладка

> _Не угадывай, где медленно и где баг, — измерь и посмотри_

---

Две частые ошибки: оптимизировать код «на глаз» и искать баг чтением кода. Обе — про угадывание. **Профилирование** отвечает на вопрос «куда уходит время/память», **отладка** — «что реально происходит в этой точке». Здесь — инструменты для обоих, от простого замера до профиля живого процесса в проде.

> **Сначала измерь, потом оптимизируй.** Интуиция про узкие места почти всегда врёт: тормозит обычно не то, что кажется. Оптимизация без профиля — трата времени на неважное. Правило: профиль → самое узкое место → фикс → снова профиль.

## Замер времени — `timeit`

Для микрозамера маленького куска кода. Гоняет его много раз и усредняет — устраняет случайный шум.

```python
import timeit

# сравнить два способа склейки строк
timeit.timeit('"".join(map(str, range(100)))', number=100_000)
timeit.timeit('s=""\nfor i in range(100): s+=str(i)', number=100_000)
```

```bash
python -m timeit -s "data=list(range(1000))" "sorted(data)"    # из терминала
```

> В Jupyter/IPython — магии `%timeit выражение` и `%%timeit` на ячейку.

## Профиль по функциям — `cProfile`

**`cProfile`** — встроенный **детерминированный** профайлер: считает, сколько раз вызвана каждая функция и сколько в ней провели времени. Показывает распределение по всей программе.

```bash
python -m cProfile -s cumulative myscript.py      # -s cumulative — сорт. по суммарному времени
```

```python
import cProfile, pstats

cProfile.run('main()', 'profile.out')             # собрать в файл
p = pstats.Stats('profile.out')
p.sort_stats('cumulative').print_stats(10)        # топ-10 функций по времени
```

Ключевые колонки: `ncalls` (число вызовов), `tottime` (время в самой функции), `cumtime` (в ней + во всём, что она вызвала). Виновника ищут по `cumtime`, горячую точку — по `tottime`.

> Построчный профиль (какая **строка** внутри функции медленная) даёт сторонний **`line_profiler`** (`@profile` + `kernprof`). В stdlib его нет.

## Профиль памяти — `tracemalloc`

**`tracemalloc`** (stdlib) — показывает, **какие строки кода** выделили больше всего памяти. Ищут утечки и перерасход.

```python
import tracemalloc

tracemalloc.start()
# ... работа программы ...
snapshot = tracemalloc.take_snapshot()
for stat in snapshot.statistics('lineno')[:10]:   # топ-10 мест по памяти
    print(stat)
```

## Профиль живого процесса — `py-spy`

**`py-spy`** — **сэмплирующий** профайлер: подключается к **уже запущенному** процессу по PID и снимает срезы стека, **не меняя код** и почти не тормозя программу. Незаменим в **проде**, когда сервис тормозит, а остановить и переписать его нельзя.

```bash
pip install py-spy
py-spy top --pid 12345               # живой «top» по функциям процесса
py-spy dump --pid 12345              # снять текущие стеки всех потоков (где виснет)
py-spy record -o flame.svg --pid 12345   # flame graph — визуальная карта времени
```

| Профайлер | Тип | Когда |
|---|---|---|
| `cProfile` | детерминированный (считает каждый вызов) | локально, точный разбор по функциям |
| `py-spy` | сэмплирующий (срезы стека) | прод, живой процесс, без правки кода |
| `tracemalloc` | по памяти | утечки и перерасход памяти |

## Отладчик — `pdb`

**`pdb`** — встроенный интерактивный отладчик: останавливает выполнение в точке и даёт смотреть переменные и идти по шагам. Ставит точку останова `breakpoint()` (Python 3.7+):

```python
def обработать(data):
    result = преобразовать(data)
    breakpoint()          # выполнение остановится здесь, откроется pdb
    return сохранить(result)
```

Команды в pdb: `n` (следующая строка), `s` (зайти внутрь вызова), `c` (продолжить), `p имя` (напечатать переменную), `l` (показать код вокруг), `w` (стек вызовов), `q` (выйти).

> `breakpoint()` лучше `import pdb; pdb.set_trace()`: короче и уважает переменную `PYTHONBREAKPOINT` (можно отключить все точки разом или подставить свой отладчик). В IDE (VS Code, PyCharm) — тот же процесс через графические брейкпоинты.

## Диагностика без отладчика

- **`logging`, а не `print`** — уровни, время, где и когда; в проде print не годится. Подробно — [logging](../../../Библиотеки/Модули/Отладка%20и%20утилиты/logging.md).
- **`faulthandler`** — печатает трейсбек при жёстком падении (segfault) или зависании: `python -X faulthandler` или `faulthandler.dump_traceback_later(secs)`.
- **`traceback`** — распечатать/сохранить стек пойманного исключения (`traceback.format_exc()`), см. [Обработка ошибок Python](../../../Ядро%20языка/Обработка%20ошибок%20Python.md).
- **`assert`** — быстрая проверка инварианта в разработке (в проде отключается флагом `-O`, поэтому не для валидации ввода).

## Рабочий цикл

```
Медленно?  →  timeit/cProfile/py-spy → найти узкое место → фикс → перепрофилировать
Течёт память?  →  tracemalloc → топ мест выделения → фикс
Баг?  →  воспроизвести → breakpoint()/pdb или logging → найти расхождение → тест на баг → фикс
```

> Починил баг — закрепи его [тестом](../../../Библиотеки/Сторонние/Тесты/Юнит-тестирование%20Python.md) (что упало — не должно упасть снова). Это и есть регрессионный тест.
