# logging

> _`print` для отладки — тупик. Логгер умеет уровни важности, метки времени и разные назначения — и всё это включается конфигом, а не переписыванием кода._

---

**logging** — стандартный модуль журналирования: запись сообщений о работе программы с указанием **важности**, времени и источника. В отличие от `print`, логи можно фильтровать по уровню, направлять в файл или систему сбора логов и включать/выключать без правки кода.

Зачем на бэкенде: на сервере `print` не видно — нужны логи, чтобы понимать, что происходит и где сломалось. Это базовый навык эксплуатации.

## Почему не print

| | `print` | `logging` |
|---|---|---|
| Важность сообщения | нет | уровни (DEBUG…CRITICAL) |
| Куда идёт | в `stdout` (можно сменить `file=`) | по умолчанию в **`stderr`**; файл, сеть — по настройке |
| Отключить в проде | удалять из кода | поднять уровень в конфиге |
| Метка времени, модуль | вручную | автоматически |

> **Почему логи по умолчанию идут в `stderr`, а не в `stdout`.** `StreamHandler` без аргумента берёт `sys.stderr` — и это осознанный выбор, а не мелочь: `stdout` зарезервирован под **результат** работы программы. Тогда `script.py > данные.csv` кладёт в файл чистые данные, а логи остаются на экране. Подробнее про разделение потоков — [Стандартные потоки — stdin, stdout, stderr](../../../Ядро%20языка/Стандартные%20потоки%20—%20stdin,%20stdout,%20stderr.md#зачем-нужен-отдельный-stderr).
>
> Побочный эффект: `stderr` буферизуется построчно, а `stdout` в конвейере — блоками по 8 КБ, поэтому логи и обычный вывод в перенаправленном потоке идут **не в том порядке**, в каком написаны. Лечится `PYTHONUNBUFFERED=1`.

## Пять уровней важности

От самого подробного к самому серьёзному. Уровень-порог отсекает всё, что ниже.

```python
import logging
logging.basicConfig(level=logging.INFO)      # показывать INFO и выше

logging.debug("детали для отладки")          # НЕ покажется (ниже INFO)
logging.info("штатное событие")              # покажется
logging.warning("что-то подозрительное")     # покажется
logging.error("ошибка, но живём дальше")     # покажется
logging.critical("всё сломалось")            # покажется
```

| Уровень | Когда |
|---|---|
| `DEBUG` | подробности для диагностики |
| `INFO` | штатный ход работы |
| `WARNING` | тревожно, но не сломалось (по умолчанию порог) |
| `ERROR` | ошибка в конкретной операции |
| `CRITICAL` | критический сбой |

## Свой логгер и формат

На практике заводят именованный логгер (обычно `__name__`) — так в сообщении видно, из какого модуля оно пришло:

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(name)s: %(message)s",
)
log = logging.getLogger(__name__)

log.info("сервис запущен")
# 2026-07-06 14:30:00 [INFO] myapp.service: сервис запущен
```

## Логировать исключения

`exception` внутри `except` добавляет к сообщению трассировку — не нужно печатать её вручную:

```python
try:
    1 / 0
except ZeroDivisionError:
    log.exception("не удалось поделить")     # в лог попадёт и текст, и traceback
```

## Устройство: логгер → хендлер → форматтер

```
log.info() ──▶ Logger (фильтр по уровню) ──▶ Handler (куда: файл/консоль) ──▶ Formatter (как выглядит)
```

- **Logger** — точка входа, к которой обращается код;
- **Handler** — назначение (консоль, файл, сеть); их может быть несколько;
- **Formatter** — вид строки (время, уровень, сообщение).
