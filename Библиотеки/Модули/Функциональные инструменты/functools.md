# functools

> _Функции в Python — объекты. `functools` даёт инструменты, чтобы их кэшировать, склеивать и настраивать._

---

**functools** — модуль высшего порядка: функции, которые **принимают функции и возвращают новые**. Главные жители — кэширование результатов (`lru_cache`), фиксация аргументов (`partial`), свёртка (`reduce`) и мост от старого сравнения к ключу сортировки (`cmp_to_key`).

Зачем на контесте: `@lru_cache` превращает наивную рекурсию в [динамическое программирование](../../../Алгоритмы/Стратегии/Динамическое%20программирование.md) одной строкой, а `cmp_to_key` решает задачи на нестандартную сортировку, где порядок задаётся сравнением пары, а не ключом.

## lru_cache / cache — мемоизация одной строкой

**`@lru_cache`** запоминает результаты по аргументам: повторный вызов с теми же аргументами берёт ответ из кэша, а не считает заново. Это готовая **мемоизация**.

```python
from functools import lru_cache

@lru_cache(maxsize=None)     # None → кэш без ограничения размера
def fib(n):
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

fib(100)     # мгновенно: без кэша было бы ~2^100 вызовов
```

С Python 3.9 есть короткий синоним **`@cache`** — это `lru_cache(maxsize=None)`.

> **Условие:** аргументы должны быть **хешируемыми** (числа, строки, кортежи — да; списки, словари — нет). Функция должна быть **чистой** — зависеть только от аргументов, иначе кэш вернёт устаревший ответ.

### Что внутри

При конечном `maxsize` кэш обязан кого-то вытеснять — отсюда `lru` в имени: выбрасывается запись, к которой дольше всего не обращались. Устроено это ровно так же, как в задаче [LRU-кэш](../../../Алгоритмы/Задачки/LRU-кэш.md): словарь `{ключ_аргументов: узел}` плюс **кольцевой двусвязный список** порядка обращений. Каждый узел — список из четырёх полей `PREV, NEXT, KEY, RESULT`, а роль обеих заглушек играет один узел `root`, замкнутый сам на себя ([фиктивный узел](../../../Алгоритмы/Приёмы/Фиктивный%20узел.md)).

Отсюда два практических следствия:

- `maxsize=None` (то же самое `@cache`) убирает список целиком — остаётся голый словарь, и это **быстрее**, но кэш растёт без предела. Для рекурсии в контесте это норма, для долгоживущего сервиса — утечка.
- Служебные методы `cache_info()` и `cache_clear()` покажут попадания и сбросят кэш; в тестах сброс обязателен, иначе кэш переживёт тест.

```python
fib.cache_info()      # → CacheInfo(hits=98, misses=101, maxsize=None, currsize=101)
fib.cache_clear()
```

> **Про «`maxsize` степенью двойки».** Совет ходит по статьям и был в документации Python 3.3–3.4 («The LRU feature performs best when maxsize is a power-of-two»). В актуальной доке и в docstring 3.13 этой фразы уже нет — реализация давно другая. Вреда от степени двойки нет, но и опираться на неё как на действующую рекомендацию не стоит.

### Три ловушки, на которых `lru_cache` ломается

**1. На методе класса декоратор держит объект живым.** Кэш общий на класс, а `self` попадает в ключ — значит ссылка на экземпляр лежит в кэше и мешает сборщику. Дока говорит прямо: *«If a method is cached, the `self` instance argument is included in the cache»*, и кэш хранит ссылки на аргументы, пока они не вытеснятся. Проверка `weakref`: объект с таким декоратором переживает `del` и `gc.collect()`.

```python
class Solution:
    @lru_cache(maxsize=None)      # ⚠️ утечка: экземпляры не умирают
    def solve(self, n): ...
```

Замены: кэш на **внутренней функции** внутри метода, `@cached_property` (для методов без аргументов) либо вынести чистую функцию из класса.

**2. С Python 3.12 `sys.setrecursionlimit` не поднимает глубину рекурсии через `lru_cache`.** Декоратор написан на C, а глубина C-стека ограничена отдельно. Замер на 3.13 при лимите 50 000: ручной словарь доходит до 49 998 вызовов, `@lru_cache` — до **999**. Для глубоких ДП это значит: однострочник падает там, где кэш руками работает ([подробно](../../../Алгоритмы/Приёмы/Мемоизация.md), [баг-репорт CPython](https://github.com/python/cpython/issues/112215)).

**3. На `async def`-функции кэш ломается со второго вызова.** `lru_cache` запоминает то, что функция вернула, а корутинная функция возвращает **объект-корутину**, а не результат. Дождаться корутины можно ровно один раз:

```python
@lru_cache(maxsize=None)
async def fetch(x):
    await asyncio.sleep(0.01)
    return x * 2

await fetch(5)     # → 10
await fetch(5)     # → RuntimeError: cannot reuse already awaited coroutine
```

Лечится кэшированием **задачи** вместо корутины (`asyncio.ensure_future`) — `Task` можно ждать многократно. Разбор с рабочим кодом — в [заметке об асинхронных декораторах](../../../Ядро%20языка/Декораторы%20для%20асинхронных%20функций.md#ловушка-lru_cache-на-корутине).

## reduce — свернуть последовательность в одно значение

**`reduce`** применяет функцию попарно слева направо, накапливая результат. В Python 3 вынесен из встроенных в `functools`.

```python
from functools import reduce

reduce(lambda acc, x: acc + x, [1, 2, 3, 4])        # → 10   (((1+2)+3)+4)
reduce(lambda acc, x: acc * x, [1, 2, 3, 4], 1)     # → 24   (с начальным значением)
```

Часто читаемее взять готовое (`sum`, `math.prod`) — `reduce` нужен для нестандартной свёртки.

## cmp_to_key — сортировка через сравнение пары

Иногда порядок нельзя задать одним ключом — только правилом «кто раньше» для **пары** элементов. **`cmp_to_key`** превращает такой компаратор (`-1 / 0 / 1`) в `key` для `sorted`.

```python
from functools import cmp_to_key

# собрать наибольшее число из кусочков: "3","30","34","5","9" → "9534330"
def сравни(a, b):
    return (int(b + a) > int(a + b)) - (int(b + a) < int(a + b))

куски = ["3", "30", "34", "5", "9"]
"".join(sorted(куски, key=cmp_to_key(сравни)))      # → '9534330'
```

## partial — зафиксировать часть аргументов

**`partial`** создаёт новую функцию с уже подставленными аргументами.

```python
from functools import partial

def степень(основание, показатель):
    return основание ** показатель

куб = partial(степень, показатель=3)
куб(5)          # → 125
```

Удобно, когда API требует функцию одного аргумента (`map`, колбэки), а у тебя — двух.

## wraps — не терять «лицо» функции при декораторе

Свой декоратор оборачивает функцию и по умолчанию **затирает** её имя и docstring. **`@wraps`** копирует метаданные оригинала на обёртку.

```python
from functools import wraps

def логировать(func):
    @wraps(func)                 # сохранить func.__name__, __doc__
    def обёртка(*args, **kwargs):
        print(f"вызов {func.__name__}")
        return func(*args, **kwargs)
    return обёртка
```

Для [декоратора-класса](../../../Ядро%20языка/Декоратор%20с%20состоянием.md) декоратор `@wraps` не подходит — там тот же перенос делают вызовом `update_wrapper(self, func)` в `__init__`.

> В стопке из нескольких декораторов `@wraps` нужен **каждому**: пропустил у нижнего — верхний увидит имя `wrapper` вместо настоящего ([разбор](../../../Ядро%20языка/Декораторы%20Python.md#несколько-декораторов-на-одной-функции)).

## Каталог

| Инструмент | Зачем |
|---|---|
| `lru_cache` / `cache` | мемоизация по аргументам (ДП) |
| `reduce` | свёртка последовательности в одно значение |
| `cmp_to_key` | компаратор пары → ключ сортировки |
| `partial` | зафиксировать часть аргументов |
| `wraps` | сохранить метаданные при декораторе |
| `update_wrapper` | то же, но вызовом, а не декоратором — для класса-декоратора |
| `cached_property` | ленивое кэшируемое свойство класса |
| `total_ordering` | достроить все сравнения из `__eq__` и одного из `<`/`>` |
