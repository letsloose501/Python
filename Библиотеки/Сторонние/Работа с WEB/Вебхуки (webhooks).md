# Вебхуки (webhooks)

> _«Не звони мне — я сам позвоню»: сервис сам стучится к тебе, когда есть новость_

---

**Вебхук (webhook)** — способ, которым один сервис уведомляет другой о событии: как только что-то произошло (пришла оплата, запушили коммит, доставили письмо), сервис-источник сам шлёт **HTTP POST** на заранее указанный тобой URL. По сути это «обратный вызов через интернет»: не ты опрашиваешь чужой API, а он сам присылает событие.

## Проблема: поллинг против вебхука

Как узнать, что на чужом сервисе что-то изменилось? Два подхода:

| | **Поллинг (polling)** | **Вебхук (webhook)** |
|---|---|---|
| Кто инициирует | ты дёргаешь чужой API по таймеру | сервис сам шлёт тебе POST |
| Свежесть данных | задержка до следующего опроса | почти мгновенно |
| Нагрузка | 99% запросов впустую («ещё нет?») | запрос только когда есть событие |
| Кто держит эндпоинт | никто | **ты** — публичный URL-приёмник |

**Поллинг** — «звонить каждые 5 минут и спрашивать, не пришло ли». **Вебхук** — «оставить номер, перезвонят сами». Поэтому вебхуки называют *reverse API* или *push-уведомлениями сервер-серверу*.

## Две роли

- **Провайдер (источник)** — сервис, где происходят события и который шлёт POST: GitHub, Stripe, Telegram, платёжка.
- **Потребитель (приёмник)** — **твой** сервер: публичный HTTPS-эндпоинт, который принимает, проверяет и обрабатывает событие.

```
Событие у провайдера ──HTTP POST (JSON + подпись)──▶ твой эндпоинт /webhooks/...
   (оплата прошла)                                        │
                                                          ├─ проверить подпись
                                                          ├─ вернуть 2xx (быстро!)
                                                          └─ отдать работу в очередь
```

## Анатомия входящего запроса

Вебхук — это обычный HTTP-запрос, у которого:

- **метод** — почти всегда `POST`;
- **тело** — `JSON` с данными события (`payload`): тип события, время, объект;
- **заголовки** — метаданные: `Content-Type: application/json`, идентификатор доставки и, главное, **подпись** для проверки подлинности.

## Безопасность — это главное

Твой URL публичный, значит POST на него может отправить **кто угодно**. Без проверки злоумышленник пришлёт фейковое «оплата прошла». Поэтому приёмник обязан убедиться, что запрос действительно от провайдера.

### Проверка подписи (HMAC)

Провайдер и ты знаете общий **секрет** (webhook secret). Провайдер считает от тела запроса **HMAC** — хеш с этим секретом — и кладёт в заголовок. Ты считаешь HMAC сам и сравниваешь. Совпало — запрос подлинный и тело не подменяли; секрет по сети при этом не передаётся.

```python
import hmac, hashlib

def проверить_github(secret: bytes, body: bytes, подпись: str) -> bool:
    # подпись из заголовка вида "sha256=abcd…"
    ожидаемая = "sha256=" + hmac.new(secret, body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(ожидаемая, подпись)   # НЕ ==  (см. ниже)
```

> Сравнивай подписи **только** через `hmac.compare_digest`, а не оператором `==`. Обычное сравнение выходит на первом различающемся байте, и по времени ответа можно побайтово подобрать подпись (**timing-атака**). `compare_digest` сравнивает за постоянное время. Модуль `hmac` — поверх [hashlib](../../../Библиотеки/Модули/Безопасность%20и%20интернет/hashlib.md).

Заголовок подписи у каждого провайдера свой:

| Провайдер | Заголовок | Что внутри |
|---|---|---|
| **GitHub** | `X-Hub-Signature-256` | `sha256=<hexdigest>` — HMAC-SHA256 тела |
| **Stripe** | `Stripe-Signature` | `t=<timestamp>,v1=<hexdigest>` — HMAC-SHA256 от `timestamp.тело` |

### Защита от повтора (replay)

Даже подлинный запрос можно **перехватить и отправить повторно**. Провайдеры кладут в подпись **метку времени** и подписывают её вместе с телом. Ты проверяешь, что событие свежее — обычно окно **5 минут** (tolerance у Stripe).

```python
import time
if abs(time.time() - timestamp) > 300:      # старше 5 минут — отклонить
    raise ValueError("устаревший вебхук — возможен replay")
```

> Не ставь окно `0` — это отключает проверку свежести. И принимай вебхуки только по **HTTPS** ([TLS](../../../Алгоритмы/Иные/HTTPS%20и%20обмен%20ключами%20Диффи%20—%20Хеллмана.md)): по открытому HTTP тело и подпись видны в перехвате.

## Надёжность приёма

### Быстро ответить, потом обрабатывать

Провайдер ждёт ответ несколько секунд, иначе считает доставку неудачной. Поэтому эндпоинт должен **сразу вернуть `2xx`** (обычно `200`), а тяжёлую работу отдать в фоновую **очередь** — [Celery](../../../Библиотеки/Сторонние/Celery.md)/[Redis](../../../Библиотеки/Сторонние/Redis.md).

```
приём → проверить подпись → положить задачу в очередь → вернуть 200
                                                             │
                                          worker обрабатывает в своём темпе
```

Синхронная обработка внутри эндпоинта опасна: всплеск доставок (например, в начале месяца, когда продлеваются все подписки) вызовет таймауты и потерю событий.

### Идемпотентность

Провайдеры гарантируют доставку **at-least-once** — «хотя бы один раз», значит **одно событие может прийти дважды** (ретрай после таймаута, сбой сети). Обработчик обязан быть **идемпотентным**: повтор не должен приводить к двойному эффекту (два списания, два письма).

Приём: у каждого события есть уникальный `id` (у Stripe — `evt_…`, у GitHub — заголовок `X-GitHub-Delivery`). Запоминай обработанные id и пропускай дубли.

```python
if событие["id"] in уже_обработанные:      # уже видели — тихо подтвердить
    return {"ok": True}
уже_обработанные.add(событие["id"])
обработать(событие)
```

> ⚠️ Схема выше — учебная. В бою она **не выдерживает параллельных доставок**: два одновременных повтора одного события оба пройдут проверку и оба обработаются. Проверка и отметка должны быть одной атомарной операцией — вставкой id в таблицу с `UNIQUE`. Разбор — Гонка, которую пропускают почти все, каталог механизмов — Идемпотентность на практике — выбор стратегии.

### Ретраи и порядок

- Ответил не-`2xx` или не ответил вовремя → провайдер **повторит** доставку (обычно с экспоненциальной задержкой) — ещё одна причина для идемпотентности.
- **Порядок не гарантирован**: события могут прийти не в том порядке, в каком случились. Опирайся на метку времени внутри payload, а не на порядок получения.

## Сквозной пример: приёмник на FastAPI

Эндпоинт для вебхуков GitHub: проверка подписи по сырому телу → постановка в очередь → быстрый `200`.

```python
import hmac, hashlib, json
from fastapi import FastAPI, Request, Header, HTTPException
from tasks import обработать_событие      # Celery-задача

app = FastAPI()
SECRET = b"...секрет из настроек вебхука..."

@app.post("/webhooks/github")
async def github_webhook(
    request: Request,
    x_hub_signature_256: str = Header(None),
    x_github_delivery: str = Header(None),      # уникальный id доставки
):
    body = await request.body()                 # 1. СЫРЫЕ байты — подпись считается по ним
    ожидаемая = "sha256=" + hmac.new(SECRET, body, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(ожидаемая, x_hub_signature_256 or ""):
        raise HTTPException(403, "bad signature")  # 2. подделка → 403

    событие = json.loads(body)                  # 3. парсим ПОСЛЕ проверки
    обработать_событие.delay(x_github_delivery, событие)  # 4. в очередь Celery
    return {"ok": True}                          # 5. сразу 2xx, не ждём обработку
```

Как читать: тело берём **сырым** (`await request.body()`) и подпись считаем именно по этим байтам — иначе проверка развалится (см. ловушку ниже). Всё, что дольше миллисекунд, уходит в `.delay()` воркеру.

## Ловушки

**Подпись по пересобранному JSON вместо сырого тела.** Классическая ошибка: распарсить JSON, потом сериализовать обратно и от него считать HMAC.

```python
# НЕПРАВИЛЬНО — подпись не сойдётся
data = await request.json()
body = json.dumps(data).encode()      # порядок ключей и пробелы изменились!
проверить(SECRET, body, подпись)      # provider считал по ДРУГИМ байтам

# ПРАВИЛЬНО — сырые байты запроса
body = await request.body()
проверить(SECRET, body, подпись)
```

Причина: HMAC считается **по байтам**. `json.dumps` может переставить ключи, убрать/добавить пробелы, поменять экранирование — тело станет другим, хеш не совпадёт. Подпись проверяй **до** любого парсинга, по исходным байтам.

**Тяжёлая работа внутри эндпоинта** — таймаут и потеря событий на всплеске. Фикс: сразу `2xx`, обработка в очереди.

**Не проверять подпись «на своём проекте»** — публичный URL примет фейк от любого. Подпись обязательна всегда.
