# OAuth 2.0

> _«Войти через Google» — дать доступ, не отдавая пароль_

---

**OAuth 2.0** — стандартный протокол **авторизации**: он позволяет приложению получить ограниченный доступ к данным пользователя на другом сервисе, **не передавая ему пароль**. Именно он стоит за кнопками «Войти через Google/GitHub/VK». Это не библиотека, а протокол (RFC 6749), который реализуют разные библиотеки и сервисы.

## Проблема, которую решает

Допустим, стороннему приложению нужен доступ к твоим фото в облаке. Отдать ему **логин и пароль** — опасно: оно получит полный контроль над аккаунтом и будет хранить твой пароль. OAuth решает это так: пароль ты вводишь **только** на сайте облака, а приложению выдаётся ограниченный **токен** — «пропуск» на конкретные действия, который можно отозвать.

## Четыре роли

| Роль | Кто это | Пример |
|---|---|---|
| **Resource Owner** | владелец данных (пользователь) | ты |
| **Client** | приложение, которому нужен доступ | стороннее приложение |
| **Authorization Server** | выдаёт токены после согласия | сервер Google |
| **Resource Server** | хранит данные, пускает по токену | API Google Photos |

## Как это работает (Authorization Code Flow)

Самый распространённый сценарий — с кодом авторизации:

```
1. Пользователь жмёт «Войти через Google» в приложении (Client)
2. Client перенаправляет его на Authorization Server (Google)
3. Пользователь вводит пароль ТАМ и подтверждает доступ (scope)
4. Google возвращает Client'у одноразовый authorization code
5. Client меняет code на ACCESS TOKEN (запрос сервер-сервер)
6. Client идёт с токеном в Resource Server за данными
```

```
Пользователь ──▶ Client ──▶ Authorization Server (вход + согласие)
                   ▲                  │ code
                   └──────────────────┘
                   code → access token → Resource Server (данные)
```

Ключевой момент: пароль вводится только на шаге 3 — на стороне сервиса, а приложение его никогда не видит.

## Токены и scope

- **Access token** — «пропуск» для доступа к данным; короткоживущий, шлётся в заголовке `Authorization: Bearer <token>`.
- **Refresh token** — долгоживущий; обменивается на новый access token, когда тот истёк, без повторного входа.
- **Scope** — область доступа: что именно разрешено (`read:photos`, `email`). Пользователь видит и подтверждает scope на шаге согласия.

Эта механика токенов — та же, что у [JWT в DRF](../../../Фреймворки/DJANGO/Разделение%20доступа%20в%20DRF.md#jwt-authentication); часто access token и есть JWT.

## Как это делают на Python

Руками эту пляску не пишут: обмен кода на токен, `state` против CSRF, подстановка заголовка в каждый запрос — всё берёт на себя **`requests-oauthlib`**, надстройка над [requests](../../../Библиотеки/Сторонние/Работа%20с%20WEB/requests.md).

```bash
pip install requests-oauthlib
```

Сначала приложение регистрируют у провайдера и получают три вещи: **ClientID**, **Client secret** и **Redirect URI** _(у Яндекса — на [oauth.yandex.ru/client/new](https://oauth.yandex.ru/client/new))_.

```python
from requests_oauthlib import OAuth2Session

# 1. собрать ссылку, по которой пользователь пойдёт давать согласие
сессия = OAuth2Session(CLIENT_ID, redirect_uri=REDIRECT_URI, scope=['cloud_api:disk.app_folder'])
ссылка, state = сессия.authorization_url('https://oauth.yandex.ru/authorize')
print('Открой и подтверди доступ:', ссылка)

# 2. пользователь вернулся на redirect_uri — в адресе лежит authorization code
адрес_возврата = input('Вставь адрес, на который тебя перекинуло: ')

# 3. обменять code на access token (это запрос сервер-сервер, тут нужен secret)
токен = сессия.fetch_token(
    'https://oauth.yandex.ru/token',
    authorization_response=адрес_возврата,
    client_secret=CLIENT_SECRET,
)

# 4. дальше сессия — обычный requests.Session, но сама шлёт Authorization в каждом запросе
инфо = сессия.get('https://cloud-api.yandex.net/v1/disk').json()
print(инфо['total_space'])
```

**Как это читать.** Шаги 1–3 — это ровно пункты 2–5 схемы выше, только кодом. `state` библиотека генерирует и проверяет сама: это случайная строка, по которой на возврате видно, что ответ пришёл на **твой** запрос, а не подсунут чужим сайтом. После `fetch_token` объект `сессия` ведёт себя как [requests.Session](../../../Библиотеки/Сторонние/Работа%20с%20WEB/requests.md#сессии) — токен подставляется в заголовок автоматически, руками его больше не трогают.

> **Секреты — не в коде.** `CLIENT_SECRET` и полученный токен дают полный доступ в рамках scope. Держи их в переменных окружения или конфиге вне репозитория и внеси файл в `.gitignore` — см. пример с `config.json` в [requests](../../../Библиотеки/Сторонние/Работа%20с%20WEB/requests.md#класс-клиент-к-api--инкапсуляция-токена-и-запросов).

## Авторизация, а не аутентификация

> OAuth 2.0 отвечает на вопрос **«что приложению разрешено делать»** (авторизация), а не «кто пользователь» ([аутентификация](../../../Аутентификация%20—%20методы%20и%20протоколы.md)). Для входа-идентификации поверх OAuth построен отдельный слой — **OpenID Connect** (OIDC), который добавляет `id_token` с данными пользователя. «Войти через Google» — это как раз OIDC над OAuth.

## Где встречается

- Кнопки «Войти через…» на сайтах (через OpenID Connect);
- доступ приложений к API сервисов (Google, GitHub, платёжные системы);
- выдача токенов для собственного API (в связке с [DRF](../../../Фреймворки/DJANGO/Разделение%20доступа%20в%20DRF.md)).

## Связи

- [Разделение доступа в DRF](../../../Фреймворки/DJANGO/Разделение%20доступа%20в%20DRF.md) — токены и Bearer-заголовки, та же механика, что access token OAuth;
- Аутентификация — OAuth про авторизацию; для входа нужен OpenID Connect поверх;
- [requests](../../../Библиотеки/Сторонние/Работа%20с%20WEB/requests.md) — клиент, которым приложение обменивает code на токен и ходит в API;
- [JWT — подпись и проверка токенов](../../../JWT%20—%20подпись%20и%20проверка%20токенов.md) — что внутри access token, если он JWT: подпись, JWKS, валидация; там же opaque-токены и интроспекция;
- [HTTPS и обмен ключами Диффи — Хеллмана](../../../Алгоритмы/Иные/HTTPS%20и%20обмен%20ключами%20Диффи%20—%20Хеллмана.md) — OAuth работает только по HTTPS: токены нельзя слать открыто.
