# GraphQL

> _Один эндпоинт, а что именно вернуть — решает клиент, а не сервер_

---

**GraphQL** — язык запросов к API и среда его выполнения на сервере. В отличие от [REST](../../../Фреймворки/DJANGO/API.md#что-такое-rest-api), где сервер задаёт набор адресов и форму ответа, здесь клиент присылает **описание нужных ему данных**, а сервер отдаёт ровно их — ни полем больше, ни полем меньше. Разработан в Facebook в 2012 году под мобильные приложения, открыт в 2015-м.

## Проблема: что не так с REST

Экран профиля показывает имя пользователя, его последние три поста и число подписчиков. В REST это выглядит так:

```
GET /users/42            → всё про пользователя: 30 полей, нужны 2
GET /users/42/posts      → все посты, нужны 3
GET /users/42/followers  → весь список, нужно только количество
```

Две болезни разом:

- **Over-fetching** — сервер прислал 30 полей, клиенту нужны два. Лишний трафик, особенно заметный на мобильной сети.
- **Under-fetching** — одного запроса не хватает, приходится делать три подряд, каждый со своей задержкой сети.

Обходной путь в REST — заводить эндпоинты под каждый экран (`/users/42/profile-screen`), но их становится столько же, сколько экранов, и каждый редизайн требует правки бэкенда.

GraphQL решает это одним запросом на один эндпоинт `/graphql`:

```graphql
query {
  user(id: 42) {
    name
    posts(last: 3) { title }
    followersCount
  }
}
```

Ответ повторяет форму запроса:

```json
{ "data": { "user": {
    "name": "Аня",
    "posts": [{ "title": "..." }, { "title": "..." }, { "title": "..." }],
    "followersCount": 128
}}}
```

## Схема и типы

**Схема** — контракт API: какие есть типы, поля и операции. Она строго типизирована и служит одновременно документацией — клиент может запросить у сервера саму схему (**интроспекция**) и построить по ней автодополнение.

```graphql
type User {
  id: ID!                 # ! — поле не может быть null
  name: String!
  posts(last: Int): [Post!]!
}

type Post {
  title: String!
  author: User!
}

type Query {              # точка входа для чтения
  user(id: ID!): User
}

type Mutation {           # точка входа для изменения
  createPost(title: String!): Post!
}
```

## Три вида операций

| Операция | Что делает | Аналог в REST |
|---|---|---|
| **query** | читает данные | `GET` |
| **mutation** | изменяет данные | `POST` / `PUT` / `PATCH` / `DELETE` |
| **subscription** | подписка на события, сервер шлёт обновления сам | [Вебхуки (webhooks)](../../../Библиотеки/Сторонние/Работа%20с%20WEB/Вебхуки%20%28webhooks%29.md) или WebSocket |

Технически и query, и mutation уходят на сервер **POST-запросом** на один и тот же URL — разделение чисто семантическое: мутации сервер выполняет последовательно, запросы может параллельно.

## Резолверы

**Резолвер** — функция, которая умеет добыть значение одного поля. Схема говорит *что* бывает, резолверы — *откуда это брать*. Выполняя запрос, сервер обходит дерево полей и вызывает резолвер на каждое.

На Python две основные библиотеки: **Strawberry** (современная, на аннотациях типов и dataclass'ах) и **Graphene** (старше, больше кода). Пример на Strawberry — установка `pip install "strawberry-graphql[cli]"`:

```python
import strawberry

@strawberry.type
class Post:
    title: str

@strawberry.type
class User:
    id: strawberry.ID
    name: str

    @strawberry.field                       # ← резолвер поля posts
    def posts(self, last: int = 10) -> list[Post]:
        return получить_посты(self.id, last)

@strawberry.type
class Query:
    @strawberry.field
    def user(self, id: strawberry.ID) -> User:
        return получить_пользователя(id)

schema = strawberry.Schema(query=Query)
```

Библиотека даёт готовые интеграции для [FastAPI](../../../Фреймворки/FastAPI.md), [Django](../../../Фреймворки/DJANGO/Django.md) и [Flask](../../../Фреймворки/FLASK.md) — схема подключается как обычный роут.

## Чем расплачиваешься

GraphQL не «лучше REST», у него другой набор проблем — и на собеседовании ценят именно это знание.

**N+1 запросов.** Резолверы вызываются на каждое поле каждого объекта. Запрос «100 постов и автор каждого» — это 1 запрос за посты и 100 за авторов. Лечится **DataLoader**: он копит вызовы за один тик цикла событий и делает один batch-запрос. Та же болезнь, что и [N+1 в ORM](../../../Фреймворки/DJANGO/ORM%20Django.md#ловушка-n1-запросов), но здесь она не видна в коде — её создаёт форма клиентского запроса.

**HTTP-кеш не работает.** Все запросы — POST на один URL, поэтому ни браузер, ни CDN, ни nginx закешировать ответ не могут. В REST `GET /users/42` кешируется бесплатно. Нужен кеш на уровне приложения ([Redis](../../../Библиотеки/Сторонние/Redis.md), persisted queries).

**Клиент может уронить сервер.** Вложенность `user → posts → author → posts → author…` формально валидна, а стоит экспоненциально. Обязательны ограничения: максимальная глубина, стоимость запроса, таймаут.

**Коды ответов бесполезны.** GraphQL почти всегда отвечает `200 OK`, а ошибки кладёт в поле `errors` тела. Мониторинг «по числу 5xx» ничего не покажет.

**Загрузка файлов и бинарные данные** — не его задача, обычно оставляют отдельному REST-эндпоинту.

## Когда брать

| Ситуация | Выбор |
|---|---|
| Много разных клиентов (веб, iOS, Android), каждому нужен свой срез данных | **GraphQL** |
| Фронтенд меняется часто, бэкенд не успевает за эндпоинтами | **GraphQL** |
| Данные сильно связаны, экраны собирают их из нескольких сущностей | **GraphQL** |
| Простой CRUD, один клиент | **REST** — проще и кешируется |
| Публичное API, важны кеш и предсказуемая нагрузка | **REST** |
| Общение между микросервисами, нужна скорость | **gRPC** |

> Ответ на собеседовании: GraphQL — не замена REST, а решение конкретной боли «клиенту нужен свой набор полей, а эндпоинтов на всех не напасёшься». Платишь за это кешем, защитой от тяжёлых запросов и борьбой с N+1.
