# RabbitMQ

> _Почта для программ: отправитель кладёт письмо, брокер доставит его нужному получателю_

---

**RabbitMQ** — брокер сообщений: посредник, который принимает сообщения от одних программ (**producer**) и надёжно доставляет их другим (**consumer**). Он реализует протокол **AMQP** и берёт на себя маршрутизацию, буферизацию и гарантии доставки. Написан на Erlang, славится надёжностью — поэтому его берут там, где терять задачи нельзя (платежи, заказы), и как «серьёзный» брокер для [Celery](../../Библиотеки/Сторонние/Celery.md) вместо [Redis](../../Библиотеки/Сторонние/Redis.md).

## Проблема: зачем нужен брокер сообщений

Пусть сервис A хочет отдать работу сервису B. Если A вызывает B **напрямую**, возникают проблемы:

- B недоступен или перегружен → A ждёт или падает;
- B медленный → A блокируется на время обработки;
- B нужно масштабировать → A должен знать про все его копии.

**Брокер** разрывает эту связь. A кладёт сообщение в брокер и сразу свободен; B забирает, когда готов. Если B упал — сообщение ждёт в очереди; если B много — они разбирают очередь параллельно.

```
Producer ──сообщение──▶ [ RabbitMQ: буфер + маршрутизация ] ──▶ Consumer(ы)
 (не ждёт)                    сообщение ждёт, если некому                разбирают в своём темпе
```

Это даёт **развязку** (producer и consumer не знают друг о друге), **буферизацию** (пики нагрузки сглаживаются) и **надёжность** (сообщение не теряется, пока не обработано).

## Модель AMQP

Ключевое отличие RabbitMQ от простых очередей: producer шлёт сообщение **не в очередь напрямую**, а в **обменник (exchange)**, а тот по правилам раскладывает его по очередям.

```
Producer ──▶ EXCHANGE ──(binding + routing key)──▶ QUEUE ──▶ Consumer
             обменник        правило маршрута       очередь
```

- **Producer** — отправитель сообщения.
- **Exchange (обменник)** — точка входа: получает сообщение и решает, в какие очереди его положить (или никуда).
- **Queue (очередь)** — буфер, где сообщение ждёт потребителя. Хранит сообщения в порядке FIFO.
- **Binding (привязка)** — правило «эта очередь слушает этот обменник» (часто с ключом маршрутизации).
- **Routing key** — «адрес» сообщения; по нему обменник решает, куда его направить.
- **Consumer** — получатель: подписан на очередь, забирает и обрабатывает сообщения.

## Типы обменников (exchange)

Как именно обменник раскладывает сообщения — зависит от его типа:

| Тип | Правило маршрутизации | Применение |
|---|---|---|
| **direct** | routing key **точно** совпадает с ключом привязки | адресная доставка в конкретную очередь |
| **fanout** | во **все** привязанные очереди, routing key игнорируется | broadcast, pub/sub |
| **topic** | routing key по **шаблону**: `*` — одно слово, `#` — любое число слов | гибкая маршрутизация по категориям |
| **headers** | по совпадению **заголовков** сообщения, а не routing key | сложные условия без routing key |

_Обменник по умолчанию (пустое имя `''`) — это direct-обменник, где routing key = имя очереди. Поэтому «положить прямо в очередь `tasks`» = опубликовать в `''` с routing key `tasks`._

```
# topic-обменник: routing key = "order.created"
order.*   ловит  order.created, order.paid       (* = ровно одно слово)
order.#   ловит  order.created, order.eu.paid    (# = ноль и более слов)
```

## Подтверждения и надёжность

RabbitMQ старается **не терять** сообщения — но только если его правильно настроить.

- **Acknowledgement (ack)** — consumer подтверждает обработку. Пока `basic_ack` не пришёл, сообщение считается «в работе»; если consumer отключился, не подтвердив — сообщение **вернётся в очередь** другому. С `auto_ack=True` подтверждение шлётся при доставке — быстрее, но при падении consumer сообщение теряется.
- **Durable queue + persistent message** — чтобы очередь и сообщения пережили **перезапуск брокера**, нужны обе вещи: очередь объявлена `durable=True` **и** сообщение помечено `delivery_mode=2`. Одно без другого не спасёт.
- **Prefetch / QoS** — `basic_qos(prefetch_count=1)`: не давать consumer новое сообщение, пока он не подтвердил текущее. Так быстрые воркеры не простаивают, а медленные не завалены — **честное распределение** (fair dispatch).
- **Dead Letter Exchange (DLX)** — куда отправлять сообщения, которые отвергли (`nack`), которые протухли по TTL или переполнили очередь. Обычно — в отдельную очередь «на разбор», чтобы не терять и не зациклить повторы.

## Пример на Python (pika)

Клиент AMQP для Python — **`pika`**. Классический сценарий — рабочая очередь (work queue).

```bash
pip install pika
```

```python
# producer.py — отправитель
import pika

conn = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
ch = conn.channel()
ch.queue_declare(queue='tasks', durable=True)          # очередь переживёт рестарт брокера

ch.basic_publish(
    exchange='',                                        # обменник по умолчанию
    routing_key='tasks',                                # = имя очереди
    body='обработать заказ 42',
    properties=pika.BasicProperties(delivery_mode=2),   # persistent-сообщение
)
conn.close()
```

```python
# consumer.py — получатель
import pika

conn = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
ch = conn.channel()
ch.queue_declare(queue='tasks', durable=True)

def callback(ch, method, properties, body):
    process(body)                                       # 1. обработать
    ch.basic_ack(delivery_tag=method.delivery_tag)      # 2. подтвердить ПОСЛЕ обработки

ch.basic_qos(prefetch_count=1)                          # по одному в руки
ch.basic_consume(queue='tasks', on_message_callback=callback)
ch.start_consuming()                                    # слушать бесконечно
```

Как читать: producer публикует в очередь и уходит; несколько запущенных consumer'ов разбирают `tasks` **параллельно** (competing consumers). Ack после обработки + `prefetch_count=1` гарантируют, что упавший воркер не «съест» сообщение — оно уйдёт другому.

## Паттерны обмена

- **Work queue** (рабочая очередь) — одна очередь, много consumer'ов делят нагрузку. Каждое сообщение достаётся **одному** воркеру. _Фоновые задачи._
- **Publish/Subscribe** — `fanout`-обменник шлёт копию сообщения **всем** подписанным очередям. _Уведомления, рассылка событий._
- **Routing** — `direct`/`topic`-обменник направляет сообщение выборочно по routing key. _Логи по уровням, события по типам._
- **RPC** — запрос-ответ через две очереди (`reply_to` + `correlation_id`): клиент шлёт запрос и ждёт ответ в отдельной очереди.

## Повторы и Dead Letter Queue (DLQ)

Сообщение упало в обработке (ошибка в consumer, `nack`). Что дальше? Наивный `requeue=True` возвращает его **в ту же очередь сразу** — и если ошибка стабильная (битые данные, недоступная зависимость), сообщение крутится в **бесконечном цикле**, забивая consumer. Нужна стратегия: несколько повторов с паузой, а потом — «на разбор».

**Dead Letter Exchange (DLX) / Dead Letter Queue (DLQ)** — обменник (и стоящая за ним очередь), **куда RabbitMQ отправляет «мёртвые» сообщения**. Сообщение становится dead-letter, если:
- его отвергли с `basic_reject`/`basic_nack` и `requeue=False`;
- истёк его **TTL** (время жизни);
- очередь переполнилась (превышен лимит длины).

```
Основная очередь ──(nack, requeue=false / TTL / overflow)──▶ DLX ──▶ DLQ (очередь «на разбор»)
        ▲                                                                    │
        └──────────── retry-очередь с TTL (пауза), потом назад ◀────────────┘
```

Очередь объявляют с указанием, куда отправлять мёртвые сообщения:

```python
ch.queue_declare(queue='tasks', durable=True, arguments={
    'x-dead-letter-exchange': 'dlx',        # куда уходят dead-letter из этой очереди
    'x-message-ttl': 60000,                 # (опц.) TTL сообщения — 60 c
    'x-max-length': 100000,                 # (опц.) лимит длины очереди
})
```

**Ретрай с задержкой (backoff) через TTL + DLX.** Классический трюк без плагинов: сообщение из основной очереди при сбое уходит в **retry-очередь**, у которой задан TTL (пауза) и DLX обратно на основную. Отлежав TTL, оно возвращается — получается повтор **с задержкой**. Счётчик попыток держат в заголовке (`x-death` или свой), и после N попыток отправляют уже в **финальную DLQ** — там сообщения ждут ручного разбора, не теряясь и не зацикливаясь.

- **Exponential backoff** — паузу увеличивают с каждой попыткой (1с → 5с → 30с) через разные retry-очереди с разным TTL: не долбить упавшую зависимость.
- **Poison message** («ядовитое» сообщение) — то, что падает всегда (битые данные). Его цель — не повторять вечно, а после лимита увести в DLQ на разбор.
- Готовый плагин `rabbitmq_delayed_message_exchange` умеет отложенную доставку без ручных retry-очередей.

> DLQ — это не «мусорка», а **очередь на разбор**: сюда попадает то, что не удалось обработать за N попыток. Её мониторят (растёт → что-то системно ломается) и разбирают вручную или отдельным процессом. Повторная доставка из DLQ требует идемпотентного обработчика — см. Гарантии доставки и идемпотентность.

## RabbitMQ или Redis как брокер

Оба работают брокером для [Celery](../../Библиотеки/Сторонние/Celery.md), но это разные инструменты:

| | [Redis](../../Библиотеки/Сторонние/Redis.md) | RabbitMQ |
|---|---|---|
| **Что это** | in-memory key-value, брокер «заодно» | специализированный брокер (AMQP) |
| **Маршрутизация** | простая (списки) | богатая: exchange, routing key, topic |
| **Надёжность доставки** | слабее, проще потерять при сбое | ack, durable/persistent, DLX |
| **Скорость/простота** | быстрее и проще для мелких задач | тяжелее в настройке, но надёжнее |
| **Бонус** | ещё и кеш/сессии в том же сервисе | панель мониторинга, гибкая маршрутизация |
| **Когда брать** | простые фоновые задачи, кеш рядом | критичные задачи, сложная маршрутизация |

> Правило: нужна максимальная простота и Redis уже есть в проекте — бери Redis. Нужны гарантии доставки, сложная маршрутизация или большой поток задач — RabbitMQ.

## Установка и панель управления

Для локальной разработки проще всего [контейнером](../../DevOps/Docker.md):

```bash
docker run -d -p 5672:5672 -p 15672:15672 rabbitmq:management
#   5672  — порт AMQP (по нему подключаются producer/consumer)
#   15672 — веб-панель управления (логин/пароль по умолчанию guest/guest)
```

Панель на `:15672` показывает очереди, обменники, скорость сообщений, потребителей — удобно смотреть, копится ли очередь.

> **Пользователь `guest` работает только с localhost.** Это защита по умолчанию: подключиться под ним с другой машины нельзя, даже с правильным паролем. Для удалённого доступа заводят своего пользователя и выдают права на vhost.

### Установка на Debian/Ubuntu

На сервере RabbitMQ ставят пакетом. Есть два пути: **apt из репозиториев Team RabbitMQ** (рекомендуемый) и **ручная установка через `dpkg`** (тестируется и поддерживается по остаточному принципу).

Поддерживаются Ubuntu 20.04 / 22.04 / 24.04 и Debian 11 (Bullseye) / 12 (Bookworm) / 13 (Trixie).

> **Главная ловушка: не ставить из штатного репозитория дистрибутива.** Пакеты RabbitMQ там отстают от актуальных на много релизов и обычно уже вне community-поддержки. Между релизами Debian проходят годы, поэтому обновиться потом тяжело.

**Зависимость от Erlang/OTP.** RabbitMQ написан на Erlang, и версия Erlang — не деталь, а совместимость: у каждого релиза RabbitMQ свой диапазон поддерживаемых версий. Erlang в стандартных репозиториях дистрибутивов тоже сильно устарел и современными версиями RabbitMQ не поддерживается. Актуальные ветки (26.x, 27.x) берут из репозиториев Team RabbitMQ или из Launchpad PPA.

```
Штатный репозиторий Debian/Ubuntu ──▶ старый RabbitMQ + старый Erlang ──▶ несовместимость
Репозитории Team RabbitMQ         ──▶ актуальные обе части            ──▶ рабочая связка
```

Практический порядок: подключить репозитории (свои для Erlang и для RabbitMQ), поставить ключи подписи, затем `rabbitmq-server`. В документации на каждый дистрибутив дан готовый скрипт, который делает всё это одной командой.

После установки сервис называется `rabbitmq-server` и работает от непривилегированного пользователя `rabbitmq`. Управление — через `systemctl`, для установки и работы с сервисом нужен sudo.

## Ловушки

**`auto_ack=True` при важных задачах** — подтверждение шлётся при доставке, до обработки. Consumer упал в процессе — сообщение потеряно.

```python
ch.basic_consume(queue='tasks', on_message_callback=cb, auto_ack=True)   # ✗ теряет при падении
# ✓ — ручной ack после обработки (см. пример выше)
```

**Забыть про durability** — очередь без `durable=True` или сообщение без `delivery_mode=2` исчезнут при перезапуске брокера. Нужны **обе** пометки.

**Неограниченная очередь** — если consumer'ы медленнее producer'ов, очередь растёт, пока не кончится память. Следи за длиной (панель), ставь TTL/лимит и DLX.

**Тяжёлые сообщения** — как и с Celery, передавай **id/ссылку**, а не большой объект или файл; иначе брокер захлебнётся трафиком.

## Связи

- [Celery](../../Библиотеки/Сторонние/Celery.md) — RabbitMQ как надёжный брокер задач (альтернатива Redis);
- [Redis](../../Библиотеки/Сторонние/Redis.md) — более простой брокер + кеш; сравнение выше;
- Идемпотентность — при повторной доставке (requeue после сбоя) обработчик должен быть идемпотентным;
- Гарантии доставки и идемпотентность — at-least/at-most/exactly once, откуда берутся повторы и DLQ;
- Событийная архитектура и Kafka — брокер-очередь vs распределённый лог; когда что;
- Распределённые транзакции — RabbitMQ как транспорт событий саги и вычитки Outbox;
- Взаимодействие сервисов — асинхронная связь через брокер в ряду REST/gRPC;
- [Django](../../Фреймворки/DJANGO/Django.md) · [FastAPI](../../Фреймворки/FastAPI.md) — фоновые задачи через Celery поверх RabbitMQ;
- Компьютерные сети — RabbitMQ работает поверх TCP (порт 5672), панель — по HTTP (15672).
