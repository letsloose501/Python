# Нагрузочное тестирование — locust и k6

Вопрос «выдержит ли сервис Чёрную пятницу» имеет ровно два способа ответа: подождать пятницы или проверить заранее. **Нагрузочное тестирование** — воспроизведение реального трафика на управляемом стенде, чтобы найти потолок системы **до** того, как его найдут пользователи.

Юнит-тесты отвечают «работает ли код правильно» ([Юнит-тестирование Python](../../../Библиотеки/Сторонние/Тесты/Юнит-тестирование%20Python.md)). Нагрузочные — «работает ли он **под нагрузкой**». Это разные вопросы: код может быть безупречным и падать на 200 RPS из-за пула соединений в десять штук.

---

## Пять видов тестов

Разные вопросы требуют разной формы нагрузки.

| Вид | Форма нагрузки | На какой вопрос отвечает |
|---|---|---|
| **Smoke** | Минимальная, 1–5 пользователей | Сценарий вообще рабочий? Прогон перед остальными |
| **Load** | Ожидаемая рабочая | Держим ли обычный трафик с нужным временем ответа |
| **Stress** | Растёт, пока не сломается | Где потолок и **как именно** ломается |
| **Spike** | Резкий скачок и спад | Переживём ли всплеск (реклама, рассылка) |
| **Soak** | Средняя, но 6–24 часа | Есть ли утечки памяти и деградация со временем |

> Самый ценный для мидла — **stress**: он даёт не «выдержит/не выдержит», а число и причину. «Потолок 850 RPS, упирается в пул соединений к БД» — это ответ, с которым можно работать.

---

## Что измеряем

**Нельзя измерять среднее.** Смотрят перцентили — по той же причине, что и в [мониторинге](../../../DevOps/Наблюдаемость%20—%20метрики,%20логи,%20трейсы.md#-среднее-врёт--считай-перцентили).

- **RPS / throughput** — сколько запросов система реально обработала.
- **Latency p50 / p95 / p99** — время ответа.
- **Error rate** — доля неуспешных.
- **Насыщение ресурсов** — CPU, память, соединения БД, глубина очередей.

**Как выглядит потолок на графике:**

```
RPS   ──────╱▔▔▔▔▔╲__________     ← перестал расти и просел
           ╱        
p95   _____╱▔▔▔▔╱▔▔▔▔▔▔╱          ← начал расти раньше, чем упал RPS
errors ______________╱▔▔▔         ← пошли ошибки последними
       │        │
       │        └── точка насыщения: RPS больше не растёт,
       │            а латентность взлетает
       └── здоровая зона
```

**Точка насыщения** — момент, когда добавление нагрузки перестаёт увеличивать пропускную способность и начинает только увеличивать время ответа. Это и есть потолок, и он всегда наступает **раньше**, чем начинаются ошибки.

### Открытая и закрытая модель

Тонкость, на которой ошибаются почти все.

- **Закрытая модель** — фиксированное число виртуальных пользователей, каждый шлёт следующий запрос **после** ответа. Если сервис затормозил, нагрузка сама снизится.
- **Открытая модель** — фиксированный RPS независимо от ответов. Сервис затормозил — запросы всё равно летят и копятся.

Реальный интернет-трафик ведёт себя как **открытая** модель: пользователям всё равно, что тебе плохо. Поэтому стресс-тесты в закрытой модели дают оптимистичный результат — система «сама себя щадит».

**Термины:** **VU** (virtual user) — виртуальный пользователь, один поток сценария. **Ramp-up** — плавный набор нагрузки. **Think time** — пауза между действиями, имитирующая живого человека.

## Locust — на Python

**Locust** — инструмент, где сценарий пишется обычным Python-кодом. Родной вариант, если стек питоновский.

```python
from locust import HttpUser, task, between

class ShopUser(HttpUser):
    wait_time = between(1, 3)          # think time: пауза 1–3 с

    def on_start(self):                # выполняется один раз при старте VU
        self.client.post("/login", json={"user": "test", "password": "test"})

    @task(3)                           # вес 3 — выполняется втрое чаще
    def view_catalog(self):
        self.client.get("/catalog", name="/catalog")

    @task(1)
    def view_product(self):
        pid = random.randint(1, 1000)
        # name — чтобы 1000 разных URL не размазались по 1000 строк отчёта
        self.client.get(f"/product/{pid}", name="/product/[id]")
```

```bash
locust -f loadtest.py --host=https://staging.example.com
# веб-интерфейс на localhost:8089: задать число VU и скорость набора

locust -f loadtest.py --headless -u 500 -r 50 -t 5m --csv=result
# без UI: 500 пользователей, набор по 50/с, 5 минут, результат в CSV
```

**Плюсы:** сценарий — обычный Python, легко переиспользовать модели и логику. **Минус:** сам на Python, поэтому одна машина даёт меньше нагрузки; для больших объёмов нужен распределённый режим (master + workers).

## k6 — когда нужна нагрузка побольше

**k6** написан на Go, сценарии — на JavaScript. Одна машина выдаёт заметно больше RPS, чем locust.

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [                              // профиль нагрузки
    { duration: '2m', target: 100 },     // разгон до 100 VU
    { duration: '5m', target: 100 },     // держим
    { duration: '2m', target: 0 },       // спад
  ],
  thresholds: {                          // критерии приёмки — тест сам упадёт
    http_req_duration: ['p(95)<500'],    // p95 меньше 500 мс
    http_req_failed: ['rate<0.01'],      // ошибок меньше 1%
  },
};

export default function () {
  const res = http.get('https://staging.example.com/catalog');
  check(res, { 'status 200': (r) => r.status === 200 });
  sleep(1);
}
```

**`thresholds` — главная фишка k6:** тест возвращает ненулевой код выхода при нарушении порога, поэтому его можно поставить в [CI](../../../DevOps/CI%20CD.md) как обычную проверку. Деградация производительности ловится на пул-реквесте, а не в проде.

| | locust | k6 |
|---|---|---|
| Язык сценария | Python | JavaScript |
| Нагрузка с одной машины | Средняя | Высокая |
| Пороги приёмки в CI | Вручную | Встроенные `thresholds` |
| Когда брать | Стек Python, сложная логика сценария | Нужен объём и проверка в CI |

## 🔴 Пять ловушек

**1. Тест с одной машины.** На больших нагрузках упирается генератор, а не сервис. Признак: RPS не растёт, а CPU на машине с locust — 100%. Проверяй нагрузку **на самом генераторе** прежде чем радоваться найденному «потолку».

**2. Нет прогрева.** Первые секунды идут на JIT, заполнение пулов и прогрев кэшей. Первую минуту в измерения не включают.

**3. Нереалистичные данные.** Тысяча VU запрашивает **один и тот же** товар — всё лежит в кэше, результат прекрасный и бессмысленный. Данные должны быть распределены как в проде.

**4. Стенд не похож на прод.** Один инстанс вместо пяти, пустая база вместо 40 млн строк. Цифры со стенда не переносятся на прод напрямую — но динамика и узкое место переносятся.

**5. Тест по проду без предупреждения.** Быстрый способ устроить аварию своими руками и испортить отношения с командой. Гоняй по staging; по проду — только согласованно, в окно, с планом отката.

> ⚠️ **Нагрузочный тест без включённого мониторинга бесполезен.** Ты увидишь, что сервис лёг на 800 RPS, но не узнаешь почему. Смотреть надо одновременно: графики генератора и графики сервиса ([Prometheus и Grafana](../../../DevOps/Prometheus%20и%20Grafana.md)).

## Сквозной пример: находим потолок

**Шаг 1. Smoke.** 1 VU, 1 минута. Убеждаемся, что сценарий вообще работает и авторизация проходит.

**Шаг 2. Load.** Ожидаемая нагрузка (скажем, 100 RPS), 10 минут. Записываем p95 и долю ошибок как **базовую линию**.

**Шаг 3. Stress.** Ступеньками: 100 → 200 → 400 → 800 RPS, по 5 минут на ступень. Одновременно смотрим дашборд сервиса.

**Шаг 4. Находим точку насыщения.** Ищем ступень, где RPS перестал расти, а p95 начал взлетать.

**Шаг 5. Определяем узкое место** — по метрикам сервиса, а не догадкой:

| Что видим на дашборде | Узкое место |
|---|---|
| CPU приложения ~100% | Упёрлись в процессор — профилировать код ([Профилирование и отладка](../../../Библиотеки/Модули/Отладка%20и%20утилиты/Профилирование%20и%20отладка.md)) |
| CPU низкий, время ответа растёт | Ждём внешнего: БД, соседний сервис, диск |
| Соединений в пуле = максимум | Пул БД мал или запросы слишком долгие |
| Растёт глубина очереди | Потребители не успевают — масштабировать их |
| Память ползёт и не падает | Утечка ([Управление памятью в Python](../../../Ядро%20языка/Управление%20памятью%20в%20Python.md)) |

**Шаг 6. Чиним одно и перезамеряем.** Только одно изменение за прогон — иначе непонятно, что помогло.

**Как это читать:** цель не «получить красивое число», а пройти цикл *измерил → нашёл узкое место → починил → перемерил*. Мидла отличает именно способность назвать узкое место и показать замер до и после.
