# Юнит-тестирование Python

> **Юнит-тест** (модульный тест) — маленькая автоматическая проверка одного кусочка кода (функции, метода) в изоляции. Отвечает на вопрос «эта функция всё ещё делает то, что должна?» — и ловит поломку в ту же секунду, когда ты её внёс.

---

Без тестов каждый рефакторинг — прыжок в темноте: поменял одно, сломал другое, узнал об этом в проде. Юнит-тесты фиксируют ожидаемое поведение кода в исполняемом виде: пока они зелёные — можно смело менять реализацию. Это и страховка от регрессий, и живая документация («вот как это должно работать»), и давление на хороший дизайн (плохо тестируется — плохо спроектировано).

## Что такое «юнит»

**Юнит** (модуль) — наименьшая осмысленная единица кода: обычно **функция или метод**. Юнит-тест проверяет её **в изоляции** — без реальной базы, сети, файлов. Отсюда три свойства хорошего юнит-теста:

- **Быстрый** — миллисекунды, чтобы гонять сотни на каждый запуск.
- **Изолированный** — не зависит от других тестов, БД, порядка запуска.
- **Детерминированный** — один и тот же результат всегда (нет случайности, времени, сети).

## AAA — структура теста

Любой тест читается по схеме **Arrange – Act – Assert** (подготовь — сделай — проверь):

```python
def test_add():
    a, b = 2, 3          # Arrange — подготовить данные
    result = add(a, b)   # Act    — выполнить проверяемое действие
    assert result == 5   # Assert — сравнить с ожидаемым
```

Один тест — **одно** поведение. Не «проверить всё про функцию», а конкретный случай: обычный вход, крайний случай, ошибка.

## unittest — тесты в стандартной библиотеке

**`unittest`** — встроенный фреймворк (порт JUnit), не требует установки — важно там, где сторонние пакеты нельзя (контест Яндекса, окружение без pip). Тесты — методы класса-наследника `TestCase`, проверки — методы `assert*`:

```python
import unittest

def divide(a, b):
    if b == 0:
        raise ValueError("деление на ноль")
    return a / b

class TestDivide(unittest.TestCase):
    def setUp(self):                       # выполняется ПЕРЕД каждым тестом
        self.cases = [(6, 2, 3), (9, 3, 3)]

    def test_ok(self):
        for a, b, exp in self.cases:
            self.assertEqual(divide(a, b), exp)

    def test_zero(self):
        with self.assertRaises(ValueError):   # проверить, что бросается ошибка
            divide(1, 0)

if __name__ == "__main__":
    unittest.main()          # найти и запустить все test_*
```

Основные проверки `TestCase`:

| Метод | Проверяет |
|---|---|
| `assertEqual(a, b)` | `a == b` |
| `assertTrue(x)` / `assertFalse(x)` | истинность |
| `assertIsNone(x)` / `assertIsNotNone(x)` | `x is None` |
| `assertIn(a, b)` | `a in b` |
| `assertRaises(Err)` | код бросает исключение `Err` |
| `assertAlmostEqual(a, b)` | равенство float с округлением |

`setUp`/`tearDown` — подготовка и уборка **вокруг каждого** теста (например, создать/закрыть временный объект).

## unittest vs pytest

`unittest` — в стандартной библиотеке, многословнее (классы, `assertEqual`). [pytest](../../../Библиотеки/Сторонние/Тесты/pytest.md) — сторонний, но короче и мощнее: тест это просто функция с `assert`, есть [фикстуры](../../../Библиотеки/Сторонние/Тесты/pytest.md#фикстуры) и [параметризация](../../../Библиотеки/Сторонние/Тесты/pytest.md#параметризация). В проектах чаще берут pytest; `unittest` — когда нельзя ставить зависимости.

```python
# то же самое на pytest — без класса и assertEqual:
import pytest

def test_ok():
    assert divide(6, 2) == 3

def test_zero():
    with pytest.raises(ValueError):
        divide(1, 0)
```

## Изоляция и моки

Юнит нельзя тестировать вместе с реальной сетью/БД — медленно и недетерминированно. **Мок** (mock, «заглушка») — поддельный объект, который подставляют вместо настоящей зависимости: он записывает, как его вызывали, и возвращает заранее заданное. Инструмент — `unittest.mock`.

```python
from unittest.mock import Mock, patch

def register(user, notifier):
    notifier.send(f"Привет, {user}")     # notifier — внешняя зависимость (сеть)
    return True

def test_register_sends_greeting():
    fake = Mock()                                    # заглушка вместо реального notifier
    register("Иван", fake)
    fake.send.assert_called_once_with("Привет, Иван")  # проверяем, КАК его вызвали
```

**`patch`** временно подменяет объект прямо там, где он используется (не создавая аргумент):

```python
@patch("myapp.requests.get")             # подменить requests.get в модуле myapp
def test_fetch(mock_get):
    mock_get.return_value.json.return_value = {"id": 1}   # что «вернёт сеть»
    assert fetch_user(1)["id"] == 1
    mock_get.assert_called_once()
```

> **Мокай на границе с внешним миром** (сеть, БД, время, файлы), а не свою же логику. Если замокал половину тестируемой функции — тест проверяет моки, а не код.

### `patch` — не выбор, а следствие плохого дизайна

Две подмены выше выглядят как равноправные варианты, но это не так. `patch` нужен ровно тогда, когда **подменить нечего**: код сам создаёт зависимость внутри себя.

```python
# зависимость создана внутри — остаётся только patch по строковому пути
class OrderService:
    def __init__(self):
        self.sms = UnisenderClient()      # в тесте это реально отправит SMS

# зависимость принята снаружи — подмена обычным аргументом
class OrderService:
    def __init__(self, sms: SmsSender):
        self.sms = sms

OrderService(FakeSms())                   # ни patch, ни путей импорта
```

Почему это важнее, чем кажется:

- **`patch` завязан на строку** `"myapp.services.orders.UnisenderClient"`. Переехал модуль, поменялся импорт — тест молча перестал что-либо подменять и начал ходить в настоящий сервис.
- **Тесты стоят денег.** Сервис, который сам создаёт SMS-клиент, на каждом прогоне шлёт настоящие SMS по настоящему тарифу. Это самый приземлённый аргумент за [внедрение зависимостей](../../../ООП/Принципы/Принципы%20разработки%20—%20DRY,%20KISS,%20DI.md#di-против-dip--техника-против-принципа) — и обычно единственный, который убеждает.
- **Тестируемость — не отдельное свойство кода.** Если класс тяжело покрыть тестом, у него, как правило, нарушен [DIP](../../../ООП/Принципы/SOLID%20Python.md#d--dependency-inversion-инверсия-зависимостей). Тест здесь работает индикатором дизайна.

Где собирать настоящие реализации, если внутрь их класть нельзя, — [композиционный корень](../../../ООП/Принципы/Композиционный%20корень.md); в тестах его роль играет `conftest.py` с фикстурами.

### Виды дублёров: mock, stub, fake, spy, dummy

«Мок» в разговоре — зонтичный термин, но строго **тестовый дублёр (test double)** бывает пяти видов (классификация Джерарда Месароша). Они делятся по тому, **что** подменяют и **как** проверяются:

|Дублёр|Что делает|Проверка теста|
|---|---|---|
|**Dummy**|пустышка для обязательного параметра, не используется|—|
|**Stub**|возвращает заранее заданный ответ (задаёт *вход* теста)|по результату (state)|
|**Spy**|как stub, но ещё **записывает**, как его вызвали|по результату + постфактум|
|**Mock**|заранее заданы **ожидания** вызовов, сам падает, если нарушены|по взаимодействию (behavior)|
|**Fake**|рабочая, но упрощённая реализация (in-memory БД вместо настоящей)|по результату (state)|

Ключевое различие — **что проверяем**: stub/fake/dummy проверяют **состояние** (какой результат получили), mock/spy — **поведение** (как вызвали зависимость).

```python
notifier = Mock()

# как STUB — только подсовываем ответ:
notifier.is_online.return_value = True     # управляем входом
assert notify(user, notifier) == "sent"

# как MOCK — проверяем факт и параметры вызова:
notify(user, notifier)
notifier.send.assert_called_once_with("Привет")   # ожидание на взаимодействие
```

> В Python `unittest.mock.Mock` **один играет все роли**: `return_value` делает из него stub, `assert_called_*` — mock/spy. Отсюда и путаница в терминах. **Fake** же обычно пишут руками — например, свой `FakeRepo` со словарём вместо БД: он реально работает, но живёт только в тесте.

**Что выбирать.** Нужен *ответ* зависимости — хватит **stub**. Проверяешь *факт вызова* (письмо ушло, платёж инициирован) — **mock/spy**. Зависимость сложная и вызывается многократно (репозиторий, кэш) — удобнее **fake**, чем настраивать десяток stub-ответов.

## Пирамида тестирования

Тесты бывают разного масштаба — их держат в пропорции «пирамиды»:

```
        ╱╲        E2E — весь путь через UI/HTTP (мало, медленные, хрупкие)
       ╱──╲
      ╱ инт ╲     Интеграционные — связка модулей (БД, API) (средне)
     ╱──────╲
    ╱  юнит   ╲   Юнит — отдельные функции в изоляции (много, быстрые)
   ╱──────────╲
```

- **Юнит** — основа: их много, они быстрые, ловят баги логики.
- **Интеграционные** — проверяют, что модули работают вместе (реальная БД, API-эндпоинт).
- **E2E** — весь сценарий целиком; их мало, они медленные и ломкие.

## TDD — тест сначала

**TDD** (Test-Driven Development) — сначала тест, потом код. Цикл **red → green → refactor**:

1. 🔴 **Red** — написать падающий тест на ещё не существующую функцию.
2. 🟢 **Green** — написать минимальный код, чтобы тест прошёл.
3. 🔵 **Refactor** — улучшить код, тесты держат его корректным.

Не обязателен, но дисциплинирует: код с самого начала пишется тестируемым.

## Ловушки

```python
# НЕПРАВИЛЬНО — тест зависит от реальной сети: медленно и нестабильно
def test_weather():
    assert get_weather("Москва")["temp"] > -50   # упадёт, если API недоступен

# ПРАВИЛЬНО — замокать сеть, проверять свою логику:
@patch("app.requests.get")
def test_weather(mock_get):
    mock_get.return_value.json.return_value = {"temp": 20}
    assert get_weather("Москва")["temp"] == 20
```

> **Тестируй поведение, а не реализацию.** Тест, привязанный к внутренним деталям (какие приватные методы вызвались), ломается при любом рефакторинге, хотя поведение не изменилось. Проверяй вход → выход и наблюдаемые эффекты.

## Сквозной пример

Функция с валидацией + внешняя зависимость (отправка письма). Покрываем корректный вход, ошибку и взаимодействие с зависимостью.

```python
# service.py
def create_user(name, email, mailer):
    if "@" not in email:
        raise ValueError("некорректный email")
    mailer.send(email, f"Добро пожаловать, {name}")   # внешний эффект
    return {"name": name, "email": email}

# test_service.py
import unittest
from unittest.mock import Mock
from service import create_user

class TestCreateUser(unittest.TestCase):
    def test_ok(self):                               # обычный случай
        mailer = Mock()
        user = create_user("Иван", "i@mail.ru", mailer)
        self.assertEqual(user["name"], "Иван")
        mailer.send.assert_called_once()             # письмо отправлено

    def test_bad_email(self):                        # крайний случай — ошибка
        with self.assertRaises(ValueError):
            create_user("Иван", "плохой", Mock())
```

Как читать: `test_ok` проверяет и результат (`user`), и взаимодействие (`mailer.send` вызван), при этом реальная почта не шлётся — вместо неё `Mock`. `test_bad_email` фиксирует, что на неверный email функция бросает `ValueError`.

## Не путать со стресс-тестированием

Юнит-тест и [стресс-тест](../../../Алгоритмы/Приёмы/Стресс-тестирование.md) — разные инструменты под разные задачи, и один не заменяет другой:

| | **Юнит-тест** (эта заметка) | **Стресс-тест** |
|---|---|---|
| **Вопрос** | Работает ли код так, как задумано? | На каком входе я ошибаюсь? |
| **Входы** | придумываешь сам, фиксированные | генерируются случайно, тысячами |
| **Сравнение** | с ожидаемым значением | с эталонным решением или инвариантами |
| **Результат** | pass / fail | **контрпример** |
| **Где живёт** | репозиторий, CI | контест и отладка, выбрасывается после |

Коротко: юнит-тест **проверяет то, что ты уже придумал**; стресс-тест **придумывает за тебя то, о чём ты не подумал**. В `tasks-api` нужен первый, на контесте Яндекса — второй.
