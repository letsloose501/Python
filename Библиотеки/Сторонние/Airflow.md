# Airflow

> _Расписание для пайплайнов: не «выполни задачу», а «выполни двадцать задач в правильном порядке, каждую ночь, и покажи, где сломалось»_

---

**Apache Airflow** — оркестратор рабочих процессов: планирует и запускает цепочки задач по расписанию, следит за порядком выполнения, перезапускает упавшее и показывает всю картину в веб-интерфейсе. Пайплайны описываются обычным кодом на [Python](../../Python.md), а не конфигом — отсюда девиз «workflows as code». Актуальная мажорная версия — Airflow 3.

Типичный пользователь — дата-инженер: каждую ночь выгрузить данные из десяти источников, преобразовать, сложить в хранилище, пересчитать витрины, разослать отчёты.

## Проблема: чем плох cron

Одну задачу по расписанию отлично запускает cron. Как только задач становится несколько и они зависят друг от друга, начинаются вопросы, на которые cron не отвечает:

- Шаг 3 упал — как перезапустить **только его**, не гоняя шаги 1 и 2 заново?
- Шаг 2 идёт дольше обычного — как не начать шаг 3 раньше времени?
- Вчерашний запуск не отработал — как «догнать» пропущенный день?
- Где посмотреть, сколько шёл каждый шаг за последний месяц?

Airflow отвечает на все четыре: он хранит состояние каждого запуска каждой задачи в базе, знает граф зависимостей и умеет рестартовать с места падения.

## DAG — что это и почему граф

**DAG (Directed Acyclic Graph)** — направленный ациклический граф: задачи-вершины, зависимости-рёбра, циклов нет. Ациклический — значит, порядок выполнения всегда однозначен и пайплайн гарантированно завершается.

```
        ┌──▶ преобразовать_А ──┐
выгрузить                       ├──▶ сложить_в_хранилище ──▶ отправить_отчёт
        └──▶ преобразовать_Б ──┘
```

Две ветки в середине независимы — Airflow запустит их параллельно, а `сложить_в_хранилище` подождёт обе.

Термины, которые путают:

- **DAG** — сам пайплайн, его описание.
- **Task** — узел графа, одна единица работы.
- **DAG Run** — конкретный запуск DAG'а за конкретную дату.
- **Task Instance** — конкретный запуск одной задачи в рамках одного DAG Run. Именно у него есть статус (`success`, `failed`, `up_for_retry`).

## Из чего состоит Airflow

| Компонент | Роль |
|---|---|
| **Scheduler** | решает, что и когда пора запускать, и отдаёт задачи исполнителю |
| **Executor** | как именно выполнять задачи — настройка планировщика, а не отдельный сервис |
| **DAG Processor** | читает файлы с DAG'ами и складывает их разбор в базу; в Airflow 3 — отдельный процесс |
| **Metadata Database** | PostgreSQL или MySQL: статусы, история запусков, переменные, подключения |
| **API Server** | REST API и веб-интерфейс: посмотреть, запустить вручную, разобраться в падении |
| **Worker** | процесс, который непосредственно выполняет задачу (при распределённых исполнителях) |

Исполнители различаются масштабом: `LocalExecutor` — процессы на одной машине, `CeleryExecutor` — пул воркеров через [Celery](../../Библиотеки/Сторонние/Celery.md) и брокер ([RabbitMQ](../../Библиотеки/Сторонние/RabbitMQ.md) или [Redis](../../Библиотеки/Сторонние/Redis.md)), `KubernetesExecutor` — под на каждую задачу.

## Как пишут DAG

Современный способ — **TaskFlow API**: декораторы `@dag` и `@task` превращают обычные функции в задачи, а зависимости выводятся из передачи значений.

```python
from datetime import datetime
from airflow.sdk import dag, task

@dag(schedule="0 3 * * *", start_date=datetime(2026, 1, 1), catchup=False)
def ночной_отчёт():

    @task
    def выгрузить() -> list[dict]:
        return [{"id": 1, "sum": 100}, {"id": 2, "sum": 200}]

    @task
    def посчитать(строки: list[dict]) -> int:
        return sum(s["sum"] for s in строки)

    @task
    def отправить(итог: int):
        print(f"выручка за сутки: {итог}")

    отправить(посчитать(выгрузить()))     # ← зависимости заданы вызовами

ночной_отчёт()
```

Зависимость `выгрузить → посчитать → отправить` Airflow вывел сам из того, что результат одной функции передан в другую.

Классический способ — **операторы**. **Оператор** — готовый шаблон задачи: «выполнить bash-команду», «сделать SQL-запрос», «вызвать Python-функцию». Зависимости задаются оператором `>>`:

```python
from airflow.providers.standard.operators.bash import BashOperator

выгрузить = BashOperator(task_id="выгрузить", bash_command="./dump.sh")
загрузить = BashOperator(task_id="загрузить", bash_command="./load.sh")

выгрузить >> загрузить        # сначала выгрузить, потом загрузить
```

Отдельный вид — **сенсор** (sensor): оператор, который ждёт внешнего события (появился файл, ответил API, отработал другой DAG) и только потом пропускает пайплайн дальше.

## Ключевые настройки

- **`schedule`** — расписание в формате cron (`"0 3 * * *"`) или пресетом (`"@daily"`). `None` — только ручной запуск.
- **`start_date`** — дата, с которой пайплайн считается существующим.
- **`catchup`** — догонять ли пропущенные интервалы. `catchup=True` при `start_date` годичной давности запустит **365 прогонов сразу** — классическая ошибка новичка, поэтому обычно ставят `False`.
- **`retries` / `retry_delay`** — сколько раз перезапустить упавшую задачу и с какой паузой.

## Ловушки

**Код на верхнем уровне файла выполняется постоянно.** DAG Processor перечитывает файлы каждые несколько секунд, и всё, что лежит вне функций-задач, выполняется при каждом разборе:

```python
# НЕПРАВИЛЬНО — запрос к базе на каждом парсинге файла
данные = pd.read_sql("SELECT * FROM huge_table", conn)

@task
def обработать():
    return данные.sum()

# ПРАВИЛЬНО — тяжёлое внутри задачи
@task
def обработать():
    данные = pd.read_sql("SELECT * FROM huge_table", conn)
    return данные.sum()
```

**XCom — не для данных.** Обмен значениями между задачами (**XCom**, cross-communication) идёт **через метабазу**, поэтому годится только для мелочи: путь к файлу, идентификатор, число. Датафрейм передают, положив его в S3 или на диск, а через XCom пуская ссылку.

**Задачи должны быть идемпотентны.** Airflow перезапускает упавшее сам. Задача «добавить строки в таблицу» после третьего ретрая утроит данные; правильная формулировка — «перезаписать партицию за такую-то дату». Подробнее — Гарантии доставки и идемпотентность.

## Airflow или Celery — вопрос с собеседования

Инструменты решают разные задачи, и путать их — ошибка:

| | [Celery](../../Библиотеки/Сторонние/Celery.md) | Airflow |
|---|---|---|
| Единица работы | одна задача | граф задач с зависимостями |
| Кто запускает | приложение в ответ на событие («юзер нажал кнопку») | планировщик по расписанию |
| Задержка | миллисекунды | минуты, шаг расписания |
| Состояние | результат задачи | вся история запусков каждого шага |
| Типичное применение | отправить письмо, сжать картинку | ночной ETL, пересчёт витрин |

Коротко: Celery — фон для веб-приложения, Airflow — расписание для пайплайнов данных. Они не конкуренты и часто соседствуют: Airflow может использовать Celery как исполнитель.

## Связи

- [Celery](../../Библиотеки/Сторонние/Celery.md) — фоновые задачи из веб-приложения, а не пайплайны по расписанию;
- [RabbitMQ](../../Библиотеки/Сторонние/RabbitMQ.md), [Redis](../../Библиотеки/Сторонние/Redis.md) — брокеры под `CeleryExecutor`;
- Гарантии доставки и идемпотентность — почему задачи Airflow обязаны быть идемпотентны;
- [Docker](../../DevOps/Docker.md) — стандартный способ поднять Airflow локально (`docker compose`);
- Анализ данных — что обычно происходит внутри задач ETL-пайплайна.
