# Redis

> _Remote Dictionary Server — гигантский словарь в оперативной памяти_

---

**Redis** — сверхбыстрое key-value хранилище, которое держит данные **в оперативной памяти** (in-memory). За счёт этого чтение и запись занимают микросекунды — на порядки быстрее дисковых БД вроде PostgreSQL. Расплата — объём ограничен ОЗУ, а данные по умолчанию не переживают перезагрузку. Отсюда и роли Redis: кеш, брокер очередей ([Celery](../../Библиотеки/Сторонние/Celery.md)), хранилище сессий, счётчики, блокировки — там, где нужна скорость, а не долговечность.

## In-memory: скорость ценой памяти

Обычная база хранит данные на диске — надёжно, но медленно. Redis держит их в RAM:

- **Плюс** — очень быстро (сотни тысяч операций в секунду), задержки в микросекундах.
- **Минус** — данные ограничены объёмом памяти и **волатильны**: при перезапуске теряются (если не включить сохранение на диск).

Ещё одна причина скорости — Redis **однопоточный**: одна команда выполняется целиком, без гонок и блокировок. Поэтому все простые операции **атомарны** по определению.

## Структуры данных

Redis — не просто «строка → строка». Значение бывает разных типов, и под каждый есть свои команды.

### String — строка / число

Базовый тип: строка, число, даже сериализованный JSON или картинка (до 512 МБ).

```
SET user:1 "Alex"          # записать
GET user:1                 # → "Alex"
SET session:x "d" EX 3600  # с TTL 1 час
INCR visits                # атомарно +1 (счётчики) → 1
INCRBY visits 10           # +10
APPEND log "line"          # дописать
MSET a 1 b 2               # записать несколько разом
```

### List — список (очередь/стек)

Двусвязный список строк. Толкают и снимают с обоих концов — отсюда очереди и стеки.

```
LPUSH q "task1"      # добавить слева
RPUSH q "task2"      # добавить справа
LRANGE q 0 -1        # все элементы
LPOP q               # снять слева
BRPOP q 5            # блокирующе ждать элемент до 5 с — основа очереди задач
LLEN q               # длина
```

### Hash — словарь полей

Значение = набор пар «поле → значение». Идеально для объектов (профиль, товар).

```
HSET user:1 name "Alex" age 30
HGET user:1 name        # → "Alex"
HGETALL user:1          # все поля
HINCRBY user:1 age 1    # атомарно увеличить поле
HDEL user:1 age
```

### Set — множество уникальных

Неупорядоченное множество без дублей + операции пересечения/объединения.

```
SADD tags "python" "redis"
SISMEMBER tags "python"   # → 1 (есть)
SMEMBERS tags             # все элементы
SCARD tags                # размер
SINTER tags1 tags2        # пересечение (общие теги)
```

### Sorted Set — множество с рейтингом

Каждый элемент имеет **score** (число); хранится отсортированным. Основа лидербордов и топов. Внутри — пара «хеш-таблица + [скип-лист](../../Данные/Структуры%20данных/Список%20с%20пропусками.md)»: хеш даёт доступ по значению, скип-лист держит порядок по score.

```
ZADD board 100 "Alex" 250 "Ben"
ZRANGE board 0 -1 WITHSCORES        # по возрастанию score
ZREVRANGE board 0 2                 # топ-3 (по убыванию)
ZRANK board "Alex"                  # позиция игрока
ZINCRBY board 50 "Alex"            # +50 к очкам
```

### Специальные типы

- **Bitmap** — биты в строке: онлайн-статусы, «зашёл ли пользователь в день N» экономно (`SETBIT`, `BITCOUNT`).
- **Stream** — журнал событий (append-only) с группами потребителей: очереди с гарантиями, event sourcing (`XADD`, `XREAD`).
- **Geo** — координаты и поиск «что рядом» (`GEOADD`, `GEOSEARCH`).
- **JSON** — документ с адресацией по пути: менять одно поле, не перезаписывая весь объект (`JSON.SET`, `JSON.GET`).
- **Vector set** — элементы с векторами-эмбеддингами и поиск похожих (`VADD`, `VSIM`) — см. [Поиск, JSON и векторы](#поиск-json-и-векторы).

### Вероятностные структуры

Отдельное семейство типов, которое **меняет точность на память**: вместо честного хранения всех элементов держит их хеш-отпечатки и отвечает приблизительно. Для многих задач приблизительного ответа достаточно, а выигрыш по памяти — на порядки.

| Структура | Отвечает на вопрос | Команды |
|---|---|---|
| **[Bloom filter](../../Алгоритмы/Иные/Фильтр%20Блума.md)** | «этот элемент уже был?» | `BF.RESERVE`, `BF.ADD`, `BF.EXISTS`, `BF.MADD`, `BF.MEXISTS` |
| **Cuckoo filter** | то же, но с удалением | `CF.ADD`, `CF.EXISTS`, `CF.DEL` |
| **Count-min sketch** | «сколько раз встретился элемент?» | `CMS.INITBYPROB`, `CMS.INCRBY`, `CMS.QUERY` |
| **Top-K** | «какие элементы самые частые?» | `TOPK.RESERVE`, `TOPK.ADD`, `TOPK.LIST`, `TOPK.QUERY` |
| **t-digest** | «какой у меня 99-й перцентиль?» | `TDIGEST.CREATE`, `TDIGEST.ADD`, `TDIGEST.QUANTILE`, `TDIGEST.CDF` |
| **[HyperLogLog](../../Алгоритмы/Иные/HyperLogLog.md)** | «сколько уникальных элементов?» | `PFADD`, `PFCOUNT`, `PFMERGE` |

**Bloom filter** — самая известная. Гарантия у неё **односторонняя**:

> Отрицательный ответ **точен**: «нет» значит, элемента точно не было. Положительный ответ — с вероятностью ошибки: «есть» может оказаться ложным срабатыванием. Удалять элементы нельзя.

Именно поэтому её ставят **перед** дорогой проверкой: «такой логин занят?», «эту карту уже помечали украденной?», «этот баннер пользователю уже показывали?». Отрицательный ответ закрывает вопрос сразу, положительный — отправляет в настоящую базу.

```
BF.RESERVE bikes:models 0.001 1000000    # 0.1% ложных срабатываний на 1 млн элементов
BF.ADD bikes:models "Smoky Mountain Striker"
BF.EXISTS bikes:models "Smoky Mountain Striker"    # → 1
```

Выигрыш по памяти против обычного Set: при 0.1% ошибки нужно **14.4 бита** на элемент (при 0.01% — 19.2 бита), тогда как Set на IP-адреса тратит около 320 бит на элемент.

**Count-min sketch** всегда **завышает** счётчик (виноваты коллизии), поэтому годится только для крупных величин: порог доверия равен `error × общее_число_событий`, всё ниже — шум, который приравнивают к нулю. Для равномерно распределённого потока структура плохо подходит — она про «слонов», а не про «мышей».

**Top-K** решает соседнюю задачу — не «сколько раз», а «кто в топе»: тренды хештегов, всплеск запросов с одного IP при DDoS. `TOPK.ADD` при вытеснении возвращает имя элемента, выпавшего из топа, — это готовое событие «состав топа изменился».

**t-digest** оценивает перцентили, не храня и не сортируя все значения: классическое «какая задержка у 99% запросов». Умеет и **усечённое среднее** (`TDIGEST.TRIMMED_MEAN`) — среднее без выбросов, например между 10-м и 90-м перцентилем.

## Ключи и время жизни (TTL)

Ключам задают **срок жизни** — по истечении Redis сам их удаляет. Это и делает его идеальным кешем.

```
EXPIRE user:1 60     # жить 60 секунд
TTL user:1           # сколько осталось (-1 без TTL, -2 нет ключа)
PERSIST user:1       # снять TTL — сделать вечным
DEL user:1           # удалить сейчас
EXISTS user:1        # есть ли ключ
```

Опции команды `SET` совмещают запись и условие в один атомарный шаг:

```
SET k v EX 60        # с TTL 60 с (PX — в миллисекундах)
SET k v NX           # записать, ТОЛЬКО если ключа ещё нет (основа блокировок)
SET k v XX           # записать, только если ключ уже есть
```

> **Соглашение об именах** — иерархия через двоеточие: `user:1:sessions`, `cache:products:42`. Redis не требует этого, но так ключи читаемы и группируемы.

## Атомарность, транзакции и пайплайны

Однопоточность делает каждую команду атомарной. Для нескольких команд:

- **`MULTI`/`EXEC`** — транзакция: команды копятся и выполняются одним блоком, без вклинивания чужих.
- **`WATCH`** — оптимистичная блокировка: если наблюдаемый ключ изменился до `EXEC`, транзакция отменяется.
- **Пайплайн** — послать пачку команд одним сетевым походом (не про атомарность, а про **скорость**: убирает задержки round-trip).
- **`EVAL` (Lua)** — выполнить скрипт на сервере атомарно: сложная логика без гонок и лишних round-trip.

## Сохранение на диск (persistence)

Чтобы данные пережили перезапуск, Redis умеет писать на диск двумя способами:

| | **RDB** (снапшот) | **AOF** (журнал) |
|---|---|---|
| Что | периодический дамп всей памяти | лог каждой изменяющей команды |
| Плюс | компактно, быстрый рестарт | почти без потерь данных |
| Минус | теряешь данные между снапшотами | файл больше, восстановление дольше |

Часто включают оба. Но помни: основной сценарий Redis — быстрый доступ, а не единственная копия данных.

## Вытеснение при нехватке памяти (eviction)

Память кончилась — Redis по политике `maxmemory-policy` решает, что удалять:

- `noeviction` — не удалять, отвечать ошибкой на запись (по умолчанию);
- `allkeys-lru` — вытеснять давно не используемые (**для кеша** — самый частый выбор);
- `allkeys-lfu` — вытеснять редко используемые;
- `volatile-lru` / `volatile-ttl` — только среди ключей с выставленным TTL.

## Pub/Sub — обмен сообщениями

Издатель шлёт в **канал**, подписчики получают в реальном времени. Сообщения не хранятся: кто не подписан — не увидит (для гарантий доставки берут Streams).

```
SUBSCRIBE news        # подписчик слушает канал
PUBLISH news "hello"  # издатель шлёт всем подписчикам
```

## Поиск, JSON и векторы

Современный Redis — уже не только «быстрый словарь». В Redis Open Source встроен **поисковый движок (Query Engine)**: по полям документов строится индекс, и по нему выполняются запросы — фильтры по значениям и диапазонам, полнотекстовый поиск, агрегации. В связке с типом **JSON** это даёт документное хранилище с поиском, а не только доступ по ключу.

**Vector set** — тип, появившийся в Redis 8.0. Устроен как Sorted Set, но вместо числа-score с каждым элементом лежит **вектор-эмбеддинг**, и искать можно «похожие по смыслу».

```
VADD points VALUES 2 1.0 1.0 pt:A        # добавить элемент с вектором [1.0, 1.0]
VDIM points                               # размерность векторов → 2
VSIM points VALUES 2 0.9 0.1              # найти ближайшие к вектору
VSIM points ELE pt:A WITHSCORES COUNT 4   # ближайшие к уже существующему элементу
VSETATTR points pt:A '{"size":"large","price":18.99}'   # прицепить JSON-атрибуты
VSIM points ELE pt:A FILTER '.size == "large" && .price > 20'   # похожие + фильтр
```

Внутри — граф **HNSW** и **приблизительный** поиск ближайших соседей: результат не гарантированно точен, зато не требует перебора всей коллекции (подробно — Индексы для векторов). Векторы хранятся квантованными, поэтому `VEMB` возвращает значения чуть отличающиеся от исходных.

> Ценность `FILTER` в том, что он объединяет два условия в одном запросе: «похоже по смыслу» **и** «подходит по атрибутам». Иначе пришлось бы искать соседей, а потом отфильтровывать их в приложении — и не угадать, сколько кандидатов запрашивать.

Отсюда роль Redis в задачах поверх языковых моделей: семантический поиск, рекомендации, поиск дубликатов и **RAG** — подтягивание релевантного контекста к запросу. Альтернатива внутри реляционной БД — pgvector.

## Паттерны применения

- **Кеш (cache-aside)** — самый частый сценарий: перед тяжёлым запросом к PostgreSQL смотрим в Redis; нет — считаем и кладём с TTL.
- **Брокер очередей** — очередь задач и backend результатов для [Celery](../../Библиотеки/Сторонние/Celery.md).
- **Сессии** — быстрое хранилище пользовательских сессий веб-приложения.
- **Rate limiting** — счётчик запросов с TTL: `INCR` + `EXPIRE` (сколько раз за минуту) — как [throttling DRF](../../Фреймворки/DJANGO/Разделение%20доступа%20в%20DRF.md#throttling--ограничение-частоты).
- **Распределённая блокировка** — `SET lock <id> NX EX 30`: только один процесс захватит ключ (лидер, крон в одном экземпляре).
- **Лидерборды** — Sorted Set с очками (`ZREVRANGE` — топ).
- **Pub/Sub** — уведомления и события между сервисами в реальном времени.

## Работа из Python (redis-py)

Клиент — библиотека `redis`:

```bash
pip install redis
```

```python
import redis

r = redis.Redis(host='127.0.0.1', port=6379, db=0, decode_responses=True)
#   decode_responses=True — получать str вместо bytes

# строки и TTL
r.set('user:1', 'Alex')
r.set('session:abc', 'data', ex=3600)      # TTL 1 час
r.incr('visits')                            # счётчик

# хеш — объект
r.hset('user:1', mapping={'name': 'Alex', 'age': 30})
r.hgetall('user:1')                         # {'name': 'Alex', 'age': '30'}

# sorted set — лидерборд
r.zadd('board', {'Alex': 100, 'Ben': 250})
r.zrevrange('board', 0, 2, withscores=True) # топ-3

# кеш-паттерн cache-aside
def get_product(pid):
    key = f'product:{pid}'
    if (cached := r.get(key)) is not None:
        return json.loads(cached)           # попадание в кеш
    product = db_query(pid)                  # промах — идём в БД
    r.set(key, json.dumps(product), ex=300)  # положить с TTL 5 мин
    return product

# пайплайн — пачка команд одним походом
with r.pipeline() as pipe:
    pipe.set('a', 1).incr('a').get('a')
    pipe.execute()                           # [True, 2, '2']

# распределённая блокировка (context manager поверх SET NX)
with r.lock('import:lock', timeout=30):
    do_critical_section()

# pub/sub
p = r.pubsub()
p.subscribe('news')
for message in p.listen():
    print(message)
```

## Масштабирование

- **Репликация** — реплики только для чтения снимают нагрузку и дают резерв.
- **Sentinel** — автоматический перевод реплики в мастера при падении (высокая доступность).
- **Cluster** — шардирование: данные разложены по нескольким узлам, когда не влезают в память одной машины.

Redis Cluster устроен не как кольцо и не как схема с сервером метаданных, а на **фиксированных слотах**: пространство ключей заранее разбито на **16 384 слота**, номер считается как `CRC16(ключ) % 16384`, а каждый узел владеет набором слотов и знает, кто владеет остальными. Клиент может прийти на любой узел и получит перенаправление `MOVED`.

> Слоты **переносятся на живом кластере** (`CLUSTER SETSLOT` с состояниями `MIGRATING`/`IMPORTING`, ключи переезжают командой `MIGRATE`, запросы к ещё не переехавшим ключам получают редирект `ASK`). Чего в Redis нет — автоматического балансировщика: решение о переносе принимает человек или `redis-cli --cluster reshard`.

⚠️ **Ключи одной операции должны лежать в одном слоте.** Мультиключевые команды (`MGET`, транзакции, скрипты) в кластере работают, только если все ключи в одном слоте; для этого используют **хеш-теги** — в расчёт слота берётся часть имени в фигурных скобках: `{user:42}:profile` и `{user:42}:cart` гарантированно окажутся вместе.

## Ловушки

**`KEYS *` в проде** — блокирует однопоточный сервер, пока обходит все ключи. Для перебора — `SCAN` (курсор, порциями).

```
KEYS user:*     # ✗ — на большой базе подвесит сервер
SCAN 0 MATCH user:* COUNT 100   # ✓ — итеративно, не блокирует
```

**Забыть TTL на кеше** — ключи копятся, память кончается, срабатывает вытеснение (или ошибка при `noeviction`). Кешу почти всегда нужен `EX`.

**Считать Redis надёжным хранилищем** — по умолчанию данные волатильны. Единственную копию важных данных в Redis не держат.

**Открытый Redis без пароля** — исторически без аутентификации; открытый в интернет порт 6379 = чужой доступ ко всем данным. Нужны пароль (`requirepass`), `protected-mode` и файрвол.

## Связи

- [Celery](../../Библиотеки/Сторонние/Celery.md) — использует Redis как брокер очереди и backend результатов;
- [RabbitMQ](../../Библиотеки/Сторонние/RabbitMQ.md) — специализированный AMQP-брокер; альтернатива Redis, когда нужны гарантии доставки и маршрутизация;
- [Django](../../Фреймворки/DJANGO/Django.md) · [FastAPI](../../Фреймворки/FastAPI.md) — подключают Redis как кеш и хранилище сессий;
- PostgreSQL — дисковая реляционная БД; Redis часто кеширует запросы к ней;
- Программирование/Базы данных/Стратегии кэширования — cache-aside и остальные стратегии, инвалидация, stampede: как правильно использовать Redis как кеш;
- [Список с пропусками](../../Данные/Структуры%20данных/Список%20с%20пропусками.md) — структура под Sorted Set;
- Векторный поиск — vector sets в Redis 8 как векторная база; там же HNSW и pgvector для сравнения;
- [Фильтр Блума](../../Алгоритмы/Иные/Фильтр%20Блума.md) — теория структуры, которая в Redis живёт как команды `BF.*`;
- Эмбеддинг — что именно лежит в векторе элемента;
- Буферный пул — те же политики вытеснения, но внутри самой базы;
- Идемпотентность — хранилище обработанных id (дедупликация вебхуков, задач);
- [HyperLogLog](../../Алгоритмы/Иные/HyperLogLog.md) — вероятностный подсчёт уникальных, реализован в Redis;
- [Throttling](../../Фреймворки/DJANGO/Разделение%20доступа%20в%20DRF.md#throttling--ограничение-частоты) — счётчики частоты на Redis.
