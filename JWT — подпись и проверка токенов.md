# JWT — подпись и проверка токенов

> _Подпись доказывает, кто выпустил токен. Она его не прячет_

---

**JWT** (JSON Web Token, RFC 7519) — токен, который несёт данные о пользователе прямо в себе и подтверждает их **подписью**. Сервису не нужно ходить в базу за сессией: он проверяет подпись локально и верит содержимому. Здесь — как устроена эта подпись, почему в микросервисах она обязана быть **асимметричной**, и что кроме подписи нужно проверить, чтобы токен нельзя было подделать.

Про пару access/refresh и выдачу токенов — [Oauth 2.0](Библиотеки/Сторонние/Работа%20с%20WEB/Oauth%202.0.md) и [DRF](Фреймворки/DJANGO/Разделение%20доступа%20в%20DRF.md#jwt-authentication); здесь только механика подписи и валидации.

## Проблема: кто умеет проверять, тот умеет и подделывать

В монолите всё просто. Один сервер выпускает токен, подписывая его секретной строкой, и сам же его проверяет — той же строкой. Секрет знает один процесс, вопросов нет.

Теперь тот же токен в микросервисах. Сервисов десять: заказы, платежи, уведомления, аналитика. Каждый должен уметь проверить пришедший токен → каждому нужен секрет → **каждый из десяти сервисов теперь может выпустить токен от имени кого угодно**. Утёк секрет из самого неважного сервиса аналитики — злоумышленник выписывает себе токен администратора платежей.

> **Это и есть главный вопрос темы.** При **общем секрете** проверка и выпуск — одна и та же способность. Разделить их умеет только асимметричная криптография: подписывает **приватный** ключ, проверяет **публичный**.

```
Симметрично (HS256)                  Асимметрично (RS256/ES256)
───────────────────                  ──────────────────────────
auth   [секрет] ──выпуск             auth   [приватный 🔒] ──выпуск
orders [секрет] ──проверка+выпуск❗   orders [публичный 🔓] ──только проверка
pay    [секрет] ──проверка+выпуск❗   pay    [публичный 🔓] ──только проверка
```

## Из чего состоит токен

Три части через точку — `header.payload.signature`. Каждая закодирована **base64url** ([base64](Библиотеки/Модули/Форматы%20данных/base64.md), вариант без `+` и `/`, чтобы жить в URL и заголовках).

```
eyJhbGciOiJSUzI1NiIsImtpZCI6ImF1dGgtMSJ9 . eyJzdWIiOiI0MiIsImV4cCI6MTc5MDAwMDAwMH0 . QXJ0aHVy…
└────────── header ──────────────────────┘ └───────── payload ───────────────────┘ └ signature ┘
```

- **header** — как токен подписан: `{"alg": "RS256", "typ": "JWT", "kid": "auth-1"}`;
- **payload** — набор утверждений (**claims**) о пользователе: `{"sub": "42", "iss": "auth", "exp": 1790000000}`;
- **signature** — подпись первых двух частей.

```python
import base64, json

header, payload, signature = token.split(".")
json.loads(base64.urlsafe_b64decode(payload + "=="))
# → {'sub': '42', 'iss': 'auth', 'exp': 1790000000}   ← без ключа, без пароля, кем угодно
```

> ⚠️ **Подпись ≠ шифрование.** base64 — это кодирование, а не шифр: payload читает любой, кто перехватил токен, включая браузер пользователя. Подпись гарантирует **целостность и авторство**, но не тайну. Пароли, номера карт, внутренние идентификаторы платежей в токен не кладут — только то, что не жалко показать. _(Если содержимое действительно надо спрятать — это уже JWE, отдельный стандарт, RFC 7516.)_

`+ "=="` в примере — добуривание паддинга: base64url в JWT хранится без `=` на конце, а `b64decode` их требует.

## Что именно подписывается

Подпись считается не от JSON и не от токена целиком, а от **строки-склейки первых двух частей** — она называется signing input:

```
signing input = base64url(header) + "." + base64url(payload)
                └────────────────────┬────────────────────┘
                                     │  SHA-256 → хеш фиксированной длины
                                     ▼
                        подпись приватным ключом (RSA / ECDSA)
                                     ▼
JWT = base64url(header) . base64url(payload) . base64url(signature)
```

Хешируют, а не подписывают текст напрямую, потому что асимметричные операции медленные: дешевле свернуть данные в 32 байта хеша и подписать их (почему подписывают хеш). Меняется хоть один байт в header или payload — меняется хеш, и подпись перестаёт сходиться.

Отсюда же следует, что **исправить payload и оставить старую подпись нельзя**: подпись привязана ровно к этим байтам.

## HS256 против RS256 и ES256

Алгоритм подписи объявлен в поле `alg` заголовка. Практически используются три (полный список — RFC 7518):

| | **HS256** | **RS256** | **ES256** |
|---|---|---|---|
| Что под капотом | HMAC-SHA256 | RSASSA-PKCS1-v1_5 + SHA-256 | ECDSA на кривой P-256 + SHA-256 |
| Ключи | **один общий секрет** | пара: приватный + публичный | пара: приватный + публичный |
| Кто может выпустить | все, у кого секрет | только владелец приватного | только владелец приватного |
| Кто может проверить | все, у кого секрет | все — ключ публичный | все — ключ публичный |
| Размер подписи | 32 байта | 256 байт (ключ 2048 бит) | 64 байта |
| Скорость | очень быстро | подпись медленно, проверка быстро | быстро в обе стороны |
| Статус в RFC 7518 | Required | Recommended | Recommended+ |
| Где уместен | монолит: сам выпустил — сам проверил | микросервисы, внешние потребители | то же, но токен и подпись компактнее |

Минимальный размер RSA-ключа по RFC 7518 — **2048 бит**. ES256 при сопоставимой стойкости даёт подпись в четыре раза короче — заметно, когда токен летит в каждом запросе.

### Под капотом: HS256 — вообще не подпись

Технически HS256 — это **MAC** (код аутентификации сообщения, MAC), а не цифровая подпись. Разница в том, на какой вопрос они отвечают:

- **MAC** доказывает: «это сделал кто-то, кто знает секрет»;
- **цифровая подпись** доказывает: «это сделал владелец конкретного приватного ключа».

Пока держатель секрета один, разницы не видно. Как только их двое — MAC перестаёт отвечать на вопрос «кто именно из вас». Микросервисная архитектура — это ровно случай «держателей много», поэтому симметричный вариант в ней неприменим (Монолит и микросервисы, Взаимодействие сервисов).

## Как проверяется подпись

Проверяющему нужен только публичный ключ. Четыре шага:

```
1. Разбить токен по точкам:      header . payload . signature
2. Взять из header поле kid  →   найти нужный публичный ключ
3. Пересчитать хеш строки        base64(header) + "." + base64(payload)
4. Проверить публичным ключом, что signature соответствует этому хешу
```

Сошлось — доказаны сразу две вещи: **(а)** токен выпущен владельцем приватного ключа, **(б)** ни один байт не менялся по дороге. Не сошлось — `401`, без вариантов.

Асимметрия здесь и окупается: проверяющий сервис получил всё необходимое для проверки и **при этом не получил способности выпускать токены**. Публичный ключ можно печатать в документации.

## Откуда берётся публичный ключ: JWKS

Раздать ключ по сервисам можно руками — положить PEM-файл в конфиг или секрет-хранилище. Работает, но при **ротации** (плановой смене ключа) придётся обойти все сервисы и всё передеплоить.

Стандартный путь — **JWKS** (JSON Web Key Set, RFC 7517): издатель публикует свои публичные ключи по HTTP, а сервисы забирают их сами.

```json
GET https://auth.example.com/.well-known/jwks.json

{ "keys": [
    { "kty": "RSA", "kid": "auth-2026-07", "use": "sig", "alg": "RS256",
      "n": "0vx7ago…", "e": "AQAB" },
    { "kty": "RSA", "kid": "auth-2026-04", "use": "sig", "alg": "RS256",
      "n": "3ZlmQd8…", "e": "AQAB" }
] }
```

- **`kid`** (key id) — имя ключа. Издатель кладёт его в header токена, проверяющий по нему выбирает нужный ключ из набора. Без `kid` пришлось бы перебирать все ключи подряд.
- **`kty`** — тип ключа (`RSA`, `EC`), **`use: "sig"`** — ключ для подписи, а не для шифрования, **`n`/`e`** — сами компоненты RSA-ключа (для EC вместо них `crv`, `x`, `y`).

> **Путь `/.well-known/jwks.json` — распространённое соглашение, а не требование стандарта.** Правильный способ его узнать — метаданные издателя: `GET /.well-known/openid-configuration` (OpenID Connect Discovery) или `/.well-known/oauth-authorization-server` (RFC 8414); в ответе есть поле **`jwks_uri`** с настоящим адресом. Хардкодить путь можно, но тогда переезд издателя ломает проверку.

### Кэширование и ротация

Ходить за ключами на каждый запрос бессмысленно — они меняются раз в месяцы. Рабочая схема:

1. Скачать JWKS один раз, держать в памяти с TTL (5–15 минут — типично).
2. Пришёл токен с **незнакомым `kid`** — перечитать JWKS (значит, был выпущен новый ключ) и попробовать снова.
3. Не нашёлся и после обновления — отбой, `401`.

Ротация без простоя строится на том же `kid`: издатель **сначала** добавляет новый ключ в JWKS, **потом** начинает им подписывать, а старый держит в наборе, пока не истекут все выданные под ним токены (то есть ещё `exp` времени). Проверяющие подхватывают новый ключ сами, по незнакомому `kid`.

> Кэш обязан иметь TTL и защиту от штурма: если тысяча запросов с неизвестным `kid` придёт одновременно, наивная реализация устроит тысячу параллельных походов к издателю. Обновление ключей делают под замком, а частоту перезагрузки ограничивают.

## Что проверять кроме подписи

Валидная подпись отвечает только на вопрос «не подделан ли токен». Она **не** отвечает, выпущен ли он для тебя и не протух ли. Обязательный набор проверок:

| Проверка | Где | Что означает |
|---|---|---|
| **whitelist `alg`** | header | принимать только явно разрешённые алгоритмы — `algorithms=["RS256"]` |
| **`kid`** | header | каким ключом подписан (нужен для ротации) |
| **`iss`** (issuer) | payload | токен выпустил **твой** издатель, а не чужой |
| **`aud`** (audience) | payload | токен предназначен **твоему** сервису, а не соседнему |
| **`exp`** (expiration) | payload | не истёк |
| **`nbf`** (not before) | payload | уже вступил в силу |
| **`iat`** (issued at) | payload | не выпущен «в будущем»; заодно возраст токена |
| **`sub`** (subject) | payload | о ком токен — кладётся в `current_user` |
| **`jti`** (JWT id) | payload | уникальный id — по нему работает список отозванных |

Плюс два режимных правила: токен берут **из заголовка `Authorization: Bearer …`**, не из URL (URL оседает в логах, истории браузера и `Referer`), и сам токен **никогда не пишут в логи**.

- **`aud` — самая пропускаемая проверка.** Без неё токен, выданный для сервиса аналитики, примет и сервис платежей: подпись-то валидная, издатель тот же.
- **Часы расходятся.** На `exp`/`nbf` дают допуск (leeway) в 30–60 секунд, иначе рассинхрон машин даёт случайные `401`.
- **Отзыв.** Подписанный токен валиден до `exp`, отменить его нечем — забанил пользователя, а он ещё 15 минут работает. Лечится коротким TTL access-токена и списком отозванных `jti` в Redis, но это уже состояние на сервере, то есть частичный отказ от главного плюса JWT.
- **`typ`.** Для access-токенов OAuth есть отдельный тип `at+jwt` (RFC 9068) — проверка `typ` не даёт скормить сервису токен другого назначения (например, `id_token`).

## Атаки на проверку подписи

Обе классические атаки бьют не в криптографию, а в то, что наивная библиотека **доверяет полю `alg` из самого токена** — то есть спрашивает у злоумышленника, как проверять его же подпись.

### `alg: none`

RFC 7515 предусматривает значение `none` — «подписи нет». Задумано для случаев, когда целостность обеспечена снаружи (например, туннелем TLS). Атака: взять валидный токен, поправить payload на `"roles": ["admin"]`, поставить в header `{"alg": "none"}`, отрезать подпись и оставить пустую третью часть. Уязвимая библиотека видит `none`, ничего не проверяет и возвращает payload как доверенный.

### Путаница HS256 / RS256 (algorithm confusion)

Тоньше и потому опаснее. Публичный ключ издателя **открыт по определению** — он лежит в JWKS. Злоумышленник:

1. берёт публичный RSA-ключ жертвы (скачивает с её же `/.well-known/jwks.json`);
2. меняет в header `"alg": "RS256"` на `"alg": "HS256"`;
3. подписывает токен алгоритмом HMAC, **используя байты публичного ключа как общий секрет**.

Сервис, который передаёт в проверку «свой ключ» и позволяет токену выбирать алгоритм, увидит `HS256`, возьмёт тот же публичный ключ уже в роли секрета — и подпись **сойдётся**. Токен подделан публичной информацией.

```python
import jwt

# НЕПРАВИЛЬНО — алгоритм берётся из самого токена
payload = jwt.decode(token, public_key)
# alg: none → подпись вообще не проверяется
# alg: HS256 → public_key используется как HMAC-секрет, а он общедоступен

# ПРАВИЛЬНО — белый список алгоритмов, токен в выборе не участвует
payload = jwt.decode(token, public_key, algorithms=["RS256"])
```

> **Почему так.** `alg` — это подсказка от отправителя, а отправителем может быть кто угодно. Алгоритм проверки должен задавать **принимающий**, исходя из типа своего ключа, и жёстко: ждём RS256 — значит, HS256 и `none` отвергаем не глядя. RFC 8725 (JWT Best Current Practices) формулирует это как требование к библиотекам: вызывающий обязан иметь возможность указать допустимые алгоритмы, и никакие другие использоваться не должны. Современный PyJWT поэтому делает `algorithms` обязательным параметром.

Оба сценария — иллюстрация общего принципа [веб-безопасности](Веб-безопасность.md): не давать вводу управлять тем, как этот же ввод будет проверяться.

## Альтернатива: opaque-токены и интроспекция

Не всякий токен — JWT. **Opaque-токен** (непрозрачный) — просто случайная строка-идентификатор ([secrets.token_urlsafe](Библиотеки/Модули/Безопасность%20и%20интернет/secrets.md)), за которой в базе сервиса авторизации лежит вся информация. Внутри — ничего: ни ролей, ни срока, ни имени.

Проверить подпись у него нечем, поэтому проверяют **интроспекцией** (RFC 7662): сервис спрашивает у издателя, жив ли токен.

```http
POST /introspect HTTP/1.1
Authorization: Basic <credentials сервиса>     ← эндпоинт закрыт: иначе им перебирают токены
Content-Type: application/x-www-form-urlencoded

token=mF_9.B5f-4.1JqM
```

```json
{ "active": true, "sub": "42", "aud": "orders",
  "scope": "read:orders", "exp": 1790000000, "iss": "https://auth.example.com" }
```

Обязательное поле ответа ровно одно — **`active`**; остальные клеймы издатель добавляет по желанию.

| | **JWT (самодостаточный)** | **Opaque + интроспекция** |
|---|---|---|
| Что внутри | данные + подпись | случайный идентификатор |
| Как проверяется | локально, публичным ключом | сетевым запросом к издателю |
| Сеть на каждый запрос | нет | **да** |
| Отзыв | только до `exp` (или список `jti`) | **мгновенный** |
| Утечка содержимого | payload читает любой | не раскрывает ничего |
| Узкое место | нет | сервис авторизации |
| Свежесть прав | на момент выпуска | всегда актуальные |

**Почему интроспекция дороже:** каждый запрос пользователя превращается в дополнительный сетевой вызов — растёт задержка, а сервис авторизации становится общим узким местом и единой точкой отказа: он лёг — встали все сервисы. Ровно от этого JWT и уходит.

**Когда она всё же оправдана:** нужен мгновенный отзыв (банк, доступ к деньгам), токен уходит наружу и его содержимое нельзя показывать, права меняются часто. Компромисс встречается и гибридный: opaque-токен наружу, JWT — внутри периметра, обмен на шлюзе.

## Как снизить нагрузку на сервис авторизации

Порядок здесь — от главного к добавкам:

1. **Не ходить к нему вообще** — асимметричная подпись и локальная проверка. Это и есть основной ответ; всё остальное — оптимизации поверх.
2. **Кэшировать JWKS** по `kid` с TTL, а не тянуть ключи на каждый запрос.
3. **Валидировать один раз на API gateway**, а внутрь передавать уже разобранный контекст (`X-User-Id`). Тогда внутренний трафик обязан быть защищён отдельно — **mTLS**, иначе такой заголовок подделает любой, кто попал в сеть.
4. **Короткий access + долгий refresh** — обращения к сервису авторизации происходят только при обновлении пары, а не при каждом запросе.
5. **Кэшировать результат интроспекции** на короткий TTL, если токены opaque.
6. **Список отозванных держать в Redis** рядом с сервисом, а не запросом в auth.
7. **Горизонтально масштабировать сам сервис** — называется последним: это лечение симптома, а не причины.

## Сквозной пример: издатель и потребитель

Сервис авторизации выпускает токены, сервис заказов их проверяет, общего секрета между ними нет.

**Шаг 1. Ключевая пара** — приватный ключ не покидает сервис авторизации.

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out private.pem
openssl rsa -in private.pem -pubout -out public.pem
```

**Шаг 2. Сервис авторизации выпускает токен.**

```python
import time, uuid, jwt                       # pip install "pyjwt[crypto]"

PRIVATE_KEY = open("private.pem").read()
KID = "auth-2026-07"                         # имя текущего ключа

def issue_access_token(user_id: str, audience: str) -> str:
    now = int(time.time())
    payload = {
        "iss": "https://auth.example.com",   # 1. кто выпустил
        "sub": user_id,                      # 2. о ком токен
        "aud": audience,                     # 3. какому сервису предназначен
        "iat": now,                          # 4. когда выпущен
        "exp": now + 900,                    # 5. живёт 15 минут
        "jti": str(uuid.uuid4()),            # 6. id токена — для отзыва
        "roles": ["user"],                   # 7. НЕ секреты: payload читают все
    }
    return jwt.encode(payload, PRIVATE_KEY, algorithm="RS256",
                      headers={"kid": KID})  # 8. kid → по нему найдут ключ в JWKS
```

**Шаг 3. Он же публикует публичный ключ.**

```python
import json
from cryptography.hazmat.primitives.serialization import load_pem_public_key
from jwt.algorithms import RSAAlgorithm

def jwks() -> dict:                          # отдаётся по GET /.well-known/jwks.json
    public_key = load_pem_public_key(open("public.pem", "rb").read())
    key = json.loads(RSAAlgorithm.to_jwk(public_key))
    key |= {"kid": KID, "use": "sig", "alg": "RS256"}   # kid проставляем сами
    return {"keys": [key]}                   # при ротации здесь лежат оба ключа
```

**Шаг 4. Сервис заказов проверяет — не зная ни секрета, ни приватного ключа.**

```python
import jwt
from jwt import PyJWKClient

jwks_client = PyJWKClient(
    "https://auth.example.com/.well-known/jwks.json",
    cache_jwk_set=True, lifespan=300,        # 1. кэш ключей на 5 минут
)

def current_user(token: str) -> dict:
    key = jwks_client.get_signing_key_from_jwt(token).key   # 2. ключ по kid из header
    return jwt.decode(
        token, key,
        algorithms=["RS256"],                # 3. белый список: alg из токена не слушаем
        issuer="https://auth.example.com",   # 4. iss — наш издатель
        audience="orders",                   # 5. aud — токен для НАС
        leeway=30,                           # 6. допуск на рассинхрон часов
        options={"require": ["exp", "iat", "iss", "aud", "sub"]},   # 7. клеймы обязательны
    )
```

**Как это читать.** Шаги 2–3 у издателя: подписал приватным ключом, пометил `kid`, опубликовал публичный. Шаги 2–7 у потребителя — это и есть полная валидация: `PyJWKClient` сам сходит за JWKS, закэширует набор и перечитает его, если `kid` незнакомый (то есть ротация переживается без деплоя). `algorithms=["RS256"]` закрывает `alg: none` и путаницу HS256/RS256; `issuer`/`audience` отвечают на «от кого и для кого»; `require` не даёт принять токен, где обязательный клейм просто отсутствует. Все ошибки PyJWT наследуются от `jwt.InvalidTokenError` — ловить достаточно её и возвращать `401`:

```python
try:
    user = current_user(token)
except jwt.InvalidTokenError:                # ExpiredSignature, InvalidAudience, InvalidSignature…
    raise HTTPException(status_code=401, detail="invalid token")
```

Приватного ключа в сервисе заказов нет нигде — выпустить токен он физически не может. В этом вся суть.
