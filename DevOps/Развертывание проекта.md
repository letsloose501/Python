# Развертывание проекта

> _«В разработке код работает у тебя; в проде — у всех остальных»_

---

**Развёртывание** (deployment) — процесс запуска приложения на боевом сервере так, чтобы к нему могли обращаться реальные пользователи. Во время разработки хватает `runserver` на `localhost`; в проде нужен постоянно работающий сервер приложений за обратным прокси, с базой, статикой и секретами вне кода.

Заметка предполагает, что сервер уже подготовлен по [Работа с сервером](../DevOps/Работа%20с%20сервером.md) (есть пользователь, пакеты, база, firewall). Здесь — как положить на него конкретный проект и довести до рабочего сайта.

## Почему `runserver` не для прода

Встроенный сервер Django (`manage.py runserver`) создан для разработки: он однопоточный, не держит нагрузку, не отдаёт статику эффективно и сам разработчик прямо предупреждает не использовать его в проде. Боевая схема — из трёх слоёв:

```
Интернет ──▶ Nginx ──▶ Gunicorn ──▶ Django-приложение ──▶ PostgreSQL
            (прокси,   (сервер       (твой код)            (данные)
             статика)   приложений)
```

Каждый слой делает своё: **nginx** принимает запросы и отдаёт статику, **gunicorn** запускает Python-код в несколько процессов, **приложение** обрабатывает логику, **база** хранит данные.

## Шаг 1. Код и окружение

Забираем проект из репозитория и ставим зависимости в изолированное [виртуальное окружение](../Библиотеки/Модули/Система%20и%20окружение/venv.md) — чтобы пакеты проекта не мешались с системными.

```bash
git clone https://github.com/user/project.git
cd project
python3 -m venv venv             # создать окружение в папке venv
source venv/bin/activate         # активировать (в приглашении появится (venv))
pip install -r requirements.txt  # поставить зависимости проекта
```

> `requirements.txt` — список зависимостей с версиями (`pip freeze > requirements.txt` его генерирует). Он и есть гарантия, что на сервере соберётся то же окружение, что у тебя.

## Шаг 2. Переменные окружения (.env)

Секреты и настройки, зависящие от среды (ключи, пароли, хосты), **не хранят в коде** — иначе они утекут в git. Их держат в файле `.env` рядом с проектом (он в `.gitignore`) и читают в рантайме.

```bash
nano .env
```

```ini
SECRET_KEY=длинный-случайный-ключ
DEBUG=False
ALLOWED_HOSTS=203.0.113.10,mysite.ru
DB_ENGINE=django.db.backends.postgresql
DB_NAME=mydb
DB_USER=myuser
DB_PASSWORD=secret
DB_HOST=localhost
DB_PORT=5432
```

Читаем их в `settings.py` через **python-dotenv**:

```python
import os
from dotenv import load_dotenv

load_dotenv()                                   # подхватить переменные из .env

SECRET_KEY = os.getenv('SECRET_KEY')
DEBUG = os.getenv('DEBUG') == 'True'            # os.getenv всегда возвращает строку!
ALLOWED_HOSTS = os.getenv('ALLOWED_HOSTS').split(',')
```

> **`DEBUG=True` в проде — дыра в безопасности:** при ошибке Django покажет пользователям трейсбек с настройками и кусками кода. В проде всегда `DEBUG=False`, а в `ALLOWED_HOSTS` — только свои домены и IP.

## Шаг 3. Миграции и статика

Готовим базу и собираем статические файлы:

```bash
python manage.py migrate          # применить схему БД (создать таблицы)
python manage.py collectstatic    # собрать статику всех приложений в STATIC_ROOT
```

Для `collectstatic` в `settings.py` должно быть настроено, куда складывать файлы, — оттуда их будет раздавать nginx:

```python
STATIC_URL = '/static/'
STATIC_ROOT = os.path.join(BASE_DIR, 'static')   # папка, куда collectstatic всё соберёт
```

## Шаг 4. WSGI/ASGI — мост «приложение ↔ сервер»

Сервер приложений (gunicorn) и Python-код общаются через стандартный интерфейс. Их два:

| | WSGI | ASGI |
|---|---|---|
| **Расшифровка** | Web Server Gateway Interface | Asynchronous Server Gateway Interface |
| **Модель** | синхронная, запрос за запросом | асинхронная, конкурентные запросы |
| **Для чего** | обычный Django/Flask | async-приложения, WebSocket, [asyncio](../Библиотеки/Модули/Параллелизм/Asyncio%20Event%20Loop%20и%20aiohttp.md) |
| **Точка входа** | `project/wsgi.py` | `project/asgi.py` |

Django из коробки поставляет `wsgi.py` — этот объект и запускает gunicorn.

> Здесь интерфейс нужен как точка запуска. Как он устроен изнутри — сигнатура `application(environ, start_response)`, словарь `environ`, события `scope/receive/send` и почему middleware это декоратор — в [WSGI и ASGI — интерфейс сервера и приложения](../WSGI%20и%20ASGI%20—%20интерфейс%20сервера%20и%20приложения.md).

## Шаг 5. Gunicorn — сервер приложений

**Gunicorn** — де-факто стандартный WSGI-сервер для Python: запускает твоё приложение в нескольких процессах-**воркерах**, распределяя между ними запросы.

```bash
pip install gunicorn
gunicorn project.wsgi:application --bind 0.0.0.0:8000 --workers 3
```

- **`project.wsgi:application`** — путь к WSGI-объекту в формате `модуль:переменная` (модуль `project/wsgi.py`, переменная `application`).
- **`--bind`** / `-b` — где слушать: пара интерфейс:порт. `0.0.0.0` — все интерфейсы, `127.0.0.1` — только изнутри машины ([разница и почему «снаружи не видно»](../DevOps/Работа%20с%20сервером.md#сетевые-интерфейсы-127001-и-0000)). В связке с nginx слушают не порт, а **unix-сокет** (быстрее и не торчит наружу): `--bind unix:/home/deploy/project/project.sock`.
- **`--workers`** / `-w` — число процессов. Документация ориентирует на 2–4 на ядро.

### Значения по умолчанию

Их полезно знать наизусть: почти все «странности» gunicorn объясняются именно ими.

| Настройка | По умолчанию | Что значит |
|---|---|---|
| `bind` | `127.0.0.1:8000` | **только петля** — снаружи не видно, пока не задашь своё |
| `workers` | `1` | один процесс; масштабируют вручную |
| `worker_class` | `sync` | по запросу за раз на воркер, без keep-alive |
| `threads` | `1` | потоков на воркер (имеет смысл с `gthread`) |
| `timeout` | `30` | см. ловушку ниже — это **не** таймаут запроса |
| `graceful_timeout` | `30` | сколько ждать, пока воркер доработает при перезапуске |
| `keepalive` | `2` | ожидание следующего запроса в keep-alive-соединении |
| `max_requests` | `0` | перезапуск воркера после N запросов; `0` — выключено |

> **`timeout` — не таймаут запроса, а таймаут молчания воркера.** Формулировка документации: воркеры, молчащие дольше указанного, убиваются и перезапускаются. Это heartbeat между мастером и воркером, а не ограничение на время обработки. Отсюда типичное недоумение «поставил `--timeout 5`, а долгий запрос всё равно выполняется»: у синхронного воркера отсчёт совпадает с обработкой, а у асинхронного — нет, потому что воркер продолжает отвечать мастеру. Ограничивать время самого запроса надо на стороне nginx или в коде.

**`max_requests`** — лекарство от утечек памяти: воркер сам перезапускается, отработав N запросов, и утечка не копится. К нему добавляют `max_requests_jitter`, чтобы воркеры не перезапустились все разом.

### Классы воркеров

```bash
gunicorn app:application -k gthread --threads 4     # -k / --worker-class
```

| Класс | Когда |
|---|---|
| **`sync`** (по умолчанию) | простое приложение за nginx; один запрос за раз, keep-alive нет |
| **`gthread`** | пул потоков на воркер: keep-alive и умеренная конкурентность дешевле, чем лишние процессы |
| **`gevent`**, **`tornado`** | много одновременных соединений на корутинах |
| **`asgi`** | ASGI-приложения — FastAPI, Starlette, Quart |

> **Нативный ASGI появился в самом gunicorn.** Воркер `asgi` добавлен в версии **24.0.0** (бета) и стал стабильным в **25.1.0**: asyncio, HTTP/1.1 с keep-alive, WebSocket и протокол Lifespan — без сторонних зависимостей.
>
> ```bash
> gunicorn project.asgi:application -k asgi --workers 4
> ```
>
> Это отменяет прежнюю схему с воркером uvicorn (`-k uvicorn_worker.UvicornWorker`): менеджер процессов, логирование и конфиг остаются гуникорновские, а ASGI работает штатно. Про выбор «gunicorn или чистый uvicorn» — [REST API на FastAPI](../Фреймворки/REST%20API%20на%20FastAPI.md#uvicorn-и-gunicorn--кто-из-них-зачем).

### Конфиг вместо длинной команды

Флаги выносят в файл `gunicorn.conf.py` — он же читается по умолчанию:

```python
bind = "unix:/home/deploy/project/project.sock"
workers = 3
worker_class = "gthread"
threads = 4
max_requests = 1000
max_requests_jitter = 100
accesslog = "/var/log/gunicorn/access.log"
errorlog = "/var/log/gunicorn/error.log"
```

```bash
gunicorn -c gunicorn.conf.py project.wsgi:application
gunicorn --help                    # полный список опций
```

Любую настройку можно передать и через переменную окружения `GUNICORN_CMD_ARGS` — удобно в контейнере, где команду менять не хочется.

## Шаг 6. systemd-юнит для приложения

Чтобы gunicorn работал постоянно и поднимался после перезагрузки, оформляем его сервисом [systemd](../DevOps/Работа%20с%20сервером.md#systemd--сервисы-которые-сами-перезапускаются). Файл `/etc/systemd/system/gunicorn.service`:

```ini
[Unit]
Description=gunicorn daemon for project
After=network.target                 # стартовать после поднятия сети

[Service]
User=deploy
Group=www-data
WorkingDirectory=/home/deploy/project
ExecStart=/home/deploy/project/venv/bin/gunicorn \
          project.wsgi:application \
          --workers 3 \
          --bind unix:/home/deploy/project/project.sock

[Install]
WantedBy=multi-user.target           # автозапуск в обычном многопользовательском режиме
```

```bash
sudo systemctl daemon-reload         # перечитать юниты
sudo systemctl start gunicorn
sudo systemctl enable gunicorn       # автозапуск при загрузке
sudo systemctl status gunicorn       # проверить, что работает
```

## Шаг 7. Nginx — обратный прокси и статика

> Подробно про nginx как веб-сервер — обратный прокси, балансировка, конфиг, vs Apache/Caddy — в [nginx](../DevOps/nginx.md).

**Nginx** стоит на входе: статику отдаёт сам (быстро), а всё остальное проксирует gunicorn через сокет. Конфиг сайта — `/etc/nginx/sites-available/project`:

```nginx
server {
    listen 80;
    server_name 203.0.113.10 mysite.ru;      # IP и домены сайта

    location /static/ {                      # статику nginx отдаёт напрямую
        root /home/deploy/project;
    }

    location / {                             # всё прочее — в gunicorn
        include proxy_params;
        proxy_pass http://unix:/home/deploy/project/project.sock;
    }
}
```

Включаем сайт символической ссылкой в `sites-enabled` и перезапускаем nginx:

```bash
sudo ln -s /etc/nginx/sites-available/project /etc/nginx/sites-enabled/
sudo nginx -t                        # проверить конфиг на ошибки
sudo systemctl restart nginx
```

- **`sites-available`** — все описанные сайты; **`sites-enabled`** — включённые (ссылки на них). Так сайт можно выключить, не удаляя конфиг.
- **`location /static/`** идёт **до** `location /`: nginx выбирает наиболее конкретное совпадение и статику до gunicorn не пропускает.

## Сквозной пример: деплой Django от clone до домена

Полный порядок на уже подготовленном сервере ([Работа с сервером](../DevOps/Работа%20с%20сервером.md)).

```bash
# 1. Код и окружение
cd /home/deploy
git clone https://github.com/user/project.git && cd project
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt gunicorn

# 2. Конфиг и подготовка
nano .env                              # секреты, DEBUG=False, ALLOWED_HOSTS
python manage.py migrate               # схема БД
python manage.py collectstatic         # статика в STATIC_ROOT

# 3. Проверить, что вообще стартует
gunicorn project.wsgi:application --bind 0.0.0.0:8000   # открыть IP:8000, затем Ctrl+C

# 4. Оформить сервисом и прокси
sudo nano /etc/systemd/system/gunicorn.service   # юнит из Шага 6
sudo systemctl daemon-reload
sudo systemctl start gunicorn && sudo systemctl enable gunicorn

sudo nano /etc/nginx/sites-available/project      # конфиг из Шага 7
sudo ln -s /etc/nginx/sites-available/project /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl restart nginx
#   → сайт открывается по IP/домену на порту 80
```

**Как это читать.** Сначала поднимаем код и окружение, затем проверяем, что gunicorn в принципе запускает приложение (шаг 3), и только потом заворачиваем его в systemd и прячем за nginx. Такой порядок ловит ошибки по одной, а не все разом в конце.

## Обновление (redeploy)

Выкатка новой версии — всегда одна и та же короткая последовательность:

```bash
cd /home/deploy/project
git pull origin main               # забрать свежий код
source venv/bin/activate
pip install -r requirements.txt    # если менялись зависимости
python manage.py migrate           # если менялась схема БД
python manage.py collectstatic --noinput
sudo systemctl restart gunicorn    # перезапустить, чтобы подхватил новый код
```

Именно эти команды и автоматизирует [CI CD](../DevOps/CI%20CD.md) — чтобы после каждого пуша они выполнялись сами.
