# Наблюдаемость — метрики, логи, трейсы

Код выкатили, он работает. Через неделю пользователь пишет «у вас тормозит». Вопрос: как ты узнаешь, **что именно** тормозит и **когда началось**, не имея доступа к его экрану?

**Наблюдаемость** (observability) — свойство системы, позволяющее понять её внутреннее состояние по тому, что она выдаёт наружу. Это и есть граница между «умею писать код» и «умею держать сервис»: джуна спрашивают, как написать эндпоинт, мидла — как понять, почему этот эндпоинт стал отвечать за 3 секунды.

> **Мониторинг ≠ наблюдаемость.** Мониторинг отвечает на **заранее заданные** вопросы («жив ли сервис?»). Наблюдаемость позволяет задать вопрос, который ты не придумал заранее («почему тормозит только у пользователей из Казани после обеда?»).

---

## Три столпа

Три разных сигнала, каждый отвечает на свой вопрос. Они не заменяют друг друга.

| Сигнал | Отвечает на вопрос | Пример | Стоимость хранения |
|---|---|---|---|
| **Метрики** | Что происходит? Сколько? | RPS упал с 500 до 30 | Дёшево (числа) |
| **Логи** | Что именно случилось в этом случае? | `OperationalError: connection refused` | Дорого (текст) |
| **Трейсы** | Где потерялось время? | Из 3 с запроса 2.8 с — вызов сервиса платежей | Средне (обычно семплируют) |

Типичный порядок расследования: **метрика показала аномалию → трейс показал, какой шаг тормозит → лог объяснил причину.**

```
Алерт «p95 вырос»  ──▶  Метрика: рост с 14:20
                          │
                          ▼
                   Трейс: 90% времени в вызове billing
                          │
                          ▼
              Лог billing: "connection pool exhausted"
```

## Метрики

**Метрика** — числовое измерение, снимаемое регулярно и хранимое как временной ряд.

### Четыре типа

- **Counter** (счётчик) — только растёт: число запросов, число ошибок. Сбрасывается при рестарте, поэтому смотрят не значение, а **скорость роста**.
- **Gauge** (индикатор) — может расти и падать: занятая память, число соединений в пуле, длина очереди.
- **Histogram** (гистограмма) — распределение по «корзинам»: сколько запросов уложилось в 10 мс, 50 мс, 100 мс. Из неё считают перцентили.
- **Summary** — то же, но перцентили считает сам клиент. Минус: их **нельзя складывать** между инстансами. Обычно берут histogram.

### 🔴 Среднее врёт — считай перцентили

Самая частая ошибка новичка в мониторинге.

```
Время ответа 10 запросов: 9 по 100 мс + 1 за 5000 мс

среднее = 590 мс   ← «ну, приемлемо»
p50     = 100 мс   ← половина быстрее этого
p95     = 5000 мс  ← каждый двадцатый ждёт 5 секунд
```

**Перцентиль p95 = 5000 мс** значит: 95% запросов быстрее 5 секунд, а 5% — медленнее. Именно эти 5% пишут в поддержку. Среднее их прячет, перцентиль показывает.

> Смотри **p50, p95, p99**. p50 — как живёт типичный пользователь, p99 — как живёт самый несчастный. Если p99 в десять раз больше p50, у тебя есть проблема, которую среднее не покажет никогда.

### Какие метрики снимать: RED и USE

Две готовые схемы, чтобы не изобретать набор с нуля.

**RED — для сервисов** (что видит пользователь):
- **R**ate — запросов в секунду;
- **E**rrors — доля неуспешных;
- **D**uration — время ответа (в перцентилях).

**USE — для ресурсов** (что происходит с железом):
- **U**tilization — процент занятости (CPU, диск);
- **S**aturation — очередь ожидания (load average, глубина очереди);
- **E**rrors — ошибки устройства.

> Начни с RED на каждый эндпоинт. Три метрики закрывают 80% вопросов «что со сервисом».

### ⚠️ Ловушка: кардинальность

**Кардинальность** — число уникальных комбинаций меток (labels) у метрики. Каждая комбинация — отдельный временной ряд в базе.

```python
# НЕПРАВИЛЬНО — user_id в метке
requests.labels(endpoint="/order", user_id=user.id).inc()
# 1 млн пользователей → 1 млн временных рядов → Prometheus падает

# ПРАВИЛЬНО — только ограниченные множества
requests.labels(endpoint="/order", method="POST", status="200").inc()
# ~50 комбинаций
```

Правило: в метку идёт только то, у чего **конечное и небольшое** число значений. `user_id`, `email`, `trace_id`, полный URL с параметрами — никогда. Их место в логах.

## Логи

**Лог** — запись о конкретном событии в конкретный момент.

### Структурные логи вместо строк

```python
# НЕПРАВИЛЬНО — попробуй потом это распарсить
log.info(f"Пользователь {user_id} оформил заказ {order_id} за {ms} мс")

# ПРАВИЛЬНО — машиночитаемо, ищется фильтром
log.info("order_created", extra={
    "user_id": user_id, "order_id": order_id,
    "duration_ms": ms, "trace_id": trace_id,
})
```

Структурный лог — это **JSON**, а не предложение. По нему можно построить запрос «все заказы дороже 10 000 за последний час», а по строке — только `grep`.

### Уровни осмысленно

| Уровень | Когда | Кто читает |
|---|---|---|
| `DEBUG` | Детали для отладки, в проде обычно выключен | Разработчик локально |
| `INFO` | Значимое событие бизнес-логики: заказ создан | Расследование постфактум |
| `WARNING` | Странно, но обработано: ретрай сработал | Смотрят при разборе |
| `ERROR` | Операция провалилась, нужен человек | Алерт |
| `CRITICAL` | Сервис не может работать | Будят ночью |

> **Главное правило логов:** если на строку `ERROR` никто не реагирует, это не `ERROR`. Понизь уровень или почини причину. Лог, который все игнорируют, хуже отсутствующего — он создаёт иллюзию контроля.

### Что не логировать никогда

Пароли, токены, номера карт, персональные данные. Лог живёт годами, читается многими и попадает в сторонние системы ([Веб-безопасность](../Веб-безопасность.md)).

## Трейсы

**Трейс** — путь одного запроса через все сервисы, разбитый на этапы.
**Спан** (span) — один этап внутри трейса: вызов БД, поход в соседний сервис, тяжёлое вычисление.

```
trace_id: abc123                                    всего 850 мс
├─ span: POST /order                    [========================] 850
│  ├─ span: SELECT user                 [==]                        40
│  ├─ span: POST billing/charge         [==================]       620   ← вот оно
│  │   └─ span: SELECT card             [=]                         30
│  └─ span: INSERT order                [===]                       80
```

Без трейса ты видишь только «850 мс» и гадаешь. С трейсом сразу ясно: 620 мс из 850 — в billing.

**Ключевая идея — `trace_id` проходит насквозь.** Сервис A генерирует его, кладёт в заголовок, сервис B принимает и передаёт дальше. Тот же `trace_id` пишется в логи — и по одному идентификатору собирается вся картина.

**OpenTelemetry** — вендонезависимый стандарт и набор библиотек для сбора трейсов, метрик и логов. Ставится один раз, а бэкенд (Jaeger, Tempo, коммерческий) можно менять.

## Алерты

**Алерт** — правило «если метрика ведёт себя так, разбуди человека».

**Алерти на симптом, а не на причину.** «CPU 90%» — причина, и она может быть нормой. «p95 времени ответа выше 2 с десять минут подряд» — симптом: пользователю плохо прямо сейчас.

**SLI / SLO / SLA** — три уровня одного разговора о качестве:

- **SLI** (indicator) — что измеряем: доля запросов быстрее 300 мс.
- **SLO** (objective) — внутренняя цель: 99.9% запросов быстрее 300 мс за месяц.
- **SLA** (agreement) — обещание клиенту с деньгами за нарушение. Ставится **ниже** SLO, чтобы был запас.

**Error budget** (бюджет ошибок) — сколько можно ломаться, не нарушив SLO. При SLO 99.9% за 30 дней бюджет ≈ **43 минуты** недоступности. Пока бюджет есть — катим фичи; сожгли — останавливаемся и чиним надёжность. Это превращает спор «релизить или стабилизировать» в арифметику.

> ⚠️ **Усталость от алертов.** Если алерты срабатывают часто и без действия — их перестают читать, и тогда пропускают настоящий. Правило: **на каждый алерт есть, что сделать**. Не знаешь, что делать по алерту — это дашборд, а не алерт.

## Health-чеки: liveness ≠ readiness

Два разных вопроса, которые постоянно путают ([Kubernetes](../DevOps/Kubernetes.md)).

- **liveness** — «процесс жив?» Провалился → контейнер **перезапускают**.
- **readiness** — «готов принимать трафик?» Провалился → из балансировки **убирают**, но не убивают.

```python
# НЕПРАВИЛЬНО — проверка БД в liveness
@app.get("/health/live")
def live():
    db.execute("SELECT 1")     # БД моргнула → перезапуск всех подов → лавина
    return {"ok": True}

# ПРАВИЛЬНО — зависимости только в readiness
@app.get("/health/live")
def live():
    return {"ok": True}        # процесс отвечает — значит жив

@app.get("/health/ready")
def ready():
    db.execute("SELECT 1")     # БД лежит → выведут из ротации, вернут когда оживёт
    return {"ok": True}
```

Причина ошибки в первом варианте: перезапуск не чинит недоступную БД, а массовый рестарт добивает её ещё и потоком новых подключений.

## Сквозной пример: доводим сервис до наблюдаемого

**Шаг 1. Метрики RED на каждый эндпоинт.**

```python
from prometheus_client import Counter, Histogram, make_asgi_app

REQ = Counter("http_requests_total", "Всего запросов",
              ["method", "endpoint", "status"])
LAT = Histogram("http_request_duration_seconds", "Время ответа",
                ["method", "endpoint"])

@app.middleware("http")
async def metrics(request, call_next):
    with LAT.labels(request.method, request.url.path).time():
        response = await call_next(request)
    REQ.labels(request.method, request.url.path, response.status_code).inc()
    return response

app.mount("/metrics", make_asgi_app())   # Prometheus придёт сюда сам
```

**Шаг 2. Структурные логи с `trace_id`.** Middleware читает заголовок `traceparent`, кладёт id в контекст, логгер подмешивает его в каждую запись.

**Шаг 3. Health-чеки** — два эндпоинта, как выше.

**Шаг 4. Дашборд** — три графика на сервис: RPS, доля 5xx, p50/p95/p99. Больше на первом экране не нужно.

**Шаг 5. Один алерт** — доля 5xx выше 1% пять минут подряд. Работает — добавляй следующий.

Порядок важен: метрики без дашборда бесполезны, дашборд без алерта требует, чтобы кто-то смотрел, а алерт без плана действий — шум.
