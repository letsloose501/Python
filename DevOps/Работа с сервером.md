# Работа с сервером

> _«It works on my machine» → «then we'll ship your machine»_ — так родились контейнеры, но сначала нужен сам сервер

---

**Сервер** — это всегда включённый компьютер, доступный из интернета, на котором крутится твоё приложение, чтобы к нему могли обращаться пользователи. Своя машина для этого не годится: её выключают, у неё «серый» IP и нет гарантий доступности. Поэтому арендуют **VPS** и управляют им удалённо через терминал по SSH.

Эта заметка — про сервер **как машину**: как его получить, войти, завести пользователей, поставить пакеты, закрыть лишние порты и поднять базу. Как выкатить на него конкретный проект — в [Развертывание проекта](../DevOps/Развертывание%20проекта.md).

## VPS — арендованный компьютер

**VPS** (Virtual Private Server) — виртуальный сервер: провайдер нарезает мощный физический сервер на изолированные виртуальные машины и сдаёт их в аренду. Ты получаешь свой кусок с гарантированными CPU, RAM, диском и **белым (публичным) IP**, доступным из любой точки сети.

- **Провайдеры:** Timeweb, Selectel, Yandex Cloud, VK Cloud, DigitalOcean, Hetzner, AWS EC2.
- **ОС по умолчанию** — обычно **Ubuntu Server LTS**: бесплатна, стабильна, гигантское комьюнити, все инструкции написаны под неё.
- При заказе провайдер даёт **IP-адрес**, логин `root` и пароль (или сразу принимает твой SSH-ключ).

## SSH — вход на сервер

**SSH** (Secure Shell) — протокол защищённого удалённого доступа к терминалу сервера. Весь трафик шифруется, поэтому по SSH безопасно вводить команды и пароли через открытый интернет.

```
ssh root@203.0.113.10        # войти под root на сервер с этим IP
ssh user@mysite.ru -p 2222   # другой пользователь и нестандартный порт
```

### Ключи вместо пароля

Пароль можно подобрать перебором — сервер в интернете **постоянно** сканируют боты. Надёжнее вход по **паре ключей**: приватный хранится у тебя и никогда не покидает машину, публичный кладётся на сервер.

```
Твоя машина                          Сервер
┌──────────────┐                     ┌──────────────────────────┐
│ id_ed25519   │ приватный (секрет)  │                          │
│ id_ed25519.pub ─── копируется ───▶ │ ~/.ssh/authorized_keys   │
└──────────────┘                     └──────────────────────────┘
```

```bash
ssh-keygen -t ed25519 -C "почта@example.com"   # создать пару ключей
#   → ~/.ssh/id_ed25519      приватный — НИКОМУ не отдавать
#   → ~/.ssh/id_ed25519.pub  публичный — можно раздавать

cat ~/.ssh/id_ed25519.pub          # показать публичный ключ, чтобы скопировать
ssh-copy-id user@203.0.113.10      # автоматически положить его на сервер
```

- **`ssh-keygen`** — генерирует пару. `ed25519` современнее и короче устаревшего `rsa`.
- **`ssh-copy-id`** дописывает публичный ключ в `~/.ssh/authorized_keys` на сервере. После этого вход идёт без пароля — сервер проверяет, что у тебя есть парный приватный ключ.

> После настройки ключей отключи вход по паролю в `/etc/ssh/sshd_config` (`PasswordAuthentication no`) — это отсекает перебор паролей.

## Пользователи и sudo

Работать под `root` опасно: любая опечатка выполняется с абсолютными правами и может снести систему. Заводят **обычного пользователя** и дают ему право повышать привилегии через `sudo` только когда нужно.

```bash
adduser deploy                 # создать пользователя (спросит пароль и данные)
usermod -aG sudo deploy        # добавить в группу sudo → право выполнять команды как root
```

- **`adduser имя`** — создаёт пользователя с домашней папкой `/home/имя`.
- **`usermod -aG sudo имя`** — `-aG` добавляет (`-a`) в группу (`-G`) `sudo`, не выкидывая из остальных. Забудешь `-a` — перезапишешь список групп.
- **`sudo команда`** — выполнить одну команду с правами root (спросит твой пароль). Так видно, где именно ты действуешь как администратор.

## Пакеты — менеджер apt

В Ubuntu/Debian софт ставят из репозиториев менеджером **apt** — он сам подтягивает зависимости и версии.

```bash
sudo apt update                # обновить СПИСОК доступных пакетов (не сам софт)
sudo apt upgrade               # обновить установленные пакеты до свежих версий
sudo apt install python3-venv python3-pip postgresql nginx   # поставить пачкой
```

> `apt update` и `apt upgrade` — разное: первое обновляет *каталог* (что вообще доступно), второе — сами программы. Всегда `update` перед `install`, иначе поставится по устаревшему списку.

Типовой набор для backend на [Python](../Python.md): `python3-venv` (виртуальные окружения), `python3-pip`, `postgresql` (база), `nginx` (веб-сервер), `git`.

## Firewall — UFW

**Firewall** (межсетевой экран) закрывает все порты, кроме явно разрешённых, — чтобы наружу торчали только нужные сервисы. В Ubuntu удобная надстройка — **UFW** (Uncomplicated Firewall).

```bash
sudo ufw allow OpenSSH         # разрешить SSH (порт 22) — иначе запрёшь сам себя!
sudo ufw allow 'Nginx Full'    # разрешить HTTP (80) и HTTPS (443)
sudo ufw enable                # включить firewall
sudo ufw status                # показать правила
```

> **Сначала разреши SSH, потом включай UFW.** Иначе `enable` отрубит твоё же соединение, и на сервер будет не зайти (только через веб-консоль провайдера).

## PostgreSQL на сервере

Реляционную базу PostgreSQL ставят прямо на сервер. После установки в системе появляется служебный пользователь `postgres` — под ним заходят в консоль базы `psql`.

```bash
sudo -u postgres psql          # войти в psql под системным пользователем postgres
```

Внутри `psql` создают пользователя и базу под проект:

```sql
CREATE USER myuser WITH PASSWORD 'secret';   -- пользователь БД с паролем
CREATE DATABASE mydb OWNER myuser;           -- база, владелец — myuser
GRANT ALL PRIVILEGES ON DATABASE mydb TO myuser;
\q                                           -- выйти из psql
```

- **`CREATE USER … WITH PASSWORD`** — роль для подключения из приложения. Приложение будет ходить в базу под ней, а не под `postgres`.
- **`CREATE DATABASE … OWNER`** — база проекта с назначенным владельцем.
- **`\q`** — выход. Команды `psql` начинаются с `\` (`\l` — список баз, `\du` — список ролей, `\c db` — подключиться к базе).

> Приложению для подключения нужна строка вида `postgresql://myuser:secret@localhost:5432/mydb` — её кладут в `.env` (см. [Развертывание проекта](../DevOps/Развертывание%20проекта.md#шаг-2-переменные-окружения-env)).

## Сетевые интерфейсы: 127.0.0.1 и 0.0.0.0

Классическая ситуация: приложение на сервере запустилось, в логах всё чисто, firewall открыт — а снаружи страница не открывается. Причина обычно не в сети, а в том, **на каком интерфейсе** приложение слушает.

**Сетевой интерфейс** — точка подключения машины к сети. Их всегда несколько, и они бывают реальные и виртуальные:

```
        ┌──────────────── сервер ─────────────────┐
        │                                          │
внешний │  реальный интерфейс   203.0.113.10  ◀────┼──── из интернета
        │                                          │
        │  виртуальный (loopback) 127.0.0.1        │  ← только внутри машины
        │                                          │
        └──────────────────────────────────────────┘
```

- **`127.0.0.1`** (он же `localhost`) — **петлевой** интерфейс. Трафик, отправленный на него, не покидает машину. Есть на любой ОС, даже без сети вообще.
- **Реальный интерфейс** — тот, у которого внешний или локальный сетевой адрес; через него приходят запросы снаружи.

Сервер слушает не «порт вообще», а пару **интерфейс : порт**. И вот отсюда следствие:

> Приложение, привязанное к `127.0.0.1:8000`, снаружи недоступно **в принципе** — ни firewall, ни проброс портов тут ни при чём. Запрос с другой машины приходит на реальный интерфейс, а там никто не слушает.

**`0.0.0.0`** — не адрес, а указание «слушать на **всех** интерфейсах сразу»:

```bash
python manage.py runserver 0.0.0.0:8000            # Django: по умолчанию 127.0.0.1!
gunicorn project.wsgi:application --bind 0.0.0.0:8000
uvicorn main:app --host 0.0.0.0 --port 8000
```

Посмотреть, кто и где реально слушает:

```bash
ss -tlnp              # в столбце Local Address будет 127.0.0.1:8000 или 0.0.0.0:8000
```

### То же самое внутри контейнера

Здесь та же логика ловит второй раз, и уже неочевидно. У контейнера **свой** сетевой стек, и `-p 8000:8000` пробрасывает порт на интерфейс **контейнера**. Если приложение внутри слушает `127.0.0.1`, то это петля самого контейнера — проброс упирается в пустоту.

Поэтому в [Dockerfile](../DevOps/Docker.md) пишут именно `--host 0.0.0.0`: изнутри контейнера это «слушать всё», а наружу выпускает уже `-p`.

### Когда 0.0.0.0 — неправильный ответ

На проде за обратным прокси всё наоборот. Если наружу смотрит [Nginx](#nginx--веб-сервер-и-обратный-прокси), то приложению **не нужно** быть доступным напрямую:

```bash
gunicorn project.wsgi:application --bind 127.0.0.1:8000   # только через Nginx
```

Так порт приложения физически не отвечает из интернета, и его нельзя обойти мимо прокси — мимо TLS, ограничения частоты и логов. `0.0.0.0` уместен на этапе «поднял и проверил, что живо», а в боевой схеме наружу смотрит один Nginx.

## systemd — сервисы, которые сами перезапускаются

Запущенный вручную процесс умрёт, как только закроешь SSH-сессию или сервер перезагрузится. Чтобы приложение работало **постоянно** и поднималось после ребута, его оформляют как сервис для **systemd** — системного менеджера служб в Linux.

**Юнит** — файл-описание сервиса в `/etc/systemd/system/имя.service`. Управление — командой `systemctl`:

```bash
sudo systemctl start   myapp     # запустить сейчас
sudo systemctl enable  myapp     # автозапуск при загрузке сервера
sudo systemctl status  myapp     # состояние (работает / упал) и последние логи
sudo systemctl restart myapp     # перезапустить (после обновления кода)
sudo systemctl daemon-reload     # перечитать .service-файлы после их правки
journalctl -u myapp -f           # смотреть логи сервиса в реальном времени
```

Как написать сам `.service`-файл для приложения (gunicorn) — в [Развертывание проекта](../DevOps/Развертывание%20проекта.md#шаг-6-systemd-юнит-для-приложения).

## Nginx — веб-сервер и обратный прокси

**Nginx** — быстрый веб-сервер. На проде он стоит «на входе»: принимает запросы из интернета на портах 80/443 и либо отдаёт **статику** (картинки, CSS, JS) сам, либо проксирует запрос приложению (**обратный прокси**). Устанавливается как пакет (выше), управляется через systemd или `nginx -s`:

```bash
sudo systemctl start nginx       # запустить
nginx -t                         # проверить конфиг на ошибки перед перезагрузкой
sudo systemctl reload nginx      # применить новый конфиг без обрыва соединений
```

Сигналы `nginx -s`: `stop` (резко), `quit` (мягко, доработав текущие запросы), `reload` (перечитать конфиг), `reopen` (переоткрыть лог-файлы). Настройка reverse proxy под конкретное приложение — в [Развертывание проекта](../DevOps/Развертывание%20проекта.md#шаг-7-nginx--обратный-прокси-и-статика).

## Сквозной пример: готовим сервер с нуля

Порядок действий от пустого VPS до состояния «можно выкатывать проект».

```bash
# Шаг 1. Заказать VPS на Ubuntu, получить IP и войти под root
ssh root@203.0.113.10

# Шаг 2. Создать рабочего пользователя и дать ему sudo
adduser deploy
usermod -aG sudo deploy

# Шаг 3. Положить свой SSH-ключ этому пользователю (с локальной машины)
#   exit → на своей машине:
ssh-copy-id deploy@203.0.113.10
ssh deploy@203.0.113.10          # дальше работаем под deploy, не под root

# Шаг 4. Обновить систему и поставить пакеты
sudo apt update && sudo apt upgrade -y
sudo apt install -y python3-venv python3-pip postgresql nginx git

# Шаг 5. Закрыть firewall, оставив SSH и web
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'
sudo ufw enable

# Шаг 6. Создать базу и пользователя БД
sudo -u postgres psql
#   CREATE USER myuser WITH PASSWORD 'secret';
#   CREATE DATABASE mydb OWNER myuser;
#   \q
```

**Как это читать.** Сначала обезопасили доступ (отдельный пользователь + ключ), затем поставили софт, закрыли лишние порты и подняли базу. Сервер готов — дальше на него разворачивают приложение по заметке [Развертывание проекта](../DevOps/Развертывание%20проекта.md).
