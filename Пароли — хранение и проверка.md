# Пароли — хранение и проверка

> _База данных когда-нибудь утечёт. Вопрос только в том, что достанется тому, кто её откроет._

---

Пароль нельзя хранить так, чтобы его можно было прочитать, — ни в открытом виде, ни в зашифрованном (ключ шифрования лежит рядом и утечёт вместе с базой). Хранят **результат необратимой функции**, а при входе повторяют вычисление и сравнивают результаты.

Всё содержание темы — в том, **какой именно** функцией и с какими параметрами.

---

## Почему обычный хеш не годится

`SHA-256` спроектирован быстрым: это его достоинство для контрольных сумм и недостаток для паролей. Современная видеокарта считает миллиарды `SHA-256` в секунду, поэтому перебор всех паролей длиной до восьми символов — вопрос часов, а словарь из миллиарда популярных паролей проверяется за секунды.

Нужна функция, **намеренно медленная и жадная до памяти**, чтобы каждая попытка стоила атакующему заметных ресурсов, а честному серверу — десятков миллисекунд один раз за вход.

---

## Соль

**Соль** — случайная строка, своя для каждого пользователя; она хранится рядом с хешем в открытом виде.

```
хеш = f(пароль + соль)      соль своя у каждого → одинаковые пароли дают разные хеши
```

Что она даёт:

- **радужные таблицы бесполезны** — предпосчитанную таблицу пришлось бы строить под каждую соль отдельно;
- **одинаковые пароли не видны** — без соли две одинаковые строки в базе выдают, что у людей совпал пароль;
- **атака идёт по одному пользователю**, а не по всей базе разом.

Соль не секрет — её задача не спрятать, а **обесценить массовость**. Все современные функции генерируют и хранят её сами, внутри итоговой строки.

**Перец** (pepper) — дополнительный секрет, общий для всего приложения и хранящийся **вне базы** (в переменных окружения, HSM). Если утекла только база — перебор невозможен без перца. Если утекло всё — перец не помогает.

## Чем хешируют

| Функция | Год | Сопротивление | Статус |
|---|---|---|---|
| **PBKDF2** | 2000 | только процессорное время | приемлемо, если требует сертификация (FIPS) |
| **bcrypt** | 1999 | время + небольшая память | рабочий выбор для существующих систем |
| **scrypt** | 2009 | время + настраиваемая память | хорош, но реже поддержан |
| **Argon2id** | 2015 | время + память + защита от side-channel | **выбор по умолчанию** для нового кода |

**Argon2** — победитель Password Hashing Competition (2015); вариант `id` совмещает стойкость к атакам по времени и к перебору на видеокартах. Рекомендация OWASP: минимум **19 МиБ памяти, 2 итерации, 1 поток**.

Для **bcrypt** ключевой параметр — фактор трудоёмкости (work factor): **не ниже 10**, и подбирается так, чтобы проверка занимала десятки миллисекунд на боевом железе. Отдельная особенность — **пароль обрезается на 72 байтах**: всё, что длиннее, молча игнорируется, и это ловушка для тех, кто разрешает длинные парольные фразы.

## Проверка входа

```python
# pip install argon2-cffi
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

ph = PasswordHasher()                       # параметры по умолчанию уже разумные

def register(password: str) -> str:
    return ph.hash(password)                # 1. соль внутри, результат — одна строка

def login(stored: str, password: str) -> bool:
    try:
        ph.verify(stored, password)         # 2. сравнение внутри — постоянного времени
    except VerifyMismatchError:
        return False
    if ph.check_needs_rehash(stored):       # 3. параметры устарели — пересчитать
        save(ph.hash(password))             #    момент входа: пароль в руках только здесь
    return True
```

Читать так: хеш хранится одной строкой (в ней и алгоритм, и параметры, и соль), проверка сравнивает результаты за постоянное время, а `check_needs_rehash` даёт бесплатную миграцию — при следующем входе пользователь незаметно переезжает на усиленные параметры.

> **Сравнивать хеши обычным `==` нельзя.** Оно останавливается на первом несовпавшем байте, и по времени ответа подбирается правильный хеш побайтово. В `argon2`/`bcrypt` защита встроена; если сравниваете руками — `hmac.compare_digest` ([hashlib](Библиотеки/Модули/Безопасность%20и%20интернет/hashlib.md)).

## Что вокруг хеширования

Хеш защищает базу после утечки, но не защищает вход. Рядом обязаны стоять:

- **ограничение частоты попыток** — по учётной записи и по IP, с задержкой или блокировкой; без него перебор идёт прямо через форму входа;
- **проверка по спискам утечек** — пароль сверяют с базой скомпрометированных (у Have I Been Pwned это делается по первым пяти символам хеша, сам пароль не покидает сервер);
- **длина вместо «сложности»** — [NIST SP 800-63B](https://pages.nist.gov/800-63-3/sp800-63b.html) рекомендует требовать минимум 8 символов и разрешать до 64+, **не** навязывать обязательные спецсимволы и **не** требовать периодической смены без признаков компрометации: эти правила гонят людей к «Password1!» и записыванию на бумажке;
- **одинаковый ответ на неверный логин и неверный пароль** — иначе форма превращается в способ узнать, кто зарегистрирован;
- **второй фактор** для чувствительных операций ([Аутентификация — методы и протоколы](Аутентификация%20—%20методы%20и%20протоколы.md#чего-в-разборах-обычно-не-хватает)).

## Ловушки

- **`sha256(пароль)` в базе.** Классика утечек: миллиард вариантов проверяется за секунды.
- **Одна соль на всех** (или соль из логина). Возвращает ровно те проблемы, ради которых соль вводили.
- **Своя «хитрая» схема** вроде двойного `md5` с перестановкой символов. Медленнее не становится, а разбор занимает у атакующего вечер.
- **Пароль длиннее 72 байт в bcrypt.** Хвост отбрасывается: «правильная лошадь батарейка скобка» и её усечённая версия войдут одинаково.
- **Пароль в логах.** Тело запроса с формой входа не должно попадать в логи и трейсы целиком.
- **Ограничение длины пароля сверху** (`max_length=12`) — прямой запрет на парольные фразы.
- **Перец в той же базе.** Тогда это просто ещё одна соль.
