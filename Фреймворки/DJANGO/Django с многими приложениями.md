# Django с многими приложениями

> _Бэкенд отдаёт данные, фронтенд их рисует — каждый занят своим_

---

Классический [Django](../../Фреймворки/DJANGO/Django.md) сам рисует HTML-страницы. Но современные сайты часто строят иначе: **отдельный фронтенд** (React, Vue) и **Django как чистый backend**, который отдаёт только данные через [REST API](../../Фреймворки/DJANGO/API.md). Иногда за одним сайтом стоит и несколько бэкендов. Эта заметка — про такую архитектуру и главную её сложность: **CORS**.

## Монолит против разделённого фронта и бэка

| | Монолит (обычный Django) | Разделённые фронт и бэк |
|---|---|---|
| **Кто рисует HTML** | сервер (шаблоны Django) | фронтенд (React/Vue) в браузере |
| **Что отдаёт сервер** | готовые страницы | JSON-данные ([API](../../Фреймворки/DJANGO/API.md)) |
| **Шаблоны Django** | нужны | не используются |
| **Клиентов** | обычно один (браузер) | много: сайт, мобильное, десктоп |

В разделённой схеме фронтенд — самостоятельное приложение: он шлёт запросы на бэкенд, получает данные и, если они есть, отрисовывает интерфейс. Бэкенд про фронтенд ничего не знает — общаются они через **контракт REST**.

> **REST — это как ГОСТ:** набор правил, как один сервис общается с другим. Обе стороны договариваются об адресах ресурсов, методах и формате (JSON) — и дальше разрабатываются независимо.

## Проблема CORS

> Здесь — настройка под Django. Что такое источник, откуда берётся преполётный `OPTIONS` и почему CORS не защищает API — Политика одного источника и CORS.

Фронтенд (`localhost:5173`) и бэкенд (`localhost:8000`) живут на **разных источниках** (origin = протокол + домен + порт). Браузер из соображений безопасности по умолчанию **блокирует** запросы между разными источниками — это политика **CORS** (Cross-Origin Resource Sharing). Без настройки фронтенд просто не сможет достучаться до API.

```
Фронтенд                     Бэкенд
localhost:5173  ──запрос──▶  localhost:8000
                ◀─BLOCKED─   (другой origin → браузер режет ответ)
```

Чтобы разрешить нужные источники, на бэкенд ставят **django-cors-headers**:

```bash
pip install django-cors-headers
```

Настройка в `settings.py`:

```python
INSTALLED_APPS = [
    ...,
    'rest_framework',
    'corsheaders',      # приложение CORS
    'api',              # твой backend-приложение
]

MIDDLEWARE = [
    'corsheaders.middleware.CorsMiddleware',   # ← в самом начале списка!
    ...,
]

# какие источники (фронтенды) пускать к API
CORS_ALLOWED_ORIGINS = [
    'http://localhost:5173',    # Vite / React dev-сервер
    'http://127.0.0.1:5500',    # Live Server
]
```

- **`CorsMiddleware`** ставится **в начало** `MIDDLEWARE` — оно должно обработать запрос раньше остальных, чтобы проставить нужные заголовки ответа.
- **`CORS_ALLOWED_ORIGINS`** — белый список фронтендов. Только перечисленные источники смогут обращаться к API.

## Сквозной пример: React-фронт + Django-бэк

```
проект/
├── backend/        Django + DRF: отдаёт JSON на /api/...
└── frontend/       React (Vite на :5173): рисует интерфейс
```

**Шаг 1. Бэкенд** — обычный DRF-проект с API ([API](../../Фреймворки/DJANGO/API.md), [CRUD В DRF](../../Фреймворки/DJANGO/CRUD%20В%20DRF.md)).

**Шаг 2. Открыть бэкенд для фронта** — поставить `django-cors-headers` и прописать `CORS_ALLOWED_ORIGINS` (см. выше).

**Шаг 3. Фронтенд** — шлёт запросы на бэкенд и рисует данные:

```javascript
fetch('http://localhost:8000/api/v1/products/')
    .then(res => res.json())
    .then(data => renderProducts(data));   // отрисовать в React
```

**Как это читать.** Бэкенд не знает про React и не рендерит HTML — только отдаёт JSON. Фронтенд отдельным приложением ходит на бэкенд по REST-контракту. `django-cors-headers` разрешает браузеру эти кросс-доменные запросы — без него ответы бэкенда блокировались бы.
