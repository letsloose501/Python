# Сигналы Django

> _Объявление по громкой связи: «модель сохранилась» — кто подписан, тот отреагирует_

---

**Сигнал** — механизм оповещения: одна часть проекта объявляет, что событие произошло, а другие части, подписавшиеся заранее, автоматически на него реагируют. Отправитель не знает, кто его слушает, и слушателей может быть сколько угодно — это [паттерн Наблюдатель](../../ООП/Паттерны/Паттерны%20поведения.md#наблюдатель), встроенный в [Django](../../Фреймворки/DJANGO/Django.md).

Классический пример: пользователь зарегистрировался — надо создать ему профиль, отправить приветственное письмо и записать событие в аналитику. Три несвязанных действия, и ни одно из них не должно жить внутри кода регистрации.

## Проблема: зачем это нужно

Без сигналов побочные действия приходится вписывать в то место, которое их запускает:

```python
# views.py — код регистрации разрастается чужой логикой
def register(request):
    user = User.objects.create_user(...)
    Profile.objects.create(user=user)        # ← профиль
    send_welcome_email(user)                 # ← письмо
    analytics.track("signup", user.id)       # ← аналитика
    return redirect("home")
```

Плохо здесь то, что регистрация теперь **знает** про профили, почту и аналитику. Добавили четвёртое действие — правим регистрацию. Создали пользователя из админки или из management-команды — ничего не сработает, потому что этот код лежит во view.

Сигнал переворачивает зависимость: событие «пользователь сохранён» испускает **сама модель**, а реагирует тот, кто подписался. Создание пользователя откуда угодно — из view, из админки, из shell — вызовет всех подписчиков.

```
User.save() ──▶ post_save ──┬──▶ создать профиль
                            ├──▶ отправить письмо
                            └──▶ записать в аналитику
```

## Встроенные сигналы

Django испускает сигналы сам, вручную ничего слать не надо. Самые ходовые — из `django.db.models.signals`:

| Сигнал | Когда срабатывает | Полезные аргументы |
|---|---|---|
| `pre_save` | перед записью объекта в БД | `instance`, `raw`, `using` |
| `post_save` | после записи | `instance`, **`created`** (True при вставке), `update_fields` |
| `pre_delete` | перед удалением | `instance` |
| `post_delete` | после удаления | `instance` |
| `m2m_changed` | изменилась связь ManyToMany | `action` (`pre_add`, `post_add`, `post_remove`…), `pk_set` |

Есть и не про модели:

- `django.core.signals.request_started` / `request_finished` — начало и конец обработки запроса;
- `django.core.signals.setting_changed` — настройка изменена (полезно в тестах);
- `django.contrib.auth.signals.user_logged_in` / `user_logged_out` / `user_login_failed`.

## Как подписаться

Два способа. Декоратор читается лучше:

```python
# accounts/signals.py
from django.conf import settings
from django.db.models.signals import post_save
from django.dispatch import receiver
from .models import Profile

@receiver(post_save, sender=settings.AUTH_USER_MODEL)
def создать_профиль(sender, instance, created, **kwargs):
    if created:                      # ← только при создании, не при каждом save()
        Profile.objects.create(user=instance)
```

Явный вызов делает то же самое:

```python
post_save.connect(создать_профиль, sender=settings.AUTH_USER_MODEL)
```

Полная сигнатура — `Signal.connect(receiver, sender=None, weak=True, dispatch_uid=None)`.

- **`sender`** — от кого слушаем. Без него обработчик сработает на сохранение **любой** модели проекта.
- **`dispatch_uid`** — уникальная строка-идентификатор. Защищает от двойной подписки: если модуль импортируется дважды, обработчик всё равно зарегистрируется один раз.
- **`**kwargs` в сигнатуре обязателен** — Django передаёт служебные аргументы, и без него будет `TypeError`.

## Где регистрировать — `apps.py`

Файл `signals.py` сам себя не импортирует, а значит `@receiver` не выполнится и подписки не будет. Импорт делают в методе `ready()` конфигурации приложения — он вызывается один раз при старте, когда модели уже загружены:

```python
# accounts/apps.py
from django.apps import AppConfig

class AccountsConfig(AppConfig):
    default_auto_field = "django.db.models.BigAutoField"
    name = "accounts"

    def ready(self):
        from . import signals        # ← импорт внутри метода, не сверху файла
```

> Импорт стоит **внутри** `ready()`, а не в шапке `apps.py`: на момент разбора файла приложения ещё не загружены, и импорт моделей сверху уронит проект с `AppRegistryNotReady`.

## Свой сигнал

Когда нужно событие, которого у Django нет:

```python
# orders/signals.py
import django.dispatch

заказ_оплачен = django.dispatch.Signal()      # объявили

# orders/services.py
def оплатить(order):
    order.status = "paid"
    order.save()
    заказ_оплачен.send(sender=Order, order=order)   # испустили
```

`send()` вызывает обработчики по очереди и **падает**, если хоть один бросил исключение. `send_robust()` ловит исключения обработчиков и возвращает их в списке результатов — остальные подписчики при этом отработают.

## Ловушки

**Рекурсия `post_save`.** Обработчик сохраняет тот же объект → снова `post_save` → бесконечный цикл:

```python
# НЕПРАВИЛЬНО — сам себя вызывает
@receiver(post_save, sender=Article)
def проставить_слаг(sender, instance, **kwargs):
    instance.slug = slugify(instance.title)
    instance.save()                      # ← снова post_save

# ПРАВИЛЬНО — пишем мимо сигналов, точечным UPDATE
@receiver(post_save, sender=Article)
def проставить_слаг(sender, instance, **kwargs):
    Article.objects.filter(pk=instance.pk).update(slug=slugify(instance.title))
```

`QuerySet.update()` не дёргает `save()`, а значит и сигнал не испускает. Ещё проще — переопределить `save()` модели или использовать `pre_save`, где объект ещё не записан и `instance.slug = ...` достаточно.

**Массовые операции сигналы не шлют.** `bulk_create()`, `bulk_update()`, `QuerySet.update()` и `QuerySet.delete()` работают одним SQL-запросом, минуя `save()`/`delete()` каждого объекта. Профили после `User.objects.bulk_create([...])` не создадутся — это не баг, а цена скорости.

**Отладка.** Вызов неявный: в коде регистрации не видно, что после `save()` уйдёт письмо. Трассировка ведёт в `django/dispatch/dispatcher.py`, а не в твой модуль.

## Когда НЕ использовать

Официальная документация прямо предупреждает: сигналы **создают видимость** слабой связанности, но легко приводят к коду, который тяжело понять, менять и отлаживать. Где можно — вызывай обработчик напрямую.

Практический критерий:

| Ситуация | Решение |
|---|---|
| Отправитель и получатель — в одном твоём проекте | **явный вызов функции** или сервисный слой |
| Реагируешь на чужую модель (`User` из `contrib.auth`, модель из сторонней библиотеки) | сигнал — единственный способ, не правя чужой код |
| Пишешь переиспользуемое приложение и не знаешь, кто им воспользуется | свой сигнал как точка расширения |
| Логика — часть бизнес-процесса («оплатили → отгрузили») | **сервисная функция**, не сигнал: процесс должен читаться сверху вниз |

> Правило на собеседовании: «сигналы — для реакции на чужой код и для точек расширения; свою бизнес-логику лучше вызывать явно». Ответ «сигналы — это круто, они всё развязывают» показывает, что человек не отлаживал проект, где их 30 штук.
