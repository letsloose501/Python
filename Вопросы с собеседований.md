# Вопросы с собеседований — стажёр, джун, мидл

Справочник для подготовки: что спрашивают на каждом грейде и как отвечать.

> 🗣 **Вторая половина собеседования — не техническая.** Самый частый вопрос к Python-разработчику вообще — «расскажи о себе», и рядом с ним «о своём опыте», «о лучших проектах», «планы на развитие», «зарплатные ожидания». Каркасы ответов на них — в [Вопросы про опыт и мотивацию](Вопросы%20про%20опыт%20и%20мотивацию.md).

> 🎯 **Внизу файла — отдельный блок [«Реальный собес»](Вопросы%20с%20собеседований.md#-реальный-собес--36-вопросов-подряд-28072026):** 36 вопросов в том порядке, в каком их задали на одном собеседовании. Читать его стоит не вместо разделов по грейдам, а после — он показывает, как вопросы **сцепляются в связки** и куда ведёт цепочка.

> **Главное наблюдение:** темы на всех грейдах почти одни и те же. Меняется **сторона вопроса**. Джуна спрашивают «что такое индекс», мидла — «вот `EXPLAIN`, почему индекс не использовался». Поэтому один и тот же список тем годится на все три грейда — важно, на какую глубину ты можешь по нему пройти.

---

## Как отвечать (работает на любом грейде)

1. **Сначала подход вслух, потом код.** На секциях Яндекса собеседующий прямо не пустит писать, пока не услышит эффективное решение.
2. **Уточняй условия.** «Массив отсортирован? Числа могут быть отрицательными? Что делать с пустым входом?» — это не признак незнания, а признак инженера.
3. **Называй сложность сам**, не дожидаясь вопроса: «это $O(n \log n)$ по времени и $O(n)$ по памяти».
4. **Не знаешь — скажи, но выскажи гипотезу.** Не глухое «не знаю», а «точно не помню, но предположу так, потому что…». Выдуманный уверенный ответ видно насквозь, а честная гипотеза — плюс.
5. **Не спорь.** Просят переписать рабочий код — переписывай: так проверяют реакцию на требования.

# 🟢 Стажёр

Проверяют язык, базовые структуры данных и умение вообще довести решение до конца.

## Python — основы

**Чем список отличается от кортежа?**
Список изменяемый, кортеж — нет. Из-за неизменяемости кортеж **хешируемый**: может быть ключом словаря и элементом множества. Кортеж чуть компактнее и быстрее при переборе. → [Составные типы данных Python](Данные/Составные%20типы%20данных%20Python.md)

**Что такое изменяемые и неизменяемые типы?**
Неизменяемые (`int`, `str`, `tuple`, `frozenset`) нельзя поменять на месте — любая «модификация» создаёт новый объект. Изменяемые (`list`, `dict`, `set`) меняются по месту, поэтому две переменные могут указывать на один объект и видеть чужие изменения.

**Чем `is` отличается от `==`?**
`==` сравнивает значения, `is` — тождество объектов (один и тот же адрес). Проверять на `None` надо через `is`. ⚠️ Ловушка: малые целые и короткие строки кэшируются интерпретатором, поэтому `a is b` иногда истинно случайно — полагаться на это нельзя. → [Ловушки Python](Ядро%20языка/Ловушки%20Python.md)

**Почему изменяемый объект нельзя ставить значением по умолчанию?**
```python
def add(item, target=[]):   # НЕПРАВИЛЬНО
    target.append(item); return target
add(1)  # [1]
add(2)  # [1, 2] ← тот же список!
```
Значение по умолчанию вычисляется **один раз при определении функции** и живёт в `__defaults__`. Правильно — `target=None` и создавать внутри. → [Функции Python](Ядро%20языка/Функции%20Python.md)

**Что такое list comprehension и чем он лучше цикла?**
Компактная форма создания списка: `[x*2 for x in nums if x > 0]`. Быстрее ручного цикла с `append`, потому что не вызывает метод на каждой итерации. → [Синтаксические конструкции Python](Ядро%20языка/Синтаксические%20конструкции%20Python.md)

**Что такое генератор?**
Функция с `yield`, которая отдаёт значения по одному и не хранит их все в памяти. `range(10**9)` работает мгновенно, а список из миллиарда элементов не поместится в память.

**Чем итератор отличается от генератора?**
Самый частый вопрос раздела. **Итератор** — любой объект с `__iter__` и `__next__`, который помнит позицию и по `next()` отдаёт следующий элемент или бросает `StopIteration`. **Генератор** — частный случай итератора, который Python создаёт за тебя из функции с `yield` или из выражения `(x*2 for x in nums)`. Отношение одностороннее: каждый генератор — итератор, но не каждый итератор — генератор (класс с `__next__` генератором не является). Практический вывод: то же поведение генератор даёт в разы меньшим кодом, потому что `yield` сам сохраняет состояние между вызовами. → [Синтаксические конструкции Python](Ядро%20языка/Синтаксические%20конструкции%20Python.md#итераторы), [Разворачивание вложенных списков (flatten) Python](Ядро%20языка/Разворачивание%20вложенных%20списков%20%28flatten%29%20Python.md)

**Чем итератор отличается от итерируемого объекта?**
`Iterable` — то, у чего есть `__iter__` (список, строка, словарь): по нему можно пройти много раз, каждый `for` берёт **новый** итератор. `Iterator` — то, у чего есть и `__iter__`, и `__next__`: одноразовый, после исчерпания отдаёт пустоту. Поэтому `list(gen)` второй раз вернёт `[]`.

**Что такое контекстный менеджер и как его написать?**
Объект, который гарантирует, что ресурс будет освобождён, даже если внутри блока произошло исключение — это `with`. Два способа реализации: класс с `__enter__` / `__exit__` или функция с декоратором `@contextlib.contextmanager`, где код до `yield` — вход, после — выход. `__exit__` получает информацию об исключении и, если вернёт `True`, подавит его. → [Синтаксические конструкции Python](Ядро%20языка/Синтаксические%20конструкции%20Python.md#контекстные-менеджеры), [contextlib](Библиотеки/Модули/Отладка%20и%20утилиты/contextlib.md)

**Что такое lambda и когда её уместно применять?**
Анонимная функция из одного выражения: `lambda x: x * 2`. Уместна там, где функция нужна на один раз и как аргумент — `sorted(users, key=lambda u: u.age)`. Присваивать её имени (`f = lambda x: ...`) не стоит: это то же `def`, но без имени в трейсбеке. → [Функции Python](Ядро%20языка/Функции%20Python.md)

**Что такое `*args` и `**kwargs`?**
`*args` собирает позиционные аргументы в кортеж, `**kwargs` — именованные в словарь. Нужны, когда число аргументов заранее неизвестно, и для проброса аргументов дальше без их перечисления: `super().__init__(*args, **kwargs)`. Звёздочки — это операторы упаковки/распаковки, а имена `args`/`kwargs` — просто соглашение. → [Функции Python](Ядро%20языка/Функции%20Python.md)

**Что означают одинарное и двойное подчёркивание в имени?**
`_имя` — соглашение «это внутреннее, снаружи не трогай»; язык ничего не запрещает. `__имя` — включает **name mangling**: интерпретатор переименовывает атрибут в `_КлассИмя__имя`, чтобы наследник случайно его не перекрыл. `__имя__` — dunder, зарезервировано за протоколами языка, свои так называть нельзя. Отдельно `_` — «значение не нужно» (`for _ in range(3)`). → [Инкапсуляция Python](ООП/Принципы/Инкапсуляция%20Python.md)

**Python компилируемый или интерпретируемый?**
И то и другое, и на этом ловят. CPython сначала **компилирует** исходник в байткод (`.pyc` в `__pycache__`), а затем **интерпретирует** байткод виртуальной машиной. То есть компиляция есть, но не в машинный код, и происходит она при запуске, а не заранее. → [Python](Python.md)

**Зачем нужен PEP 8?**
PEP 8 — руководство по оформлению кода Python: отступы в 4 пробела, `snake_case` для функций и переменных, `CapWords` для классов, длина строки, порядок импортов. Смысл не в красоте, а в том, что код читают чаще, чем пишут: единый стиль убирает споры на ревью и снижает цену переключения между файлами. Проверяется автоматически — `ruff`, `flake8`, `black`. → [Стиль кода Python — PEP 8 и Google Style Guide](Ядро%20языка/Стиль%20кода%20Python%20—%20PEP%208%20и%20Google%20Style%20Guide.md), [Линтеры и форматтеры](Ядро%20языка/Линтеры%20и%20форматтеры.md)

**Почему `0.1 + 0.2 != 0.3`?**
Числа с плавающей точкой хранятся в двоичной системе, и 0.1 в ней бесконечная дробь. Для денег берут `Decimal`. → [decimal](Библиотеки/Модули/Работа%20с%20числами/decimal.md)

**Что такое `None` и почему его проверяют через `is`?**
Единственный объект своего типа `NoneType` — **синглтон**: во всей программе он один, поэтому `x is None` сравнивает адреса и не вызывает чужой код. `==` переопределяется через `__eq__`, и класс вправе объявить себя равным чему угодно; `is` подменить нельзя. ⚠️ Отдельная ловушка — писать `if not x` вместо `if x is None`: ложны также `0`, `""` и `[]`, и «значения нет» смешивается с «значение пустое». → [Специальные типы данных Python](Данные/Специальные%20типы%20данных%20Python.md)

**Чем `yield` отличается от `return`?**
`return` завершает функцию и уничтожает её кадр; `yield` **приостанавливает** её — локальные переменные и точка остановки сохраняются до следующего `next()`. Одно наличие `yield` в теле меняет саму функцию: вызов больше не выполняет код, а возвращает объект-генератор, и тело стартует только на первом `next()`. ⚠️ `return` внутри генератора разрешён, но значение вызывающему не отдаётся — оно кладётся в `StopIteration.value`. → [Генераторы](Ядро%20языка/Синтаксические%20конструкции%20Python.md#генераторы)

**Как устроена f-строка и чем она лучше остальных способов?**
`f"{user.name}: {total:.2f}"` — интерполяция: выражения в фигурных скобках вычисляются и подставляются на место. Быстрее `%` и `.format()`, потому что компилируется в сборку строки на уровне байткода, без разбора шаблона в рантайме. Сверх базового стоит знать: после двоеточия идёт мини-язык форматирования (`:.2f`, `:>10`, `:,`) — тот же, что у `format()`; `f"{x=}"` печатает `x=5` и экономит время на отладке. ⚠️ В логировании f-строку не берут: `logger.debug(f"...")` собирает строку всегда, даже когда уровень отключён — там оставляют `logger.debug("%s", x)`. → [string](Библиотеки/Модули/Текст%20и%20строки/string.md)

## Встроенные функции и современный синтаксис

Раздел, на котором спотыкаются пришедшие в Python из другого языка: задачу решают циклом со счётчиком там, где есть готовая конструкция. Спрашивают не ради эрудиции — по этим ответам видно, пишешь ты на Python или на C внутри Python.

**Зачем `enumerate` и `zip`?**
`enumerate(seq)` отдаёт пары «индекс, элемент» и избавляет от ручного счётчика (`start=1`, если нумерация с единицы). `zip(a, b)` идёт по нескольким последовательностям параллельно, отдавая кортежи. Обе ленивые — возвращают итератор, а не список. ⚠️ Ловушка `zip`: он **молча обрезает по самой короткой** последовательности; чтобы это стало ошибкой, есть `strict=True` (с 3.10). Приём, который стоит назвать: `zip(*матрица)` транспонирует её. → [itertools](Библиотеки/Модули/Функциональные%20инструменты/itertools.md)

**Что делают `map` и `filter` и почему их берут реже comprehension?**
`map(f, seq)` применяет функцию к каждому элементу, `filter(f, seq)` оставляет те, где `f` истинна; оба возвращают **итераторы**. Comprehension обычно читаемее: не требует отдельной функции и совмещает преобразование с условием в одной строке. `map` выигрывает там, где функция **уже существует** и лямбда не нужна: `nums = list(map(int, input().split()))` — стандартное чтение ввода в контестных задачах, и оно же быстрее comprehension, потому что цикл идёт целиком в C. ⚠️ `map(lambda x: ..., seq)` этого преимущества не даёт и проигрывает comprehension по читаемости — это худший из вариантов. → [Функции Python](Ядро%20языка/Функции%20Python.md)

**Как отсортировать список объектов, в том числе по двум критериям?**
`sorted(users, key=lambda u: u.age)` — `key` вычисляется **один раз на элемент**, а не на каждое сравнение. Два критерия — кортеж: `key=lambda u: (-u.score, u.name)` даёт убывание очков, при равенстве — имя по алфавиту. Минус работает только для чисел; для разнонаправленной сортировки по строке пользуются **стабильностью**: сортируют дважды, начиная с менее значимого ключа. ⚠️ `list.sort()` сортирует на месте и возвращает `None` — `x = lst.sort()` кладёт в `x` пустоту; `sorted()` возвращает новый список из любого итерируемого. → Сортировка, [operator](Библиотеки/Модули/Функциональные%20инструменты/operator.md)

**Чем `__str__` отличается от `__repr__`?**
`__str__` — вид для пользователя (его зовут `print()` и f-строка), `__repr__` — однозначный вид для разработчика, в идеале похожий на вызов конструктора: `Point(x=1, y=2)`. Резерв работает **в одну сторону**: определён только `__repr__` — `str()` возьмёт его; наоборот не бывает. ⚠️ Классическая ловушка: `print(obj)` показывает `__str__`, а `print([obj])` — `__repr__`, потому что контейнер зовёт `repr()` у элементов. Отсюда правило: пишешь только один метод — пиши `__repr__`. → [Магические методы Python](Ядро%20языка/Магические%20методы%20Python.md)

**Что такое оператор `:=` и где он уместен?**
«Морж» (PEP 572, с 3.8) — присваивание **внутри выражения**: имя получает значение, и оно же становится результатом. Убирает повторное вычисление: `if (m := re.search(p, s)):` вместо поиска один раз до `if` и второй внутри. Так же читается `while (chunk := f.read(8192)):`. В comprehension позволяет посчитать значение один раз и им же отфильтровать: `[y for x in data if (y := f(x)) > 0]`. ⚠️ Отдельной инструкцией не работает: `x := 5` — синтаксическая ошибка, нужны скобки. Мера одна — читаемость: где хватает обычного присваивания, «морж» только запутывает. → [Операторы Python](Ядро%20языка/Операторы%20Python.md)

**Что такое `dataclass` и когда он не нужен?**
Декоратор, который по аннотированным полям сам генерирует `__init__`, `__repr__` и `__eq__` — класс-хранилище перестаёт быть двумя десятками строк рутины. `frozen=True` делает объект неизменяемым и хешируемым, `slots=True` (с 3.10) убирает `__dict__`. ⚠️ Изменяемый дефолт запрещён явно: `items: list = []` падает `ValueError` **при создании класса** — нужен `field(default_factory=list)`. Главное отличие, которого ждут: **типы `dataclass` не проверяет** — аннотации остаются метаданными, и в поле `age: int` спокойно ляжет строка. Нужна валидация — это [pydantic](Библиотеки/Сторонние/pydantic.md); нужна неизменяемость и поведение кортежа — `NamedTuple`. → [dataclass](Библиотеки/Модули/Типы%20и%20объекты/dataclass.md)

**Что появилось в Python 3.10 и дальше?**
Вопрос на то, следишь ли ты за языком. Опорные точки: **3.10** — `match` (структурное сопоставление с образцом), `X | Y` в аннотациях вместо `Optional` и `Union`, сообщения об ошибках с указанием места; **3.11** — заметное ускорение интерпретатора и группы исключений с `except*`; **3.12** — новый синтаксис дженериков `def f[T](...)`; **3.13–3.14** — сборка без GIL (free-threading), в 3.14 переставшая быть экспериментальной. ⚠️ Про `match` спрашивают с подвохом: это **не** замена цепочке `if` — ценность в разборе структуры, `case Point(x=0, y=y)` распаковывает объект и связывает имена. → [Match Case Python](Ядро%20языка/Match%20Case%20Python.md), [typing](Библиотеки/Модули/Типы%20и%20объекты/typing.md)

**Разверни строку.**
Идиоматично — срез с шагом: `s[::-1]`. `"".join(reversed(s))` даёт то же, но `reversed()` возвращает **итератор** и сам по себе строкой не является. `list.reverse()` разворачивает на месте и только список. ⚠️ Развернуть строку «на месте» нельзя в принципе: строки неизменяемы, любой способ создаёт новую и стоит $O(n)$ памяти. Если вопрос задан на секции, чаще хотят не срез, а **[два указателя](Алгоритмы/Приёмы/Два%20указателя.md)** по списку символов с $O(1)$ дополнительной памяти — уточни, что именно проверяют. → [string](Библиотеки/Модули/Текст%20и%20строки/string.md), [Список](Данные/АТД/Список.md)

## Структуры данных и сложность

**Почему поиск в списке — $O(n)$, а во множестве — $O(1)$?**
Список хранит элементы подряд и при `x in list` перебирает их. Множество и словарь построены на **хеш-таблице**: от значения считается хеш, он указывает на ячейку — проверка за константу. Яндекс формулирует это так: *«90% проблем с производительностью возникают из-за линейного поиска»*. → [Хеш-таблица](Данные/Структуры%20данных/Хеш-таблица.md)

**Когда $O(1)$ у словаря деградирует до $O(n)$?**
При массовых **коллизиях** — когда много ключей дают один хеш и попадают в одну ячейку. На практике редко, но принципиально возможно.

**Что такое амортизированная сложность?**
Средняя стоимость операции на длинной серии. `list.append` — $O(1)$ амортизированно: обычно это запись в свободную ячейку, но иногда список кончается и происходит перевыделение с копированием за $O(n)$. Разложенное на все вставки, это даёт константу. Не путать со средним случаем: средний — усреднение по случайным **данным**, амортизированный — по последовательности **операций**, и он гарантирован на любых данных. → Амортизация

**Вот код с `while` внутри `while`. Это $O(n^2)$?**
Вопрос-ловушка: вложенность сама по себе ничего не доказывает. Считать надо не циклы, а **число необратимых событий**. В [циклической сортировке](Алгоритмы/Приёмы/Циклическая%20сортировка.md) внутренний обмен каждый раз ставит элемент на его окончательное место, мест всего `n`, значит обменов не больше `n − 1` — и весь код линейный. Тот же аргумент у [монотонного стека](Алгоритмы/Приёмы/Монотонный%20стек.md): каждый элемент кладётся и снимается один раз.

**Как найти пропавшее число в массиве от 0 до n за $O(1)$ памяти?**
Три способа, и хорошо назвать все: (1) формула суммы — `n*(n+1)//2 - sum(nums)`; (2) XOR индексов и значений — всё парное гасится; (3) [циклическая сортировка](Алгоритмы/Приёмы/Циклическая%20сортировка.md) — расставить числа по своим индексам. Важное отличие: сумма может **переполниться** — при `n = 10⁵` идеальная сумма превышает $2^{31}$, и в C++/Java на `int` решение сломается. В Python целые неограниченные, поэтому проблема не видна — но назвать её стоит. → [Битовые приёмы](Алгоритмы/Приёмы/Битовые%20приёмы.md)

**Зачем нужен XOR в задачах, если есть словарь?**
XOR даёт $O(1)$ памяти вместо $O(n)$. Работает на трёх свойствах: `x ^ x = 0`, `x ^ 0 = x`, порядок не важен. Отсюда: сложив XOR-ом весь массив, всё, что встречается парами, взаимно уничтожается, и остаётся единственное непарное значение. → [Битовые приёмы](Алгоритмы/Приёмы/Битовые%20приёмы.md)

**Почему `list.pop(0)` — $O(n)$, а `deque.popleft()` — $O(1)$?**
Список — непрерывный массив: удаление с начала сдвигает все элементы. `deque` — двусвязная структура блоков, у неё оба конца дешёвые. → [collections](Библиотеки/Модули/Коллекции%20и%20структуры%20данных/collections.md)

**Чем стек отличается от очереди?**
Стек — LIFO (последним пришёл, первым вышел), очередь — FIFO. Стек — отмена действий и обход в глубину, очередь — обработка по порядку и обход в ширину. → Абстрактные типы данных (АТД)

**Что такое «O большое»?**
Способ описать, как растёт время (или память) при росте входных данных, отбросив константы и младшие слагаемые. Не «сколько секунд», а «во сколько раз хуже станет, если данных станет вдвое больше». $O(1)$ — не зависит от размера, $O(\log n)$ — двоичный поиск, $O(n)$ — один проход, $O(n \log n)$ — хорошая сортировка, $O(n^2)$ — вложенный цикл. Называй сложность **сам**, не дожидаясь вопроса. → Вычислительная сложность

**Назови сложность операций основных структур.**
Заготовка, которую стоит помнить наизусть:

| Операция | list | dict / set | deque |
|---|---|---|---|
| доступ по индексу / ключу | $O(1)$ | $O(1)$ | $O(n)$ в середине |
| поиск значения (`in`) | $O(n)$ | $O(1)$ | $O(n)$ |
| вставка в конец | $O(1)$ аморт. | $O(1)$ | $O(1)$ |
| вставка/удаление в начало | $O(n)$ | — | $O(1)$ |

**Чем массив отличается от списка Python?**
Классический массив — непрерывный блок памяти с элементами **одного** типа и фиксированного размера. `list` в Python — динамический массив **ссылок** на объекты: типы могут быть разными, размер растёт сам, но каждый элемент — лишняя косвенность и память под объект. Настоящий массив в Python — это `array.array` или `numpy.ndarray`; их и берут, когда важны память и скорость численных операций. → [Массив](Данные/Структуры%20данных/Массив.md), [array](Библиотеки/Модули/Коллекции%20и%20структуры%20данных/array.md), [numpy](Библиотеки/Сторонние/numpy.md)

**Максимальная сумма подряд идущих элементов — как за один проход?**
[Алгоритм Кадане](Алгоритмы/Приёмы/Алгоритм%20Кадане.md): на каждом шаге выбор из двух — продолжить накопленную сумму или начать заново с текущего элемента, `cur = max(cur + x, x)`; ответ — максимум всех `cur`. $O(n)$ времени, $O(1)$ памяти. Ловушка, на которой валятся: инициализировать нулём нельзя — на массиве из одних отрицательных получится 0, то есть ответ «пустой подмассив», которого условие не разрешает. Начинать надо с `nums[0]`.

**Задача про акции (купить дешевле, продать дороже) — это какой приём?**
Формально бегущий минимум: помним минимальную цену слева и максимум разности. Но по сути это тот же Кадане, применённый к массиву **разностей** соседних цен: прибыль сделки — сумма ежедневных изменений между покупкой и продажей, значит лучшая сделка = подмассив изменений с максимальной суммой. Хороший ответ — назвать обе формулировки и показать, что это одна задача. → [Алгоритм Кадане](Алгоритмы/Приёмы/Алгоритм%20Кадане.md#121-best-time-to-buy-and-sell-stock--та-же-задача)

**Как работает бинарный поиск и когда он неприменим?**
На **отсортированном** массиве смотрим середину, сравниваем с искомым и отбрасываем половину — $O(\log n)$. Неприменим на неотсортированных данных и на структурах без доступа по индексу за $O(1)$ (связный список). Если поиск разовый, сортировать ради него не имеет смысла: сортировка сама по себе $O(n \log n)$. → Алгоритмы поиска, [bisect](Библиотеки/Модули/Коллекции%20и%20структуры%20данных/bisect.md)

## Инструменты и окружение

**Чем фреймворк отличается от библиотеки?**
Направлением вызова. Библиотеку **ты вызываешь** из своего кода (`requests.get(...)`) — управление у тебя. Фреймворк **вызывает тебя**: ты заполняешь его слоты (view, модель, обработчик), а порядок работы задаёт он. Это называют «инверсией управления». Бытовая аналогия: библиотека — набор инструментов, фреймворк — цех, куда ты приходишь работать по его правилам. → [Django](Фреймворки/DJANGO/Django.md), [FLASK](Фреймворки/FLASK.md), [FastAPI](Фреймворки/FastAPI.md)

**Зачем нужно виртуальное окружение?**
Изолирует зависимости проекта от системного Python и от других проектов: проекту A нужен Django 4, проекту B — Django 5, и без изоляции они конфликтуют. Плюс делает окружение воспроизводимым — `requirements.txt` или `poetry.lock` позволяют собрать те же версии на другой машине. → [venv](Библиотеки/Модули/Система%20и%20окружение/venv.md)

**Какие команды Git используешь каждый день?**
`git status`, `git add`, `git commit -m`, `git pull`, `git push`, `git checkout -b` для новой ветки, `git log --oneline`, `git diff`. Про ветки важно понимать не команды, а модель: **ветка — это подвижный указатель на коммит**, а не копия папки, поэтому создание ветки почти ничего не стоит. → GIT

## Простое ООП

**Что такое класс и объект?**
Класс — описание, объект — конкретный экземпляр по этому описанию. Класс задаёт, какие атрибуты и методы будут; объект хранит свои значения.

**Назови четыре принципа ООП.**
Инкапсуляция (спрятать внутреннее, дать интерфейс), наследование (переиспользовать поведение), полиморфизм (один вызов — разное поведение), абстракция (выделить существенное). → [Принципы ООП в Python](ООП/Принципы/Принципы%20ООП%20в%20Python.md)

**Почему у одной и той же машины в гоночной игре и в навигаторе будут разные классы?**
Потому что в класс попадает не «всё про объект», а то, что нужно задаче: в гонках — максимальная скорость, разгон, дрифт, тюнинг; в навигаторе — позиция и скорость. Универсального «правильного» класса `Машина` не существует. Критерий простой: поле остаётся, если его читает хотя бы один сценарий программы. → [Моделирование — что попадает в класс](ООП/Принципы/Моделирование%20—%20что%20попадает%20в%20класс.md)

**Получает ли класс-наследник копию полей и методов родителя?**
Нет. В `__dict__` наследника лежит только объявленное в нём самом, а недостающее ищется по цепочке [MRO](ООП/Принципы/Наследование%20Python.md#mro--порядок-разрешения-методов) в момент обращения. Отсюда практическое следствие: правка базового класса видна и наследникам, и уже созданным объектам. → [Наследование Python](ООП/Принципы/Наследование%20Python.md#наследование--не-копирование)

**Чем `__init__` отличается от `__new__`?**
Спрашивают часто и именно как сравнение. `__new__` — **создаёт** объект: это статический метод, получает класс `cls` и возвращает новый экземпляр. `__init__` — **настраивает** уже созданный: получает `self`, присваивает атрибуты и возвращает `None`. Порядок такой: `Точка(1, 2)` → `__new__` → если он вернул экземпляр этого класса, вызывается `__init__`. В обычном коде трогают только `__init__`; `__new__` нужен для неизменяемых типов (наследник `str`, `tuple` — менять значение после создания уже поздно), для синглтона и в метаклассах. → [Магические методы Python](Ядро%20языка/Магические%20методы%20Python.md#жизненный-цикл-объекта)

## ООП и устройство языка

**`@classmethod` против `@staticmethod` против обычного метода?**
Обычный получает `self` (экземпляр), `classmethod` — `cls` (класс), `staticmethod` — ничего. `classmethod` нужен для **альтернативных конструкторов**: `return cls(...)`, а не `return МойКласс(...)` — иначе сломается наследование. → [Принципы ООП в Python](ООП/Принципы/Принципы%20ООП%20в%20Python.md)

**Определил `__eq__`, объект перестал быть хешируемым. Почему?**
Python сбрасывает `__hash__` в `None` при определении `__eq__`: равные объекты обязаны иметь равный хеш, и автоматически это не гарантировать. Нужен — определи `__hash__` явно. → [Магические методы Python](Ядро%20языка/Магические%20методы%20Python.md)

**Что такое декоратор?**
Функция, которая принимает функцию и возвращает новую, обёрнутую. Используется для логирования, кэширования (`lru_cache`), проверки прав — всего, что нужно навесить, не трогая тело функции. `@wraps` сохраняет имя и docstring оригинала. → [Декораторы Python](Ядро%20языка/Декораторы%20Python.md)

**Как применить декоратор без `@`?**
`@` — только синтаксический сахар: `my_func = deco(my_func)`. Для параметрического — `my_func = deco(param)(my_func)`. Вопрос-разминка: из ответа сразу видно, понимает ли человек, что декоратор просто возвращает замену функции. → [Декораторы Python](Ядро%20языка/Декораторы%20Python.md)

**Напиши декоратор, ограничивающий число вызовов функции.**
Три уровня: фабрика с лимитом → декоратор → обёртка. Счётчик живёт в замыкании, и обёртке нужен `nonlocal`, иначе `UnboundLocalError` — присваивание делает имя локальным. Подвох, который стоит назвать самому: на методе класса такой счётчик **общий для всех экземпляров**, потому что декоратор применяется один раз при разборе класса. → [Декоратор с состоянием](Ядро%20языка/Декоратор%20с%20состоянием.md)

**Почему внешнюю переменную можно прочитать без `nonlocal`, а изменить — нельзя?**
Чтение не создаёт локального имени, а присваивание создаёт — и делает имя локальным для всей функции целиком, ещё на этапе компиляции. Поэтому `if x == 0` работает, а `x += 1` падает с `UnboundLocalError`. Проверяется по `co_varnames` / `co_freevars`. → [Декоратор с состоянием](Ядро%20языка/Декоратор%20с%20состоянием.md#зачем-nonlocal)

**В каком порядке применяются и выполняются несколько декораторов?**
Применяются снизу вверх (`@A @B @C` → `A(B(C(f)))`), а выполняются сверху вниз: вход `A → B → C`, тело, выход `C → B → A`. Практический вывод: `@login_required` ставят **выше** `@cache`, иначе проверка прав окажется за кэшем. → [Декораторы Python](Ядро%20языка/Декораторы%20Python.md#несколько-декораторов-на-одной-функции)

**Что будет, если надеть обычный декоратор на `async def`-функцию?**
Ошибки не будет — и это худшее. Вызов корутинной функции возвращает объект-корутину мгновенно, поэтому обёртка оборачивает не работу, а её создание: таймер намеряет микросекунды, retry ничего не поймает. Чинится тем, что обёртка объявляется `async def`, а оригинал вызывается через `await`. Сам декоратор при этом остаётся синхронным. → [Декораторы для асинхронных функций](Ядро%20языка/Декораторы%20для%20асинхронных%20функций.md)

**Как написать декоратор, работающий и с обычными, и с асинхронными функциями?**
Держать внутри две обёртки и выбирать по `inspect.iscoroutinefunction(func)` в момент декорирования, а не на каждом вызове. Именно `inspect`, а не `asyncio`: `asyncio.iscoroutinefunction` объявлен устаревшим в 3.14 и удаляется в 3.16. → [Декораторы для асинхронных функций](Ядро%20языка/Декораторы%20для%20асинхронных%20функций.md#универсальный-декоратор--на-оба-вида-функций)

**Можно ли навесить `@lru_cache` на асинхронную функцию?**
Нет. Закэшируется объект-корутина, а его можно дождаться один раз — второй `await` даёт `RuntimeError: cannot reuse already awaited coroutine`. Кэшировать надо `Task` (`asyncio.ensure_future`), его можно ждать многократно. → [functools](Библиотеки/Модули/Функциональные%20инструменты/functools.md)

**Что такое замыкание?**
Функция, которая помнит переменные из окружения, где была создана, даже после выхода из него.

**Чем `copy` отличается от `deepcopy`?**
`copy` копирует верхний уровень, вложенные объекты остаются общими — изменение вложенного списка видно в обеих копиях. `deepcopy` копирует рекурсивно. → [copy](Библиотеки/Модули/Типы%20и%20объекты/copy.md)

**Как Python управляет памятью?**
Основной механизм — **подсчёт ссылок**: объект удаляется, когда счётчик обнулился. Циклические ссылки счётчиком не ловятся, для них есть отдельный **поколенческий сборщик мусора**. → [Управление памятью в Python](Ядро%20языка/Управление%20памятью%20в%20Python.md)

**Что делает `@property`?**
Превращает метод в атрибут: снаружи пишут `user.age`, а внутри выполняется код — можно посчитать значение, провалидировать или залогировать. Нужен для того, чтобы **не ломать интерфейс**: поле было публичным, появилась логика — оборачиваешь в `property`, и весь вызывающий код продолжает работать. Пара `@x.setter` задаёт присваивание. → [Инкапсуляция Python](ООП/Принципы/Инкапсуляция%20Python.md)

**Зачем нужен `super()`?**
Вызвать реализацию из следующего класса **по MRO**, а не «из родителя». Разница видна при множественном наследовании: жёсткий вызов `Родитель.__init__(self)` пропустит часть цепочки, а `super().__init__()` пройдёт по всем классам ровно один раз. → [Наследование Python](ООП/Принципы/Наследование%20Python.md)

**Что такое MRO?**
**Method Resolution Order** — порядок, в котором Python ищет метод по цепочке наследования. Строится алгоритмом **C3-линеаризации**: класс идёт раньше своих родителей, порядок родителей сохраняется. Смотрят через `Класс.__mro__` или `Класс.mro()`. Если непротиворечивый порядок построить нельзя, класс не создастся — `TypeError` прямо на этапе объявления. → [Наследование Python](ООП/Принципы/Наследование%20Python.md#mro--порядок-разрешения-методов)

**Что такое миксин?**
Класс, который добавляет **одну функциональность** и не предназначен для самостоятельного создания объектов: своего состояния почти не имеет, конструктор обычно не определяет. Так добавляют «умение» нескольким несвязанным классам (`LoggingMixin`, `JSONSerializableMixin`) без общего предка. По соглашению ставят слева в списке баз, чтобы он был раньше основного класса в MRO. → [Наследование Python](ООП/Принципы/Наследование%20Python.md)

**Что такое `__slots__` и зачем?**
Объявление фиксированного набора атрибутов класса. Python перестаёт заводить каждому экземпляру словарь `__dict__` и хранит поля в компактной структуре: экономия памяти в разы и чуть более быстрый доступ. Цена — нельзя добавить атрибут на лету и нельзя иметь `__dict__`/`__weakref__` без явного указания. Берут, когда объектов миллионы (точки, записи лога), а не «для скорости» в общем случае. → [Магические методы Python](Ядро%20языка/Магические%20методы%20Python.md)

**Что не так с `items = []` в теле класса?**
Список создаётся **один раз** при выполнении тела класса и становится общим для всех экземпляров и всех наследников: `append` у одного объекта видят все остальные. Та же природа, что у изменяемого аргумента по умолчанию. Изменяемое состояние заводят в `__init__`; в теле класса оставляют только неизменяемое (`hp = 100`) — его переприсваивают, а не мутируют. → [Наследование Python](ООП/Принципы/Наследование%20Python.md#наследование--не-копирование)

**Зачем `@abstractmethod`, если метод можно просто оставить пустым?**
Пустое тело откладывает обнаружение ошибки в бесконечность: забыл переопределить или опечатался в имени — вызовется родительская заглушка, вернёт `None`, программа поедет дальше с неверным состоянием. `raise NotImplementedError` падает при первом вызове, `@abstractmethod` — уже при создании объекта. Пустое тело оправдано только для hook-метода, где «ничего не делать» — валидное поведение (`setUp` в `unittest`). → [Абстракция Python](ООП/Принципы/Абстракция%20Python.md#три-вида-заглушки-в-базовом-классе--и-цена-выбора)

**Если в Python есть duck typing, зачем ABC и `Protocol`?**
Полиморфизму общий предок в Python не нужен — в список кладутся любые объекты, метод разрешается в рантайме. ABC и `Protocol` дают другое: ошибку раньше (при создании объекта вместо падения в проде), проверку mypy до запуска, общий код в одном месте и явный список того, что обязан уметь новый класс. Выбор: `Protocol` — если классы уже есть и менять их нельзя; ABC — если семейство пишешь сам. → [Полиморфизм Python](ООП/Принципы/Полиморфизм%20Python.md#зачем-базовый-класс-если-работает-утиная-типизация)

**Что такое метакласс?**
Класс, экземплярами которого являются **классы**. Обычный класс создаёт объекты, метакласс — создаёт классы: `type` и есть метакласс по умолчанию. Нужен, когда надо вмешаться в создание всей иерархии — валидировать наличие методов, автоматически регистрировать подклассы. В реальном коде почти всегда хватает декоратора класса или `__init_subclass__`; метакласс — ответ на вопрос «а знаешь ли ты, как устроен язык», а не повседневный инструмент. → [Метаклассы Python](Ядро%20языка/Метаклассы%20Python.md)

**Что такое SOLID? Расшифруй.**
Пять принципов проектирования классов:

- **S**RP — единственная ответственность: у класса одна причина для изменения.
- **O**CP — открыт для расширения, закрыт для изменения: новое поведение добавляем новым кодом, а не правкой рабочего.
- **L**SP — подстановка Лисков: наследник должен работать везде, где ожидается родитель, не ломая контракт.
- **I**SP — разделение интерфейсов: лучше несколько узких, чем один «на всё».
- **D**IP — инверсия зависимостей: модули зависят от абстракций, а не от конкретных реализаций.

Сильный ответ добавляет пример нарушения: класс, который и считает заказ, и шлёт письмо, и пишет в БД, нарушает SRP — его меняют по трём разным причинам. → [SOLID Python](ООП/Принципы/SOLID%20Python.md)

**Что такое DRY и KISS?**
**DRY** (don't repeat yourself) — один факт живёт в одном месте; дублирование опасно тем, что копии расходятся при правке. **KISS** (keep it simple) — простое решение предпочтительнее умного. ⚠️ Ловушка: DRY доводят до абсурда, склеивая случайно похожий код — потом одну «общую» функцию рвут на части, потому что случаи разошлись. Дублирование дешевле неправильной абстракции. → [Принципы разработки — DRY, KISS, DI](ООП/Принципы/Принципы%20разработки%20—%20DRY,%20KISS,%20DI.md)

**Какие паттерны знаешь и где применял?**
Отвечать надо не списком из 23 названий, а тремя-четырьмя, которые реально понимаешь. Безопасный набор: **Одиночка** (один экземпляр на программу — конфиг, пул соединений), **Фабрика** (создание объекта решается в одном месте), **Стратегия** (взаимозаменяемые алгоритмы за общим интерфейсом), **Декоратор** (обёртка, добавляющая поведение). ⚠️ Важная оговорка: в Python половина паттернов из книги GoF решается языковыми средствами — Одиночка это просто модуль, Стратегия — функция как аргумент. Это и хотят услышать. → [Паттерны проектирования](ООП/Паттерны/Паттерны%20проектирования.md), [Порождающие паттерны](ООП/Паттерны/Порождающие%20паттерны.md)

**Что такое Singleton и как его сделать в Python?**
Паттерн «один экземпляр на всю программу». Способы: переопределить `__new__`, использовать метакласс, применить декоратор класса — или, самое питоничное, **просто модуль**: он импортируется один раз, и его переменные и есть общее состояние. ⚠️ Критика по делу: синглтон — глобальное состояние, оно мешает тестам (не подменишь) и прячет зависимости. Часто лучше передать объект явно. → [Порождающие паттерны](ООП/Паттерны/Порождающие%20паттерны.md#одиночка)

**Что такое внедрение зависимостей (DI)?**
Объект не создаёт то, что ему нужно, а **получает** это снаружи — через конструктор или аргумент. Было `self.db = PostgresRepo()`, стало `def __init__(self, repo)`. Выгода — тестируемость: в тест передаём заглушку, не трогая продовый код. Это практическое воплощение буквы D в SOLID. В [FastAPI](Фреймворки/FastAPI.md) встроено как `Depends`. → [Принципы разработки — DRY, KISS, DI](ООП/Принципы/Принципы%20разработки%20—%20DRY,%20KISS,%20DI.md)

**Зачем нужны аннотации типов, если Python их не проверяет?**
В рантайме они действительно ничего не проверяют — это метаданные в `__annotations__`. Пользу дают три вещи: статический анализатор (`mypy`) ловит ошибки до запуска, IDE даёт автодополнение и рефакторинг, а сигнатура становится документацией. Плюс на них построены целые библиотеки: [pydantic](Библиотеки/Сторонние/pydantic.md) валидирует по аннотациям, [FastAPI](Фреймворки/FastAPI.md) по ним же генерирует документацию. → [typing](Библиотеки/Модули/Типы%20и%20объекты/typing.md)

**Всегда ли нужно следовать SOLID?**
Нет, и уверенное «всегда» — плохой ответ. SOLID решает **стоимость изменения кода, который поддерживают несколько человек годами**. Нет этой задачи — остаётся только цена: лишние слои, прыжки по файлам, контракты, которые надо поддерживать. На скрипте в 500 строк с одним автором пользы не будет. Сильный ответ добавляет три вещи: применять **по буквам, а не пакетом** (дешевле всего SRP и ISP); **не переписывать рабочий проект «под SOLID»**; критерий — стало ли понятнее, а не «покрыты ли все пять». → [SOLID Python](ООП/Принципы/SOLID%20Python.md#сколько-solid-нужно-проекту)

**Как нарушить принцип подстановки Лисков, если типы совпадают?**
Совпадения сигнатур мало — LSP про **договор**. Три способа сломать его при верных типах: потомок кидает исключение, которого не было у родителя (`ValueError` на длинном сообщении); потомок усиливает предусловие (родитель принимал любую строку, потомок — только непустую); потомок возвращает нужный тип, но не то по смыслу (строку `"успешно сформировано"` вместо самого сообщения). Формально правил шесть — Лисков и Винг, 1994. → [SOLID Python](ООП/Принципы/SOLID%20Python.md#шесть-правил-лисков--винг)

**Что из SOLID проверит mypy, а что нет?**
Проверит ровно сигнатуры: сужение возвращаемого типа и расширение требований к аргументу в переопределении (на этом mypy прямо печатает «This violates the Liskov substitution principle»), а также несоответствие объекта `Protocol`. Не увидит: класс на четыре ответственности (SRP), `if/elif` вместо расширения (OCP), `raise NotImplementedError` вместо реализации, создание зависимостей внутри класса (DIP), подмену смысла результата. Типизатор проверяет **форму** договора, а не его смысл. → [SOLID Python](ООП/Принципы/SOLID%20Python.md#что-из-solid-python-проверяет-сам)

**Где в приложении создавать конкретные реализации, если внутрь классов нельзя?**
В [композиционном корне](ООП/Принципы/Композиционный%20корень.md) — одном месте рядом с точкой входа: `main()`, `lifespan` в [FastAPI](Фреймворки/FastAPI.md), `conftest.py` в тестах. Там же живёт всё неизбежное ветвление (`S3Storage() if prod else LocalStorage()`), поэтому сервисы о вариантах не знают вовсе. ⚠️ Ловушка вопроса: назвать в ответ Service Locator (`container.get(Repo)` посреди кода) — это антипаттерн, зависимость прячется, и по сигнатуре класса больше не видно, что ему нужно.

**Твой класс тяжело покрыть тестом — о чём это говорит?**
Почти всегда — о нарушении DIP: класс сам создаёт зависимости, поэтому подменить их можно только через `unittest.mock.patch` по строковому пути импорта. Такой тест ломается при переезде модуля, причём молча — начинает ходить в настоящий сервис. Признак, что стало плохо по-настоящему: прогон тестов реально отправляет SMS или письма. Тестируемость — не отдельное свойство кода, а индикатор дизайна. → [Юнит-тестирование Python](Библиотеки/Сторонние/Тесты/Юнит-тестирование%20Python.md#patch--не-выбор-а-следствие-плохого-дизайна)

## Базы данных

**Что такое индекс и почему не индексировать всё?**
Отдельная структура (обычно B-tree), ускоряющая поиск по колонке. Каждый индекс **замедляет запись** (его надо обновлять) и занимает место. → PostgreSQL

**Какие бывают JOIN?**
`INNER` — только совпадения; `LEFT` — все из левой плюс совпадения; `RIGHT` — зеркально; `FULL` — все с обеих сторон. ⚠️ Ловушка: условие на правую таблицу в `WHERE` после `LEFT JOIN` превращает его в `INNER` — такое условие место в `ON`. → SQL

**Что такое ACID?**
Atomicity (всё или ничего), Consistency (инварианты сохраняются), Isolation (транзакции не мешают друг другу), Durability (зафиксированное переживёт сбой). ⚠️ Не начинай с расшифровки — начни с задачи: «транзакция нужна, когда одну операцию нельзя выразить одним запросом, например перевод денег». И отдели, что даёт база, а что ты: атомарность и долговечность база обеспечивает сама, ограничения описываешь ты, уровень изоляции выбираешь тоже ты. → Транзакции и ACID

**Что произойдёт, если внутри транзакции нарушить ограничение?**
Запрос упадёт с ошибкой, а транзакция перейдёт в состояние «отменена»: все следующие запросы в ней будут падать с `current transaction is aborted`, пока не сделаешь `ROLLBACK` (или откат к `SAVEPOINT`). Частая ошибка — поймать исключение и продолжить работать в той же транзакции. → A — атомарность

**Почему ограничение лучше держать в базе, а не проверять в коде?**
В таблицу пишет не только твой код: миграции, крон, соседний сервис, руки из консоли. Проверка в приложении покрывает один путь, ограничение — все. Плюс проверка `SELECT` перед `INSERT` не спасает от гонок: между ними есть окно, а `UNIQUE` проверяется атомарно с записью. Дружелюбный текст ошибки при этом остаётся задачей приложения. → Ограничения целостности

**Как обеспечивается долговечность — что происходит при `COMMIT`?**
Через **WAL**: сначала на диск уходит запись журнала о том, что изменилось, и только потом (позже, пачкой) — сами страницы данных. `COMMIT` возвращает управление после того, как журнал сброшен на диск вызовом `fsync`. После аварии база доигрывает журнал с последней контрольной точки. ⚠️ Сильный ответ добавляет: «зафиксировано» — это шкала, а не да/нет; `synchronous_commit = off` разменивает последние ~0,6 с транзакций на скорость, но не портит данные, в отличие от `fsync = off`. → Журнал WAL и долговечность

**Когда нужен Serializable, если Repeatable Read уже есть?**
⚠️ Вопрос-ловушка. Ответ «когда две транзакции меняют одну строку» — неверный: это уже ловит Repeatable Read (обе дают `could not serialize access due to concurrent update`). Serializable нужен, когда инвариант связывает **разные** строки и конфликта записи нет вообще — это write skew. Его собственная ошибка звучит иначе: `due to read/write dependencies among transactions`. → Чем Serializable на самом деле отличается от Repeatable Read

**Что такое N+1 и как чинить?**
Достали список из N записей, потом на каждую сделали отдельный запрос за связанной сущностью — итого N+1 обращений. Чинится жадной загрузкой: `JOIN`, `selectinload` в SQLAlchemy, `select_related` в Django. → [ORM Django](Фреймворки/DJANGO/ORM%20Django.md)

**Зачем нужна нормализация и когда её нарушают?**
Убирает дублирование и аномалии обновления. Сознательно нарушают (**денормализация**) ради скорости чтения, когда `JOIN` дорог.

**Чем SQL-база отличается от NoSQL и когда что брать?**
Реляционная БД хранит данные в таблицах по жёсткой схеме, даёт `JOIN` и транзакции с ACID. NoSQL — зонтичный термин для нескольких семейств: документные (MongoDB), ключ-значение ([Redis](Библиотеки/Сторонние/Redis.md)), колоночные (ClickHouse), графовые. Общее у них — свободная схема и горизонтальное масштабирование, ценой связей и гарантий. ⚠️ Правильный ответ — не «NoSQL быстрее», а «зависит от формы данных»: связанные сущности с инвариантами → SQL; разнородные документы, огромный поток записи, кеш → NoSQL. Дефолт для бэкенда — PostgreSQL, отступать от него нужно с аргументом. → Базы данных, PostgreSQL

**Чем `WHERE` отличается от `HAVING`?**
`WHERE` фильтрует **строки до** группировки, `HAVING` — **группы после** `GROUP BY` и агрегатов. Поэтому `WHERE COUNT(*) > 5` — ошибка: на момент `WHERE` агрегата ещё не существует. Порядок выполнения: `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`. Знание этого порядка отвечает сразу на несколько вопросов, включая «почему нельзя использовать алиас из `SELECT` в `WHERE`». → SQL

**Чем репликация отличается от шардирования?**
**Репликация** — те же данные на нескольких серверах: спасает от потери данных и разгружает **чтение** (реплики отвечают на `SELECT`). **Шардирование** — разные части данных на разных серверах по ключу: разгружает **запись** и объём. Репликация масштабирует чтение, шардирование — запись; часто применяют вместе. ⚠️ Шардирование ломает `JOIN` между шардами и глобальную уникальность — это дорогая мера, а не первый шаг оптимизации. → Базы данных, Распределённые вычисления

**Что такое SQL-инъекция и как от неё защититься?**
Атака, когда пользовательский ввод попадает в текст запроса и меняет его смысл: в поле логина пишут `' OR 1=1 --`. Защита одна — **параметризованные запросы**, где драйвер передаёт значения отдельно от SQL: `cursor.execute("SELECT * FROM users WHERE name = %s", (name,))`. Экранирование руками и «фильтрация плохих слов» — не защита. ORM параметризует запросы сам, но `raw()` и `extra()` возвращают дыру обратно. → [Веб-безопасность](Веб-безопасность.md), SQL

**Что такое self-join и когда он нужен?**
Соединение таблицы с самой собой под двумя псевдонимами — когда связь идёт внутри одной таблицы: `сотрудники.руководитель_id` указывает на `сотрудники.id`. ⚠️ Ловушка выбора типа: `INNER JOIN` молча потеряет самого верхнего начальника, у которого `руководитель_id IS NULL`, — нужен `LEFT JOIN`. Важное ограничение, которое стоит назвать самому: self-join разворачивает иерархию **на один уровень**; «все подчинённые на любой глубине» — это уже рекурсивный CTE. → Self-join — таблица соединяется сама с собой

**Чем представление отличается от материализованного?**
Обычное `VIEW` данных не хранит: при обращении подставляется его текст и запрос выполняется заново — то есть оно **ничего не ускоряет**, а даёт инкапсуляцию логики и раздачу прав на срез данных. `MATERIALIZED VIEW` хранит результат физически: чтение мгновенное, можно строить индексы, но данные устаревают до `REFRESH`. ⚠️ Частая беда — представления поверх представлений: планировщик получает многоэтажную конструкцию, и план вырождается незаметно. → Представления (VIEW)

**Как найти и удалить дубликаты строк?**
`ROW_NUMBER() OVER (PARTITION BY ключ_дубля ORDER BY создан)` нумерует строки внутри группы одинаковых, дальше удаляется всё с номером больше 1. Именно `ROW_NUMBER`, а не `RANK`: последний выдал бы всем дублям единицу, и удалять было бы нечего. `ORDER BY` внутри окна решает, какая копия считается оригиналом. Сильный ответ добавляет: сначала тот же запрос гоняют `SELECT`-ом, а от повторения проблемы спасает не скрипт, а `UNIQUE`-ограничение. → Оконные функции, Ограничения целостности

## Сеть и HTTP

**Чем TCP отличается от UDP?**
TCP устанавливает соединение, гарантирует доставку и порядок, умеет управлять потоком. UDP просто шлёт датаграммы — быстрее, но без гарантий. Видео и игры — UDP, всё остальное обычно TCP. → Компьютерные сети

**Что происходит при вводе URL в браузер?**
DNS-резолв имени в IP → TCP-соединение → TLS-рукопожатие для HTTPS → HTTP-запрос → ответ сервера → рендеринг. Хороший ответ раскладывает это по уровням OSI. Сильный — разворачивает первый шаг: кэш браузера → кэш ОС и файл `hosts` → рекурсивный резолвер → корень → TLD → авторитетный сервер. → Что происходит, когда нажимаешь Enter

**Как устроен DNS и почему он масштабируется?**
Иерархия зон с делегированием: корень знает только, кто отвечает за `com`; `com` — кто отвечает за `google.com`. Никто не хранит данные нижних уровней, поэтому нагрузка расходится. Сверху — кэш на каждом уровне (браузер, ОС, резолвер провайдера), из-за которого до корня доходят единицы запросов. ⚠️ Частая путаница: **резолвер и авторитетный сервер — разные роли**. `8.8.8.8` — резолвер, он ищет ответ и кэширует; `ns1.google.com` — авторитетный, он ответом владеет. → DNS

**Чем рекурсивный запрос отличается от итеративного?**
При рекурсивном клиент просит готовый ответ (флаг `RD`) и ждёт — всю цепочку обходит резолвер. При итеративном сервер отвечает не адресом, а отсылкой «спроси вон у тех». Корневые и TLD-серверы работают **только** итеративно: рекурсию они не дают, иначе легли бы под нагрузкой. → Рекурсивно и итеративно

**Почему DNS работает поверх UDP?**
Обмен укладывается в один пакет туда и один обратно — рукопожатие TCP стоило бы дороже самой работы. Соединение хранить не на что (у резолвера миллионы клиентов), потеря дешева (переспросим), запрос идемпотентен. Порт 53. По TCP уходит, когда ответ не влез в лимит и взведён бит `TC`, при передаче зоны (`AXFR`) и в DoT. ⚠️ Сильный ответ добавит: тех самых **512 байт** из RFC 1035 хватало ровно на 13 корневых серверов — отсюда это число, а не из традиции. → Протокол DNS — сообщения и транспорт

**Сколько в мире корневых DNS-серверов?**
Вопрос с подвохом. **13 — это количество имён** (`a`–`m`), а не машин: физических инстансов около двух тысяч, и держат их 12 независимых организаций, а не одна ICANN. Размножены они через **anycast** — один IP анонсируется из множества точек мира, маршрутизация сама ведёт к ближайшей. Отсюда и отказоустойчивость, и размазывание DDoS. → Приём 3: anycast — один адрес, много машин

**Можно ли балансировать нагрузку через DNS и в чём подвох?**
Можно: несколько `A`-записей на одно имя (round-robin), плюс GeoDNS для выбора региона. Подвох в том, что это балансировка **крупным мазком**: нет проверки здоровья (упавший сервер отдаётся весь TTL), кэш резолвера крупного провайдера перекашивает распределение, привязки сессии нет. Внутри дата-центра балансируют на L4/L7, где видно состояние бэкендов. → DNS в роли балансировщика нагрузки

**Как переехать на новый IP без простоя?**
Понизить TTL записи **заранее** — за сутки до переезда выставить 60 секунд. Тогда к моменту смены адреса во всех кэшах лежит короткоживущая запись и мир узнает о переезде за минуту. ⚠️ Наоборот не работает: если сменить адрес и только потом спохватиться про TTL, старая запись уже разошлась по кэшам и доживёт свой срок. После переезда TTL возвращают. → TTL — единственный рычаг управления

**Что такое DNSSEC и шифрует ли он запросы?**
**Нет, не шифрует** — это главная ловушка вопроса. DNSSEC подписывает записи цифровой подписью: даёт подлинность и целостность, защищая от отравления кэша. Цепочка доверия идёт по той же иерархии — родительская зона хранит `DS` (хеш ключа ребёнка), корневой ключ вшит в резолвер. Конфиденциальность — это уже **DoH/DoT**, они шифруют канал до резолвера, но записей не проверяют. Вместе, а не вместо. → Защита DNS — DNSSEC, DoH и DoT

**Чем `POST` отличается от `PUT`?**
`POST` создаёт и **не идемпотентен** (два вызова — две сущности). `PUT` заменяет ресурс целиком и идемпотентен: сколько раз ни повтори, результат один. → HTTP

**Что значат коды 401 и 403?**
`401 Unauthorized` — ты не представился (нет или невалиден токен). `403 Forbidden` — представился, но прав не хватает.

**Что такое CORS?**
Механизм, которым сервер разрешает браузеру **отдать JavaScript чужой страницы ответ** на запрос к себе. По умолчанию действует политика одного источника: скрипт не может прочитать ответ с другого источника (схема + хост + порт). ⚠️ Главная ловушка: CORS **не защищает твой API**. Запрос доходит до сервера и выполняется (у простых запросов преполёта нет), браузер лишь не отдаёт ответ скрипту; а `curl`, Postman и любой бэкенд игнорируют CORS вовсе. Он защищает сеанс пользователя, а не сервер — сервер защищают аутентификация и проверка прав. → Политика одного источника и CORS

**Почему запрос с JSON вызывает два обращения к серверу вместо одного?**
Это преполёт (preflight). Простым считается запрос с методом `GET`/`HEAD`/`POST` и `Content-Type` из короткого списка, куда `application/json` не входит. Поэтому браузер сначала шлёт `OPTIONS` с `Access-Control-Request-Method`, получает разрешение и только затем настоящий запрос. Кешируется через `Access-Control-Max-Age`. ⚠️ Преполёт уходит **без куки и токена** — требовать на нём авторизацию нельзя, иначе CORS не заработает никогда. → Простые запросы и преполётные

**Чем кука отличается от заголовка?**
Кука передаётся теми же HTTP-заголовками (`Set-Cookie` в ответе, `Cookie` в запросе) — разница в поведении браузера: он сам сохраняет куку и сам прикладывает её к каждому запросу к этому сайту. Отсюда и удобство (фронтенду не нужно ничего хранить), и риск: браузер приложит её и к запросу с чужого сайта — это и есть механика CSRF. → Куки

**Что делают флаги `Secure`, `HttpOnly` и `SameSite`?**
`Secure` — слать только по HTTPS. `HttpOnly` — скрыть от `document.cookie`, чтобы XSS не утащил сеанс. `SameSite` — слать ли куку при запросах с чужих сайтов: `Strict` (никогда), `Lax` (только при переходе по ссылке безопасным методом), `None` (всегда, обязательно с `Secure`). ⚠️ Частая ошибка в ответе: «`Lax` — это все GET». Нет: `GET` через `fetch()`, `<img>` или внутри `<iframe>` куку не получит, нужна именно навигация верхнего уровня. → SameSite

**Как передать файл по HTTP?**
Три способа: `multipart/form-data` (файл вместе с полями, обычные размеры), `application/octet-stream` (только байты, зато читаются потоком — для больших файлов), Base64 внутри JSON (маленькие файлы, цена ровно +33 % объёма). ⚠️ Сильный ответ добавляет четвёртый: большой файл лучше вообще не гнать через бэкенд — выдать предподписанную ссылку и грузить напрямую в S3. И что лимит размера ставится на nginx, а не в приложении: до Python тело уже дошло. → Передача файлов по HTTP

**Как HTTP связан с ограничением частоты запросов?**
Кодом `429 Too Many Requests`. Отдать его может и веб-сервер (грубый лимит по IP — запрос до приложения не дойдёт), и само приложение (лимит по бизнес-правилу, счётчик в Redis). Вместе с `429` полагается слать `Retry-After` — иначе клиент не знает, когда повторить, и продолжит долбиться. → Ограничение частоты запросов

**В чём суть REST?**
REST — не протокол и не формат, а **архитектурный стиль**. Ключевые ограничения: ресурсы адресуются URL (`/users/42`, существительное во множественном числе, не `/getUser`), действие задаёт HTTP-метод, сервер **не хранит состояние клиента** (каждый запрос самодостаточен), ответы явно помечены как кешируемые или нет, интерфейс единообразен. Практический вывод из stateless: сессию нельзя держать в памяти процесса — иначе второй инстанс за балансировщиком её не увидит. → [API](Фреймворки/DJANGO/API.md#что-такое-rest-api)

**Чем аутентификация отличается от авторизации?**
**Аутентификация** — «кто ты» (проверка логина и пароля, токена). **Авторизация** — «что тебе можно» (проверка прав на действие). Идентификация — ещё до них: заявление «я такой-то». Ровно этому соответствует пара кодов: `401` — не аутентифицирован, `403` — аутентифицирован, но не авторизован. → [Разделение доступа в DRF](Фреймворки/DJANGO/Разделение%20доступа%20в%20DRF.md)

**Что такое JWT и из чего он состоит?**
**JSON Web Token** — подписанный токен из трёх частей через точку: **header** (алгоритм), **payload** (данные — id пользователя, срок жизни `exp`), **signature** (подпись header+payload секретом сервера). Подпись позволяет проверить токен, не обращаясь к базе, — отсюда stateless-аутентификация. ⚠️ Ловушки: payload только **закодирован** base64, а не зашифрован — секреты туда класть нельзя; выданный токен нельзя отозвать до истечения `exp` (поэтому access делают коротким, а обновляют по refresh-токену). → [Разделение доступа в DRF](Фреймворки/DJANGO/Разделение%20доступа%20в%20DRF.md), [Веб-безопасность](Веб-безопасность.md)

## Асинхронность

**Что такое GIL и что именно он ограничивает?**
Глобальная блокировка интерпретатора: одновременно байткод CPython исполняет только один поток. Ограничивает **CPU-задачи** — потоки их не ускоряют. На **IO-задачах** GIL отпускается на время ожидания, поэтому потоки там работают. → Асинхронность и многопоточность

**Потоки, процессы, корутины — когда что?**
Процессы — CPU-задачи (обходят GIL, но дороги). Потоки — IO с блокирующими библиотеками. Корутины (`asyncio`) — много одновременных IO-операций, самые дешёвые. → [CPU-bound против IO-bound](Библиотеки/Модули/Параллелизм/CPU-bound%20против%20IO-bound.md)

**Что будет, если в `async def` вызвать блокирующую функцию?**
Заблокируется весь event loop: все остальные корутины встанут. Тяжёлое надо уносить в `run_in_executor` или в отдельный процесс.
⚠️ Сильный ответ добавляет уточнение: **блокирующий код в асинхронном приложении есть всегда** — арифметика, разбор JSON, проверка заголовков тоже держат loop. Вопрос не в наличии блокировки, а в её длительности: микросекунды это норма, сотни миллисекунд — авария. → [Блокирующий код в event loop](Библиотеки/Модули/Параллелизм/Блокирующий%20код%20в%20event%20loop.md)

**Ускоряет ли `async` код сам по себе?**
Нет. Отдельно взятая асинхронная функция работает столько же, сколько синхронная, и даже чуть дольше — сверху ложатся планирование корутины и переключения loop'а (условные 200 мс против 203 мс). Ускоряется не функция, а **пропускная способность**: пока одна корутина ждёт ответа, интерпретатор обслуживает другие. Отдельный пользователь ответ быстрее не получит. → [Asyncio Event Loop и aiohttp](Библиотеки/Модули/Параллелизм/Asyncio%20Event%20Loop%20и%20aiohttp.md#что-асинхронность-не-ускоряет)

**Дают большой кусок async-кода и просят найти плохое — что искать?**
Частая секция на живом кодинге. Порядок осмотра:
1. **синхронные библиотеки внутри `async def`** — `requests`, `time.sleep`, синхронный драйвер БД;
2. **`async def` без единого `await`** — она хуже обычной функции: обещает конкурентность, которой нет;
3. **последовательные независимые `await`** — три по 100 мс дают 300 вместо 100, лечится `gather`/`TaskGroup`;
4. **одна сессия БД, расшаренная между корутинами** в `gather` — [`AsyncSession` не рассчитан на конкурентные задачи](Библиотеки/Сторонние/ORM/SQLAlchemy.md#ловушка-одна-сессия-на-несколько-корутин);
5. **тяжёлый счёт в корутине** — поток его не спасёт из-за GIL, нужен процесс.

**`await` — это всегда настоящая асинхронность?**
Нет, и это неочевидный вопрос. Часть библиотек с приставкой `aio-` под асинхронным синтаксисом просто уносят работу в **пул потоков**. Канонический пример — `aiofiles`: у файлов в ОС нет полноценного асинхронного ввода-вывода (POSIX AIO слаб, native AIO требует `O_DIRECT`, io_uring молод и только в Linux), поэтому каждое открытие файла занимает поток. На больших файловых нагрузках это упирается в пул и деградирует. → [Асинхронная работа с файлами](Библиотеки/Модули/Параллелизм/Асинхронная%20работа%20с%20файлами.md)

**Чем отличаются threading, multiprocessing и asyncio?**
Один из самых частых вопросов раздела, спрашивают именно как сравнение трёх:

| | `threading` | `multiprocessing` | `asyncio` |
|---|---|---|---|
| Что запускает | потоки в одном процессе | отдельные процессы | корутины в одном потоке |
| Память | общая | своя у каждого, обмен через pickle | общая |
| GIL | мешает: байткод по очереди | обходится — свой интерпретатор на процесс | не мешает: поток один |
| Переключение | вытесняющее, решает ОС | вытесняющее | кооперативное, только на `await` |
| Цена одной единицы | ~МБ | десятки МБ | ~КБ |
| Для чего | I/O с блокирующими библиотеками | CPU-задачи | много одновременных I/O |

Короткая формулировка: **CPU-bound → процессы, I/O-bound → asyncio, а потоки — когда I/O, но библиотека не умеет async.** → Асинхронность и многопоточность, [CPU-bound против IO-bound](Библиотеки/Модули/Параллелизм/CPU-bound%20против%20IO-bound.md)

**Что такое event loop?**
Цикл, который держит очередь готовых к продолжению корутин: берёт одну, выполняет до ближайшего `await`, на месте ожидания откладывает её и берёт следующую. Никакой параллельности здесь нет — есть **конкурентность**: пока одна корутина ждёт ответа сети, процессор занят другой. Отсюда и главное правило: любая блокирующая операция останавливает весь цикл. → [Asyncio Event Loop и aiohttp](Библиотеки/Модули/Параллелизм/Asyncio%20Event%20Loop%20и%20aiohttp.md)

**Чем корутина отличается от потока?**
Поток переключает **операционная система** в любой момент (вытесняющая многозадачность) — отсюда гонки и необходимость блокировок. Корутина отдаёт управление **сама**, только в точке `await` (кооперативная многозадачность) — между двумя `await` код атомарен, и часть проблем синхронизации исчезает. Плата — одна «жадная» корутина без `await` вешает всё.

## Тестирование

**Чем мок отличается от стаба?**
Стаб просто возвращает заготовленный ответ. Мок дополнительно **проверяет, как его вызывали** (сколько раз, с какими аргументами). → [Юнит-тестирование Python](Библиотеки/Сторонние/Тесты/Юнит-тестирование%20Python.md)

**Что такое пирамида тестирования?**
Много быстрых юнит-тестов внизу, меньше интеграционных, совсем мало e2e наверху. Перевёрнутая пирамида — медленный и хрупкий прогон.

## Фреймворки

**Django или FastAPI — что выберешь?**
Django — «батарейки в комплекте»: ORM, админка, аутентификация, миграции из коробки, синхронный по умолчанию. FastAPI — тонкий async-слой поверх Starlette и [pydantic](Библиотеки/Сторонние/pydantic.md): валидация и документация из аннотаций типов, ORM и админку подключаешь сам. Выбор по задаче: классическое приложение с админкой и формами → Django; высоконагруженный API, много внешних вызовов, нужен async → FastAPI. ⚠️ «FastAPI быстрее» — плохой ответ: выигрыш только на I/O-bound нагрузке, на CPU-задачах разницы нет. → [Django](Фреймворки/DJANGO/Django.md), [FastAPI](Фреймворки/FastAPI.md)

**Что такое middleware?**
Слой-обёртка вокруг обработки запроса: код выполняется **до** view и **после** него, для всех запросов сразу. Через него делают логирование, замер времени, CORS, аутентификацию, обработку исключений. Устроен как цепочка: каждый middleware получает следующий и решает, вызвать его или ответить самому (например, вернуть `403`, не пуская запрос дальше). Это тот же [паттерн Декоратор](ООП/Паттерны/Структурные%20паттерны.md#декоратор), но на уровне запроса. → [Django](Фреймворки/DJANGO/Django.md), [FastAPI](Фреймворки/FastAPI.md)

**Почему QuerySet называют ленивым?**
Он не идёт в базу при создании: `Product.objects.filter(...)` только строит запрос. SQL выполняется в момент, когда результат действительно нужен — итерация, `len()`, `list()`, срез с шагом, `bool()`. Благодаря этому фильтры можно накапливать по частям, и уйдёт **один** запрос. ⚠️ Обратная сторона: `if qs:` и следом `for x in qs:` — это два обращения к базе, если между ними QuerySet не закеширован. → [ORM Django](Фреймворки/DJANGO/ORM%20Django.md)

**Чем `select_related` отличается от `prefetch_related`?**
Оба лечат [N+1](Фреймворки/DJANGO/ORM%20Django.md#ловушка-n1-запросов), но по-разному. `select_related` делает **`JOIN` в одном запросе** — работает для «многие к одному» и «один к одному» (`ForeignKey`, `OneToOne`). `prefetch_related` делает **второй запрос** и склеивает результаты в Python — нужен для «многие ко многим» и обратных связей, где `JOIN` размножил бы строки. → [ORM Django](Фреймворки/DJANGO/ORM%20Django.md)

**Зачем нужен сериализатор?**
Переводит объекты Python в примитивы для JSON и обратно, а на обратном пути ещё и **валидирует** входные данные и правила уровня объекта. Без него пришлось бы руками собирать словари и проверять каждое поле. В DRF это `Serializer` / `ModelSerializer`, в FastAPI ту же роль играют модели [pydantic](Библиотеки/Сторонние/pydantic.md). → [CRUD В DRF](Фреймворки/DJANGO/CRUD%20В%20DRF.md)

**Что такое `Depends` и приведи пример из практики?**
Внедрение зависимостей: функция готовит ресурс, FastAPI вызывает её сам и подставляет результат в аргумент ручки. Два примера, которых ждут: (1) **сессия БД через `yield`** — одна транзакция на один HTTP-запрос, соединение само возвращается в пул, а в тестах подменяется через `dependency_overrides`; (2) **пагинация** — вместо повтора `page`/`limit` в двадцати ручках один класс-зависимость с валидацией и вычисленным `offset`. Отдельно стоит назвать кэш: в пределах одного запроса зависимость вызывается **один раз**, даже если её просят три места. → [Depends — зависимости в FastAPI](Фреймворки/Depends%20—%20зависимости%20в%20FastAPI.md)

**Какие минусы у `BackgroundTasks`?**
Нет персистентности (задача живёт в памяти воркера — редеплой или падение процесса убивает её безвозвратно), нет ретраев, расписания и мониторинга, не масштабируется на другие машины. Плюс две вещи, о которых обычно не думают: задачи выполняются **последовательно**, а не параллельно, а ресурс из `Depends` с `yield` в фоновой задаче использовать нельзя — передавай id и открывай своё соединение внутри. Вывод: `BackgroundTasks` — для лёгкого и некритичного; всё, где нужна гарантия выполнения, — [Celery](Библиотеки/Сторонние/Celery.md) с брокером. ⚠️ Заблуждение из той же темы: в фон выносят **не только синхронные** функции — async-задачу Starlette запустит в event loop, обычную отправит в пул потоков. → [FastAPI](Фреймворки/FastAPI.md), [Celery](Библиотеки/Сторонние/Celery.md)

**Зачем нужны и uvicorn, и gunicorn одновременно?**
Роли разные: **uvicorn** — ASGI-сервер, он *обрабатывает* запросы; **gunicorn** — менеджер процессов, он *следит* за воркерами и поднимает упавшего. Отсюда историческая связка. ⚠️ Сейчас ответ нужно дополнять: с uvicorn **0.30** у него есть свой менеджер процессов, а `uvicorn.workers.UvicornWorker` устарел (переехал в пакет `uvicorn-worker`). А в [Kubernetes](DevOps/Kubernetes.md) gunicorn не нужен вовсе — роль супервизора берёт кластер, и в контейнере держат **один** процесс uvicorn, масштабируясь репликами. → [REST API на FastAPI](Фреймворки/REST%20API%20на%20FastAPI.md#uvicorn-и-gunicorn--кто-из-них-зачем)

**Чем синхронный эндпоинт отличается от асинхронного? Можно ли вообще писать `def`?**
Можно, и RPS не рухнет: `def`-ручку FastAPI выносит в **пул потоков**, `async def` — выполняет в общем **event loop**. Loop дешевле: переключение между корутинами происходит внутри Python, без объектов ОС и без переключения контекста, поэтому одновременных соединений держится больше. Обе модели решают одну и ту же задачу — **I/O-bound** нагрузку. ⚠️ Ловушка вопроса: «потоки — для CPU» неверно; CPU-задачу не спасают ни потоки (GIL), ни loop — только процессы. И худший вариант из всех — блокирующий вызов внутри `async def`. → [FastAPI](Фреймворки/FastAPI.md#ловушка-блокирующий-код-в-async-def), [CPU-bound против IO-bound](Библиотеки/Модули/Параллелизм/CPU-bound%20против%20IO-bound.md)

**Как тестировать FastAPI?**
Ключевая мысль: **сервер поднимать не нужно**. `TestClient` (или `httpx.AsyncClient` с `ASGITransport`) подменяет транспорт и вызывает ASGI-приложение прямо в процессе — работают все роутеры, зависимости и middleware, но без сокета и порта. Дальше: `pytest` + `pytest-asyncio`/`anyio` для async-тестов, `dependency_overrides` для подмены сессии и пользователя, настоящий PostgreSQL через testcontainers, изоляция транзакцией с откатом. ⚠️ `TestClient` запускает `lifespan` только внутри `with`-блока — без него пул соединений не поднимется. ⚠️ SQLite вместо Postgres «для скорости» — тестирование другой СУБД. → [Тестирование FastAPI-приложений](Фреймворки/Тестирование%20FastAPI-приложений.md)

## Инструменты — Git, Docker, брокеры

**Что такое Docker и какую проблему он решает?**
Упаковывает приложение вместе со всем окружением — интерпретатором, библиотеками, системными пакетами — в **образ**, который одинаково запускается везде. Это ответ на «у меня работает, а на сервере нет». В отличие от виртуальной машины, контейнер использует ядро хоста и не тащит целую ОС: старт за секунды, вес в десятки раз меньше. → [Docker](DevOps/Docker.md)

**Чем образ отличается от контейнера и что такое слои?**
**Образ** — неизменяемый шаблон, **контейнер** — запущенный экземпляр образа (как класс и объект). Образ состоит из **слоёв**: каждая инструкция `Dockerfile` добавляет свой, слои переиспользуются и кешируются. Отсюда практическое правило: сначала копировать `requirements.txt` и ставить зависимости, и только потом копировать код — иначе правка одной строки кода инвалидирует кеш и пересобирает всё. → [Docker](DevOps/Docker.md)

**Зачем нужен docker compose?**
Описывает несколько связанных контейнеров одним YAML-файлом: приложение, база, Redis, nginx. Поднимает их одной командой, заводит общую сеть (контейнеры видят друг друга по имени сервиса) и хранит тома. Без него пришлось бы вручную писать десяток `docker run` с флагами сети и портов. → [Docker](DevOps/Docker.md)

**Что такое многоступенчатая сборка и зачем она?**
Несколько `FROM` в одном Dockerfile: в финальный образ попадает только последняя стадия, из предыдущих забирают готовые артефакты через `COPY --from=builder`. Смысл — компилятор и заголовочные файлы нужны, чтобы **собрать** зависимости, и не нужны, чтобы их **запускать**; без разделения весь инструментарий едет в прод. Вторая выгода, о которой обычно не говорят: секреты сборки (токен приватного репозитория) остаются в стадии `builder`, и через `docker history` финального образа их не достать. → [Docker](DevOps/Docker.md#многоступенчатая-сборка-multi-stage)

**Почему процесс в контейнере не стоит запускать от root?**
По умолчанию он именно от `root`, а изоляция контейнера не абсолютна: пробой в приложении плюс неудачно смонтированный том — и права на хосте шире, чем предполагалось. Чинится `RUN useradd` + `USER app`. ⚠️ Два следствия, которые и проверяют: `USER` действует на всё **ниже** себя, поэтому `apt-get install` ставят до него, а порты ниже 1024 непривилегированному пользователю недоступны — приложение слушает 8000, наружу отдаётся `-p 80:8000`. → [Docker](DevOps/Docker.md#не-запускать-от-root)

**Что делает `HEALTHCHECK` и перезапустит ли он контейнер?**
Задаёт команду, по которой Docker решает, живо ли приложение внутри: статус в `docker ps` идёт `starting` → `healthy`/`unhealthy`, `--start-period` даёт фору на запуск. ⚠️ Вопрос-ловушка во второй половине: **сам Docker unhealthy-контейнер не перезапускает**, он только меняет статус; `restart: always` реагирует на завершение процесса, а не на здоровье. Перезапуск по здоровью — забота оркестратора ([Kubernetes](DevOps/Kubernetes.md), liveness probe). Реальная польза в Compose — `depends_on` с `condition: service_healthy`, чтобы приложение ждало, пока база начнёт принимать запросы. → [Docker](DevOps/Docker.md#healthcheck--жив-ли-процесс-внутри)

**Чем `git merge` отличается от `git rebase`?**
`merge` создаёт **коммит слияния** и сохраняет реальную историю с ветвлениями. `rebase` **переписывает** коммиты ветки поверх новой базы — история становится линейной, но коммиты получают новые хеши. ⚠️ Главное правило: не делать `rebase` веток, которые уже запушены и с которыми работают другие — у них останутся старые коммиты, и история разъедется. Типичный компромисс: `rebase` для своей локальной ветки перед вливанием, `merge` — в основную. → GIT

**Что делает `cherry-pick`?**
Переносит **один конкретный коммит** из одной ветки в другую, создавая его копию с новым хешем. Нужен, когда фикс сделан в ветке разработки, а на прод надо взять только его, не тащя остальное. ⚠️ Злоупотребление приводит к дублированию коммитов и конфликтам при последующем слиянии веток.

**Что такое Git Flow?**
Модель ветвления с долгоживущими `main` и `develop` плюс `feature/`, `release/`, `hotfix/`. Придумана под релизы версиями. Для сервиса с непрерывной выкладкой её обычно считают избыточной и берут **trunk-based**: короткие ветки от `main`, частые вливания, фичи прячутся за флагами. Хороший ответ называет обе модели и говорит, почему выбор зависит от того, как часто вы катите. → GIT

**Зачем нужен Redis и что он умеет кроме кеша?**
In-memory хранилище ключ-значение: данные в оперативной памяти, отсюда скорость. Кроме кеша — брокер для [Celery](Библиотеки/Сторонние/Celery.md), распределённая блокировка, счётчики и rate limiting, очереди на списках, pub/sub, сессии. Умеет TTL на ключ и атомарные операции (`INCR`), что и делает его удобным для счётчиков. ⚠️ Память конечна: без TTL и политики вытеснения Redis упрётся в лимит. → [Redis](Библиотеки/Сторонние/Redis.md)

**Зачем нужен Celery?**
Выносит долгие операции (письма, отчёты, обработка файлов) из HTTP-запроса в фоновые воркеры, чтобы пользователь не ждал. Состоит из трёх частей: приложение кладёт задачу в **брокер** ([RabbitMQ](Библиотеки/Сторонние/RabbitMQ.md) или [Redis](Библиотеки/Сторонние/Redis.md)), **воркер** её забирает и выполняет, результат кладётся в **backend**. ⚠️ Задача должна быть идемпотентной: при `acks_late` и падении воркера её выполнят повторно. → [Celery](Библиотеки/Сторонние/Celery.md), Гарантии доставки и идемпотентность

**Чем Kafka отличается от RabbitMQ?**
RabbitMQ — классический брокер: маршрутизирует сообщение потребителю и **удаляет** после подтверждения; силён гибкой маршрутизацией и подходит для задач-команд. Kafka — распределённый **лог**: сообщения пишутся в партицию и хранятся заданное время, потребитель сам держит смещение (offset) и может перечитать историю; силён пропускной способностью и несколькими независимыми читателями одного потока. Коротко: RabbitMQ — «выдать задание работнику», Kafka — «поток событий, который читают многие». → [RabbitMQ](Библиотеки/Сторонние/RabbitMQ.md), Событийная архитектура и Kafka

## Производительность и БД

**Запрос стал тормозить. Твои действия?**
По шагам: воспроизвести и замерить → `EXPLAIN (ANALYZE, BUFFERS)` → посмотреть, есть ли `Seq Scan` на большой таблице и совпадает ли оценка строк с фактом → проверить, подходит ли индекс (порядок колонок, селективность) → если план хорош, а медленно — смотреть блокировки и нагрузку. ⚠️ Не начинать с «добавим кэш»: кэш **спрячет** проблему, а при первом промахе она вернётся. → PostgreSQL, Программирование/Базы данных/Стратегии кэширования

**Индекс есть, но не используется. Почему?**
Частые причины: функция над колонкой (`WHERE lower(email) = ...` — нужен функциональный индекс); несовпадение типов; низкая селективность (планировщик решил, что seq scan дешевле); неверный порядок колонок в составном индексе; устаревшая статистика — лечится `ANALYZE`.

**Какой уровень изоляции возьмёшь и зачем?**
`Read Committed` (умолчание PostgreSQL) — почти всегда. `Repeatable Read` — когда внутри транзакции несколько чтений должны быть согласованы (отчёт). `Serializable` — когда есть инвариант между разными строками (write skew), и обязателен ретрай на ошибку сериализации. → Программирование/Базы данных/Уровни изоляции и аномалии

**Что такое потерянное обновление и как его избежать?**
Две транзакции прочитали значение, обе посчитали в приложении и записали — одна правка затёрта. Решения: атомарный `UPDATE ... SET x = x - 1 WHERE x > 0`, пессимистичная блокировка `FOR UPDATE` или оптимистичная через версию строки.

**Что такое дедлок и что с ним делать?**
Две транзакции ждут друг друга по кругу. PostgreSQL обнаруживает цикл и убивает одну. Профилактика: **всегда захватывать ресурсы в одном порядке**, держать транзакции короткими, ретраить оставшиеся. → Программирование/Базы данных/Блокировки и дедлоки

**Как выкатить миграцию на таблице в 50 млн строк без даунтайма?**
Стратегия **expand-contract**: добавить новое nullable-поле → заполнять пачками в фоне → начать писать в оба → переключить чтение → удалить старое. Никаких `ALTER TABLE ... SET NOT NULL DEFAULT` одним куском: он берёт `ACCESS EXCLUSIVE` и блокирует всё. Индексы — только `CREATE INDEX CONCURRENTLY`. → Миграции и zero-downtime

## Кэш и надёжность

**Кэш протух у всех сразу, база легла. Что не так?**
**Cache stampede**: тысяча запросов одновременно пошли в базу за одним ключом. Лечится джиттером в TTL (ключи протухают вразнобой) и блокировкой на перестроение — в базу идёт один, остальные ждут его результат. → Программирование/Базы данных/Стратегии кэширования

**Почему при обновлении данных кэш надо удалять, а не перезаписывать?**
Перезапись создаёт гонку: два параллельных обновления могут записать значения в обратном порядке, и в кэше останется старое. Удаление такой гонки не создаёт — следующий читатель просто сходит в источник.

**Как правильно ретраить?**
Только идемпотентные операции (либо `Idempotency-Key`), экспоненциальная задержка **с джиттером**, не больше 3 попыток, ретраи только на одном уровне цепочки, `4xx` не ретраить. Без джиттера повторы синхронизируются в волны и добивают поднимающийся сервис. → Устойчивость — таймауты, ретраи, circuit breaker

**Зачем нужен circuit breaker?**
Если сервис лежит, каждый запрос к нему — это ожидание таймаута для **твоего** пользователя и лишняя нагрузка для упавшего. Размыкатель после порога ошибок отклоняет запросы сразу, периодически пропуская пробный. Быстрый отказ лучше медленного.

**Как обеспечить обработку сообщения ровно один раз?**
Строго exactly-once в распределённой системе недостижим. На практике делают **at-least-once + идемпотентность потребителя**: у сообщения есть ключ, обработчик запоминает обработанные и повтор игнорирует. → Гарантии доставки и идемпотентность

## Эксплуатация

**Пользователи жалуются, что тормозит. С чего начнёшь?**
Не с чтения кода, а с метрик: когда началось, у всех или у части, что изменилось (релиз, рост трафика). Дальше по цепочке — метрика показала аномалию, трейс показал медленный шаг, лог объяснил причину. → [Наблюдаемость — метрики, логи, трейсы](DevOps/Наблюдаемость%20—%20метрики,%20логи,%20трейсы.md)

**Почему нельзя смотреть на среднее время ответа?**
Оно прячет хвост. При 9 запросах по 100 мс и одном за 5 с среднее 590 мс выглядит приемлемо, а каждый двадцатый пользователь ждёт 5 секунд. Смотреть надо p50, p95, p99.

**Какие метрики снимать с сервиса?**
RED: Rate, Errors, Duration. Для ресурсов — USE: Utilization, Saturation, Errors. ⚠️ Не класть в метки высококардинальные значения (`user_id`, `trace_id`) — Prometheus захлебнётся числом временных рядов. → [Prometheus и Grafana](DevOps/Prometheus%20и%20Grafana.md)

**Чем liveness отличается от readiness?**
`liveness` — процесс жив, провал ведёт к **перезапуску**. `readiness` — готов принимать трафик, провал **выводит из балансировки**. ⚠️ Классическая ошибка — проверять БД в liveness: база моргнула, все поды перезапустились и добили её волной переподключений.

**Что такое SLO и error budget?**
SLO — внутренняя цель по качеству (99.9% запросов быстрее 300 мс за месяц). Error budget — сколько допустимо ломаться: при 99.9% за 30 дней это ≈43 минуты. Бюджет есть — катим фичи, сожгли — останавливаемся и чиним надёжность.

## Архитектура

**Монолит или микросервисы?**
Правильный ответ — «зависит», и надо назвать от чего. Микросервисы дают независимый деплой и масштабирование, но добавляют сетевые отказы, распределённые транзакции и эксплуатационную сложность. Небольшой команде почти всегда лучше модульный монолит. ⚠️ Ответ «микросервисы, потому что современно» — минус. → Монолит и микросервисы

**Спроектируй сокращатель ссылок.**
Каркас ответа: уточнить требования и нагрузку (RPS, объём) → прикинуть числа → API (`POST /links`, `GET /{code}`) → генерация кода (счётчик в base62 против хеша с проверкой коллизий) → хранение и индекс → кэш горячих ссылок → масштабирование чтения репликами. Оценка нагрузки вслух ценится больше, чем красивая схема. → [Проектирование систем (system design)](Проектирование%20систем%20%28system%20design%29.md)

**Что такое CAP-теорема?**
При сетевом разделении приходится выбирать между согласованностью и доступностью — обеспечить обе невозможно. ⚠️ Частая ошибка: считать, что «выбираем два из трёх» всегда. Разделение (P) — не выбор, а данность распределённой системы. → Распределённые вычисления

**Как тестировать код, который ходит в БД и внешний API?**
База — интеграционным тестом на **настоящей** СУБД через testcontainers, изоляция транзакцией с откатом. Внешний API — мок транспорта или контрактные тесты. ⚠️ SQLite вместо PostgreSQL — ловушка: тестируешь другую базу, зелёный тест ничего не гарантирует. → [Интеграционные тесты и testcontainers](Библиотеки/Сторонние/Тесты/Интеграционные%20тесты%20и%20testcontainers.md)

**Зачем нужен CQRS и когда его применять?**
Разделить модель записи и модель чтения, потому что требования к ним противоположные: записи нужна корректность (валидация, инварианты, границы агрегата), чтению — скорость и своя форма данных под каждый экран. Плюс нагрузка обычно перекошена: чтений на порядки больше. Применять точечно — в одном компоненте или ограниченном контексте, где болит, а не по всей системе. Признаки, что пора: репозиторий на 50 методов, запросы через несколько агрегатов, пять и более соединений в горячем запросе. → CQRS — разделение моделей чтения и записи

**🔴 CQRS — это ведь команды и хендлеры?**
Нет, и это главный миф темы. `CreateProductCommand` + `CreateProductCommandHandler` — отдельный паттерн, который хорошо сочетается с CQRS, но не является им. Можно разделить модели чтения и записи на обычных сервисах, без единого объекта-команды; можно нашпиговать проект хендлерами, оставшись при одной модели. CQRS — это **две модели вместо одной**, всё остальное детали реализации.

**🗣 Вопрос-ловушка: CQRS требует Event Sourcing и отдельной базы?**
Не требует ни того, ни другого. Минимальный CQRS — разные классы и репозитории на одной базе. Дальше по лестнице: две схемы в одной СУБД, потом разные хранилища (Postgres + Elasticsearch/ClickHouse). Автор термина Грег Янг прямо перечисляет: _CQRS is not Event Sourcing_, _CQRS does not require a message bus_, _CQRS is not a top level architecture_.

**Как обновляется read-модель и что при этом ломается?**
Синхронно (в одной транзакции с записью) — строгая согласованность, но запись замедляется, а упавшая проекция **откатывает корректную запись пользователя**. Асинхронно (событие в очередь или фоновый воркер) — запись быстрая и независимая, ценой лага в секунды-минуты. Ключевая деталь, которую ждут: «сохранить в БД и отправить событие» — две операции без общей транзакции, поэтому нужен Outbox. И проекция обязана перестраиваться с нуля.

**Пользователь сохранил данные, обновил страницу — изменений нет. Что произошло и как чинить?**
Скорее всего чтение ушло в отстающую копию: реплику, кэш или асинхронную проекцию. Это не баг, а итоговая согласованность. Чинится на двух уровнях: технически — гарантией **read-your-writes** (читать свои изменения с мастера/write-модели, прилипание сессии), продуктово — честным интерфейсом: оптимистичное обновление на клиенте плюс статус «публикуется». ⚠️ Ответ «поставим sleep на клиенте» — минус: лаг непостоянен. → Согласованность в конечном счёте

**Может ли команда возвращать значение?**
По канону CQS Бертрана Мейера — нет, команда `void`, «вопрос не должен менять ответ». Прагматично — возвращают минимум: идентификатор созданной сущности или статус с ошибками валидации. Возвращать из команды весь агрегат не стоит: это стирает границу между командой и запросом, детали клиент дочитает запросом.

**Чем шардирование отличается от репликации и партиционирования?**
Репликация копирует **все** данные на несколько машин — это про отказоустойчивость и масштаб чтения, от объёма она не спасает. Партиционирование режет таблицу на части **внутри одной машины** — про отсечение лишнего при запросе. Шардирование режет данные **между машинами** — единственное из трёх, что снимает потолок по объёму и записи. На практике сочетают: каждый шард сам по себе реплицирован. → Шардирование

**Как выбрать ключ шардирования?**
Главное правило: **что читают вместе, должно лежать вместе**. Посты режут по `user_id`, сообщения по `chat_id`, мультиарендный сервис — по `tenant_id`. Признаки плохого ключа: запрос идёт во все шарды (ключ не совпадает с шаблоном чтения), один шард горячее прочих, шард растёт быстрее прочих. ⚠️ Шардирование по автоинкрементному `id` или дате отправляет всю свежую запись в последний шард.

**🔴 Как клиент узнаёт, на каком шарде лежат его данные?**
Два подхода. **Сервер метаданных**: отдельная служба хранит «диапазон ключей → шард» (по отдельным ключам не хранят — не влезет) и умеет балансировать, деля и перенося диапазоны. Так работают Bigtable, Spanner, MongoDB (config server), Citus. **Согласованное хеширование**: центральной службы нет, серверы и ключи лежат на кольце хешей, ключ принадлежит первому серверу по часовой стрелке; так работают Dynamo и Cassandra. Развилка: баланс и диапазонные запросы против доступности и скорости роста кластера. → Как найти нужный шард: два подхода

**Что такое согласованное хеширование и зачем виртуальные узлы?**
При обычном `hash(ключ) % N` смена числа серверов переносит почти все ключи. Кольцо хешей переносит в среднем **K/N** — теоретический минимум: новый узел забирает дугу у одного соседа. Виртуальные узлы нужны потому, что на малом числе серверов дуги получаются разной длины, а при отказе весь участок достаётся одному соседу; каждый физический узел занимает много точек на кольце, и нагрузка выравнивается. ⚠️ Redis Cluster — **не** согласованное хеширование, а 16 384 фиксированных слота. → Согласованное хеширование

**Что ломается после шардирования?**
Кросс-шардовые запросы (всё без ключа шардирования идёт во все шарды, ответ ждёт самый медленный), соединения между шардами, транзакции (внутри шарда обычный ACID, между — 2PC или сага), уникальность и автоинкремент (только в пределах шарда, отсюда UUID), вторичные индексы (локальный требует опроса всех шардов, глобальный сам шардирован по другому ключу). Плюс ресэрдинг — отдельный проект с двойной записью и миграцией.

**Дали матрицу с лабиринтом — как решать и что сказать?**
Сначала назвать, что граф здесь **неявный**: вершина — клетка, ребро — переход к соседу, список смежности не нужен. Дальше — развилка из трёх решений с их ценой: рекурсивный DFS (пять строк, но на большом поле `RecursionError` — глубина рекурсии равна размеру компоненты), итеративный DFS (стек не переполнит, пик памяти всё равно до $n \cdot m$), BFS (единственный даёт кратчайший путь, память расходуется предсказуемее). Вывод: «на практике возьму BFS, готов написать любой». Оценка обоих — $O(n \cdot m)$ по времени и памяти. → [Обход клетчатого поля](Алгоритмы/Приёмы/Обход%20клетчатого%20поля.md)

**🔴 В чём разница между итеративным DFS и BFS?**
В одной строке: DFS снимает элемент с конца (стек), BFS — с начала (очередь). Всё остальное совпадает. Из-за этой строки один проваливается вглубь, а второй расходится волной и потому находит кратчайший путь. ⚠️ Частая ошибка на секции — пометить клетку посещённой **при извлечении** из очереди: тогда она попадает туда несколько раз, очередь распухает, а расстояния ломаются. Правило: пометил — сразу положил.

**Как найти ближайший из многих источников?**
Не запускать BFS от каждого. **Мультистарт**: положить все источники в очередь до начала цикла с расстоянием 0 — волна расходится от всех сразу, каждая клетка достаётся ближайшему. Вместо $O(k \cdot n \cdot m)$ получается $O(n \cdot m)$. ⚠️ Уточнение, которое ценят: если цель одна, а источников много, ещё проще запустить обычный BFS **от цели** и остановиться на первом встреченном источнике.

**🗣 Вопрос-ловушка: шардирование повышает надёжность?**
Само по себе — **снижает**. Без репликации отказ одной машины делает недоступной 1/N всех данных, то есть вероятность частичного отказа растёт с числом шардов. Надёжность даёт репликация поверх шардирования: каждый шард — свой кластер «ведущий + реплики».

## Идемпотентность и вебхуки

**Что такое идемпотентность?**
Свойство операции: повторный вызов с теми же параметрами оставляет систему в том же состоянии, что и однократный. Не путать с безопасностью (safety): `GET` и безопасен, и идемпотентен; `DELETE` идемпотентен, но не безопасен (состояние меняет); `POST` — ни то, ни другое.
Зачем это вообще: сеть ненадёжна, клиент не знает, дошёл ли его запрос, и **ретраит**. Если операция не идемпотентна — второй платёж, второй заказ. Лечится **ключом идемпотентности**: клиент генерирует UUID и шлёт в `Idempotency-Key`, сервер хранит «ключ → результат» и при повторе возвращает сохранённый ответ, не выполняя действие заново. → Гарантии доставки и идемпотентность, HTTP

**🗣 Вопрос-ловушка: `DELETE` вернул 200, а на повтор 404. Это нарушает идемпотентность?**
Нет. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods) определяет идемпотентность через **эффект на сервере**, прямо оговаривая «even if the response status code might differ». После обоих запросов ресурса нет — состояние одинаково. Хороший ответ продолжается так: **клиенту от этого не легче** — по `404` он не поймёт, его ли ретрай удалил ресурс. Отсюда различение идемпотентности **по состоянию** (защищает данные) и **по ответу** (защищает клиента); второе даёт только сохранение ответа под ключом. → Два вида идемпотентности: по состоянию и по ответу

**Какие есть способы сделать операцию идемпотентной, кроме ключа?**
Шесть механизмов, и выбор идёт от того, **откуда берётся признак тождества операции**: `UNIQUE`-ограничение (ключ — поле данных), upsert, детерминированный id (вычислен из бизнес-полей), ключ идемпотентности (придуман клиентом), дедупликация по `event_id` (пришёл от отправителя). Шестой — оптимистичная блокировка — в этот ряд **не входит**, см. следующий вопрос. Правило выбора: есть естественный уникальный признак → ограничение; создаётся сущность без такого признака → ключ; обрабатывается сообщение → дедупликация. → Идемпотентность на практике — выбор стратегии

**🗣 Вопрос-ловушка: оптимистичная блокировка обеспечивает идемпотентность?**
Нет, она решает другую задачу — **потерянное обновление**, то есть гонку двух *разных* операций. Свой же ретрай действительно не применится дважды (`WHERE версия = 3` не совпадёт), но клиент получит «0 строк» — **тот же ответ**, что и при чужом опережении, и отличить «мой эффект уже применён» от «меня опередили» по нему нельзя. Плюс механизм неприменим к созданию: у несуществующей строки нет версии. → Программирование/Базы данных/Блокировки и дедлоки

**Как реализовать `Idempotency-Key` на сервере?**
Таблица с `PRIMARY KEY (владелец, ключ)`, где хранится не факт «видели», а **результат целиком**: код ответа, тело, отпечаток запроса, статус. Порядок операций: сначала `INSERT` ключа, потом работа. Три ветки при занятом ключе — другой отпечаток → `422`, статус `выполняется` → `409`, `готово` → сохранённый ответ. Ключ и эффект пишутся **одной транзакцией**, TTL — по окну реальных ретраев (у Stripe 24 часа). → Ключ идемпотентности

**🗣 Вопрос-ловушка: почему `if seen(id): return` перед обработкой недостаточно?**
Это **check-then-act**: между проверкой и эффектом есть окно, и два одновременных дубля проходят проверку оба. Одной транзакции мало — на Read Committed (умолчание Postgres) обе транзакции законно не видят чужую незафиксированную вставку. Спасает `UNIQUE`-ограничение: **вставка ключа делается первой операцией и сама служит захватом права на работу** — кто вставил, тот выполняет, остальные ловят `IntegrityError`. Альтернатива — уровень Serializable. → Гонка, которую пропускают почти все

**Что вернуть, если пришёл знакомый ключ, но с другим телом запроса?**
Ошибку (`422`). Отдать сохранённый ответ — соврать клиенту (он просил списать 500, получит ответ на 100); выполнить — нарушить обещание ключа. Поэтому вместе с ключом хранят **отпечаток запроса** — хеш пути и тела. Так делает Stripe.

**Является ли `Idempotency-Key` стандартом?**
Строго — нет, и это хороший маркер аккуратности. Отдельного RFC не существует: черновик IETF `draft-ietf-httpapi-idempotency-key-header` дошёл до версии 07 (октябрь 2025) и **истёк, не став RFC**. Это устоявшееся отраслевое соглашение, закреплённое практикой Stripe. Заголовок пишется **без префикса `X-`** — тот признан устаревшим [RFC 6648](https://www.rfc-editor.org/rfc/rfc6648.html) ещё в 2012-м.

**Что такое webhook?**
Обратный вызов по HTTP: не ты опрашиваешь чужой сервис, а он сам шлёт `POST` на твой заранее зарегистрированный URL, когда происходит событие. Принцип «не звоните нам — мы позвоним вам». → [Вебхуки (webhooks)](Библиотеки/Сторонние/Работа%20с%20WEB/Вебхуки%20%28webhooks%29.md)

**Чем webhook отличается от обычного эндпоинта, который вызывает клиент?**
Технически это тот же HTTP-эндпоинт — разница в том, **кто инициатор и как строится доверие**:

| | Обычный эндпоинт | Webhook |
|---|---|---|
| Инициатор | твой клиент | внешняя система |
| Аутентификация | сессия/токен пользователя | **подпись тела** (HMAC общим секретом) в заголовке, проверка `timestamp` от replay, allowlist IP |
| Семантика | запрос → ответ с данными, клиент ждёт | уведомление о событии |
| Ответ | полезная нагрузка | быстрый `2xx`, обработка **асинхронно** — иначе отправитель словит таймаут |
| Доставка | один раз | ретраи отправителя ⇒ **at-least-once**, дубликаты гарантированы |

Последняя строка и объясняет, почему про идемпотентность спросили **прямо перед этим**: обработчик вебхука обязан быть идемпотентным по `event_id`, иначе ретрай отправителя превратится во второе списание.

**Когда оправдан webhook?**
Когда событие **редкое и непредсказуемое по времени**: оплата прошла, статус доставки изменился, пришёл коммит. Поллинг здесь — трата: 99% запросов возвращают «ничего нового», а задержка всё равно равна интервалу опроса.
Когда **не** оправдан: нужен ответ здесь и сейчас (это обычный запрос); получатель без публичного URL, за NAT (тогда поллинг или long-polling); поток событий очень плотный — тогда не вебхуки, а брокер/стрим (Событийная архитектура и Kafka).

## Проектирование БД и индексы

**Что надо учесть при проектировании базы данных?**
Каркас ответа — от главного к деталям:
1. **Сущности и связи**: 1:1, 1:N, N:M через таблицу-связку.
2. **Ключи**: суррогатный (`id`) vs естественный; `FOREIGN KEY` и поведение при удалении (`ON DELETE CASCADE/RESTRICT/SET NULL`).
3. **Ограничения как инварианты**: `NOT NULL`, `UNIQUE`, `CHECK` — правило должна держать база, а не только код, иначе его обойдут мимо приложения.
4. **Типы**: точные деньги — `NUMERIC`, а не `float`; время — с таймзоной; не хранить всё как `text`.
5. **Нормализация до 3НФ как отправная точка**, денормализация — осознанно.
6. **Индексы под реальные запросы**, а не «на всякий случай».
7. **Рост**: объём, паттерн доступа (читают или пишут), партиционирование, архивация.
8. **Изменяемость**: миграции и то, как накатить их без простоя → Миграции и zero-downtime.
Главный тезис, который стоит сказать вслух: **схему проектируют от запросов**, а не от красоты модели. → Базы данных

**Что такое нормальные формы и когда имеет смысл их нарушать?**
- **1НФ** — значения атомарны, нет повторяющихся групп и списков в одной ячейке.
- **2НФ** — 1НФ + нет зависимости неключевого атрибута от **части** составного ключа.
- **3НФ** — 2НФ + нет транзитивных зависимостей (неключевой атрибут не зависит от другого неключевого).
Нарушают ради **чтения**: слишком много `JOIN` на горячем пути; витрины и аналитика; кэш агрегатов (счётчик комментариев прямо в записи); **исторические снимки** — в заказе хранится цена на момент покупки, и это не дублирование, а намеренная фиксация факта.
Цена: возвращаются аномалии обновления — консистентность теперь держишь ты (триггер, транзакция, пересчёт). Правило: **нормализуй сразу, денормализуй по замеру**, а не заранее.

**Что такое индексы в базе данных?**
Отдельная структура (по умолчанию B-tree), которая хранит отсортированные значения столбца и ссылки на строки. Позволяет найти строки, не читая таблицу целиком: $O(\log n)$ вместо $O(n)$.
В PostgreSQL: **B-tree** (`=`, `<`, `>`, `BETWEEN`, `ORDER BY`, `LIKE 'abc%'`), **Hash** (только `=`), **GIN** (`jsonb`, массивы, полнотекстовый поиск), **GiST**, **BRIN** (огромные таблицы с естественным порядком). Составной индекс работает **по левому префиксу**: индекс `(a, b)` помогает запросу по `a` и по `a, b`, но не по одному `b`. → PostgreSQL

**Какие минусы у индексов?**
- **Замедляют запись**: каждый `INSERT`/`UPDATE`/`DELETE` обновляет **каждый** индекс таблицы.
- **Занимают место** — иногда больше самой таблицы.
- **Требуют обслуживания**: раздувание (bloat), `VACUUM`, `REINDEX`.
- **Планировщик может их не выбрать** — а статистика устареть, и тогда индекс есть, а толку нет.
- Создание на живой таблице **блокирует** запись (спасает `CREATE INDEX CONCURRENTLY`).

**Бывают ли кейсы, когда поиск по столбцу через `WHERE` есть, но индекс не нужен?**
Да, и их больше, чем кажется:
- **Таблица маленькая** — прочитать 200 строк последовательно дешевле, чем прыгать через индекс; планировщик сам выберет seq scan.
- 🔴 **Низкая селективность** — условие отбирает большую долю таблицы (`WHERE is_active = true`, где активны 95%). Случайный доступ по индексу к половине таблицы дороже, чем прочитать её подряд. Это главный ответ.
- **Запрос редкий** — отчёт раз в сутки не стоит того, чтобы платить за него каждой записью.
- **Столбец в составном индексе левым префиксом** — отдельный индекс избыточен.
- **Условие неиндексируемое как написано**: `WHERE lower(email) = …` без функционального индекса, приведение типа (`col::text = …`), ведущий `%` в `LIKE`, `!=`/`NOT IN`.
- Таблица «только пишется», а читается пакетно раз в период.

**На какие типы данных в столбцах не стоит накидывать индекс?**
Точнее — решает не тип, а **кардинальность и размер**:
- **Булев / enum из двух-трёх значений** — толку почти нет. Исключение: **частичный индекс** `CREATE INDEX … WHERE status = 'pending'`, когда нужных строк мало, а ищут только их.
- **Длинный текст / blob** — B-tree по большой строке дорог и упирается в лимит размера ключа; для текста нужен GIN по `tsvector`, а не B-tree.
- **`jsonb` целиком** — B-tree по документу бесполезен, нужен GIN или индекс по конкретному выражению.
- **Часто обновляемые столбцы** — каждый `UPDATE` переписывает индекс.
- Столбцы, по которым **никогда не фильтруют и не сортируют**.

**В чём разница между `EXPLAIN` и `EXPLAIN ANALYZE`?**
`EXPLAIN` показывает **план**, выбранный планировщиком, с **оценками** (`cost`, `rows`, `width`) — запрос **не выполняется**.
`EXPLAIN ANALYZE` **выполняет** запрос и добавляет фактические цифры: `actual time`, `actual rows`, `loops`.
🎯 Главная польза — сравнить **estimated rows с actual rows**: сильное расхождение означает устаревшую статистику (лечится `ANALYZE`) или плохо оцениваемое условие, и это корень большинства историй «почему не взял индекс».
⚠️ Практическая ловушка: `ANALYZE` **реально выполняет** запрос — `INSERT`/`UPDATE`/`DELETE` оборачивай в транзакцию с `ROLLBACK`. Полезная опция — `BUFFERS`: сколько страниц прочитано из кэша, а сколько с диска.

## Пагинация

**Как сделать постраничную выдачу и что в ней ломается на больших данных?**
Базовый вариант — `ORDER BY … LIMIT :n OFFSET (:page-1)*:n`. Ломаются две вещи:
1. **Скорость**: сложность $O(\text{offset}+\text{limit})$ — пропущенные строки база вычисляет и выбрасывает. На 10 млн строк `OFFSET 5 000 000` ≈ 758 мс против 0,6 мс на `OFFSET 1000`.
2. **Согласованность**: страницы пересчитываются заново, поэтому вставка в начало списка даёт **дубли** между страницами, удаление — **пропуски**.
Решение — keyset: «отдай строки после вот этой», а не «пропусти столько-то». → Пагинация — offset, keyset и гибрид

**🔴 Индекс же есть — почему `OFFSET` всё равно медленный?**
Главный вопрос темы. Индекс ускоряет поиск **значения**, а не отсчёт строк: порядковых номеров в B+-дереве не хранится, поэтому «строку номер 986 300» приходится искать проходом по листьям. В плане это видно так: узел `Limit` показывает `rows=20`, а вложенный `Index Scan` под ним — `actual rows=986320`. Формулировка «при большом offset индекс не используется» **неверна** — он используется, просто по нему идут пешком.

**Как выглядит keyset-запрос и почему в ключе два поля?**
```sql
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC LIMIT 20
```
Второе поле — уникальный **разрешитель ничьих**: без него две записи с одинаковым `created_at` дадут либо дубль, либо пропуск, потому что база не знает, какую из них клиент уже видел. Сравнение кортежей ложится на составной индекс `(created_at DESC, id DESC)` — нужен индекс, совпадающий с `ORDER BY` и по составу, **и по направлению**.

**Пользователь листает ленту и видит одну и ту же запись дважды. Где баг?**
Почти наверняка `OFFSET`-пагинация плюс активная вставка новых записей: окно едет, и строки, уже показанные на первой странице, съезжают на вторую. Второй кандидат — `ORDER BY` без уникального хвоста. Оба чинятся переходом на keyset; «починить», обернув в транзакцию, нельзя — страницы читаются разными запросами.

**Keyset не умеет прыгать на страницу 5000. Что делать, если номера страниц требуются?**
Гибрид: один тяжёлый запрос достаёт **одну** запись со смещением (`LIMIT 1 OFFSET 99980`) — её ключ становится **якорем**, дальше обычный keyset. Якоря кэшируют или считают фоном. Перед этим стоит спросить, нужны ли номера вообще: Elasticsearch по умолчанию просто запрещает уходить глубже `from + size = 10 000`, поисковики обрезают выдачу, ленты живут на бесконечном скролле.

**Как дёшево отдать «страница 3 из N»?**
Никак — точный `COUNT(*)` с фильтром сканирует все подходящие строки и часто дороже самой выдачи. Варианты: отдавать `has_more` вместо `total` (запросив `limit + 1` строку); приблизительная оценка (`reltuples` из `pg_class`, `rows` из `EXPLAIN`); кэш точного значения с TTL; «более 1000 результатов» без уточнения. Показательно, что GitHub не отдаёт `rel="last"`, когда не может его вычислить.

**🗣 Вопрос-ловушка: курсор кодируют в base64 — это ради безопасности?**
Нет. Base64 — обратимое кодирование без ключа, раскодировать его может кто угодно. Его роль — упаковать JSON в строку, безопасную для URL, и сделать позицию **непрозрачной для контракта**, чтобы клиент не начал её конструировать сам. Если подмена курсора опасна (внутри `user_id`), нужна **подпись HMAC**, а права всё равно проверяются на сервере. → Курсор в API — контракт пагинации

**🗣 Вопрос-ловушка: cursor-пагинация — это SQL-курсор?**
Нет, это разные вещи. **API-курсор** — строка в ответе, состояния на сервере не держит, между страницами сервер может перезапуститься. **SQL-курсор** (`DECLARE CURSOR`) живёт внутри транзакции, даёт согласованный снимок, но требует держать открытую транзакцию на каждого читателя — в веб-API не годится. Третье значение слова — `conn.cursor()` в psycopg, объект драйвера.

## UPSERT — связка из трёх вопросов

**Как реализовать запрос, который обновляет сущность, если она есть, или вставляет, если нет?**
```sql
INSERT INTO users (email, name) VALUES ($1, $2)
ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name
RETURNING id;
```
Обязательное условие — на конфликтующий столбец есть **уникальный индекс или ограничение**, иначе базе не по чему определять конфликт. `DO NOTHING` — если обновлять не надо. В PostgreSQL 15+ есть ещё стандартный `MERGE`.
Почему не «`SELECT` → `if` → `INSERT`/`UPDATE`» в коде: между `SELECT` и `INSERT` влезет другое соединение, и ты получишь либо `IntegrityError`, либо дубль. Это **гонка**, и чинится она только блокировкой или ретраем — то есть сложнее, чем один `ON CONFLICT`.

**Сколько SQL-запросов выполняется под капотом при такой операции?**
Здесь и валят — надо развести два уровня.
**Со стороны приложения — один statement, один round-trip.** Внутри базы это тоже **одна атомарная операция**, а не «`SELECT`, потом `INSERT`»: движок пытается вставить, нарушение уникального индекса перехватывается, и в той же транзакции выполняется `UPDATE` конфликтующей строки — под блокировкой этой строки.
Практический вывод, ради которого спрашивают: **`ON CONFLICT` снимает гонку именно потому, что проверка и запись — одно действие, защищённое уникальным индексом**, а не два разнесённых во времени запроса.

**Бэкенд обращается к базе один раз или два при использовании `ON CONFLICT`?**
**Один.** Одно обращение, один statement — в этом и смысл: два обращения дают и лишнюю сетевую задержку, и окно для гонки. Если нужен результат (id, обновлённая строка) — `RETURNING`, и данные придут тем же запросом.

## Асинхронность

**Какие способы параллельного или почти параллельного запуска кода в Python существуют?**
Формулировка «почти параллельного» — подсказка: спрашивают, понимаешь ли ты разницу между параллелизмом и конкурентностью.
- **`threading`** — потоки, но **GIL**: параллельно по CPU не выполняются. На I/O GIL отпускается ⇒ годится для I/O-bound.
- **`multiprocessing`** — процессы, свой интерпретатор у каждого ⇒ **настоящий параллелизм** для CPU-bound; цена — накладные расходы на запуск и сериализацию данных.
- **`concurrent.futures`** — единый интерфейс над обоими: `ThreadPoolExecutor` / `ProcessPoolExecutor`.
- **`asyncio`** — конкурентность **в одном потоке**, кооперативная: переключение только на `await`. Это и есть «почти параллельно».
- **Вне процесса**: очередь задач ([Celery](Библиотеки/Сторонние/Celery.md) + [RabbitMQ](Библиотеки/Сторонние/RabbitMQ.md)), несколько воркеров gunicorn/uvicorn.
- **Мимо GIL**: C-расширения и [numpy](Библиотеки/Сторонние/numpy.md) (внутри отпускают GIL), в 3.13+ — экспериментальная сборка без GIL.
Правило выбора: **I/O-bound → asyncio или потоки, CPU-bound → процессы**. → [CPU-bound против IO-bound](Библиотеки/Модули/Параллелизм/CPU-bound%20против%20IO-bound.md), Асинхронность и многопоточность

**В чём разница между coroutine и task?**
**Корутина** — объект, который возвращает вызов `async def`-функции. Сам по себе он **ничего не выполняет**: пока его не заавейтили или не отдали в event loop, это только описание работы (отсюда предупреждение `coroutine was never awaited`).
**Task** — обёртка над корутиной, уже **запланированная в event loop** (`asyncio.create_task`). Создание таски немедленно ставит корутину в очередь на выполнение и даёт хендл: `cancel()`, `done()`, `result()`, коллбэки.
Практическая разница в одну строку:
```python
await coro1(); await coro2()                    # последовательно: 100 + 100 = 200 мс
t1, t2 = asyncio.create_task(coro1()), asyncio.create_task(coro2())
await t1; await t2                              # конкурентно: ≈100 мс
```
**Task — это то, что превращает «асинхронный код» в «код, который работает одновременно».** → [Asyncio Event Loop и aiohttp](Библиотеки/Модули/Параллелизм/Asyncio%20Event%20Loop%20и%20aiohttp.md)

**Есть ли смысл в функции с несколькими `await` подряд?**
Продолжение предыдущего вопроса, и ответ «смотря какие».
**Смысл есть**, когда вызовы **зависимы** (второй нуждается в результате первого) или важен порядок (шаги сценария, транзакция).
**Смысла нет**, когда вызовы независимы: три `await` по 100 мс дают 300 мс, а `asyncio.gather(*coros)` — около 100. Это типичная ошибка: код асинхронный, а выигрыша нет.
Отдельно стоит сказать: `async def`, внутри которой нет ни одного настоящего `await` (или стоит **блокирующий** синхронный вызов), **хуже обычной функции** — она не отпускает event loop и вешает весь сервис. Блокирующее выносится в `asyncio.to_thread` / `run_in_executor`.

## Слои приложения и SQLAlchemy

**Как называются файлы, где лежит роут, где работа с базой и где промежуточное звено?**
Вопрос про **слои**, общепринятые имена в FastAPI-проекте:
- **роуты** — `routers/` (или `api/v1/endpoints/`); во Flask — `views.py` и блюпринты;
- **работа с базой** — `repository.py` / `crud.py` / `dao.py`; рядом `models.py` (таблицы) и `schemas.py` (pydantic-схемы);
- **промежуточное звено** — **`services/`**, сервисный слой с бизнес-логикой; в терминах чистой архитектуры — `use_cases/`.
Плюс `dependencies.py` (DI), `config.py`, `db.py`/`session.py`.
Смысл разделения формулируется так: **роутер знает про HTTP и ничего про SQL; репозиторий знает про SQL и ничего про HTTP; сервис знает бизнес-правила и не знает ни про то, ни про другое.** → Чистая архитектура и DDD, [REST API на FastAPI](Фреймворки/REST%20API%20на%20FastAPI.md)
⚠️ «Промежуточное звено» по-русски можно понять и как **middleware** — это другое (сквозная обработка запроса: логи, CORS, аутентификация). Уточняющий вопрос здесь уместен и идёт в плюс.

**Если нужно объединить данные пользователя и его чатов, куда класть этот код?**
В **сервисный слой**: это бизнес-операция над несколькими сущностями, и она не принадлежит ни роутеру (тот только принимает запрос и сериализует ответ), ни репозиторию (тот работает со своей таблицей).
Нюанс, который стоит проговорить самому: если объединение — это `JOIN` / `selectinload`, то **сам запрос делает репозиторий одним обращением** (иначе получишь классическую **N+1**: сначала пользователь, потом по запросу на каждый чат), а сервис уже собирает из этого ответ. То есть **SQL-объединение — в репозиторий, смысловая сборка — в сервис**.
Держать это в роутере — прямой путь к «толстым вьюхам»: логику нельзя переиспользовать и нельзя протестировать без HTTP.

**В каком стиле пишешь работу с базой: ORM или Core?**
Честный рабочий ответ: **ORM по умолчанию, Core точечно** — и главное объяснить границу.
ORM даёт identity map, отслеживание изменений, связи и заметно меньше кода. На **Core** или `text()` переходят там, где ORM мешает: массовые операции (bulk insert/update — объект на строку слишком дорого), тяжёлая аналитика с CTE и оконными функциями, специфика диалекта (`ON CONFLICT`), и случаи, когда SQL нужно видеть буквально.
Стоит упомянуть **стиль 2.0**: `select(User).where(...)` + `session.execute()` — единый API, который заметно стёр границу между ORM и Core. → [SQLAlchemy](Библиотеки/Сторонние/ORM/SQLAlchemy.md)

**Как обрабатываешь ошибки от SQLAlchemy, например нарушение уникальности?**
```python
try:
    session.add(user)
    await session.commit()
except IntegrityError as e:
    await session.rollback()
    raise UserAlreadyExists(user.email) from e   # доменная ошибка, роутер → 409
```
Четыре тезиса, которые тут и проверяют:
1. **`rollback()` обязателен.** После ошибки сессия непригодна, следующий же запрос упадёт с `PendingRollbackError`.
2. **Ловить, а не проверять заранее.** «Сначала `SELECT` — есть ли такой email» — та же гонка, что в вопросе про UPSERT. Правильный подход — EAFP: пробуем и ловим.
3. **Различать, какое ограничение упало**: `e.orig` даёт `UniqueViolation` psycopg с `constraint_name` — по нему маппишь на понятную ошибку API (**409**, а не 500).
4. **Наверх отдавать доменную ошибку**, а не `IntegrityError`: слой БД не должен протекать в роутер. → [Обработка ошибок Python](Ядро%20языка/Обработка%20ошибок%20Python.md)

**Как бы ты работал с ошибкой превышения лимита запросов к внешнему API — например, 60 запросов в минуту?**
Сверху вниз, от «не допустить» к «пережить»:
- **Ограничить себя на клиенте**: `asyncio.Semaphore` на конкурентность + **token bucket** на частоту (`aiolimiter`). Лимит известен заранее — глупо узнавать о нём из ошибок.
- **Слушать сервис**: `429 Too Many Requests` + заголовки `Retry-After`, `X-RateLimit-Remaining/Reset` — ждать столько, сколько сказали, а не гадать.
- **Ретраи с экспоненциальным backoff и jitter** (`tenacity`) — без джиттера все клиенты синхронно ударят в одну и ту же секунду.
- **Общий счётчик, если воркеров несколько**: локальный лимитер врёт при нескольких процессах — счётчик в [Redis](Библиотеки/Сторонние/Redis.md) (`INCR` + `EXPIRE` на окно).
- **Снизить сам спрос**: кэш ответов с TTL, батчинг, дедупликация одинаковых запросов, очередь задач — превратить пик в ровный поток.
- **Circuit breaker**: сервис лежит — перестать долбить, а не ретраить в стену. → Устойчивость — таймауты, ретраи, circuit breaker

## Тестирование

**Какие технологии для тестирования и что нужно учесть в приложении, чтобы его было легко тестировать?**
Технологии: **pytest** (+ `pytest-asyncio`), фикстуры, `unittest.mock`, `httpx.AsyncClient`/`TestClient` для API, `factory-boy` для данных, **testcontainers** для реальной БД в тестах, `coverage`.
Что должно быть **в самом приложении** — это и есть содержательная половина ответа:
- 🔴 **Внедрение зависимостей.** В FastAPI — `Depends` + `dependency_overrides` в тестах. Если сессия или HTTP-клиент создаются **внутри** функции, подменить их нечем, и тест обречён ходить в настоящую базу.
- **Слои** (см. выше) — бизнес-логику можно проверить без HTTP и без БД.
- **Конфиг из окружения**, отдельная тестовая база, никаких обращений к проду.
- **Детерминизм**: время и random — через инъекцию (`freezegun`), внешние API — замоканы.
- **Изоляция**: каждый тест в транзакции с откатом либо на чистой схеме.
- Чистые функции без скрытого глобального состояния. → [pytest](Библиотеки/Сторонние/Тесты/pytest.md), [Юнит-тестирование Python](Библиотеки/Сторонние/Тесты/Юнит-тестирование%20Python.md), [Интеграционные тесты и testcontainers](Библиотеки/Сторонние/Тесты/Интеграционные%20тесты%20и%20testcontainers.md), [Тестирование FastAPI-приложений](Фреймворки/Тестирование%20FastAPI-приложений.md)

**Если ограничено время, что приоритизировать: тесты базы данных или тесты API, с которым работают пользователи?**
**Тесты API.** Три аргумента:
1. API — **контракт с пользователем**; его поломку видит он, а не ты.
2. Тест API проходит **насквозь** через все слои (роут → сервис → репозиторий → БД), то есть попутно покрывает и работу с базой. Обратное неверно.
3. Ошибки чаще живут **на стыках слоёв и в бизнес-логике**, а не в том, что `SELECT` не выберет строку.
Оговорка, которую и хотят услышать: **что из БД всё-таки тестируют отдельно** — миграции, уникальные ограничения и каскады, сложные запросы с агрегатами и оконными функциями, транзакционность. То есть приоритет — API, но точечные тесты БД остаются там, где логика живёт в самой базе.

**В чём ключевое отличие стабов и моков?**
**Стаб отвечает, мок ещё и следит.**
- **Stub** подставляет заранее заданный ответ, чтобы тест мог идти дальше. Проверка — **по состоянию/результату**. Сам провалить тест не может.
- **Mock** проверяет **взаимодействие**: что метод вызвали, столько-то раз, с такими аргументами (`assert_called_once_with`). Проверка — **по поведению**, и мок может провалить тест сам.
Рядом стоит назвать соседей: **fake** — рабочая упрощённая реализация (SQLite вместо Postgres, словарь вместо кэша); **spy** — настоящий объект, который дополнительно записывает вызовы; **dummy** — заглушка, нужная только чтобы заполнить аргумент. → [Юнит-тестирование Python](Библиотеки/Сторонние/Тесты/Юнит-тестирование%20Python.md)

**Пример алгоритма с алгоритмической сложностью $O(\cdot)$**
⚠️ Вопрос в записи усечён — какой именно класс спрашивали, неизвестно. Держи всю линейку, чтобы ответить на любой:

| Сложность | Пример |
|---|---|
| $O(1)$ | доступ по индексу в массиве, поиск в [хеш-таблице](Данные/Структуры%20данных/Хеш-таблица.md) |
| $O(\log n)$ | бинарный поиск, вставка в [кучу](Алгоритмы/Иные/Двоичная%20куча%20и%20очередь%20с%20приоритетом.md) |
| $O(n)$ | линейный проход, поиск максимума, [Два указателя](Алгоритмы/Приёмы/Два%20указателя.md) |
| $O(n \log n)$ | сортировка слиянием, Timsort, сортировка + жадный проход |
| $O(n^2)$ | вложенные циклы, пузырьковая сортировка, наивные пары |
| $O(2^n)$ | перебор подмножеств, наивные числа Фибоначчи без мемоизации |
→ Вычислительная сложность

**Написал ДП сверху вниз с `@lru_cache`, на больших `n` падает `RecursionError`. Что не так и как чинить?**
Кэш убирает **повторные** вызовы, но не глубину: цепочка `f(n) → f(n-1) → …` остаётся. Отдельно с Python 3.12 `sys.setrecursionlimit` **не поднимает** глубину рекурсии через `lru_cache` — декоратор написан на C, а C-рекурсия ограничена своим счётчиком (замер: 999 против 49 998 у ручного `dict`). Правильный ответ — **переписать снизу вверх**, там стека нет; временные меры — ручной словарь вместо декоратора или прогрев кэша шагами. → [Мемоизация](Алгоритмы/Приёмы/Мемоизация.md)

**Чем плох `@lru_cache` на методе класса?**
Кэш общий на класс, `self` входит в ключ — экземпляр остаётся жив, пока запись не вытеснится. В долгоживущем сервисе это утечка. Замены: кэш на внутренней функции, `@cached_property` (если аргументов нет), вынести чистую функцию из класса. → [functools](Библиотеки/Модули/Функциональные%20инструменты/functools.md)

**Какая сложность у наивного `fib`?**
Экспоненциальная. Если хочется точности: вызовов ровно $2F(n+1)-1$, то есть $\Theta(\varphi^n)$, $\varphi \approx 1{,}618$ — запись $O(2^n)$ верна как верхняя граница, но завышена. Follow-up обычно про то, как дойти до $O(n)$ и $O(1)$ по памяти, а дальше — до $O(\log n)$ через возведение матрицы в степень. → [Итерация](Алгоритмы/Стратегии/Итерация.md)

## Аутентификация, JWT и микросервисы

Самая длинная связка собеседования — девять вопросов, и они выстроены лесенкой: от «что такое auth» до «как проверить токен, не имея секретного ключа». Разберись в асимметричной подписи — и вся вторая половина связки отвечается одним механизмом. → [JWT — подпись и проверка токенов](JWT%20—%20подпись%20и%20проверка%20токенов.md)

**Как реализовать аутентификацию и авторизацию в сервисе?**
Сначала развести понятия: **аутентификация — кто ты** (проверка личности), **авторизация — что тебе можно** (проверка прав). Порядок всегда такой.
Реализация: хранить не пароль, а **хеш** (bcrypt/argon2 с солью, → [hashlib](Библиотеки/Модули/Безопасность%20и%20интернет/hashlib.md)) → логин выдаёт сессию в куке **или** пару токенов → на каждом запросе зависимость/middleware достаёт токен, валидирует и кладёт `current_user` → авторизация поверх: роли и права (**RBAC**) либо проверка владения объектом («эта запись твоя?»). В FastAPI — `Depends(get_current_user)` и вложенные зависимости под роли. → [Разделение доступа в DRF](Фреймворки/DJANGO/Разделение%20доступа%20в%20DRF.md), [Oauth 2.0](Библиотеки/Сторонние/Работа%20с%20WEB/Oauth%202.0.md)

**Что за пара токенов в JWT?**
**Access** — короткоживущий (5–15 минут), с ним ходят на защищённые эндпоинты; содержит `sub`, `exp`, роли; сервер его не хранит.
**Refresh** — долгоживущий (дни-недели), умеет ровно одно: обменяться на новую пару.
Зачем два: компромисс между «не спрашивать пароль каждые 15 минут» и «уметь отозвать доступ». Утёкший access протухнет сам, утёкший refresh можно отозвать.
Продвинутая деталь, которая хорошо звучит: **ротация refresh** — при обмене старый инвалидируется. Если пришёл уже использованный refresh, это признак кражи, и отзывается вся цепочка токенов пользователя (reuse detection).

**Почему refresh-токен хранится более безопасно и где?**
Не «сам по себе безопаснее» — его **специально кладут туда, куда не дотянется JS**:
- **HttpOnly cookie** + `Secure` + `SameSite=Lax/Strict` + `Path=/auth/refresh`. `HttpOnly` значит `document.cookie` его не видит ⇒ XSS не украдёт; `Path` сужает: кука уходит только на эндпоинт обновления, а не с каждым запросом.
- **Access** при этом держат в памяти JS (переменная), а не в `localStorage`.
- `localStorage` для обоих — антипаттерн: любой XSS = кража.
- На сервере refresh хранят **хешем**, как пароль, с привязкой к устройству/сессии — чтобы утечка базы не давала доступ.
Цена: раз кука уходит автоматически, возвращается **CSRF** — отсюда `SameSite` и/или CSRF-токен на `/refresh`. → [Веб-безопасность](Веб-безопасность.md)

**Какие способы есть достать refresh-токен из HTTP-only cookie?**
🎯 Правильный ответ: **из JavaScript — никак, в этом весь смысл `HttpOnly`.** Браузер сам приложит куку к запросу на нужный path (`fetch(url, {credentials: 'include'})`), но прочитать значение страница не может.
Читают её только двое: **браузер** при отправке и **бэкенд** — из заголовка `Cookie` (в FastAPI `Cookie(...)` или `request.cookies`).
Что иногда называют «способами» и почему это атаки, а не приёмы: **XSS не читает** HttpOnly-куку, но может дёрнуть `/refresh` от имени пользователя и забрать новый access — то есть `HttpOnly` снижает ущерб, но не отменяет XSS; MITM без HTTPS и без флага `Secure`; расширения браузера и devtools (у пользователя доступ есть, у страницы — нет).
Вывод для интервью: **если тебе понадобилось прочитать refresh из JS — архитектура неверна.** Обновление делается запросом на бэкенд, который читает куку сам.

**Какие минусы у JWT по сравнению с сессиями?**
- 🔴 **Нельзя отозвать.** Подписанный токен валиден до `exp`; забанил пользователя — он ещё 15 минут работает. Лечится чёрным списком или коротким TTL, но это уже состояние на сервере — то есть отказ от главного плюса.
- **Данные в токене устаревают**: сменились роли — в токене прежние.
- **Размер**: JWT в разы больше session id и летит в каждом запросе.
- **Payload не секретен**: это base64, а не шифр. **Подпись ≠ шифрование**, персональные данные туда класть нельзя.
- **Легко испортить реализацию**: `alg: none`, путаница HS256/RS256, невалидация `exp`/`aud`/`iss`, слабый секрет.
- **Хранение на клиенте** — см. предыдущий вопрос.
Плюсы сессий: мгновенный отзыв, маленькая кука, всегда свежие данные; минус — общее хранилище и его доступность.
Честный вывод: **JWT выигрывает там, где сервисов много и общее хранилище сессий дорого; в обычном монолите сессии часто проще и безопаснее.**

**Как работает аутентификация в микросервисах с использованием JWT?**
Отдельный **сервис авторизации** выдаёт подписанный токен при логине. Дальше каждый сервис **проверяет подпись сам**, никуда не ходя, — и это главный выигрыш: нет общего узкого места и лишнего сетевого вызова на каждый запрос.
Обычно перед сервисами стоит **API gateway**: валидирует токен один раз, отсекает заведомо невалидное и прокидывает внутрь уже разобранный контекст (`X-User-Id`). Внутренний трафик при этом защищают отдельно (**mTLS**), иначе подделать такой заголовок сможет любой, кто попал в сеть.
Ключевой момент, ради которого и спрашивают: **подпись должна быть асимметричной**. Приватный ключ — только у сервиса авторизации, у остальных публичный. С общим секретом любой из десяти сервисов может выпустить токен от чьего угодно имени. → Монолит и микросервисы, Взаимодействие сервисов

**Как валидировать, что токен не фишинговый?**
«Не фишинговый» = выпущен тем, кем должен, **для тебя**, и не подделан. Одной подписи мало:
- **подпись** валидным ключом и **алгоритм из белого списка** — `jwt.decode(..., algorithms=["RS256"])`. Иначе классическая атака: злоумышленник ставит `alg: none` либо подменяет RS256 на HS256 и подписывает токен **твоим же публичным ключом**, который библиотека примет за секрет;
- **`iss`** — токен выпущен твоим издателем;
- **`aud`** — предназначен твоему сервису, а не соседнему;
- **`exp`**, `nbf`, `iat` — не истёк, уже действителен, не из будущего;
- **`kid`** — каким ключом подписан (нужно для ротации);
- **`jti`** + список отозванных — если нужен отзыв;
- канал — **HTTPS**: иначе токен перехватят по дороге, и валидность ничего не значит.
И режимное: токен берут **из заголовка `Authorization`**, не из URL, и никогда не пишут в логи.

**Как валидировать токен в микросервисах, если секретный ключ недоступен?**
В этом и смысл асимметрии: **секретный ключ для проверки не нужен.** Токен подписан **приватным** ключом издателя (RS256/ES256), а проверяется **публичным** — его можно раздать всем сервисам без риска.
Как публичный ключ попадает в сервис:
- 🎯 **JWKS** — стандартный путь: издатель публикует `/.well-known/jwks.json` со списком публичных ключей и их `kid`; сервис скачивает и кэширует, при ротации подтягивает новый ключ по незнакомому `kid`;
- ключ в конфиге или секрет-хранилище — проще, но ротация ручная.
Если же токен **непрозрачный** (opaque, не JWT) — подпись проверить нечем, и остаётся **интроспекция**: спросить у сервиса авторизации через `/introspect`, валиден ли токен. Ценой сетевого вызова на каждый запрос — отсюда и следующий вопрос.

**Есть ли способы снизить нагрузку на сервис авторизации при проверке токенов?**
- 🔴 **Не ходить к нему вообще** — асимметричная подпись и локальная проверка. Это главный ответ, остальное — добавки.
- **Кэшировать JWKS** по `kid` с TTL, а не тянуть ключи на каждый запрос.
- **Кэшировать результат интроспекции** на короткий TTL, если токены opaque.
- **Валидировать один раз на шлюзе**, внутрь передавать разобранный контекст.
- **Короткий access + долгий refresh** — обращения к сервису авторизации только при обновлении.
- Список отозванных держать в Redis рядом с сервисом, а не запросом в auth.
- Горизонтально масштабировать сам сервис — но это называют **последним**, а не первым.

**Как работает проверка JWT-токена с использованием публичного и приватного ключей?**
1. JWT — три части через точку: `header.payload.signature`. Первые две — **просто base64url**, читает кто угодно.
2. Издатель считает подпись от строки `base64(header) + "." + base64(payload)` **приватным** ключом (RSA/ECDSA) — фактически подписывает её SHA-256-хеш.
3. Получатель берёт **публичный** ключ (из JWKS по `kid`), пересчитывает хеш пришедшей строки и проверяет, что подпись ей соответствует.
4. Сошлось — значит: **(а)** токен выпущен владельцем приватного ключа, **(б)** ни один байт не менялся. Не сошлось — отбой.
Почему это лучше HS256: проверяющему достаточно публичного ключа, **выпускать токены он не может**. С общим секретом всякий, кто умеет проверять, умеет и подделывать — в микросервисах это неприемлемо.
⚠️ И ещё раз: **подпись не шифрует**. Payload читается кем угодно, секреты в токен не кладут. → Криптография и безопасность, [HTTPS и обмен ключами Диффи — Хеллмана](Алгоритмы/Иные/HTTPS%20и%20обмен%20ключами%20Диффи%20—%20Хеллмана.md)

**🔴 Перечисли методы аутентификации.**
Вопрос-фильтр: слабый ответ валит в один список Basic, JWT, OAuth и SSO — а это три разных уровня. Сильный ответ раскладывает по слоям. **Методы по схеме HTTP** (`WWW-Authenticate` → `Authorization`): Basic (логин и пароль в base64), Digest (хеш от пароля и nonce), Bearer (предъявительский токен). **Методы вне схемы**: API-ключи (передаются где угодно) и сессии (работают через cookie). **Уровнем выше — не методы аутентификации вовсе**: OAuth 2.0 (делегирование доступа), OIDC (надстройка, добавляющая личность), SSO (свойство системы), SAML/OIDC (протоколы доверия между сторонами). → [Аутентификация — методы и протоколы](Аутентификация%20—%20методы%20и%20протоколы.md)

**🗣 Вопрос-ловушка: Bearer-токен и JWT — это одно и то же?**
Нет. **Bearer — способ передать** токен (`Authorization: Bearer <строка>`), **JWT — формат самого токена**. В Bearer кладут что угодно: случайную строку, JWT, зашифрованный blob. Разница практическая: случайная строка требует похода в хранилище, зато отзывается мгновенно; JWT проверяется локально, но отозвать его нечем.

**Чем API-ключ отличается от токена?**
Выдаётся заранее, без входа; обычно не истекает; не самодостаточен — сервер всё равно идёт в хранилище. Главная беда: утечка не обнаруживается, ключ работает, пока кто-то не заметит. Что должно быть: срок жизни и ротация (их вводят руками), область действия, отдельный ключ на интеграцию, и хранение **хеша** ключа, а не самого ключа.

**Сессии или токены — что выбрать?**
Сессии платят обращением к хранилищу за **мгновенный отзыв** и свежие данные; JWT платят **невозможностью отзыва** за локальную проверку и отсутствие общего хранилища. Классическому веб-приложению чаще подходят сессии, распределённой системе и мобильным клиентам — токены. Гибрид «короткий access + серверный refresh» и есть попытка получить оба свойства.

**Чем сегодня хешируют пароли и с какими параметрами?**
**Argon2id** по умолчанию (OWASP: минимум 19 МиБ памяти, 2 итерации, 1 поток), **bcrypt** — приемлемо при факторе трудоёмкости не ниже 10, PBKDF2 — если требует сертификация. Соль генерирует сама библиотека и кладёт внутрь строки хеша. ⚠️ Две детали, которые ценят: bcrypt **обрезает пароль на 72 байтах**, а сравнивать хеши через `==` нельзя — нужно сравнение постоянного времени. Миграцию параметров делают при входе через `check_needs_rehash`. → [Пароли — хранение и проверка](Пароли%20—%20хранение%20и%20проверка.md)

## Инструменты

**Расскажи про Airflow: зачем нужен этот инструмент, почему он появился, как его использовать**
**Зачем:** оркестратор пакетных пайплайнов — планирует, запускает и отслеживает задачи с зависимостями. Пайплайн описывается **кодом на Python** как **DAG** — направленный граф задач без циклов.
**Почему появился:** cron не умеет зависимостей («B после A, но только если A успела»), не даёт видимости (что упало, где, когда), не умеет ретраи, бэкфилл и параметризацию по дате. Разросшийся набор cron-скриптов становится неуправляемым — Airflow (Airbnb, 2014) вырос ровно из этой боли.
**Как использовать:** файл с DAG и расписанием, задачи — операторы (`PythonOperator`, `BashOperator`, сенсоры), зависимости через `>>`. Планировщик создаёт DAG run на каждый интервал, воркеры выполняют задачи (Celery/Kubernetes executor), UI показывает статусы и логи. Ключевое: ретраи, SLA, **бэкфилл** за прошлые даты, XCom для передачи небольших значений.
**Чего Airflow не делает** — и это спрашивают следом: он не считает данные сам (считают Spark и БД, он дирижирует), не для потоковой обработки в реальном времени (там Kafka/Flink) и не для задач раз в секунду.
🔁 И здесь возвращается **первый вопрос собеседования**: задача Airflow обязана быть **идемпотентной**, потому что ретраи и бэкфилл — норма, а не авария. → [Airflow](Библиотеки/Сторонние/Airflow.md)
