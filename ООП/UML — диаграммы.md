# UML — диаграммы

**UML** (Unified Modeling Language) — стандартный язык **графического моделирования** программ: единая нотация, чтобы нарисовать структуру и поведение системы так, чтобы её понял любой в команде. Появился в 1990-х, объединив разрозненные нотации (OMT, Booch, OOSE), стандарт консорциума OMG.

> Смысл не в красивых картинках, а в **общем языке**: одна диаграмма классов заменяет страницу описания и не даёт двусмысленности. Проектируешь и обсуждаешь до кода — правки на схеме дешевле правок в коде.

Диаграммы делятся на две семьи: **структурные** (что есть в системе) и **поведенческие** (что происходит). Для бэкендера главные — диаграмма классов и диаграмма последовательности.

## Диаграмма классов

Основная структурная диаграмма ООП. Класс — прямоугольник из трёх секций: имя, атрибуты, методы. Видимость: `+` public, `−` private, `#` protected.

```
┌────────────────────┐
│      Account       │   ← имя (курсив = абстрактный класс)
├────────────────────┤
│ − balance: float   │   ← атрибуты
├────────────────────┤
│ + deposit(sum)     │   ← методы
│ + withdraw(sum)    │
└────────────────────┘
```

### Отношения между классами

Самое важное и то, что спрашивают: чем связаны классы и какой стрелкой это рисуют.

| Отношение | Нотация | Смысл | Пример |
|---|---|---|---|
| **Обобщение** (наследование) | сплошная + пустой треугольник к родителю | «является» (is-a) | `Dog ─▷ Animal` |
| **Реализация** (интерфейса) | пунктир + пустой треугольник | класс реализует интерфейс/ABC | `PayPal ┈▷ Payment` |
| **Ассоциация** | сплошная линия/стрелка | объекты связаны, знают друг о друге | `Order ── Customer` |
| **Агрегация** | пустой ромб у «целого» | «имеет», часть **живёт без** целого | `Team ◇── Player` |
| **Композиция** | закрашенный ромб у «целого» | «состоит из», часть **не живёт без** целого | `House ◆── Room` |
| **Зависимость** | пунктир со стрелкой | использует временно (параметр, локальная переменная) | `Report ┄> DateFormatter` |

**Кратность (multiplicity)** у концов связи: `1`, `0..1`, `*` (любое число), `1..*` (один и более). _`Order 1 ── * Item` — у заказа много позиций._

> **Агрегация vs композиция** — классический вопрос. Разница в **времени жизни части**: у агрегации часть переживает целое (игрок остаётся, если распустить команду), у композиции — умирает вместе с ним (комнаты исчезают со сносом дома). Композиция — «сильное владение».

## Диаграмма последовательности (sequence)

Поведенческая: показывает **взаимодействие во времени**. Объекты — сверху, их «линии жизни» идут вниз (время), горизонтальные стрелки — сообщения (вызовы) между ними.

```
Client        Service        DB
  │              │            │
  │─ request() ─▶│            │
  │              │─ query() ─▶│
  │              │◀─ rows ────│
  │◀─ result ────│            │
```

Удобна, чтобы описать сценарий (например, обработку HTTP-запроса или оплату) по шагам.

## Другие диаграммы

- **Use case (вариантов использования)** — акторы (пользователи/системы) и что они делают с системой; описывает требования «снаружи».
- **Activity (деятельности)** — блок-схема бизнес-процесса или алгоритма (ветвления, параллельность).
- **State (состояний)** — состояния объекта и переходы между ними (заказ: создан → оплачен → отправлен).
- **Component / Deployment** — компоненты системы и их размещение на серверах (ближе к архитектуре).

## Когда применять

- **До кода** — обсудить дизайн, договориться о границах ([Принципы ООП в Python](../ООП/Принципы/Принципы%20ООП%20в%20Python.md), [Паттерны проектирования](../ООП/Паттерны/Паттерны%20проектирования.md)).
- **Документация** — диаграмма классов/последовательности объясняет систему новому человеку быстрее текста.
- **Не переусердствуй** — рисуй то, что проясняет, а не всю систему «для галочки». Диаграмма устаревает, если её не поддерживать.

> Родственная нотация из книги «банды четырёх» (GoF) — **OMT**, предшественник UML; в ней описаны паттерны в [Справочник — глоссарий и нотация](../ООП/Паттерны/Справочник%20—%20глоссарий%20и%20нотация.md). Для данных используют **ER-диаграммы** — Базы данных.
