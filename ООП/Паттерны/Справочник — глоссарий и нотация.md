# Справочник — глоссарий и нотация

> Единый словарь терминов и нотация схем, используемых при описании паттернов GoF.

Связанные файлы: [Паттерны проектирования](../../ООП/Паттерны/Паттерны%20проектирования.md) · [Принципы ООП в Python](../../ООП/Принципы/Принципы%20ООП%20в%20Python.md)

### Глоссарий ключевых терминов

|Термин|Определение|
|---|---|
|**Паттерн проектирования**|Именованное, мотивированное решение типичной задачи проектирования в конкретном контексте|
|**Абстрактный класс**|Класс, чьё единственное назначение — определить интерфейс; экземпляров не имеет|
|**Конкретный класс**|Класс без абстрактных операций; может иметь экземпляры|
|**Абстрактная операция**|Объявляет сигнатуру, но не реализует её (чисто виртуальная функция в C++)|
|**Интерфейс**|Набор всех сигнатур операций объекта; описывает множество запросов, на которые объект может ответить|
|**Тип**|Имя конкретного интерфейса|
|**Подтип**|Тип A является подтипом B, если интерфейс A содержит интерфейс B|
|**Сигнатура**|Имя операции + параметры + возвращаемое значение|
|**Динамическое связывание**|Ассоциация между запросом и операцией объекта, устанавливаемая в рантайме|
|**Полиморфизм**|Способность подставлять во время выполнения объект с совместимым интерфейсом|
|**Наследование**|Определение одного класса в терминах другого; включает наследование интерфейса и реализации|
|**Инкапсуляция**|Сокрытие представления и реализации объекта; доступ только через операции|
|**Делегирование**|Объект перенаправляет запрос другому объекту (уполномоченному), который выполняет его от имени первого|
|**Композиция объектов**|Объединение нескольких объектов для получения более сложного поведения|
|**Агрегат**|Объект, составленный из подобъектов; агрегат отвечает за части|
|**Осведомлённость**|Класс A знает о классе B, если имеет ссылку на него (слабее, чем агрегирование)|
|**Абстрактная связанность**|A абстрактно связан с B, если ссылается на тип, а не на конкретный объект|
|**Примесь (Mixin)**|Класс, спроектированный для сочетания с другими через наследование; обычно абстрактен|
|**Параметризованный тип**|Тип с неопределёнными составляющими (шаблон в C++, дженерик)|
|**Каркас**|Набор взаимодействующих классов, определяющих повторно используемый дизайн; он вызывает код разработчика|
|**Инструментальная библиотека**|Набор классов с полезной функциональностью; разработчик вызывает её код|
|**Прозрачный ящик**|Повторное использование через наследование — подкласс видит внутренности родителя|
|**Чёрный ящик**|Повторное использование через композицию — объекты не раскрывают внутреннее устройство|
|**Рефакторинг**|Реорганизация существующего кода без изменения внешнего поведения|
|**Протокол**|Интерфейс + допустимая последовательность запросов|

### Нотация схем (OMT)

> Здесь — **OMT**, нотация из книги «банды четырёх». Современный отраслевой стандарт — **UML** (обобщение/реализация/ассоциация/агрегация/композиция, диаграммы классов и последовательности): [UML — диаграммы](../../ООП/UML%20—%20диаграммы.md).

#### Схема классов

```
┌─────────────────────┐
│      ClassName      │  ← имя жирным; курсив = абстрактный
├─────────────────────┤
│ operation()         │  ← операции (курсив = абстрактная)
│ abstractOp()        │
├─────────────────────┤
│ _variable: Type     │  ← переменные экземпляра
└─────────────────────┘
```

#### Отношения между классами

|Отношение|Обозначение|Пример|
|---|---|---|
|Наследование|Линия с треугольником к родителю|`Dog → Animal`|
|Агрегирование|Линия со стрелкой + ромбик у агрегата|`Drawing ◇─→ Shape`|
|Осведомлённость|Линия со стрелкой (без ромбика)|`Client ──→ Strategy`|
|Создание экземпляра|Пунктирная линия со стрелкой|`Factory - - → Product`|
|Несколько объектов|Заполненный кружок у стрелки|`Drawing ◇─●→ Shape`|

#### Схема объектов (рантайм)

Прямоугольники с закруглёнными углами. Имя объекта: `aClassName`. Стрелки — ссылки на другие объекты.

#### Схема взаимодействий

Время идёт сверху вниз. Вертикальная линия — время жизни объекта. Горизонтальная стрелка — запрос. Пунктир → создание. Вертикальный прямоугольник → объект активен (обрабатывает запрос).

### Два принципа объектно-ориентированного проектирования

> **Программируй в соответствии с интерфейсом, а не с реализацией.** Не объявляй переменные как экземпляры конкретных классов. Придерживайся абстрактного типа — клиент не зависит от деталей и не знает, что стоит за интерфейсом.

> **Предпочитай композицию наследованию.** Наследование статично и нарушает инкапсуляцию. Композиция динамична — объекты знают только интерфейсы друг друга. Применяй наследование осознанно, а не по умолчанию.

### Жизненный цикл проекта и паттерны

**Прототипизация** — быстро создаётся работающий прототип. Основной инструмент — наследование («прозрачный ящик»).

**Экстенсивный рост** — добавляются новые требования, классы и иерархии. Система разрастается.

**Консолидация (рефакторинг)** — система реорганизуется: классы декомпозируются, наследование заменяется композицией («чёрный ящик»). Здесь часто появляются каркасы.

> Паттерны, применённые на ранних стадиях, **сокращают необходимость** рефакторинга в будущем. Даже если паттерн не был применён сразу — он подскажет, как изменить систему позже.

### Что даёт знание паттернов

**Единый словарь.** Вместо описания архитектуры на низком уровне достаточно назвать паттерн: «применяем Наблюдатель» или «это Стратегия».

**Документирование.** Код, описанный через паттерны, понять гораздо проще, чем восстанавливать архитектуру по исходникам.

**Цель рефакторинга.** Паттерны показывают, к какой структуре стремиться при реорганизации кода.

### Наследование класса vs наследование интерфейса

| |Наследование класса|Наследование интерфейса|
|---|---|---|
|**Суть**|Повторное использование реализации|Определение подтипа|
|**Что передаётся**|Код и данные|Только контракт|
|**Связанность**|Высокая|Низкая|
|**Пример**|`class Admin(User)`|`class Dog(Animal)` где `Animal` — абстрактный|

### Когда НЕ применять паттерн

Паттерн — не серебряная пуля. Каждый добавляет сложность: новые классы, косвенные вызовы, дополнительные объекты.

Применяй паттерн, только если гибкость **действительно нужна** сейчас или с высокой вероятностью понадобится, и сложность **оправдана** выгодой.

Если класс создаваемого экземпляра никогда не изменится — не нужна Абстрактная фабрика. Если алгоритм фиксирован — не нужна Стратегия.
