# Принципы ООП в Python

> ООП — парадигма программирования, где код организован вокруг **объектов**: сущностей, сочетающих данные (атрибуты) и поведение (методы). Python поддерживает ООП полностью, но не навязывает его — можно смешивать с функциональным и процедурным стилями.

### Четыре принципа

|Принцип|Суть|Файл|
|---|---|---|
|**Абстракция**|Показать только нужное, скрыть детали. Определить _что_ делает объект|[Абстракция Python](../../ООП/Принципы/Абстракция%20Python.md)|
|**Инкапсуляция**|Данные и методы в одном объекте. Контроль доступа через интерфейс|[Инкапсуляция Python](../../ООП/Принципы/Инкапсуляция%20Python.md)|
|**Наследование**|Подкласс получает всё от родителя. Переиспользование и расширение кода|[Наследование Python](../../ООП/Принципы/Наследование%20Python.md)|
|**Полиморфизм**|Одна операция — разное поведение у разных объектов|[Полиморфизм Python](../../ООП/Принципы/Полиморфизм%20Python.md)|

### Как принципы связаны

```
Абстракция → определяет интерфейс (что делает объект)
     ↓
Инкапсуляция → скрывает реализацию (как это работает внутри)
     ↓
Наследование → переиспользует и расширяет (подкласс — это родитель + добавления)
     ↓
Полиморфизм → позволяет писать обобщённый код (один вызов — разные реализации)
```

### Класс и объект — базовые понятия

**Класс** — шаблон, описывающий структуру и поведение. **Объект** — конкретный экземпляр класса.

```python
class Пользователь:              # класс — шаблон
    def __init__(self, имя):
        self.имя = имя           # атрибут экземпляра
        self.активен = True

    def приветствие(self):       # метод
        return f"Привет, {self.имя}!"

иван = Пользователь("Иван")     # объект — экземпляр класса
аня = Пользователь("Аня")       # другой объект того же класса

иван.приветствие()   # → "Привет, Иван!"
аня.приветствие()    # → "Привет, Аня!"
```

### Зачем класс, если можно функциями и модулями

Резонный вопрос: логику можно разложить по функциям, а функции — по модулям. Зачем классы?

**Класс — фабрика, производящая объекты.** Он описывает шаблон, а по нему создаётся **сколько угодно независимых экземпляров**, у каждого — своё состояние. Модуль же существует в единственном экземпляре (импортируется один раз), поэтому «много одинаковых, но со своими данными» на модулях не сделать.

Ключевое отличие — **класс связывает состояние и поведение вместе**. Без класса состояние приходится таскать между функциями руками:

```python
# функциями: состояние (баланс) снаружи, его передают в каждую функцию
def пополнить(баланс, сумма):  return баланс + сумма
def снять(баланс, сумма):      return баланс - сумма
баланс = 0
баланс = пополнить(баланс, 100)   # состояние живёт отдельно, легко забыть/испортить

# классом: состояние и операции — в одном объекте, много независимых счетов
class Счёт:
    def __init__(self):     self.баланс = 0
    def пополнить(self, x): self.баланс += x

a, b = Счёт(), Счёт()       # два независимых экземпляра, у каждого свой баланс
a.пополнить(100)            # b.баланс не тронут
```

**Бери класс, когда:**

- нужно **много экземпляров** с собственным состоянием (счета, игроки, соединения);
- **данные и поведение** логично держать вместе и защищать инварианты ([инкапсуляция](../../ООП/Принципы/Инкапсуляция%20Python.md));
- нужен **полиморфизм** — взаимозаменяемые реализации за общим интерфейсом ([Полиморфизм Python](../../ООП/Принципы/Полиморфизм%20Python.md), [ABC](../../ООП/Принципы/Абстракция%20Python.md));
- моделируешь **сущность** предметной области (Пользователь, Заказ, Фигура).

**Хватит функций/модуля, когда:**

- логика **без состояния** — вход → выход (утилиты, преобразования, вычисления);
- нужно просто **сгруппировать функции и константы** в пространство имён — для этого модуль и есть ([Модули и пакеты Python](../../Ядро%20языка/Модули%20и%20пакеты%20Python.md));
- **один экземпляр** на всю программу — модуль сам по себе синглтон.

> Не заворачивай в класс то, что могло быть функцией. Класс с одним методом и без состояния (`class Помощник: def сделать(self): ...`) — обычно замаскированная функция. Классы оправданы состоянием, полиморфизмом или инвариантами, а не сами по себе.

### Всё — объект

В Python каждое значение — объект: число, строка, функция, класс, модуль. Все они имеют тип (`type()`), атрибуты и методы.

```python
type(42)         # → <class 'int'>
type("текст")    # → <class 'str'>
type(int)        # → <class 'type'>

(42).__add__(1)  # → 43  — число тоже объект с методами
"abc".upper()    # → "ABC"
```

### Атрибуты класса vs атрибуты экземпляра

```python
class Счётчик:
    всего = 0           # атрибут класса — общий для всех экземпляров

    def __init__(self, имя):
        Счётчик.всего += 1
        self.имя = имя  # атрибут экземпляра — свой у каждого

a = Счётчик("a")
b = Счётчик("b")

Счётчик.всего   # → 2  (общий)
a.имя           # → "a" (свой)
b.имя           # → "b" (свой)
```

### Методы: instance, class, static

Три вида методов отличаются ровно одним: **что метод получает первым аргументом** — и отсюда следует всё остальное.

```python
class Пример:
    значение = 0

    def метод_экземпляра(self):      # self — конкретный объект
        return self.значение

    @classmethod
    def метод_класса(cls):           # cls — сам класс
        return cls.значение

    @staticmethod
    def статический():              # нет self и cls
        return "просто функция в классе"
```

| Вид | Первый аргумент | Видит | Когда брать |
|---|---|---|---|
| **Обычный** | `self` — экземпляр | данные экземпляра **и** класса | 95% случаев: поведение зависит от состояния объекта |
| **`@classmethod`** | `cls` — сам класс | только данные класса | **альтернативный конструктор**; счётчики и реестры на уровне класса |
| **`@staticmethod`** | — | ничего | утилита, логически принадлежащая классу, но не трогающая ни `self`, ни `cls` |

> **Главный вопрос на секции: зачем `cls`, если можно написать имя класса?** Затем, что `cls` — это **фактический** класс, а не тот, где метод объявлен. При наследовании `cls` подставит подкласс, и метод продолжит работать. Захардкоженное имя класса вернёт родителя — и наследование сломается (пример ниже).

> `@staticmethod` — сигнал «этому методу класс не нужен». Если таких методов много, класс, возможно, был замаскированным [модулем](../../Ядро%20языка/Модули%20и%20пакеты%20Python.md) — см. [раздел выше](../../ООП/Принципы/Принципы%20ООП%20в%20Python.md#зачем-класс-если-можно-функциями-и-модулями).

### Альтернативные конструкторы — `@classmethod`

У класса **один** `__init__`, но входных форматов бывает много: строка, словарь, файл, timestamp. Перегрузки конструктора, как в Java/C++, в Python нет. Питонический ответ — **альтернативный конструктор**: `@classmethod`, который приводит вход к нужному виду и возвращает `cls(...)`.

```python
class Точка:
    def __init__(self, x, y):        # единственный настоящий конструктор
        self.x, self.y = x, y

    @classmethod
    def из_строки(cls, s):           # альтернативный вход: "1,2"
        x, y = map(int, s.split(","))
        return cls(x, y)             # cls, а не Точка!

    @classmethod
    def из_словаря(cls, d):
        return cls(d["x"], d["y"])

Точка.из_строки("1,2")               # → Точка(1, 2)
```

**Почему именно `cls`, а не `Точка`** — вот цена ошибки:

```python
class Точка3D(Точка):
    pass

# ПРАВИЛЬНО: return cls(x, y)
Точка3D.из_строки("3,4")   # → Точка3D(3, 4)  — подкласс сохранён

# НЕПРАВИЛЬНО: return Точка(x, y)
Точка3D.из_строки("3,4")   # → Точка(3, 4)    — вернул РОДИТЕЛЯ, наследование сломано
```

Стандартная библиотека построена на этом приёме — по имени `from_*` / `from*` его и узнают:

```python
date.fromisoformat("2026-07-16")   # → date(2026, 7, 16)
dict.fromkeys("ab", 0)             # → {'a': 0, 'b': 0}
int.from_bytes(b'\x01\x00')        # → 256
```

> **Именуй по входу, а не по действию:** `from_json`, `from_csv`, `fromtimestamp`. Читатель сразу видит, из чего собирается объект.

**Перегрузка по типу — `singledispatchmethod`.** Когда конструктор один, а поведение должно зависеть от **типа** аргумента, `functools.singledispatchmethod` (Python 3.8+) выбирает реализацию по аннотации — вместо лестницы `if isinstance(...)`:

```python
from functools import singledispatchmethod

class Т:
    def __init__(self, v):
        self.v = v

    @singledispatchmethod
    @classmethod
    def создать(cls, arg):
        raise TypeError(f"нет перегрузки для {type(arg)}")

    @создать.register
    @classmethod
    def _(cls, arg: int):
        return cls(arg)

    @создать.register
    @classmethod
    def _(cls, arg: str):
        return cls(len(arg))

Т.создать(5).v        # → 5
Т.создать("abcd").v   # → 4  — выбрал перегрузку по типу str
```

> Диспетчеризация идёт **только по первому аргументу** и только по его типу — отсюда «single». Для двух-трёх форматов обычные `@classmethod` с говорящими именами проще и читаемее; `singledispatchmethod` берут, когда типов много и хочется убрать `isinstance`-лестницу. Функциональный аналог для обычных функций — [`functools.singledispatch`](../../ООП/Принципы/Полиморфизм%20Python.md#python-не-поддерживает-перегрузку-методов).

### Обработка исключений в контексте ООП

Исключения в Python — тоже объекты. Их иерархия построена через наследование:

|Вид|Описание|Пример|
|---|---|---|
|**Непроверяемые**|Нельзя предвидеть, падают в рантайме|`IndexError`, `ZeroDivisionError`|
|**Проверяемые**|Могут возникнуть в правильном коде|`FileNotFoundError`|

```python
class ОшибкаПриложения(Exception):   # своё исключение — тоже объект
    pass

class ОшибкаВалидации(ОшибкаПриложения):
    def __init__(self, поле, сообщение):
        self.поле = поле
        super().__init__(f"[{поле}] {сообщение}")
```

Подробнее — в [Обработка ошибок Python](../../Ядро%20языка/Обработка%20ошибок%20Python.md) и [Ошибки Python](../../Ядро%20языка/Ошибки%20Python.md).

### Сколько методов в классе — это нормально?

Жёсткого числа нет — ориентир не количество, а **связность**: все методы должны крутиться вокруг одной ответственности ([SRP](../../ООП/Принципы/SOLID%20Python.md)). Сигналы, что класс распух:

- методы делятся на несмежные группы, работающие с разными полями → класс делает несколько дел, разбей его;
- «God object» на десятки методов, знающий про всё → тоже к разделению.

Мало методов — тоже нормально: класс с одним методом и без состояния часто стоит сделать [функцией](../../ООП/Принципы/Принципы%20ООП%20в%20Python.md#зачем-класс-если-можно-функциями-и-модулями). Считай не методы, а **причины для изменения**.

### Два ключевых принципа проектирования

> **Программируй в соответствии с интерфейсом, а не с реализацией.** Используй абстрактные типы — клиент не зависит от деталей реализации.

> **Предпочитай композицию наследованию.** Наследование статично. Композиция динамична — объекты взаимодействуют через интерфейсы.

### SOLID — принципы проектирования классов

Четыре принципа выше отвечают на вопрос «из чего состоит ООП». **SOLID** — пять правил Роберта Мартина о том, как проектировать классы, чтобы код оставался гибким: легко менялся и расширялся, не ломаясь.

|Буква|Принцип|Суть|
|---|---|---|
|**S**|Единственная ответственность|Один класс — одна причина для изменения|
|**O**|Открытость/закрытость|Расширяй новым кодом, не меняй старый|
|**L**|Подстановка Лисков|Подтип подставляется вместо базового без сюрпризов|
|**I**|Разделение интерфейсов|Много узких интерфейсов лучше одного толстого|
|**D**|Инверсия зависимостей|Зависим от абстракций, деталь передаётся снаружи|

Подробно, с примерами «нарушение → фикс» на Python — [SOLID Python](../../ООП/Принципы/SOLID%20Python.md). Все пять нарушений сразу в одном живом сервисе и пошаговый разбор — [SOLID на практике — рефакторинг сервиса](../../ООП/Принципы/SOLID%20на%20практике%20—%20рефакторинг%20сервиса.md).

### Откуда взялись эти четыре принципа

Первым языком с классами, подклассами и виртуальными методами была **Simula 67** (Оле-Йохан Даль и Кристен Нюгор, Норвежский вычислительный центр). Сам термин «объектно-ориентированное программирование» ввёл **Алан Кэй** около 1967 года и воплотил его в Smalltalk.

Любопытно, что Кэй вкладывал в термин **не то**, что перечисляет таблица выше. В письме от 23 июля 2003 года он определил ООП так: обмен сообщениями, локальное хранение и защита состояния-процесса, крайне позднее связывание всего. **Ни наследования, ни полиморфизма в его определении нет** — позже он говорил, что жалеет о слове «объекты», потому что главная идея была в сообщениях.

Отсюда два практических вывода:

- **«Четыре принципа» — учебная рамка, а не канон первоисточника.** Полезная для объяснения, но не список, которому нужно соответствовать: код не становится хуже оттого, что в нём нет наследования.
- **Python в этом смысле ближе к исходной идее, чем Java.** Позднее связывание (метод ищется в рантайме), сокрытие по соглашению вместо `private`, [утиная типизация](../../ООП/Принципы/Полиморфизм%20Python.md#утиная-типизация-duck-typing) вместо обязательного общего предка — это ровно то, что Кэй считал сутью, а «жёсткая иерархия классов» — то, что наросло вокруг.
