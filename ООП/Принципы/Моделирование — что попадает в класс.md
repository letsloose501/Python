# Моделирование — что попадает в класс

Прежде чем написать класс, нужно решить, **что в него войдёт**. У реальной сущности признаков бесконечно много, в классе их будет пять-десять. Выбор делает не сущность, а **задача**: один и тот же «автомобиль» в гоночной игре и в навигаторе — два разных класса, и это не небрежность, а правильный результат.

## Проблема: «класс описывает объект реального мира»

Так объясняют ООП в каждом учебнике, и объяснение работает ровно до первого настоящего класса. Оно подсказывает вопрос **«какие свойства есть у машины?»** — а у него нет ответа. Объём двигателя, объём бака, тип резины, аэродинамика, число подстаканников, сколько мешков картошки влезет в багажник. Список не заканчивается, и ни одного основания предпочесть одно другому в нём нет.

Рабочий вопрос звучит иначе: **что об этой машине нужно знать конкретной программе**.

> Класс моделирует не вещь, а **роль вещи в задаче**. Поэтому «правильного» класса `Машина` не существует — существует правильный класс `Машина` для навигатора и другой правильный класс `Машина` для гонок.

## Одна сущность — разные классы

Гоночная игра. Важно всё, что определяет, кто победит:

```python
class Car:                                   # гонки
    def __init__(self, top_speed, acceleration, drift, color, tuning):
        self.top_speed = top_speed           # крутость и шанс на победу
        self.acceleration = acceleration
        self.drift = drift
        self.color = color                   # игрок это видит
        self.tuning = tuning
```

Навигатор. Цвет, дрифт и тюнинг не влияют ни на один сценарий — их нет:

```python
class Car:                                   # навигатор
    def __init__(self, position, speed):
        self.position = position             # где на карте
        self.speed = speed                   # чтобы посчитать время прибытия
```

Общее поле формально одно — скорость, но и она означает разное: в гонках это характеристика мощности, в навигаторе — множитель для расчёта ETA. Двигатель, топливо и коробка передач в игре свёрнуты в одно число `top_speed`: тонкости устройства на исход гонки не влияют. Это **не** урезанная версия «настоящего» класса — это две независимые модели одной предметной сущности.

## Критерий: поле оправдано сценарием

Практическое правило, отсекающее спор «а вдруг пригодится»:

> Поле остаётся в классе, если **хотя бы один сценарий программы его читает**. Поле, которое только заполняют в конструкторе и больше нигде не трогают, — мусор.

Отсюда порядок работы, обратный привычному: сначала выписываешь, **что программа должна уметь**, и только потом собираешь поля, без которых эти действия не выполнить.

```
Как обычно делают                Как надо
─────────────────                ────────
«Что бывает у машины?»           «Что программа делает с машиной?»
   ↓ список свойств                 ↓ список сценариев
   ↓ класс с 20 полями              ↓ проложить маршрут, показать ETA
   ↓ 15 из них никто не читает      ↓ нужны: позиция, скорость
                                    ↓ класс с 2 полями
```

Признаки, что модель разъехалась с задачей:

- **лишнее поле** — присваивается в `__init__`, не читается нигде;
- **недостающее поле** — сценарию нужны данные, которых в объекте нет, и их таскают отдельным параметром через всю цепочку вызовов;
- **поле-приставка** — заполняется только для одного частного случая, у остальных объектов `None`.

Это же — академический подход **responsibility-driven design** Ребекки Вирфс-Брок: проектирование начинается с вопроса «за какие действия объект отвечает», а не «какие данные он хранит». Противоположный ему data-driven подход (сначала поля, потом методы вокруг них) она прямо называет причиной слабой инкапсуляции — детали реализации выходят наружу раньше, чем становится ясен интерфейс.

## Два разных смысла слова «абстракция»

Слово одно, вещи разные, и путаница между ними — источник вопроса «зачем мне ABC, я и так скрыл поля».

| | **Абстракция-процесс** | **Абстракция-артефакт** |
|---|---|---|
| Что это | решение, что войдёт в модель | абстрактный класс или интерфейс в коде |
| Когда происходит | при проектировании, до кода | при написании кода |
| Вопрос | что существенно **для этой задачи** | какой контракт обязаны выполнить наследники |
| Инструмент | сценарии, ответственности | [`ABC`](../../ООП/Принципы/Абстракция%20Python.md#абстрактные-классы--abc), `@abstractmethod`, [`Protocol`](../../ООП/Принципы/Полиморфизм%20Python.md#typingprotocol--явные-протоколы-python-38) |
| Типичная ошибка | «моделируй реальный мир» | ABC ради ABC, интерфейс с одной реализацией |

Учебники и вводные ролики про ООП под «абстракцией» почти всегда имеют в виду **первое**; заметка [Абстракция Python](../../ООП/Принципы/Абстракция%20Python.md) и Python-инструменты — **второе**. Оба смысла законны, но решают разные задачи: первый определяет, **какие** классы вообще будут, второй — **как** зафиксировать договор между уже придуманными.

## Тот же принцип на масштабе системы

На уровне одного класса это «что попадает в поля». На уровне системы — **Bounded Context** из DDD: граница, внутри которой термин значит одно. «Клиент» в контексте продаж (лид, воронка, LTV) и «клиент» в доставке (адрес, вес посылки, окно доставки) — разные модели, и склеивать их в один класс «на всё» не нужно.

Фаулер описывает это на примере энергокомпании, где слово «счётчик» в разных отделах означало разные вещи: в разговоре двусмысленность сглаживается, в коде — нет. Вывод DDD прямой: полная унификация модели большой системы недостижима и невыгодна; вместо неё — несколько моделей и отображение между ними.

```
Гонки                          Навигатор
Car: top_speed, drift, tuning  Car: position, speed
   └──── общее только имя ────┘
```

Подробно — Bounded Context — главная идея (стратегический DDD).

## Ловушки

**Класс «на всё».** Попытка написать одну универсальную `Машину`, годную и для гонок, и для навигатора, и для автосалона. Получается [God object](../../ООП/Принципы/SOLID%20Python.md): сорок полей, из которых каждый сценарий использует пять, и ни одной причины, по которой поле можно было бы удалить.

**Иерархия по биологии, а не по поведению.** Прямое следствие установки «моделируй реальный мир»: `Penguin` наследуют от `Bird`, потому что в зоологии пингвин — птица. В коде это ложное обещание — пингвин подставляется вместо птицы и роняет всё, что вызывает `fly()`. Разбор с фиксом — [SOLID Python](../../ООП/Принципы/SOLID%20Python.md#l--liskov-substitution-подстановка-лисков).

> Наследование отвечает на вопрос «**взаимозаменяемы ли они в моём коде**», а не «родственники ли они в природе». Родство в предметной области — повод присмотреться к иерархии, но не основание её строить.

**Структура БД вместо модели.** Класс собирают по колонкам таблицы. Тогда моделью управляет не задача, а способ хранения, и в домен протекает знание про БД — см. анемичную модель и «ORM-модель = доменная модель».

**Преждевременное обобщение.** Поля «пусть будут, вдруг понадобятся». Каждое из них нужно инициализировать, сериализовать, тестировать и объяснять следующему читателю — а сценария у них нет. Дешевле добавить поле, когда сценарий появится.
