# Наследование Python

> Наследование — механизм, при котором один класс (подкласс, child) получает все атрибуты и методы другого (суперкласс, parent). Позволяет не дублировать общий код: выноси его в базовый класс, расширяй в потомках.

### Базовый синтаксис

```python
class Животное:
    def __init__(self, имя, звук):
        self.имя = имя
        self._звук = звук

    def говорить(self):
        return f"{self.имя} говорит: {self._звук}"

    def есть(self):
        return f"{self.имя} ест"

class Собака(Животное):             # наследует от Животное
    def апортировать(self):         # новый метод — только у Собаки
        return f"{self.имя} принёс мяч"

class Кошка(Животное):
    def мурлыкать(self):
        return f"{self.имя} мурлычет"

# Собака получила __init__, говорить(), есть() бесплатно
пёс = Собака("Рекс", "Гав!")
пёс.говорить()      # → "Рекс говорит: Гав!"  (метод из Животное)
пёс.апортировать()  # → "Рекс принёс мяч"      (свой метод)
```

### isinstance() и issubclass()

```python
пёс = Собака("Рекс", "Гав!")

isinstance(пёс, Собака)    # → True
isinstance(пёс, Животное)  # → True — потому что Собака наследует Животное
isinstance(пёс, Кошка)     # → False

issubclass(Собака, Животное)  # → True
issubclass(Собака, object)    # → True — все классы в Python наследуют object
```

### Наследование — не копирование

Вводные курсы часто описывают наследование так: «в классе-наследнике появляется невидимая копия всех полей и функций базового класса». Модель наглядная, но неверная, и проверяется одной строкой:

```python
class Base:
    hp = 100
    def hit(self): return "бам"

class Goblin(Base):
    def sneak(self): return "крадусь"

[k for k in Goblin.__dict__ if not k.startswith('_')]   # → ['sneak']   ← ни hp, ни hit
Goblin().hit()                                          # → 'бам'       ← но вызов работает
```

Копии нет. В `Goblin` лежит **только то, что в нём написано**, плюс ссылка на родителя в `__bases__`. Не найдя атрибут в самом классе, Python идёт вверх по цепочке [MRO](../../ООП/Принципы/Наследование%20Python.md#mro--порядок-разрешения-методов) — **в момент обращения**, а не при объявлении класса. Отсюда четыре эффекта, которые в модели «копия» необъяснимы.

**1. Базовый класс можно менять после объявления наследника** — правку увидят даже созданные раньше объекты:

```python
g = Goblin()
Base.hit = lambda self: "базу поменяли"
g.hit()             # → 'базу поменяли'  ← объект существовал ДО правки
Base.mana = 50
Goblin().mana       # → 50               ← поля не было ни в одном наследнике
```

На этом держатся monkey patching и подмена методов в тестах ([`unittest.mock.patch`](../../Библиотеки/Сторонние/Тесты/Юнит-тестирование%20Python.md)).

**2. Изменяемый атрибут класса — один на всю иерархию.** Самая дорогая ловушка отсюда:

```python
# НЕПРАВИЛЬНО
class Character:
    inventory = []                        # список создан ОДИН раз, при выполнении тела класса
    def take(self, item): self.inventory.append(item)

class Zombie(Character): pass
class Elf(Character): pass

z, e = Zombie(), Elf()
z.take("меч")
e.inventory                                          # → ['меч']  ← эльф видит добычу зомби
z.inventory is e.inventory is Character.inventory    # → True     ← это один объект
```

```python
# ПРАВИЛЬНО — изменяемое состояние принадлежит экземпляру
class Character:
    def __init__(self):
        self.inventory = []               # свой список у каждого объекта
```

Причина та же, что у [изменяемого значения по умолчанию](../../Ядро%20языка/Функции%20Python.md#значения-по-умолчанию): объект создан однажды, а `append` меняет его на месте. Неизменяемым атрибутам класса (`hp = 100`) это не грозит — их не мутируют, а переприсваивают.

**3. Присваивание не меняет класс, а заслоняет его.** Запись в экземпляр создаёт **свой** атрибут поверх классового; исходный остаётся нетронутым и снова становится виден после `del`:

```python
z = Zombie()
z.hp = 1
z.hp, Zombie.hp, z.__dict__     # → (1, 100, {'hp': 1})   ← у класса по-прежнему 100
del z.hp
z.hp                            # → 100                   ← «тень» убрана
```

Тот же порядок поиска действует и для методов: переопределение в подклассе не стирает родительский метод, а перекрывает его — потому `super()` и может до него дотянуться.

**4. Глубина иерархии не замедляет вызов.** Ожидание «чем длиннее цепочка, тем дольше поиск» не подтверждается — _замер на CPython 3.13, 2 млн вызовов_:

| Где объявлен метод | Время | Длина MRO |
|---|---|---|
| в собственном классе | 0,042 с | 2 |
| через 5 уровней наследования | 0,042 с | 7 |

Разницы нет, потому что CPython кэширует результат поиска атрибута по паре «версия типа + имя». Кэш сбрасывается через `tp_version_tag`, когда тип меняют, — то есть цену платят не за глубину, а за правку класса в рантайме.

> Практический вывод: глубокая иерархия плоха [сложностью для читателя](../../ООП/Принципы/Наследование%20Python.md#многоуровневое-наследование), а не скоростью. Оптимизировать иерархию ради производительности незачем.

### Переопределение методов (override)

Подкласс может **переопределить** метод родителя — написать свою версию с тем же именем:

```python
class Животное:
    def говорить(self):
        return "..."

class Собака(Животное):
    def говорить(self):        # переопределяем — заменяем поведение
        return "Гав!"

class Кошка(Животное):
    def говорить(self):
        return "Мяу!"

пёс = Собака()
кот = Кошка()
пёс.говорить()   # → "Гав!"  — вызвался метод Собаки, не Животного
кот.говорить()   # → "Мяу!"
```

### super() — вызов метода родителя

`super()` — вызвать метод **следующего класса по MRO**, а не просто «родителя». При одиночном наследовании это и есть прямой родитель.

#### Расширение **init**

```python
class Работник:
    def __init__(self, имя, зарплата):
        self.имя = имя
        self.зарплата = зарплата

class Менеджер(Работник):
    def __init__(self, имя, зарплата, отдел):
        super().__init__(имя, зарплата)  # инициализируем родителя
        self.отдел = отдел               # добавляем своё

м = Менеджер("Иван", 100000, "Продажи")
м.имя      # → "Иван"     (от Работник)
м.отдел    # → "Продажи"  (своё)
```

#### Расширение метода

```python
class Животное:
    def описание(self):
        return f"Животное: {self.имя}"

class Собака(Животное):
    def описание(self):
        базовое = super().описание()   # вызвали метод родителя
        return f"{базовое}, порода: {self.порода}"  # добавили своё
```

### Множественное наследование

Python позволяет наследоваться от нескольких классов одновременно:

```python
class Летающее:
    def летать(self):
        return "Лечу"

class Плавающее:
    def плыть(self):
        return "Плыву"

class Утка(Летающее, Плавающее):   # от обоих
    pass

утка = Утка()
утка.летать()   # → "Лечу"
утка.плыть()    # → "Плыву"
```

### MRO — порядок разрешения методов

Когда Python ищет метод — он идёт по **MRO** (Method Resolution Order): списку классов в определённом порядке. Алгоритм — **C3-линеаризация**: идёт **слева направо и вглубь**, но с двумя правилами — класс всегда стоит **перед** своими родителями, а общий предок **откладывается**, пока не пройдены все его потомки.

> **BFS или DFS?** Ни то, ни другое в чистом виде. Старые классы Python 2 использовали простой поиск **в глубину** слева направо (и ломались на ромбе). Новые (Python 3, C3) — это «слева направо, вглубь, но родитель после всех потомков»: ближе к интуиции «сначала вбок по родителям, потом вверх», чем к чистому BFS или DFS.

```python
class A:
    def метод(self): return "A"

class B(A):
    def метод(self): return "B"

class C(A):
    def метод(self): return "C"

class D(B, C):   # ромбовидное наследование (diamond problem)
    pass

D.mro()
# → [D, B, C, A, object]
# Python ищет: сначала D → B → C → A → object

D().метод()   # → "B"  — нашёл в B, дальше не пошёл
```

```python
# Посмотреть MRO любого класса:
print(D.__mro__)        # кортеж
print(D.mro())          # список
```

**Правило C3:** класс всегда идёт до своих родителей. Среди нескольких родителей — порядок как в объявлении.

### super() в множественном наследовании

`super()` — это **не** «вызвать родителя», это «вызвать следующий класс по MRO». При множественном наследовании это важно: `super()` делает наследование **кооперативным** — каждый класс вызывает следующего по цепочке.

```python
class A:
    def __init__(self):
        print("A.__init__")
        super().__init__()  # вызывает следующего по MRO

class B(A):
    def __init__(self):
        print("B.__init__")
        super().__init__()  # вызывает следующего по MRO — это C, не A!

class C(A):
    def __init__(self):
        print("C.__init__")
        super().__init__()

class D(B, C):
    def __init__(self):
        print("D.__init__")
        super().__init__()

# D.mro() → [D, B, C, A, object]
D()
# → D.__init__
# → B.__init__
# → C.__init__  ← super() в B вызвал C, а не A!
# → A.__init__
```

> `super()` в B вызвал C — не потому что C родитель B, а потому что C следующий в MRO класса D. Поэтому каждый класс в цепочке обязан вызывать `super()`, иначе цепочка прервётся.

### Mixin — добавление поведения без наследования

**Mixin** — небольшой класс, добавляющий одну конкретную способность. Не предназначен для самостоятельного использования.

```python
class JSONMixin:
    """Mixin: добавляет сериализацию в JSON"""
    def to_json(self):
        import json
        return json.dumps(self.__dict__)

    @classmethod
    def from_json(cls, json_str):
        import json
        данные = json.loads(json_str)
        obj = cls.__new__(cls)
        obj.__dict__.update(данные)
        return obj

class LogMixin:
    """Mixin: добавляет логирование методов"""
    def _log(self, сообщение):
        print(f"[{type(self).__name__}] {сообщение}")

class TimestampMixin:
    """Mixin: добавляет поля created_at и updated_at"""
    def __init__(self, *args, **kwargs):
        from datetime import datetime
        super().__init__(*args, **kwargs)
        self.created_at = datetime.now()
        self.updated_at = datetime.now()

# Комбинирование миксинов:
class Пользователь(TimestampMixin, JSONMixin, LogMixin):
    def __init__(self, имя, email):
        super().__init__()   # вызовет TimestampMixin.__init__
        self.имя = имя
        self.email = email

u = Пользователь("Иван", "ivan@example.com")
u.to_json()   # от JSONMixin
u._log("создан")  # от LogMixin
u.created_at  # от TimestampMixin
```

**Соглашение по именованию:** миксины обычно заканчиваются на `Mixin` или `able` (Serializable, Loggable).

#### Mixin или ABC — что выбрать

Оба подмешиваются в класс через наследование, поэтому их путают. Разница — в направлении: **миксин даёт, ABC требует**.

| | **Mixin** | **ABC** ([абстрактный класс](../../ООП/Принципы/Абстракция%20Python.md#абстрактные-классы--abc)) |
|---|---|---|
| Что несёт | **готовую реализацию** | **контракт** — список обязательных методов |
| Что делает с подклассом | добавляет способность | заставляет реализовать `@abstractmethod` |
| Экземпляр сам по себе | бессмысленен (но создастся) | **невозможен** — `TypeError` |
| Отвечает на вопрос | «что объект *умеет дополнительно*» | «что объект *обязан* уметь» |

```python
# Mixin — приносит готовый to_json(), ничего не требуя взамен
class JSONMixin:
    def to_json(self): return json.dumps(self.__dict__)

# ABC — сам ничего не приносит, но обязывает реализовать площадь()
class Фигура(ABC):
    @abstractmethod
    def площадь(self): ...
```

> Признак, что нужен **ABC**: хочешь гарантию, что метод существует, и полиморфно вызывать его у всех потомков. Признак **миксина**: один и тот же готовый код нужен нескольким несвязанным классам, а общего предка у них нет. Их **сочетают**: ABC задаёт контракт, миксины добавляют опциональные способности.

### __init_subclass__ — перехват создания подкласса

Вызывается автоматически при создании **любого** подкласса. Позволяет базовому классу реагировать на своих потомков.

```python
class Плагин:
    _реестр = {}

    def __init_subclass__(cls, имя=None, **kwargs):
        super().__init_subclass__(**kwargs)
        if имя:
            Плагин._реестр[имя] = cls

class ПлагинA(Плагин, имя="a"):
    pass

class ПлагинB(Плагин, имя="b"):
    pass

Плагин._реестр   # → {"a": ПлагинA, "b": ПлагинB}
```

### Что наследуется, что нет

```python
class Родитель:
    атрибут_класса = "общий"   # наследуется

    def __init__(self):
        self.атрибут_экземпляра = "своё"  # наследуется через super().__init__()

    def публичный_метод(self): ...        # наследуется
    def _защищённый(self): ...            # наследуется (соглашение)
    def __приватный(self): ...            # НЕ наследуется напрямую — name mangling!
    @staticmethod
    def статический(self): ...           # наследуется
    @classmethod
    def метод_класса(cls): ...           # наследуется
```

`__приватный` не наследуется напрямую — он переименован в `_Родитель__приватный`, поэтому в подклассе его нет под тем же именем. Это и есть защита инкапсуляции при наследовании.

### Смена класса на лету — `__class__`

Класс объекта можно переприсвоить в рантайме через `obj.__class__`. Меняются только **методы** (их источник — класс), а **данные экземпляра** (в `obj.__dict__`) остаются на месте, и `__init__` нового класса **не вызывается**:

```python
obj = A()
obj.__class__ = B     # методы теперь от B; но obj.x (от A) остался, obj.y нет
```

Приём легальный, но экзотический — обычно источник трудноуловимых багов. Полный разбор, почему так — в [Ловушки Python](../../Ядро%20языка/Ловушки%20Python.md#смена-класса-объекта-на-лету--__class__).

### Многоуровневое наследование

```python
class Сущность:          # уровень 1
    def сохранить(self): ...

class Пользователь(Сущность):  # уровень 2
    def войти(self): ...

class Администратор(Пользователь):  # уровень 3
    def удалить_всё(self): ...

# Администратор.mro() → [Администратор, Пользователь, Сущность, object]
```

> Глубокая иерархия (>3 уровней) — сигнал пересмотреть дизайн. Часто лучше композиция.

### Наследование vs Композиция

```python
# Наследование: "является" (is-a)
class Менеджер(Работник): ...   # Менеджер — это Работник

# Композиция: "имеет" (has-a)
class Отдел:
    def __init__(self):
        self.работники = []     # Отдел имеет Работников
```

**Предпочитай композицию наследованию** (принцип из GoF): наследование статично и нарушает инкапсуляцию (подкласс видит детали родителя). Композиция динамична — объекты взаимодействуют через интерфейсы.

```python
# Проблема наследования: Engine знает детали Vehicle
class Vehicle:
    def _internal_start(self): ...   # подкласс может случайно сломать

class Car(Vehicle): ...

# Решение через композицию:
class Engine:
    def start(self): ...

class Car:
    def __init__(self):
        self._engine = Engine()  # Engine скрыт — Car не знает деталей
```

> Подробнее о том, как наследование поддерживает полиморфизм: [Полиморфизм Python](../../ООП/Принципы/Полиморфизм%20Python.md). О защите `__` атрибутов при наследовании: [Инкапсуляция Python](../../ООП/Принципы/Инкапсуляция%20Python.md).

> Что именно потомок обязан сохранить, чтобы наследование не превратилось в ложное обещание, — вариантность аргументов и результата плюс поведенческие правила: [SOLID Python](../../ООП/Принципы/SOLID%20Python.md#шесть-правил-лисков--винг). Из шести правил mypy проверяет два — те, что про типы; остальные, включая исключения, только человек.
