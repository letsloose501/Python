# Композиционный корень

> Инверсия зависимостей отвечает на вопрос «откуда объект берёт зависимость» — снаружи. Но зависимости всё равно кто-то должен создать. **Где** — на этот вопрос отвечает композиционный корень.

---

**Композиционный корень (composition root)** — единственное место в программе, где создаются конкретные реализации и связываются друг с другом. Всё остальное приложение работает только с абстракциями и получает готовые объекты снаружи. Термин ввёл Марк Симан в 2011 году.

Правило одной строкой: **создавай зависимости как можно ближе к точке входа, используй — как можно глубже**.

```
точка входа  ─────▶  здесь и только здесь: PostgresRepo(), HttpClient(), Config()
    │
    ▼
сервисы      ─────▶  принимают готовое, знают только контракты
    │
    ▼
доменная логика ──▶  вообще не знает, что существуют БД и HTTP
```

## Зачем

Когда конкретные классы создаются по всему коду, каждое такое место — отдельная точка привязки:

```python
# БЕЗ КОРНЯ — привязка размазана по проекту
class OrderService:
    def __init__(self):
        self.db = PostgresRepo(settings.DSN)     # привязка №1

class ReportService:
    def __init__(self):
        self.db = PostgresRepo(settings.DSN)     # привязка №2

def cleanup_job():
    db = PostgresRepo(settings.DSN)              # привязка №3
```

Сменить хранилище — обойти проект и найти все три. В проекте на 200 000 строк это не поиск, а археология. Собранные в одном месте, те же три строки превращаются в одну правку:

```python
# С КОРНЕМ — привязка одна
def main() -> None:
    repo = PostgresRepo(settings.DSN)            # ← единственное место
    order_service = OrderService(repo)
    report_service = ReportService(repo)
    run(order_service, report_service)
```

Заодно решается вторая задача: **корень — это точка подмены**. В тестах вместо `PostgresRepo` подставляется заглушка, и делать это можно честным аргументом, а не `unittest.mock.patch` по строковому пути импорта ([моки](../../Библиотеки/Сторонние/Тесты/Юнит-тестирование%20Python.md#изоляция-и-моки)). Патчинг ломается при любом переезде модуля, аргумент — нет.

## Куда девать неизбежное ветвление

Полностью убрать `if` из кода нельзя: выбор провайдера по стране, выбор бэкенда по конфигу, разное поведение в dev и prod — это реальная логика. Смысл принципа не в том, чтобы ветвление исчезло, а в том, чтобы оно **жило на краю, а не в середине**:

```python
def main() -> None:
    storage = S3Storage(...) if settings.ENV == "prod" else LocalStorage(...)
    service = UploadService(storage)     # сервис про два варианта не знает вообще
```

Правило: чем глубже в приложении меняется код, тем выше риск сломать соседнее. Правка на верхнем уровне видна вся целиком и дешевле в [ревью](../../Код-ревью.md).

## Как выглядит в разных средах

| Среда | Где корень |
|---|---|
| Скрипт, CLI | функция `main()` перед запуском логики |
| [FastAPI](../../Фреймворки/REST%20API%20на%20FastAPI.md) | `lifespan` для долгоживущих ресурсов + [`Depends`](../../Фреймворки/Depends%20—%20зависимости%20в%20FastAPI.md) для запроса; подмена — `dependency_overrides` |
| [Django](../../Фреймворки/DJANGO/Django.md) | `settings.py` и `AppConfig.ready()`; фреймворк собирает объекты сам |
| [Celery](../../Библиотеки/Сторонние/Celery.md) | сигнал `worker_process_init` — у воркера свой корень, отдельный от веб-приложения |
| [pytest](../../Библиотеки/Сторонние/Тесты/pytest.md) | `conftest.py`: фикстуры и есть тестовый композиционный корень |

> У приложения бывает **несколько корней** — по одному на точку входа: веб-процесс, воркер очереди, cron-скрипт, тесты. Это нормально: общее выносят в фабрику, вызывают из каждого корня.

## Чем не является

**Не Service Locator.** Локатор — глобальный объект, у которого спрашивают зависимость посреди кода: `container.get(Repo)`. Внешне похоже на DI, по сути — та же жёсткая привязка, только спрятанная: по сигнатуре класса больше не видно, что ему нужно, и в тестах приходится настраивать глобальное состояние. Считается антипаттерном.

```python
# Service Locator — зависимость скрыта, сигнатура врёт
class OrderService:
    def place(self, order):
        repo = container.get(Repo)      # что нужно этому классу — из сигнатуры не узнать
```

**Не глобальный конфиг.** `from config import settings` внутри сервиса — это ровно та же скрытая зависимость. В тестах такой сервис не переключить на другой адрес, не подменив модуль целиком. Настройки читает корень и раздаёт значения дальше явными аргументами.

## DI-контейнеры

Когда объектов десятки, ручная сборка в `main()` разрастается. Тогда её автоматизируют контейнером: он читает аннотации типов и строит граф объектов сам. В Python это `dishka`, `dependency-injector`, `punq`.

Что важно понимать: **контейнер не заменяет принцип, а автоматизирует корень**. Если зависимости всё равно создаются внутри классов, контейнер ничего не чинит. Верно и обратное — на среднем проекте ручной сборки в `main()` хватает, и она читается лучше любого контейнера.

## Цена

- **Навигация.** Вместо очевидного `requests.post(...)` на месте — вызов через зависимость, и чтобы понять, что там на самом деле, надо идти в корень. Один файл читать проще, чем прыгать по десяти.
- **Порог входа в команде.** Схему должны понимать все, иначе рядом с корнем заведётся второй, «временный», а потом третий.
- **На маленьком проекте пользы не видно.** Она проявляется на масштабе и на тестах — см. [дозировку](../../ООП/Принципы/SOLID%20Python.md#сколько-solid-нужно-проекту).
