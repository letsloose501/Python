# SOLID на практике — рефакторинг сервиса

> [SOLID Python](../../ООП/Принципы/SOLID%20Python.md) объясняет буквы на фигурах, птицах и роботах. Проблема таких примеров в том, что каждое нарушение там уже выделено и подписано. В живом коде нарушения не подписаны и лежат вперемешку — здесь один сервис на сотню строк, в котором сломаны **все пять принципов сразу**, и пошаговый разбор, как их снимать.

---

## Задача

**Сервис уведомлений** — типовой кусок инфраструктуры: берёт откуда-то (БД, брокер, HTTP) факт «пользователю нужно сообщить X» и доставляет его по всем каналам. Не ключевой функционал компании, но трогают его постоянно: добавляются каналы, меняются провайдеры, правятся тексты.

```
                          ┌──────────────────────┐
   данные о событии  ───▶ │ NotificationService  │
   (кто, что, страна)     └──────────┬───────────┘
                                     │
                     ┌───────────────┴───────────────┐
                     ▼                               ▼
              ┌─────────────┐                 ┌─────────────┐
              │  Telegram   │                 │     SMS     │
              └─────────────┘                 └──────┬──────┘
                                          страна RU? ─┴─ нет
                                             ▼           ▼
                                       Unisender    Green SMS
```

Два канала, у SMS — два провайдера, выбор по стране. Этого хватает, чтобы воспроизвести все пять нарушений.

## Код «до»

```python
class MessageComposer(Protocol):
    def build(self, username: str, text: str) -> str: ...

class SmsComposer:
    def build(self, username: str, text: str) -> str:
        return f"{username}, {text}"
    def shorten(self, text: str) -> str:
        return text[:70]

class UnisenderComposer(SmsComposer):
    def build(self, username: str, text: str) -> str:
        message = f"{username}, {text}"
        if len(message) > 70:
            raise ValueError("слишком длинное сообщение")   # ← сюрприз, которого нет у родителя
        return message

class GreenSmsComposer(SmsComposer):
    def build(self, username: str, text: str) -> str | None:   # ← результат сузили
        if not text:
            return None
        return f"{username}, {text}"
    def shorten(self, text: str) -> str:
        raise NotImplementedError                              # ← метод не нужен, но обязан быть

class NotificationService:
    def __init__(self, user: User, text: str) -> None:
        self.user, self.text = user, text

    def send_telegram(self) -> None:
        composer = TelegramComposer()                          # ← реализация создаётся внутри
        message = composer.build(self.user.name, self.text)
        requests.post(TELEGRAM_URL, json={"chat_id": self.user.chat_id,
                                          "message": message}) # ← ещё и транспорт
        print("сообщение в Telegram отправлено")               # ← ещё и логирование

    def send_sms(self) -> None:
        if self.user.country == "RU":                          # ← новая страна = правка метода
            composer, url = SmsComposer(), UNISENDER_URL
        else:
            composer, url = GreenSmsComposer(), GREENSMS_URL
        message = composer.build(self.user.name, self.text)
        requests.post(url, json={"phone": self.user.phone, "message": message})
        print("сообщение в SMS отправлено")
```

Код работает. Проблемы начинаются, когда его нужно **менять**.

## Пять нарушений в одном файле

| Буква | Где именно | Чем аукнется |
|---|---|---|
| **S** | `send_telegram` делает четыре дела: выбирает форматировщик, форматирует, отправляет по HTTP, логирует | сменился ключ в API Телеграма — правишь метод, где заодно живёт форматирование; риск задеть соседнюю логику |
| **O** | `if country == "RU"` внутри `send_sms` | новый провайдер или новая страна = правка центрального класса, а не добавление кода сбоку |
| **L** | `UnisenderComposer.build` кидает `ValueError`, которого нет у родителя; `GreenSmsComposer.build` возвращает `str \| None` вместо `str` | подставил потомка вместо родителя (в тестах, в другой ветке) — упало или вернуло `None` там, где ждали строку |
| **I** | `shorten` объявлен в `SmsComposer`, но Green SMS он не нужен — `raise NotImplementedError` | читая базовый класс, нельзя понять, у кого метод настоящий; в проекте на 150 классов это не удержать в голове |
| **D** | `TelegramComposer()`, `SmsComposer()`, `UNISENDER_URL` берутся изнутри | в тестах не подменить: прогон тестов будет реально слать SMS **за реальные деньги** |

> Порядок разбора и порядок починки — разные. Разбирать удобно по алфавиту S→O→L→I→D, а чинить лучше **с конца**: сначала D (вынести создание зависимостей наружу), и половина остальных нарушений после этого распутывается сама.

## Что из этого ловит mypy

Естественная мысль: «поставлю статический типизатор, и он подскажет». Проверка на коде выше ([mypy](../../Ядро%20языка/Линтеры%20и%20форматтеры.md) 2.3, Python 3.13) — **одна ошибка из пяти нарушений**:

```
before.py:48: error: Return type "str | None" of "build" incompatible
    with return type "str" in supertype "SmsComposer"  [override]
```

Всё остальное — бог-класс, `if/elif` по стране, `raise NotImplementedError` в потомке, создание зависимостей внутри — проходит **молча**. Подробнее о границе «что проверяется, а что нет» — [в основной заметке](../../ООП/Принципы/SOLID%20Python.md#что-из-solid-python-проверяет-сам).

## Шаг 1. D — принять зависимости снаружи

Сервис перестаёт создавать реализации и начинает их принимать. В аннотациях стоят **контракты**, а не конкретные классы:

```python
class MessageComposer(Protocol):
    def build(self, username: str, text: str) -> str: ...

class Sender(Protocol):                       # контракт для функции, а не для класса
    def __call__(self, address: str, message: str) -> None: ...

class NotificationService:
    def __init__(
        self,
        tg_composer: MessageComposer,
        sms_composer_for: ComposerSelector,
        send_tg: Sender,
        send_sms: Sender,
    ) -> None:
        self._tg_composer = tg_composer
        self._sms_composer_for = sms_composer_for
        self._send_tg = send_tg
        self._send_sms = send_sms
```

Два момента, которые легко пропустить:

- **Зависимостью может быть функция, а не только объект.** Отправка сообщения — это одно действие, класс с единственным методом здесь лишний. Но типизировать её через `Callable[[str, str], None]` — плохой выбор: имена параметров теряются, и вызвать `send(address=..., message=...)` уже нельзя. Именно поэтому в примере выше стоит `Protocol` с `__call__` — он сохраняет имена. Разбор с проверкой — [Протокол для вызываемого объекта](../../ООП/Принципы/Полиморфизм%20Python.md#протокол-для-вызываемого-объекта).
- **Подчёркивание в `self._tg_composer`** — сигнал остальным, что это внутренняя деталь сервиса, снаружи её дёргать не нужно ([инкапсуляция](../../ООП/Принципы/Инкапсуляция%20Python.md)).

## Шаг 2. S — вынести транспорт и логирование

Форматирование, отправка и логирование — три разные причины меняться. Разводим:

```python
def send_telegram(address: str, message: str) -> None:
    print(f"[tg  → {address}] {message}")     # в бою здесь HTTP-клиент, ретраи, таймауты

class NotificationService:
    def notify_telegram(self, user: User, text: str) -> None:
        message = self._tg_composer.build(user.name, text)
        self._send_tg(address=str(user.chat_id), message=message)
```

Метод сервиса стал двумя строчками: **собрать сообщение и передать транспорту**. Всё остальное — ретраи, таймауты, `try/except`, логирование — навешивается на транспорт [декоратором](../../ООП/Паттерны/Структурные%20паттерны.md#декоратор), не трогая сервис.

> **Класс с единственным методом чаще всего должен быть функцией.** SOLID не требует заворачивать всё в классы: `def send_telegram(...)` читается лучше, чем `TelegramSender().send(...)`. Класс оправдан, когда появляется состояние — переиспользуемая HTTP-сессия, конфиг, пул соединений.

## Шаг 3. I — разрезать толстый интерфейс

`shorten` нужен одному провайдеру из двух. Значит, он не принадлежит общему контракту:

```python
class MessageComposer(Protocol):        # то, что умеют все
    def build(self, username: str, text: str) -> str: ...

class ShorteningComposer(MessageComposer, Protocol):   # то, что умеют не все
    def shorten(self, text: str) -> str: ...
```

`GreenSmsComposer` теперь соответствует узкому контракту и не обязан городить заглушку. Заглушка `raise NotImplementedError` — не «защита», а **ложь в сигнатуре**: класс объявляет, что умеет, и падает при вызове.

## Шаг 4. L — убрать сюрпризы из потомков

Оба нарушения снимаются одинаково — потомок перестаёт менять договор:

```python
class UnisenderComposer:
    LIMIT = 70
    def build(self, username: str, text: str) -> str:
        return f"{username}, {text}"[: self.LIMIT]     # обрезаем, а не падаем

class GreenSmsComposer:
    def build(self, username: str, text: str) -> str:  # ровно str, как у контракта
        return f"{username}, {text}"
```

Обрезка вместо исключения — это осознанное решение: превышение длины перестало быть ошибкой уровня форматировщика. Если по бизнесу оно всё-таки ошибка, её место — в валидации на входе, а не в потомке, который «внезапно строже родителя».

Заметь ещё одно: классы больше **не наследуют** `SmsComposer`. Соответствие протоколу в Python структурное — достаточно иметь нужные методы. Наследование здесь только создавало иерархию, которую потом приходилось не ломать.

## Шаг 5. O — выбор реализации таблицей, а не `if`

`if country == "RU"` не исчезает, он **переезжает** — из центрального класса в отдельную функцию, где превращается в таблицу соответствий:

```python
def composer_by_country(
    table: dict[str, MessageComposer],
    default: MessageComposer,
) -> ComposerSelector:
    def select(country: str) -> MessageComposer:
        return table.get(country, default)
    return select
```

Что это даёт: добавить Казахстан или Индонезию — **строка в словаре** на уровне сборки приложения, а не `elif` внутри сервиса. Функция возвращает функцию (замыкание с зафиксированными таблицей и запасным вариантом), поэтому сервис принимает её как обычную зависимость.

Приём — родня [Стратегии](../../ООП/Паттерны/Паттерны%20поведения.md#стратегия) в её словарной форме: не иерархия классов, а таблица «ключ → реализация» с запасным вариантом. Замыкание здесь можно заменить на `functools.partial(select, table, default)` — вопрос вкуса.

## Композиционный корень

Все реализации создаются в одном месте — в точке входа:

```python
def main() -> None:
    service = NotificationService(
        tg_composer=TelegramComposer(),
        sms_composer_for=composer_by_country(
            table={"RU": UnisenderComposer()},
            default=GreenSmsComposer(),
        ),
        send_tg=send_telegram,
        send_sms=send_sms,
    )
    service.notify_telegram(user, text)
    service.notify_sms(user, text)
```

Это и есть [композиционный корень](../../ООП/Принципы/Композиционный%20корень.md) — единственное место в программе, которое знает конкретные классы. Поменять Unisender на другого провайдера, подставить в тестах заглушку вместо реальной отправки, добавить страну — правится только этот блок, глубже в код лезть не надо.

Проверено: код выше проходит `mypy --strict` без замечаний и запускается.

## Что осталось не по SOLID — и почему это нормально

Полностью «по солиду» не бывает: ветвление никуда не девается, вопрос только в том, **на каком уровне** оно живёт. Что в этом примере осталось недоделанным:

- **Транспорт всё ещё смешивает бизнес-логику и инфраструктуру.** Внутри `send_sms` живёт и «какому провайдеру шлём», и «как шлём» (HTTP, брокер, БД). Следующий разумный шаг — вынести HTTP-клиент отдельно и принимать его снаружи. Это разделение — граница слоёв из чистой архитектуры.
- **Нет ретраев, таймаутов, обработки ошибок.** В боевом сервисе это обязательно, и живут они в транспорте, а не в бизнес-логике.
- **`Sender` — один контракт на два разных канала.** Пока сигнатуры совпадают, это удобно; разойдутся — придётся разделить.

> Дальше дробить можно бесконечно: вынести выбор URL по стране, вынести сборку JSON-тела, завести интерфейс для каждой функции. В какой-то момент это перестаёт помогать. Где именно — вопрос без универсального ответа, и именно поэтому тема холиварная: у каждого своя граница. В команде эту границу фиксируют **регламентом** и держатся его — не потому, что регламент правильный, а потому, что общий.

## Как рефакторить, чтобы не сломать

1. **Сначала тесты.** Без них рефакторинг — рулетка ([почему](../../Рефакторинг.md#обязательное-условие--тесты)). Здесь порядок особый: DI сам нужен для тестов, поэтому первым пишут грубый интеграционный тест «на выходе то же самое», а нормальные юнит-тесты появляются уже после шага D.
2. **По одной букве за проход.** Не «переписываем всё по SOLID», а один принцип — прогон тестов — коммит.
3. **Начинать с D.** Вынес создание зависимостей наверх — стало видно, кто от кого зависит, и остальные нарушения проступают сами.
4. **Проверять, что поведение не изменилось.** Единственная цель рефакторинга: снаружи всё работает ровно как раньше.
5. **Останавливаться, когда перестало становиться понятнее.** Это критерий, а не «пока не по всем пяти буквам».
