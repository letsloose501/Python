# Принципы разработки — DRY, KISS, DI

> Принципы разработки — не законы, а **эвристики**: короткие правила, которые держат код простым, читаемым и готовым к изменениям. Их цель одна — чтобы через полгода (тебе же) было легко понять и поменять код, не сломав остальное. [SOLID](../../ООП/Принципы/SOLID%20Python.md) — про классы; эти — про код вообще.

---

## Как объяснять любой принцип

Принцип запоминается не формулировкой, а **болью, которую он лечит**. Схема на любой вопрос «что такое принцип X»:

1. **Что говорит** — правило одной фразой.
2. **Какую боль решает** — что происходит без него.
3. **Пример** — нарушение → как правильно.

Ниже все принципы даны по этой схеме.

## DRY — Don't Repeat Yourself

**Что говорит:** каждый кусок **знания** живёт в коде в одном месте. Не копипасть логику.

**Боль без него:** одинаковый код в трёх местах — при изменении правила надо помнить про все три, забудешь одно → баг.

```python
# НАРУШЕНИЕ — формула скидки продублирована:
цена1 = товар1 * 0.9
цена2 = товар2 * 0.9      # поменяется скидка → правь везде

# DRY — знание о скидке в одном месте:
СКИДКА = 0.9
def со_скидкой(цена): return цена * СКИДКА
```

> DRY — про **дублирование знания**, а не строк. Два разных правила, которые сейчас совпали случайно, объединять не надо — иначе изменение одного сломает другое (ложный DRY).

## KISS — Keep It Simple, Stupid

**Что говорит:** выбирай **простое** решение, а не «умное». Простой код читается и правится легче.

**Боль без него:** хитрая однострочная магия экономит 5 минут при написании и стоит часы при чтении.

```python
# «Умно», но нечитаемо:
r = [x for s in m for x in s if x % 2 == 0][:5]

# KISS — понятно с первого взгляда:
r = []
for строка in m:
    for x in строка:
        if x % 2 == 0:
            r.append(x)
    ...
```

## YAGNI — You Aren't Gonna Need It

**Что говорит:** не пиши код «на будущее», которого сейчас не требует задача.

**Боль без него:** абстракции и настройки «на всякий случай» раздувают код, а нужны в итоге в 10% случаев — остальное просто мешает.

> DRY, KISS и YAGNI работают вместе: убери дублирование, но не усложняй ради гибкости, которая не нужна.

## SRP — Single Responsibility (кратко)

**Что говорит:** у класса/функции — **одна причина для изменения** (одна ответственность). Отчёт, который и считает, и форматирует, и шлёт по почте — три причины меняться в одном месте. Подробно с примером — в [SOLID Python](../../ООП/Принципы/SOLID%20Python.md).

## DI против DIP — техника против принципа

Их постоянно путают, потому что оба про «зависимости» и букву **D**. Но это **разные вещи**:

- **DIP** (Dependency Inversion Principle) — **принцип** (буква D в SOLID): код должен зависеть от **абстракций**, а не от конкретных деталей. Высокоуровневый модуль не знает про конкретную БД — только про интерфейс «хранилище».
- **DI** (Dependency Injection, инъекция зависимостей) — **техника/приём**: зависимость **передают снаружи** (в конструктор, функцию), а не создают внутри. Это один из способов *достичь* DIP.

```python
# НАРУШЕНИЕ обоих — класс сам создаёт конкретную зависимость:
class Отчёт:
    def __init__(self):
        self.бд = PostgresDB()          # жёстко привязан к Postgres

# DI — зависимость ВНЕДРЯЕТСЯ снаружи (техника):
class Отчёт:
    def __init__(self, хранилище):      # получаем готовую зависимость
        self.хранилище = хранилище

Отчёт(PostgresDB())                     # подставили Postgres
Отчёт(МокХранилище())                   # в тесте — заглушку (см. Юнит-тестирование Python)
```

DI (передали снаружи) сделал возможным DIP (класс зависит от «хранилища как интерфейса», а не от Postgres). 

| | DIP | DI |
|---|---|---|
| Что это | принцип проектирования | техника реализации |
| Говорит | завись от абстракций | передавай зависимость снаружи |
| Уровень | «как проектировать связи» | «как получить зависимость» |
| Пример в Python | аргумент-интерфейс, [ABC](../../ООП/Принципы/Абстракция%20Python.md)/`Protocol` | аргумент конструктора, `Depends` в [FastAPI](../../Фреймворки/REST%20API%20на%20FastAPI.md), фикстуры [pytest](../../Библиотеки/Сторонние/Тесты/pytest.md) |

> Короткая формула: **DIP — цель** (не привязывайся к деталям), **DI — способ** (передай деталь снаружи). Можно применять DI без строгого DIP и наоборот, но вместе они и дают гибкость.

Остаётся третий вопрос, который эта пара не закрывает: **где** тогда создавать зависимости, если внутри классов нельзя. Ответ — [композиционный корень](../../ООП/Принципы/Композиционный%20корень.md): одно место рядом с точкой входа, где собирается всё приложение. На большом проекте сборку автоматизируют DI-контейнером (`dishka`, `dependency-injector`, `punq`), но контейнер — это удобство, а не сам принцип.
