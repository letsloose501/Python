# SOLID Python

> _«Плохой код можно писать быстро, но платить за него придётся вечно.»_ — по мотивам Роберта Мартина

---

**SOLID** — пять принципов проектирования классов, которые держат ООП-код гибким: его легко менять и расширять, не ломая уже написанное. Сформулировал их Роберт Мартин («дядя Боб»): сначала по одному, колонками в журнале **The C++ Report** в 1996 году (он был его главредом), затем собрал вместе в статье «Design Principles and Design Patterns» (2000). Аббревиатуру SOLID придумал Майкл Фезерс около 2004 года. Каждая буква — отдельный принцип.

> Год важен для понимания, откуда у принципов «привкус Java». В 1996-м доминировал **C++**: Java 1.0 вышла только в январе того же года, C# — вообще в 2000-м. То есть принципы родились не из Java, а из практики языков со статической типизацией, компилятором и явными интерфейсами. Отсюда и трение с Python — см. [Что из SOLID Python проверяет сам](#что-из-solid-python-проверяет-сам).

Зачем это нужно — видно от обратного. Код без принципов со временем становится:

- **жёстким** — одна правка тянет каскад изменений в других местах;
- **хрупким** — трогаешь одно, ломается другое, внешне не связанное;
- **неповоротливым** — модуль нельзя вытащить и переиспользовать, он тащит за собой полсистемы.

SOLID — набор правил против этого. Он развивает два базовых принципа проектирования из [обзора ООП](../../ООП/Принципы/Принципы%20ООП%20в%20Python.md#два-ключевых-принципа-проектирования): _«программируй в соответствии с интерфейсом»_ (это про DIP) и _«предпочитай композицию наследованию»_ (это про OCP, LSP, DIP).

## S — Single Responsibility (единственная ответственность)

**Принцип единственной ответственности** — у класса должна быть только одна причина для изменения, то есть одна зона ответственности. Если класс отвечает и за данные, и за их хранение, и за рассылку — у него три причины меняться, и правки в одной задевают остальные.

```python
# НЕПРАВИЛЬНО — класс делает всё сразу: данные + БД + рассылка + отчёт
class User:
    def __init__(self, name, email):
        self.name = name
        self.email = email

    def save(self):                  # причина меняться №1 — сменилась БД
        db.execute("INSERT INTO users ...")

    def send_welcome(self):          # причина меняться №2 — сменился SMTP
        smtp.send(self.email, "Welcome!")

    def to_report(self):             # причина меняться №3 — сменился формат
        return f"{self.name} <{self.email}>"
```

```python
# ПРАВИЛЬНО — одна ответственность на класс
class User:                          # только данные
    def __init__(self, name, email):
        self.name = name
        self.email = email

class UserRepository:                # только хранение
    def save(self, user: User):
        db.execute("INSERT INTO users ...")

class WelcomeMailer:                 # только рассылка
    def send(self, user: User):
        smtp.send(user.email, "Welcome!")
```

> SRP — это про **высокую связность (cohesion)** внутри класса: всё в нём служит одной задаче. Родствен идее инкапсуляции — см. [Инкапсуляция Python](../../ООП/Принципы/Инкапсуляция%20Python.md).

## O — Open/Closed (открытость/закрытость)

**Принцип открытости/закрытости** — класс должен быть открыт для расширения, но закрыт для изменения. Новое поведение добавляется новым кодом, а не правкой уже работающего и оттестированного.

Маркер нарушения — растущий `if/elif` по типу объекта: каждая новая ветка требует лезть в старую функцию.

```python
# НЕПРАВИЛЬНО — новая фигура заставляет править функцию area()
def area(shape):
    if shape.kind == "circle":
        return 3.14 * shape.r ** 2
    elif shape.kind == "square":
        return shape.side ** 2
    # каждая новая фигура — ещё один elif здесь, старый код трогается снова
```

```python
# ПРАВИЛЬНО — расширяем новым классом, area()-логику не трогаем
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self) -> float: ...

class Circle(Shape):
    def __init__(self, r): self.r = r
    def area(self): return 3.14 * self.r ** 2

class Square(Shape):
    def __init__(self, side): self.side = side
    def area(self): return self.side ** 2

class Triangle(Shape):               # новая фигура — новый класс, и всё
    def __init__(self, base, h): self.base, self.h = base, h
    def area(self): return 0.5 * self.base * self.h

def total_area(shapes: list[Shape]) -> float:
    return sum(s.area() for s in shapes)   # работает и с Triangle — без правок
```

Достигается через [полиморфизм](../../ООП/Принципы/Полиморфизм%20Python.md#полиморфизм-через-наследование). На уровне паттернов OCP реализуют [Стратегия](../../ООП/Паттерны/Паттерны%20поведения.md#стратегия) (подменяемый алгоритм) и [Декоратор](../../ООП/Паттерны/Структурные%20паттерны.md#декоратор) (наращивание обязанностей обёрткой).

## L — Liskov Substitution (подстановка Лисков)

**Принцип подстановки Барбары Лисков** — объект подкласса должен подставляться всюду, где ожидается базовый класс, не ломая корректности программы. Наследование `Sub(Base)` обещает: `Sub` умеет всё, что `Base`, и ведёт себя ожидаемо. Нарушение подстановки — это ложное обещание.

```python
# НЕПРАВИЛЬНО — подтип ломает ожидания от базового типа
class Bird:
    def fly(self): ...

class Penguin(Bird):
    def fly(self):
        raise NotImplementedError("пингвины не летают")

def send_to_sky(bird: Bird):
    bird.fly()               # упадёт, если передать Penguin — подстановка сломана
```

```python
# ПРАВИЛЬНО — не навязываем подклассу поведение, которого у него нет
class Bird: ...

class FlyingBird(Bird):
    def fly(self): ...

class Penguin(Bird):         # пингвин — птица, но не из летающих
    def swim(self): ...

def send_to_sky(bird: FlyingBird):
    bird.fly()               # тип гарантирует, что метод есть и работает
```

Признаки нарушения LSP: подкласс кидает исключение на методе, который у родителя работает; **усиливает предусловия** (требует более узкий вход) или **ослабляет постусловия** (возвращает меньше, чем обещал родитель). Классический пример — `Square(Rectangle)`: если у квадрата сеттер ширины меняет заодно и высоту, код, рассчитывающий на независимость сторон прямоугольника, сломается.

### Шесть правил Лисков — Винг

Барбара Лисков и Жаннетт Винг разложили «подставляется без сюрпризов» на проверяемый список (TOPLAS, 1994). Первые три — про сигнатуру, остальные три — про поведение:

| Что | Правило | Нарушение |
|---|---|---|
| Аргументы | **контравариантны** — потомок принимает то же или шире | родитель берёт `str`, потомок — только `bytes` |
| Результат | **ковариантен** — потомок возвращает то же или уже | родитель обещает `str`, потомок — `str \| None` |
| Исключения | новые типы нельзя, только подтипы уже объявленных | родитель не падал, потомок кидает `ValueError` |
| Предусловия | нельзя **усиливать** | потомок требует непустой список там, где родитель принимал любой |
| Постусловия | нельзя **ослаблять** | родитель гарантировал отсортированный результат, потомок — нет |
| Инварианты и история | инварианты сохраняются; потомок не разрешает изменений состояния, невозможных у родителя | неизменяемый родитель, у потомка появился сеттер |

Первые два правила ловятся [статическим типизатором](../../Ядро%20языка/Линтеры%20и%20форматтеры.md) — это чистая вариантность типов. Остальные четыре, включая правило об исключениях, в аннотациях Python не выражаются вовсе и остаются на человеке и тестах.

### Нарушение, которое не видит никто

Самый неприятный случай: сигнатура совпадает буква в букву, а **смысл результата другой**.

```python
class MessageComposer(Protocol):
    def build(self, username: str, text: str) -> str: ...   # возвращает текст сообщения

class LoggingComposer:
    def build(self, username: str, text: str) -> str:
        return "сообщение успешно сформировано"             # возвращает строку. Но не ту.
```

Типы сходятся, mypy молчит, программа не падает — просто пользователю уходит служебная строка вместо уведомления. Именно поэтому LSP формулируют через **договор**, а не через сигнатуру: подстановка обязана сохранять то, ради чего метод вызывают.

> Правильная эвристика: наследуй, только если подтип действительно «является» родителем во всех сценариях его использования. Иначе — композиция. Подробнее: [Наследование Python](../../ООП/Принципы/Наследование%20Python.md#наследование-vs-композиция).

## I — Interface Segregation (разделение интерфейсов)

**Принцип разделения интерфейсов** — клиента нельзя заставлять зависеть от методов, которые он не использует. Лучше несколько узких интерфейсов, чем один «толстый»: не придётся реализовывать заглушки ради контракта.

```python
# НЕПРАВИЛЬНО — толстый интерфейс: робот обязан "уметь" есть
from abc import ABC, abstractmethod

class Worker(ABC):
    @abstractmethod
    def work(self): ...
    @abstractmethod
    def eat(self): ...

class Robot(Worker):
    def work(self): ...
    def eat(self):
        raise NotImplementedError    # роботу не нужно, но контракт требует
```

```python
# ПРАВИЛЬНО — узкие интерфейсы, класс берёт только нужные
from typing import Protocol

class Workable(Protocol):
    def work(self): ...

class Eatable(Protocol):
    def eat(self): ...

class Human:                         # умеет и работать, и есть
    def work(self): ...
    def eat(self): ...

class Robot:                         # только работает — есть не обязан
    def work(self): ...
```

Инструменты Python для узких контрактов — маленькие [ABC-интерфейсы](../../ООП/Принципы/Абстракция%20Python.md#интерфейс-через-abc--только-абстрактные-методы) или [typing.Protocol](../../ООП/Принципы/Полиморфизм%20Python.md#typingprotocol--явные-протоколы-python-38) (структурная типизация — классу даже не нужно наследовать протокол).

## D — Dependency Inversion (инверсия зависимостей)

**Принцип инверсии зависимостей** — модули верхнего уровня не должны зависеть от модулей нижнего уровня; и те, и другие зависят от абстракций. И: абстракции не зависят от деталей, детали зависят от абстракций. «Инверсия» — потому что обычная стрелка зависимости (верх → конкретный низ) переворачивается: теперь оба смотрят на общий интерфейс.

```python
# НЕПРАВИЛЬНО — верхний уровень прибит гвоздями к детали
class MySQLDatabase:
    def save(self, data): ...

class OrderService:
    def __init__(self):
        self._db = MySQLDatabase()   # жёсткая привязка к конкретной БД
    def place(self, order):
        self._db.save(order)
# сменить MySQL на Postgres = править OrderService; в тестах не подставить заглушку
```

```python
# ПРАВИЛЬНО — оба зависят от абстракции, деталь передаётся снаружи
from typing import Protocol

class Database(Protocol):            # абстракция
    def save(self, data): ...

class MySQLDatabase:
    def save(self, data): ...

class PostgresDatabase:
    def save(self, data): ...

class OrderService:
    def __init__(self, db: Database):   # зависит от абстракции, не от класса
        self._db = db
    def place(self, order):
        self._db.save(order)

OrderService(PostgresDatabase())    # деталь выбирается снаружи
OrderService(FakeDatabase())        # в тесте — подставили заглушку
```

Приём «передать зависимость снаружи, а не создавать внутри» называется **внедрение зависимостей (dependency injection)**. Это прямое выражение принципа _«программируй в соответствии с интерфейсом»_; на уровне паттернов DIP опирается на [Абстрактную фабрику](../../ООП/Паттерны/Порождающие%20паттерны.md#абстрактная-фабрика) и [Стратегию](../../ООП/Паттерны/Паттерны%20поведения.md#стратегия), а сам механизм — [композиция](../../ООП/Принципы/Наследование%20Python.md#наследование-vs-композиция).

Если зависимости приходят снаружи, кто-то должен их создать. Место, где это происходит, — [композиционный корень](../../ООП/Принципы/Композиционный%20корень.md): одна точка сборки рядом с входом в программу, дальше приложение видит только контракты.

**Главный практический драйвер DIP — тесты.** Не «красивая архитектура», а вполне денежный вопрос: сервис, который сам создаёт SMS-клиент, на каждом прогоне тестов шлёт настоящие SMS за настоящие деньги. Подставить заглушку можно, только если реализация приходит аргументом.

**Минусы, о которых обычно молчат:**

| Минус | В чём боль |
|---|---|
| Навигация | вместо `requests.post(...)` на месте — вызов зависимости; чтобы понять, что происходит, надо идти в другой файл |
| Нужны контракты | появляются `Protocol`/ABC, которых иначе не было бы; их надо придумывать и поддерживать |
| Порог входа | схему должна понимать вся команда, иначе рядом заведут «временный» глобальный клиент |
| Библиотека DI | на большом проекте ручной сборки мало, а контейнер (`dishka`, `dependency-injector`, `punq`) — ещё одна вещь для изучения |

> Полезная примета: если одна и та же логика выбора реализации повторилась во втором месте, ты всё равно вынесешь её в отдельную функцию — и придёшь к DIP сам, без книжек. До этого момента она может быть и не нужна.

## Сводка

| Буква | Принцип | Правило одной строкой | Признак нарушения | Инструмент Python |
|---|---|---|---|---|
| **S** | Единственная ответственность | Один класс — одна причина для изменения | Класс делает «и то, и это, и пятое» | Разбить на классы по ролям |
| **O** | Открытость/закрытость | Расширяй новым кодом, не меняй старый | Растущий `if/elif` по типу | ABC + полиморфизм, Стратегия, Декоратор |
| **L** | Подстановка Лисков | Подтип подставляется вместо базового без сюрпризов | Подкласс кидает `NotImplementedError`, сужает вход | Честная иерархия или композиция |
| **I** | Разделение интерфейсов | Много узких интерфейсов лучше одного толстого | Заглушки ради контракта | Маленькие ABC / `Protocol` |
| **D** | Инверсия зависимостей | Зависим от абстракций, деталь — снаружи | `self._db = MySQL()` внутри класса | `Protocol` + dependency injection |

## Что из SOLID Python проверяет сам

Ходовое возражение: «SOLID придуман для Java, где компилятор бьёт по рукам. В Python можно нарушать что угодно, и всё запустится». Наполовину верно — и важно понимать, какая именно половина.

**Чего в Python действительно нет.** Ключевого слова `interface` и обязанности реализовать объявленный метод. В Java класс, не реализовавший метод интерфейса, просто не скомпилируется — программист приходит к ISP не из любви к принципам, а потому что иначе придётся писать `throw new NotImplementedException()` в каждом классе. В Python такого давления нет: не реализовал — узнаешь при вызове, `AttributeError` в рантайме. Ближайший аналог — ABC: [`@abstractmethod`](../../ООП/Принципы/Абстракция%20Python.md#abstractmethod--детали) роняет `TypeError` при **создании** объекта, а не при вызове метода. Это раньше, но всё ещё рантайм.

**Что при этом проверяется.** Если в проекте есть аннотации и [статический типизатор](../../Ядро%20языка/Линтеры%20и%20форматтеры.md), часть SOLID он проверяет буквально. mypy на нарушении LSP печатает это прямым текстом:

```
error: Argument 2 of "build" is incompatible with supertype "SmsComposer";
       supertype defines the argument type as "str"  [override]
note: This violates the Liskov substitution principle
```

Полностью проверяются два правила Лисков — Винг из шести: вариантность аргументов и результата. Плюс соответствие объекта `Protocol` — оно ловится с перечислением расхождений в сигнатурах. Правило об исключениях не проверяется: в аннотациях Python исключения не выражаются.

**Где граница.** Проверка на сервисе, в котором сломаны все пять принципов сразу ([подробный разбор](../../ООП/Принципы/SOLID%20на%20практике%20—%20рефакторинг%20сервиса.md)), дала **одну ошибку из пяти нарушений** — сужение возвращаемого типа. Молча прошли: бог-класс на четыре ответственности, `if/elif` по стране, `raise NotImplementedError` в потомке и создание зависимостей внутри класса.

| Нарушение | Ловит mypy | Почему |
|---|---|---|
| Потомок сузил результат / расширил требования к аргументу | ✅ | это проверка сигнатур |
| Класс не соответствует `Protocol` | ✅ | структурная типизация |
| Потомок кидает новое исключение | ❌ | исключения в аннотациях Python не выражаются |
| `raise NotImplementedError` вместо реализации | ❌ | сигнатура-то на месте |
| Тот же тип, но другой смысл результата | ❌ | смысл в типах не записан |
| Один класс на четыре ответственности | ❌ | SRP — не про типы |
| `if/elif` по варианту вместо расширения | ❌ | OCP — не про типы |
| Реализация создаётся внутри класса | ❌ | DIP — не про типы |

> Вывод в две стороны. Против «Питону всё равно»: с включённым mypy — не всё равно, и часть LSP язык защищает лучше, чем принято думать. Против «поставлю mypy и буду спокоен»: типизатор проверяет **форму** договора, а не его **смысл**, и четыре нарушения из пяти он не увидит.

## SOLID вне классов

SOLID сформулирован для ООП, но три буквы из пяти работают и там, где классов нет вовсе — а в Python это половина кода:

- **S** — функция должна делать одно дело. Функция, которая сходила в БД, разобрала ответ, отправила его во внешний сервис, залогировала, сохранила файл и написала на почту, ломается при любой правке целиком.
- **O** — новое поведение добавляй новой функцией и таблицей соответствий, а не очередным `elif` в старой.
- **D** — принимай зависимость параметром. `def process(data, storage)` вместо `storage = S3()` внутри — это тот же DIP, только без классов.

**L** и **I** без иерархий и интерфейсов смысла не имеют — их аналогом в функциональном коде служит стабильность сигнатуры.

## Сколько SOLID нужно проекту

Принципы решают конкретную проблему: **стоимость изменения кода, который поддерживает несколько человек в течение лет**. Нет этой проблемы — нет и пользы, остаётся только цена: лишние слои, прыжки по файлам, контракты, которые надо придумать и поддерживать.

**Когда почти не нужен:**

- скрипт или пет-проект на несколько сотен строк;
- код с одним автором и коротким сроком жизни;
- нет интеграций и нет вариантов реализации — подменять просто нечего;
- тестов не пишут (тогда главный аргумент за DIP не работает).

**Когда окупается:**

- несколько человек и несколько лет жизни кода;
- есть тесты и есть что подменять — внешние API, платные сервисы, БД;
- реализация одной задачи заведомо не одна: провайдеры, регионы, форматы;
- код часто читают чужие глаза, включая твои же через полгода.

**Как применять, чтобы не навредить:**

1. **По буквам, а не пакетом.** Применить весь SOLID разом к проекту почти невозможно. Начинай с SRP и ISP — они дешевле всего и почти всегда улучшают читаемость. LSP и DIP — когда появилась реальная нужда (иерархия или тесты).
2. **Не переписывай рабочий проект «под SOLID».** Это рефакторинг ради ярлыка. Применяй принцип там, где уже больно менять.
3. **Дозировка, а не флажок.** SOLID применяется с коэффициентом: в модуле, который трогают каждую неделю, — плотно; в скрипте выгрузки отчёта — почти нигде.
4. **Критерий — стало ли понятнее.** Если после «правильного» интерфейса код читается хуже, интерфейс не нужен. Это тот же [YAGNI](../../ООП/Принципы/Принципы%20разработки%20—%20DRY,%20KISS,%20DI.md#yagni--you-arent-gonna-need-it): абстракция «на будущее» чаще всего это будущее не угадывает.
5. **Договориться важнее, чем быть правым.** Где проходит граница «уже достаточно разделено» — вопрос вкуса, поэтому тема холиварная. В команде границу фиксируют регламентом, и ценность регламента не в правильности, а в том, что он общий: на [ревью](../../Код-ревью.md) не спорят заново каждый раз.

> Итог одной строкой: SOLID — ориентир, а не догма. Питон гибче Java — часть задач решается функциями, утиной типизацией и `Protocol` без иерархий классов. Применяй принцип, когда он снимает реальную боль сопровождения, а не «чтобы было по SOLID».
