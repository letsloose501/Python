# Проектирование связного списка

> _Задача, которая ставит руку на указатели перед всеми остальными задачами на списки_

---

[LeetCode #707](https://leetcode.com/problems/design-linked-list/) просит написать [связный список](../../Данные/Структуры%20данных/Связный%20и%20двусвязный%20список.md) целиком: не решить задачу *на* списке, а реализовать сам список с интерфейсом **по индексам**. Ценность не в самой задаче — она несложная, — а в том, что после неё «перевернуть список» и «удалить N-й с конца» перестают быть головоломками: механика уже в пальцах.

Здесь же вылезают две ловушки, на которых валятся почти все: **голова как особый случай** и **разные границы допустимых индексов у вставки и удаления**.

---

## Что требуется

| Метод | Что делает |
|---|---|
| `get(index)` | значение по индексу или `-1`, если индекса нет |
| `addAtHead(val)` | вставить в начало |
| `addAtTail(val)` | вставить в конец |
| `addAtIndex(index, val)` | вставить перед узлом с этим индексом |
| `deleteAtIndex(index)` | удалить узел с этим индексом |

Индексация с нуля, некорректные индексы нужно **молча игнорировать** (а `get` — вернуть `-1`).

### Зачем хранить размер

Проверять индекс, бегая по списку до конца, — это лишний $O(n)$ на каждый вызов. Поэтому в объекте держат поле `size` и обновляют его при каждой вставке и удалении. Одна переменная превращает валидацию в сравнение.

> **Асимметрия границ — главный источник ошибок в этой задаче.** У вставки и у остальных операций **разные** допустимые диапазоны:
> - `get` и `deleteAtIndex`: корректен `0 ≤ index < size` — узел должен существовать;
> - `addAtIndex`: корректен `0 ≤ index ≤ size` — **равенство разрешено**, это вставка в самый конец.
>
> В списке из 4 элементов `deleteAtIndex(4)` — ошибка, а `addAtIndex(4, x)` — легальное добавление в хвост. Перепутать `>` и `>=` здесь стоит вердикта.

---

## Ход рассуждения

### Свести всё к одному методу

`addAtHead` и `addAtTail` — частные случаи `addAtIndex`, писать их отдельно не нужно:

```
addAtHead(v)  =  addAtIndex(0, v)
addAtTail(v)  =  addAtIndex(size, v)
```

Логика вставки живёт в одном месте — значит, и чинить её придётся в одном месте.

### Остановиться за один шаг до

Ключевой приём для односвязного списка. Назад по нему идти нельзя, поэтому, чтобы вставить или удалить узел на позиции `i`, надо встать на **`i - 1`** и работать оттуда.

```
удаляем узел с индексом 2:

[2] → [5] → [3] → [8]
       ↑
     встали на индекс 1 (за один до)

cur.next = cur.next.next     ← перепрыгнули через удаляемый

[2] → [5] ───────→ [8]
```

Тот же приём для вставки, только с сохранением старой ссылки:

```python
old_next = cur.next          # 1. запомнили, куда указывал сосед
cur.next = Node(val)         # 2. воткнули новый узел
cur.next.next = old_next     # 3. пришили хвост обратно
```

Порядок важен: потеряешь `old_next` до шага 3 — потеряешь весь остаток списка.

### Голова ломает и то, и другое

Приём «за один шаг до» не работает для индекса 0: **перед головой узла нет**. И проваливается это двумя разными способами:

```python
# НЕПРАВИЛЬНО — вставка в пустой список
def addAtIndex(self, index, val):
    cur = self.head              # список пуст → cur is None
    for _ in range(index - 1):
        cur = cur.next           # AttributeError на пустом списке 💀

# НЕПРАВИЛЬНО — удаление головы
def deleteAtIndex(self, index):
    ...                          # прошли по узлам, перецепили указатели
    # ...но self.head всё ещё указывает на удалённый узел 💀
    # список внешне не изменился
```

Второй случай коварнее первого: он не падает, а **тихо возвращает неверный результат**. Голова — единственный узел, на который ссылается не сосед, а сам объект списка, поэтому её удаление надо отражать в `self.head`.

Отсюда два пути: обработать нулевой индекс отдельной веткой или поставить [фиктивную голову](../../Алгоритмы/Приёмы/Фиктивный%20узел.md) и не иметь особого случая вовсе.

## Реализация: обычная, с проверкой на голову

```python
class Node:
    __slots__ = ("val", "next")

    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next


class MyLinkedList:
    def __init__(self):
        self.head = None
        self.size = 0                        # ради валидации индексов за O(1)

    def get(self, index: int) -> int:
        if index < 0 or index >= self.size:  # строго меньше: узел должен быть
            return -1
        cur = self.head
        for _ in range(index):
            cur = cur.next
        return cur.val

    def addAtHead(self, val: int) -> None:
        self.addAtIndex(0, val)

    def addAtTail(self, val: int) -> None:
        self.addAtIndex(self.size, val)      # index == size — легально

    def addAtIndex(self, index: int, val: int) -> None:
        if index < 0 or index > self.size:   # нестрого: вставка в конец разрешена
            return
        self.size += 1

        if index == 0:                       # особый случай: новая голова
            self.head = Node(val, self.head)
            return

        cur = self.head
        for _ in range(index - 1):           # встали за один шаг до
            cur = cur.next
        cur.next = Node(val, cur.next)       # Node сам сохранит старую ссылку

    def deleteAtIndex(self, index: int) -> None:
        if index < 0 or index >= self.size:
            return
        self.size -= 1

        if index == 0:                       # особый случай: сдвигаем голову
            self.head = self.head.next
            return

        cur = self.head
        for _ in range(index - 1):
            cur = cur.next
        cur.next = cur.next.next
```

**Как это читать.** Каждый изменяющий метод состоит из трёх частей: валидация индекса → правка `size` → работа с указателями, где нулевой индекс отрезан отдельной веткой с ранним `return`. Конструктор `Node(val, cur.next)` заодно избавляет от временной переменной `old_next` — новый узел получает старую ссылку прямо при создании.

## Реализация: с фиктивной головой

Ту же задачу можно написать без единого особого случая. Заводим постоянный пустой узел перед настоящей головой — и индекс 0 становится обычным индексом.

```python
class MyLinkedList:
    def __init__(self):
        self.dummy = Node()                  # заглушка, в данных не участвует
        self.size = 0

    def _node_before(self, index: int) -> Node:
        """Узел, стоящий за один шаг до позиции index. Для index=0 это заглушка."""
        cur = self.dummy
        for _ in range(index):
            cur = cur.next
        return cur

    def get(self, index: int) -> int:
        if index < 0 or index >= self.size:
            return -1
        return self._node_before(index).next.val

    def addAtHead(self, val: int) -> None:
        self.addAtIndex(0, val)

    def addAtTail(self, val: int) -> None:
        self.addAtIndex(self.size, val)

    def addAtIndex(self, index: int, val: int) -> None:
        if index < 0 or index > self.size:
            return
        prev = self._node_before(index)
        prev.next = Node(val, prev.next)     # ветки для index == 0 больше нет
        self.size += 1

    def deleteAtIndex(self, index: int) -> None:
        if index < 0 or index >= self.size:
            return
        prev = self._node_before(index)
        prev.next = prev.next.next           # голова удаляется так же, как все
        self.size -= 1
```

Разница видна сразу: обе операции сжались до двух строк, а вся навигация ушла в один общий `_node_before`. Настоящая голова теперь всегда `dummy.next` — отдельного поля `head` просто нет, а значит, нечему и рассинхронизироваться. Приём разобран отдельно: [Фиктивный узел](../../Алгоритмы/Приёмы/Фиктивный%20узел.md).

## Сложность

| Операция | Время | Почему |
|---|---|---|
| `get(index)` | $O(n)$ | нет прямой адресации, идём по цепочке |
| `addAtHead` | $O(1)$ | переставить одну ссылку |
| `addAtTail` | $O(n)$ | нужно дойти до конца |
| `addAtIndex` | $O(n)$ | дойти до `index - 1` |
| `deleteAtIndex` | $O(n)$ | то же самое |

Линейна не сама правка указателей — она всегда $O(1)$, — а **дорога до нужного места**. Это общее свойство связных списков и главная причина, по которой [массив](../../Данные/Структуры%20данных/Массив.md) остаётся выбором по умолчанию.

> **`addAtTail` можно ускорить до $O(1)$**, если хранить ещё и указатель на хвост. Но выигрыш частичный: удаление последнего узла в односвязном списке всё равно $O(n)$ — чтобы снять хвост, нужен его предшественник, а прийти к нему можно только с головы. Полностью проблему решает [двусвязный список](../../Данные/Структуры%20данных/Связный%20и%20двусвязный%20список.md#двусвязный-список).

## Ловушки

- **Перепутать границы** `>` и `>=` у вставки и удаления (см. врезку выше) — самая частая причина отказа.
- **Забыть обновить `size`.** Тогда валидация начнёт врать, и ошибка вылезет не там, где её сделали.
- **Обновить `size` до валидации.** Инкремент должен идти после проверки индекса, иначе отклонённый вызов испортит счётчик.
- **Забыть `return` после ветки с нулевым индексом.** Управление провалится в общий код, и узел вставится дважды.
- **Удалить голову, не двигая `self.head`.** Не падает, просто молча не работает — тестами ловится, глазами почти нет.
