# Жадные алгоритмы

**Жадный алгоритм** (greedy) — на каждом шаге делает **локально оптимальный** выбор в надежде, что из таких шагов сложится глобальный оптимум. Ключевая черта — **никогда не пересматривает** прошлые решения: выбрал — идёт дальше.

> **Аналогия:** сдача монетами. Нужно выдать 41 рубль — берёшь самую крупную монету, что не превышает остаток: 25 → 10 → 5 → 1. Не перебираешь варианты, просто каждый раз хватаешь самое большое.

Это делает жадные алгоритмы **очень быстрыми** (обычно сортировка + один проход), но опасными: локальный оптимум не всегда ведёт к глобальному.

---

### Когда жадность даёт оптимум

Жадный алгоритм корректен только при двух условиях:

1. **Свойство жадного выбора** (greedy choice property) — глобальный оптимум **достижим** последовательностью локально оптимальных выборов. Сделав жадный выбор сейчас, мы не отрезаем себе путь к лучшему решению.
2. **Оптимальная подструктура** — оптимум задачи содержит оптимумы подзадач (то же условие, что у [ДП](../../Алгоритмы/Стратегии/Динамическое%20программирование.md)).

Выполнены оба — жадность даёт правильный ответ и **быстрее** ДП (не нужно перебирать все варианты). Не выполнено первое — жадность **ошибается**, нужна [ДП](../../Алгоритмы/Стратегии/Динамическое%20программирование.md) или [backtracking](../../Алгоритмы/Стратегии/Поиск%20с%20возвратом.md).

> Главная ловушка: жадность **соблазнительна и часто неверна**. То, что решение «выглядит оптимальным на каждом шаге», ничего не гарантирует — свойство жадного выбора нужно **доказать**, а не предположить.

---

### Где жадность работает, а где нет

**Размен монет.** Для «канонических» систем (рубли, доллары) жадность оптимальна. Для произвольных номиналов — **нет**:

```python
def greedy_coins(coins, amount):
    coins.sort(reverse=True)
    result = []
    for c in coins:
        while amount >= c:
            amount -= c
            result.append(c)
    return result

greedy_coins([1, 5, 10, 25], 41)   # → [25, 10, 5, 1] — оптимально
greedy_coins([1, 3, 4], 6)         # → [4, 1, 1] (3 монеты), а оптимум 3+3 (2!) — жадность ошиблась
```

Для номиналов `[1, 3, 4]` правильный ответ даёт [ДП](../../Алгоритмы/Стратегии/Динамическое%20программирование.md#пример-посложнее--размен-монет).

**Выбор заявок (interval scheduling).** Максимум непересекающихся встреч. Жадность оптимальна, если брать заявки по **раннему времени окончания**:

```python
def max_activities(intervals):
    intervals.sort(key=lambda x: x[1])      # сортировка по времени ОКОНЧАНИЯ — ключ к корректности
    count, last_end = 0, float("-inf")
    for start, end in intervals:
        if start >= last_end:               # не пересекается с последней взятой
            count += 1
            last_end = end
    return count

max_activities([(1, 3), (2, 5), (4, 7), (6, 8)])   # → 3
```

Интуиция: кто освобождается раньше — оставляет больше места остальным.

**Другие классические жадные:**

- **Дробный рюкзак** — берём предметы по убыванию отношения «ценность/вес», последний можно взять частично. Оптимально. _(А вот рюкзак 0/1, где предмет неделим, жадность НЕ решает — только [ДП](../../Алгоритмы/Стратегии/Динамическое%20программирование.md).)_
- **[Код Хаффмана](../../Алгоритмы/Поиск/Код%20Хаффмана.md)** — на каждом шаге сливаем два самых редких символа. Строит оптимальный префиксный код.
- **[Алгоритм Дейкстры](../../Алгоритмы/Поиск/Алгоритм%20Дейкстры.md)** — каждый раз берём ближайший необработанный узел; это жадный выбор, который для неотрицательных весов корректен.

### Шесть каноничных задач — и ключ к каждой

Жадная задача решается, когда найден **правильный ключ сортировки**. Дальше это один проход. Ниже — типовой набор; полезно смотреть не на условия, а на колонку «ключ».

| Задача | Ключ сортировки / жадный выбор | Почему верно |
|---|---|---|
| **Размен монет** (система монет каноническая, напр. рубли) | брать самую крупную монету, что не больше остатка | у канонической системы крупная монета всегда в оптимуме. ⚠️ Для произвольных номиналов **неверно** — см. контрпример `[1, 3, 4]` выше |
| **Специи** (дробный рюкзак) | по убыванию «ценность / вес», последний предмет берём частично | делимость снимает риск: место всегда занято самым выгодным материалом |
| **Рекламная кампания** | оба массива отсортировать одинаково и перемножить попарно | максимум суммы произведений даёт сопоставление «большое с большим» (неравенство перестановок) |
| **Сбор подписей** (покрытие точками) | сортировать по **правому** концу отрезка, ставить точку в конец первого непокрытого | та же логика, что в выборе заявок: точка в правом конце покрывает максимум последующих |
| **Количество призов** (сумма различных слагаемых) | выдавать призы $1, 2, 3, \dots$, пока остаток больше следующего; остаток добавить к последнему | минимальные слагаемые дают максимальное их количество |
| **Максимальный оклад** (склейка чисел) | сортировать по правилу «$a+b$ или $b+a$ — что больше как строка» | лексикографическое сравнение склеек, а не самих чисел |

Последняя — самая коварная, потому что наивный ключ не работает:

```python
from functools import cmp_to_key

куски = ["3", "30", "34", "5", "9"]

# НЕПРАВИЛЬНО — сортировка самих строк по убыванию:
"".join(sorted(куски, reverse=True))              # → '9534303'   порядок 9 5 34 30 3

# ПРАВИЛЬНО — сравнивать СКЛЕЙКИ в двух порядках:
#   "3" + "30" = "330"  против  "30" + "3" = "303"   →  "3" должен идти раньше
def сравнить(a, b):
    return (a + b < b + a) - (a + b > b + a)      # -1 → a раньше b

"".join(sorted(куски, key=cmp_to_key(сравнить)))  # → '9534330'   9 5 34 3 30
```

**Почему наивный ключ ломается.** Лексикографически `"30" > "3"` (общий префикс, дальше длиннее), поэтому обычная сортировка ставит `30` перед `3` и теряет 27 в результате. Ключ одного элемента в принципе не может знать о втором — значит нужен попарный компаратор [`cmp_to_key`](../../Библиотеки/Модули/Функциональные%20инструменты/functools.md#cmp_to_key--сортировка-через-сравнение-пары) (готовая реализация — там же). Опора по сравнению строк — [Лексикографический порядок](../../Ядро%20языка/Лексикографический%20порядок.md); на LeetCode это [Largest Number #179](https://leetcode.com/problems/largest-number/).

> 🔴 **Жадный без доказательства — это угадывание.** На секции спросят не решение, а **почему жадный выбор верен**. По каждой задаче выше проговори обменный аргумент (следующий раздел): «возьмём оптимум, заменим его первый шаг на жадный — не ухудшилось».

---

### Как доказать корректность — обменный аргумент

**Обменный аргумент** (exchange argument) — стандартный способ доказать, что жадность оптимальна: берём произвольное оптимальное решение и показываем, что его можно шаг за шагом **превратить** в жадное, ни разу не ухудшив. Значит, жадное — не хуже любого оптимального, то есть само оптимально.

_Для выбора заявок: если оптимум взял заявку, кончающуюся позже жадной, — заменим её на жадную (та кончается раньше, значит не мешает остальным). Решение не ухудшилось._

### Жадность против ДП

Обе требуют оптимальной подструктуры, но по-разному ищут ответ:

| |Жадный|[ДП](../../Алгоритмы/Стратегии/Динамическое%20программирование.md)|
|---|---|---|
|Выбор на шаге|один локально лучший, без пересмотра|перебирает все варианты, берёт лучший|
|Скорость|очень быстро (сортировка + проход)|медленнее (все состояния)|
|Корректность|только при свойстве жадного выбора|всегда, если есть подструктура|
|Риск|легко получить неверный ответ|надёжно|

> Правило: попробуй жадность (она проще и быстрее) — но **докажи** свойство жадного выбора (обменным аргументом) или проверь на контрпримере. Не доказывается — переходи к [ДП](../../Алгоритмы/Стратегии/Динамическое%20программирование.md).

---

### Когда применять

- Задача на оптимизацию, где на каждом шаге виден **очевидно лучший** локальный выбор.
- Есть **сортировка-ключ**, после которой одно прохождение даёт ответ (по окончанию, по отношению, по весу).
- Ты можешь **доказать** корректность или это известная жадная задача (Хаффман, Дейкстра, MST-алгоритмы Прима/Краскала).

> Обзор всех стратегий и их сравнение — Алгоритмические стратегии. Контрпример к жадности почти всегда решается [ДП](../../Алгоритмы/Стратегии/Динамическое%20программирование.md).
