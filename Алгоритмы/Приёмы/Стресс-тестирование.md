# Стресс-тестирование

**Стресс-тестирование** (stress testing) — способ найти вход, на котором быстрое решение ошибается: программа сама генерирует тысячи случайных **маленьких** тестов и сравнивает ответ быстрого решения с заведомо верным медленным. Первое расхождение — готовый контрпример.

> **Аналогия:** два калькулятора. Один умный и быстрый, но, возможно, с багом. Другой тупой и медленный, но точно не врёт. Даёшь обоим одни и те же случайные числа, пока ответы не разойдутся. Разошлись — вот он, баг, вместе с числом, которое его вызывает.

Приём решает конкретную боль: **вердикт есть, а теста нет**. Яндекс Контест показывает только «Wrong answer на тесте 14» — сам тест скрыт намеренно (иначе решение можно подогнать через `if`). Гадать в такой ситуации можно час; стресс-тест находит контрпример за минуту.

---

### Зачем это тебе

- **Официальное требование.** Страница отбора Яндекса прямо советует: решение не проходит проверку — *«попробуйте учесть возможные краевые случаи, написать стресс-тесты»*. А в [Тренировках по алгоритмам](https://yandex.ru/yaintern/training/algorithm-training) это **весь блок 1**: «Тестирование собственной программы» + «Автоматизация тестирования» — *«напишем свою систему для автоматического тестирования и поиска “особых случаев”, которые ломают любое, даже самое правдоподобное, решение»*.
- **Главный KPI контеста — доля задач, сданных с первой попытки.** Руководитель группы разработки Яндекса: *«лучше сдать 3 задачи с первой попытки, чем 10 — с пятой»*. Стресс-тест — основной инструмент, который эту долю поднимает: он ловит баг **до** отправки.
- **Ключевое слово — «правдоподобное».** Стресс-тест бьёт не по решениям, которые очевидно сломаны, а по тем, которые выглядят верными и проходят твои примеры из условия. Именно они и получают WA.

---

### Три компонента

```
                    ┌─────────────┐
        ┌──────────▶│   brute()   │──── эталонный ответ ───┐
        │           │ тупой, но   │                        │
   ┌────┴────┐      │ точно верный│                        ▼
   │  gen()  │      └─────────────┘                  ┌───────────┐
   │случайный│                                       │ ответы == │
   │  ВХОД   │      ┌─────────────┐                  │     ?     │
   └────┬────┘      │   fast()    │                  └─────┬─────┘
        │           │ быстрый, но │                        │
        └──────────▶│ подозрительн│──── проверяемый ───────┘
                    └─────────────┘        ответ           │
                                                   ┌───────┴───────┐
                                                 равны         РАЗОШЛИСЬ
                                                   │               │
                                              следующая     печатаем вход —
                                              итерация      это контрпример
```

1. **`brute()` — эталон.** Тупое решение в лоб: полный перебор, $O(n^2)$ или $O(2^n)$ — скорость не важна, важна **гарантированная правильность**. Его пишешь так, чтобы в нём невозможно было ошибиться.
2. **`gen()` — генератор.** Случайный вход **маленького** размера (см. ниже — это критично).
3. **Цикл сравнения.** Гоняешь оба на одном входе, пока ответы не разойдутся.

### Базовый шаблон

Один файл, без bash-скриптов и внешних инструментов — всё на [random](../../Библиотеки/Модули/Работа%20с%20числами/random.md):

```python
import random

def brute(a):                      # эталон: перебрать все подотрезки в лоб
    return max(sum(a[i:j])
               for i in range(len(a))
               for j in range(i + 1, len(a) + 1))

def fast(a):                       # проверяемое решение
    ...

def gen():                         # маленький случайный вход
    n = random.randint(1, 8)                     # длина 1–8
    return [random.randint(-3, 3) for _ in range(n)]   # значения -3..3

for _ in range(10_000):
    a = gen()
    if brute(a) != fast(a):
        print("контрпример:", a)
        print("  brute:", brute(a), " fast:", fast(a))
        break
else:
    print("10 000 тестов — расхождений нет")
```

`for/else` здесь удобен: `else` выполняется, только если цикл **не** прервался через `break` — то есть контрпример не нашёлся ([Циклы Python](../../Ядро%20языка/Циклы%20Python.md)).

---

### Почему тесты обязаны быть маленькими

Главная ошибка новичка — генерировать массив на 1000 элементов. Тогда стресс-тест честно найдёт контрпример, но отлаживать его будет невозможно.

- **Размер 1–8, значения из узкого диапазона** (`-3..3`). Контрпример вида `[-2, 1, -1]` читается глазами за секунду, и по нему сразу видно, *какая* идея сломалась.
- **Узкий диапазон значений — не экономия, а инструмент.** `randint(-3, 3)` вместо `randint(-10**9, 10**9)` даёт много **дубликатов, нулей и повторов** — то есть ровно те вырожденные конфигурации, на которых решения и падают. Со случайными девятизначными числами дубликат не выпадет никогда.
- **Маленькие тесты быстрее.** Брутфорс за $O(2^n)$ на `n ≤ 8` — это мгновенно, можно прогнать 10 000 итераций за секунды.

> **Правило:** генератор должен создавать вход, который ты готов **прочитать вслух**. Не влезает в строку — уменьшай границы.

---

### Краевые случаи, которые генератор обязан уметь выдать

Случайность сама по себе не гарантирует, что вырожденный вход выпадет. Заложи их явно:

- **пустой вход** и **один элемент** — `randint(0, 8)`, а не `randint(2, 8)`;
- **все элементы одинаковые** — узкий диапазон значений;
- **отрицательные числа и ноль** — самая частая дыра;
- **уже отсортированный / обратно отсортированный** вход — иногда полезно генерировать отдельно;
- **границы условия** — если сказано `1 ≤ a[i] ≤ 10^9`, проверь и `1`, и `10^9`.

Языковые подвохи, которые стресс-тест ловит попутно, — в [Ловушки Python](../../Ядро%20языка/Ловушки%20Python.md) _(например, `nan` ломает `sorted`, а `float` — сравнение на равенство)_.

### Когда эталона нет: проверка инвариантов

Иногда написать `brute()` невозможно — либо задача такова, что перебор и есть само решение, либо **верных ответов несколько** (найти *любой* путь, *любую* перестановку). Тогда сравнивать `brute(a) == fast(a)` бессмысленно: оба ответа верны, но разные.

Выход — проверять не ответ, а **свойства** ответа — инварианты (это называется **property-based testing**, тестирование по свойствам):

```python
def check(a, result):
    # для сортировки: вместо сравнения с эталоном проверяем два инварианта
    assert all(result[i] <= result[i+1] for i in range(len(result)-1)), "не отсортирован"
    assert sorted(a) == sorted(result), "элементы потерялись или размножились"
```

Типовые инварианты:

| Задача | Что проверять вместо равенства |
|---|---|
| Сортировка | результат неубывает **и** мультимножество элементов совпало |
| Найти путь в графе | путь существует, рёбра реальны, начало и конец верные |
| Разбить на группы | группы не пересекаются и в сумме дают исходное множество |
| Найти максимум чего-либо | ответ достижим **и** ничего лучше брутфорс не нашёл |

> Второй инвариант в строке про сортировку важнее первого: `return []` даёт идеально «отсортированный» результат. Проверка только одного свойства пропускает целый класс багов.

---

### Когда стресс-тест не поможет

Приём мощный, но не универсальный — не трать на него время, если:

- **Нет и не может быть эталона** — брутфорс совпадает с решением (нечего сравнивать), и свойств тоже не сформулировать.
- **Баг проявляется только на больших данных** — переполнение, `TL` (Time Limit), исчерпание [предела рекурсии](../../Библиотеки/Модули/Система%20и%20окружение/sys.md#предел-рекурсии). Маленькие тесты этого не увидят: там нужен не стресс-тест, а анализ сложности и один большой тест.
- **Ошибка в чтении ввода/формате вывода** (`PE`) — стресс-тест сравнивает значения внутри программы, а не то, как ты их напечатал.
- **Решение недетерминированное** — два запуска дают разное, сравнение бессмысленно без фиксации `random.seed()`.

> Стресс-тест отвечает на вопрос **«на чём я ошибаюсь?»**, а не «почему медленно». Для «медленно» — Вычислительная сложность и [Профилирование и отладка](../../Библиотеки/Модули/Отладка%20и%20утилиты/Профилирование%20и%20отладка.md).

---

### Стресс-тест ≠ юнит-тест

Частая путаница: и то и другое «тесты», но задачи у них разные и подменять одно другим нельзя.

| | **Стресс-тест** | **Юнит-тест** ([Юнит-тестирование Python](../../Библиотеки/Сторонние/Тесты/Юнит-тестирование%20Python.md)) |
|---|---|---|
| **Вопрос** | На каком входе я ошибаюсь? | Работает ли код так, как задумано? |
| **Кто придумывает вход** | генератор, случайно | ты, вручную |
| **Что сравнивает** | ответ с **эталонным решением** | ответ с **ожидаемым значением** |
| **Нужен эталон** | да (или инварианты) | нет |
| **Количество тестов** | тысячи, одноразовые | десятки, зафиксированы навсегда |
| **Результат** | **контрпример** (новое знание) | pass / fail (подтверждение) |
| **Где живёт** | контест, отладка, выбрасывается после | репозиторий, CI, живёт с кодом |

Коротко: юнит-тест **проверяет то, что ты уже придумал**; стресс-тест **придумывает за тебя то, о чём ты не подумал**. На контесте нужен второй, в `tasks-api` — первый.

### Сквозной пример: как это ловит реальный баг

Классика — **максимальная сумма подмассива**. Быстрое решение (алгоритм Кадане) выглядит абсолютно правдоподобно и проходит все примеры из условия.

**Шаг 1. Эталон — перебор всех подотрезков, $O(n^3)$.** Ошибиться тут негде:

```python
def brute(a):
    return max(sum(a[i:j])
               for i in range(len(a))
               for j in range(i + 1, len(a) + 1))
```

**Шаг 2. Быстрое решение, $O(n)$** — с типичным багом:

```python
def fast(a):
    best = cur = 0                 # ← БАГ: старт с нуля
    for x in a:
        cur = max(0, cur + x)      # ← БАГ: «обнуляем, если ушли в минус»
        best = max(best, cur)
    return best
```

Логика кажется безупречной: копим сумму, ушли в минус — начинаем заново. На `[1, -2, 3, 4]` даёт `7` — верно.

**Шаг 3. Генератор — обязательно с отрицательными:**

```python
def gen():
    n = random.randint(1, 6)
    return [random.randint(-3, 3) for _ in range(n)]
```

**Шаг 4. Запуск** — контрпример находится за доли секунды:

```
контрпример: [-2]
  brute: -2   fast: 0
```

**Шаг 5. Разбор.** Вход из одного элемента `[-2]`. Брутфорс обязан взять хоть один элемент и отвечает `-2`. А `fast` стартует с `best = 0` и, обнуляя `cur`, возвращает `0` — то есть неявно считает, что можно взять **пустой** подмассив. Баг проявляется **только когда все числа отрицательные** — и ровно этого случая не было в примерах условия.

**Шаг 6. Фикс** — стартовать с первого элемента, а не с нуля:

```python
def fast(a):
    best = cur = a[0]
    for x in a[1:]:
        cur = max(x, cur + x)      # либо продолжаем, либо начинаем с x — но берём хотя бы один
        best = max(best, cur)
    return best
```

Перезапуск: `10 000 тестов — расхождений нет`. Вот это и есть «особый случай, который ломает правдоподобное решение».

### Второй классический баг — «два максимума» и дубликаты

Задача: найти максимальное произведение двух **различных** элементов массива. Наивное решение $O(n^2)$ перебирает пары, быстрое $O(n)$ ищет два наибольших — и вот здесь прячется ошибка, которую видно только стресс-тестом:

```python
# НЕПРАВИЛЬНО — второй максимум ищется по ЗНАЧЕНИЮ:
def fast(a):
    m1 = max(a)
    m2 = max(x for x in a if x != m1)     # на [5, 5] упадёт: подходящих элементов нет
    return m1 * m2

# ПРАВИЛЬНО — исключаем по ИНДЕКСУ, а не по значению:
def fast(a):
    i = a.index(max(a))                   # позиция первого максимума
    m2 = max(a[:i] + a[i + 1:])           # максимум среди ОСТАЛЬНЫХ позиций
    return a[i] * m2

fast([5, 5])                              # → 25   правильно: элементы различны по индексу
```

Условие говорит «два различных элемента» — то есть различных **по позиции**, а не по значению. Генератор со **узким диапазоном значений** (`randint(0, 3)` на массиве из 2–5 элементов) выдаёт дубликаты почти в каждом тесте и находит это за секунды; генератор с `randint(0, 10**9)` не найдёт никогда. Это ровно то, о чём раздел «краевые случаи, которые генератор обязан уметь выдать»: **диапазон значений важнее размера массива**.

### Как встроить в свой процесс

Положи шаблон в `algorithms/_tools/stress.py` и переиспользуй: меняются только `brute`, `fast` и `gen` — каркас один и тот же. Дальше — привычка:

```
Решил задачу → примеры прошли → ПРОГНАЛ СТРЕСС (30 сек) → отправил
                                        ↑
                            здесь ловятся почти все WA
```

Тридцать секунд на стресс-тест дешевле, чем одна неудачная попытка на контесте, — и намного дешевле, чем «обидный баг» на секции, где запустить код нельзя вовсе.

### Связи

- Вычислительная сложность — брутфорс сознательно медленный: $O(n^2)$/$O(2^n)$ на `n ≤ 8` мгновенен; вместе со стресс-тестом это блок 1 программы Тренировок Яндекса
- [Юнит-тестирование Python](../../Библиотеки/Сторонние/Тесты/Юнит-тестирование%20Python.md) — соседний, но **другой** вид тестов (таблица выше); там же `unittest`, моки и пирамида тестирования
- [Ловушки Python](../../Ядро%20языка/Ловушки%20Python.md) — краевые случаи, которые стресс-тест находит автоматически
- [random](../../Библиотеки/Модули/Работа%20с%20числами/random.md) — генерация входов; `random.seed()` для воспроизводимости
- [Профилирование и отладка](../../Библиотеки/Модули/Отладка%20и%20утилиты/Профилирование%20и%20отладка.md) — для «медленно», когда стресс-тест уже сказал «считает верно»
- Проблема индукции — почему «10 000 тестов прошли» не доказывает правильность: то же рассуждение, что у Юма и Поппера, только про код

> **Философская сноска.** Стресс-тест никогда не говорит «решение верно» — только «контрпример не найден». Это не осторожность формулировки, а прямое следствие проблемы индукции: подтверждения не доказывают общее утверждение, опровергает — один контрпример. Поппер сделал из этого метод науки: не подтверждай, а пытайся сломать. Стресс-тест — ровно этот метод, применённый к своему коду.
