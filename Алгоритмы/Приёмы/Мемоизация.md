# Мемоизация

**Мемоизация** — приём, при котором функция запоминает свои ответы по аргументам: повторный вызов с теми же аргументами возвращает готовое значение вместо повторного счёта. Это [ДП](../../Алгоритмы/Стратегии/Динамическое%20программирование.md) «сверху вниз»: пишешь обычную [рекурсию](../../Алгоритмы/Стратегии/Рекурсия.md) и навешиваешь кэш.

> **Аналогия:** решаешь задачник и выписываешь ответы на поля. Встретил тот же пример — не считаешь заново, а смотришь на поля.

Приём выглядит как одна строка `@lru_cache`, и в учебных примерах так и есть. Эта заметка — про то, что ломается, когда задача перестаёт быть учебной.

> **Где что лежит:** *почему* мемоизация превращает экспоненту в линию — в [Динамическое программирование](../../Алгоритмы/Стратегии/Динамическое%20программирование.md); описание самого декоратора и его каталог — в [functools](../../Библиотеки/Модули/Функциональные%20инструменты/functools.md); здесь — **как писать кэш руками и на какие грабли наступают**.

### Ручной кэш: куда его класть

Простейший вид — словарь на входе:

```python
def fib(n, кэш={}):          # ⚠️ так писать НЕЛЬЗЯ, см. ниже
    ...
```

Изменяемое значение по умолчанию создаётся **один раз при определении функции** ([классическая ловушка Python](../../Ядро%20языка/Ловушки%20Python.md)), поэтому кэш переживёт все вызовы и все тесты. То же и с кэшем в глобальной переменной модуля. Правильное место — **замыкание внутренней функции**:

```python
def fib(n):
    кэш = {}                                  # живёт ровно один внешний вызов

    def внутр(k):
        if k < 2:
            return k
        if k not in кэш:                      # считаем только то, чего нет
            кэш[k] = внутр(k - 1) + внутр(k - 2)
        return кэш[k]

    return внутр(n)
```

Внешняя функция задаёт границу жизни кэша, внутренняя рекурсирует. Это тот же паттерн, что у обёртки в [backtracking](../../Алгоритмы/Стратегии/Поиск%20с%20возвратом.md): наружу — чистая сигнатура, внутрь — служебное состояние.

**Три места для кэша и их цена:**

| Куда положить | Живёт | Когда годится |
|---|---|---|
| Аргумент по умолчанию `кэш={}` | вечно, скрыто | ❌ никогда — течёт и ломает тесты |
| Глобальная переменная модуля | вечно, явно | таблица, которую считают один раз на процесс |
| Замыкание внутренней функции | один внешний вызов | ✅ по умолчанию: LeetCode, собес, любой метод класса |

### Потолок, о который бьётся мемоизация

У решения «сверху вниз» есть предел, которого нет у табуляции: **глубина рекурсии**. Ровно та задача, ради которой ДП и заводят — «дай тысячное число Фибоначчи», — валит мемоизированную версию:

```python
from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

fib(1000)        # RecursionError: maximum recursion depth exceeded
```

Причина простая: кэш убирает **повторные** вызовы, но цепочка `fib(1000) → fib(999) → … → fib(1)` остаётся, и это 1000 кадров стека при лимите 1000.

> 🔴 **`@lru_cache` вдобавок режет доступную глубину — и `sys.setrecursionlimit` её не поднимает.** Декоратор реализован на C, поэтому каждый рекурсивный вызов проходит через кадр C-стека, а с Python 3.12 глубина C-рекурсии ограничена отдельно и `setrecursionlimit` на неё не влияет. Замер на Python 3.13.14 при `setrecursionlimit(50000)`:
>
> | Как кэшируем | Достигнутая глубина |
> |---|---|
> | Чистая Python-рекурсия без кэша | 49 998 |
> | Ручной `dict` в замыкании | 49 998 |
> | `@lru_cache` | **999** |
>
> То есть на глубоких ДП ручной словарь работает там, где однострочник падает. Это [известный баг-репорт CPython](https://github.com/python/cpython/issues/112215), а не особенность конкретной машины.

**Что делать, если нужна именно рекурсия на большой глубине:**

1. **Перейти на табуляцию** — снизу вверх стека нет вовсе. Это правильный ответ в 9 случаях из 10.
2. **Ручной `dict` вместо `@lru_cache`** — снимает C-потолок, но Python-лимит поднимать всё равно придётся.
3. **Прогреть кэш снизу** — вызвать `fib(100)`, `fib(200)`, … `fib(1000)`: каждый вызов уходит вглубь не больше чем на 100 кадров, а дальше берёт готовое. Работает, но это уже табуляция, притворяющаяся рекурсией.

```python
sys.setrecursionlimit(30000)     # ⚠️ слишком высокий лимит роняет интерпретатор целиком
```

### `@lru_cache` на методе класса держит объект живым

Кэш у декоратора **один на класс**, а не на экземпляр, и ключ включает `self`. Значит ссылка на объект лежит в кэше и мешает сборщику мусора — [дока говорит об этом прямо](https://docs.python.org/3/library/functools.html#functools.lru_cache): кэш хранит ссылки на аргументы и возвращаемые значения, пока они не вытеснятся или кэш не очистят.

```python
class Solution:
    @lru_cache(maxsize=None)     # ⚠️ self попадает в ключ кэша
    def fib(self, n):
        return n if n < 2 else self.fib(n - 1) + self.fib(n - 2)
```

Проверка через `weakref`: после `del` объекта и `gc.collect()` экземпляр с таким декоратором **остаётся жив**; тот же класс с кэшем на внутренней функции — умирает как положено. На LeetCode это незаметно, в долгоживущем сервисе — [утечка памяти](https://docs.python.org/3/faq/programming.html#faq-cache-method-calls).

Три рабочих замены:

- **кэш на внутренней функции** внутри метода — как в примере выше, кэш умирает вместе с вызовом;
- **`@cached_property`** — если метод без аргументов: результат хранится на экземпляре и освобождается вместе с ним;
- **вынести чистую функцию из класса** и кэшировать её — тогда `self` в ключ не попадает вовсе.

### Остальные грабли

**Аргументы должны быть хешируемыми.** Список или словарь в аргументах — `TypeError`. Лечится преобразованием на границе: `tuple(nums)` снаружи, кэшируемая функция работает с кортежем. Для сетки удобнее кэшировать координаты `(i, j)`, а саму сетку взять из замыкания.

**Функция должна быть чистой.** Кэш не знает о внешнем состоянии: если ответ зависит от поля объекта, времени или файла — вернётся устаревшее значение. Ровно поэтому чистота здесь не стилистика, а условие корректности.

**Возвращаемый список кэш не защищает.** Отдали из кэша список, вызывающий код его изменил — испорчен кэш. Возвращай кортежи или копию.

**Кэш переживает тесты.** Глобально задекорированная функция помнит ответы между тестами; в `setUp` нужен `f.cache_clear()`.

**Мемоизация не всегда даёт что-то.** Выгода ровно там, где подзадачи **перекрываются**. У [«разделяй и властвуй»](../../Алгоритмы/Стратегии/Разделяй%20и%20властвуй.md) они не пересекаются — кэш только тратит память. Дешёвая проверка: посчитать, сколько разных состояний бывает, и сравнить с числом вызовов; равны — кэшировать нечего.

### Мемоизация и кэш в проде — не одно и то же

Слова похожи, задачи разные.

| | Мемоизация | Кэш в сервисе |
|---|---|---|
| Что хранит | результаты чистой функции | ответы БД, API, отрендеренные страницы |
| Кто источник истины | сама функция | внешнее хранилище |
| Главная проблема | глубина стека, хешируемость | инвалидация, устаревание, консистентность |
| Вытеснение | обычно не нужно (кэш живёт вызов) | обязательно — [LRU](../../Алгоритмы/Задачки/LRU-кэш.md) и его родня |

Общий у них только механизм «посмотри в таблицу, прежде чем считать». Всё сложное в проде — про то, **когда выбрасывать**; в мемоизации выбрасывать не приходится, потому что ответ чистой функции не устаревает.
