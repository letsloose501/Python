# Стандартные потоки — stdin, stdout, stderr

> _`print` — не «вывод на экран», а запись в поток. Про экран программа не знает вовсе, и именно поэтому её можно подключить к файлу, конвейеру или другой машине, не тронув ни строки кода._

---

**Поток** (stream) — канал, по которому данные идут **последовательно** от источника к получателю. Что находится на другом конце — клавиатура, файл, другая программа, сетевое соединение — программе не важно: она просто читает из потока и пишет в поток.

Когда операционная система запускает процесс, она автоматически открывает ему **три потока**. Поэтому пользоваться ими можно сразу, ничего не открывая:

| Поток | Дескриптор | Назначение | По умолчанию |
|---|---|---|---|
| `sys.stdin` | `0` | откуда программа **читает** | клавиатура |
| `sys.stdout` | `1` | куда пишет **результат** | экран |
| `sys.stderr` | `2` | куда пишет **ошибки и диагностику** | экран |

Номера — это **файловые дескрипторы**, целые числа, которыми процесс адресует открытые файлы. Они те же самые, что в перенаправлениях оболочки (`2> ошибки.txt` — см. Перенаправление потоков).

В Python все три — **обычные файловые объекты**, поэтому их можно читать, писать, заменять и перенаправлять как любой файл ([io](../Библиотеки/Модули/Работа%20с%20файлами/io.md)).

## stdin и `input()`

`input()` — не магия, а тонкая обёртка над чтением строки из `sys.stdin`:

```python
имя = input("Имя: ")

# примерно то же самое вручную:
import sys
sys.stdout.write("Имя: ")
имя = sys.stdin.readline().rstrip("\n")     # ← rstrip обязателен
```

**Единственное содержательное отличие — символ новой строки.** `readline()` возвращает строку **вместе с `\n`**, а `input()` его срезает. Отсюда классическая ошибка: заменили `input()` на `sys.stdin.readline()` ради скорости — и сравнения строк перестали работать, потому что `"да\n" != "да"`.

Второе отличие: на конце ввода `input()` бросает `EOFError`, а `readline()` возвращает пустую строку `''`. Поэтому по `sys.stdin` удобно просто идти циклом — он сам кончается:

```python
for строка in sys.stdin:          # лениво, по одной строке, память не растёт
    обработать(строка.rstrip())
```

Подробнее про быстрое чтение на олимпиадных объёмах — [sys](../Библиотеки/Модули/Система%20и%20окружение/sys.md#быстрый-ввод-контест).

## stdout и `print()`

`print()` — тоже обёртка. Она пишет в `sys.stdout` и добавляет удобства:

```python
print(1, 2, 3)
# равносильно:
sys.stdout.write("1 2 3\n")
```

Что делает `print` сверх `write`:

- приводит объекты к строке через `str()` — `write` принимает **только** `str` и падает на числе;
- вставляет между аргументами разделитель `sep` (по умолчанию пробел);
- дописывает `end` в конце (по умолчанию `\n`);
- умеет писать в другой поток параметром `file`;
- умеет принудительно сбрасывать буфер параметром `flush`.

```python
print("без перевода строки", end="")
print("а", "б", sep="—")            # → а—б
print("ошибка!", file=sys.stderr)   # ← в поток ошибок
```

> `sys.stdout.write` возвращает число записанных символов. В интерактивной консоли это выглядит как лишнее число в выводе — не баг, а возвращаемое значение.

## Зачем нужен отдельный stderr

В терминале оба потока выглядят одинаково — обе строки просто появляются на экране. Разница проявляется, как только вывод **куда-то направляют**:

```bash
python script.py > log.txt
```

```
stdout ──▶ log.txt      результат ушёл в файл
stderr ──▶ экран        ошибка осталась видна
```

Это и есть смысл разделения: **результат работы можно отделить от сообщений о ходе работы**. Скрипт печатает данные в stdout, а прогресс и предупреждения в stderr — тогда `script.py > данные.csv` даёт чистый файл без мусора, а оператор всё равно видит, что происходит.

Отсюда практическое правило: **в stdout идёт только то, что является результатом**. Прогресс-бары, логи, предупреждения, приглашения ко вводу — в stderr. Именно поэтому [logging](../Библиотеки/Модули/Отладка%20и%20утилиты/logging.md) по умолчанию пишет в stderr, а не в stdout.

## Из чего состоит поток

Текстовый поток — это стопка из трёх слоёв, и знать о ней нужно, чтобы понимать буферизацию и как писать байты. Замер на CPython 3.13:

```
sys.stdout
  └─ _io.TextIOWrapper    str → bytes: кодировка, перевод строк
       └─ _io.BufferedWriter   буфер 8192 байта (io.DEFAULT_BUFFER_SIZE)
            └─ _io.FileIO      сырой дескриптор 1, системный вызов write()
```

Добраться до нижних слоёв можно атрибутами `.buffer` и `.raw`:

```python
sys.stdout.write("текст")            # str — через верхний слой
sys.stdout.buffer.write(b"\x89PNG")  # bytes — минуя кодировку
```

Так отдают двоичные данные (картинку, архив) в stdout, не ломая их перекодировкой. Обратное чтение — `sys.stdin.buffer.read()`.

> ⚠️ В библиотеке не полагайся на `.buffer` слепо: потоки могут быть подменены на `io.StringIO`, у которого этого атрибута нет вовсе. Официальная дока предупреждает об этом прямо.

## Буферизация — главная практическая ловушка

Запись в поток **не значит** запись на экран или в файл: данные копятся в буфере и уходят наружу пачкой. Правила разные для двух потоков, и в этом вся соль:

| Поток | В терминале (интерактивно) | В файл или конвейер |
|---|---|---|
| `stdout` | построчно | **блоками по 8 КБ** |
| `stderr` | построчно | **построчно** |

То есть **stderr сбрасывается сразу всегда, а stdout — только пока вывод идёт на терминал**. Стоит перенаправить вывод, и порядок строк ломается.

**Сделай → увидишь.** Программа чередует записи в два потока:

```python
import sys
for i in range(3):
    print(f"stdout {i}")
    print(f"stderr {i}", file=sys.stderr)
```

Запуск с перенаправлением в конвейер на CPython 3.13.14 даёт:

```
stderr 0        ← все три stderr вышли первыми,
stderr 1          потому что каждая строка сбрасывалась сразу
stderr 2
stdout 0        ← а stdout копился в буфере
stdout 1          и вылился целиком только при завершении процесса
stdout 2
```

Причина именно в таблице выше, а не в скорости выполнения. Отсюда две болезненные ситуации, знакомые каждому:

- **логи в Docker или CI приходят рывками либо теряются при падении** — процесс пишет в конвейер, буфер не успел сброситься;
- **логи и ошибки перемешаны не в том порядке** — как в замере.

Три способа починить, от точечного к глобальному:

```python
print("важное", flush=True)          # 1. одна строка
sys.stdout.reconfigure(line_buffering=True)   # 2. весь поток на построчный режим
```

```bash
python -u script.py                  # 3. запуск без буферизации
PYTHONUNBUFFERED=1 python script.py   #    то же переменной окружения
```

Проверено: варианты `-u` и `PYTHONUNBUFFERED=1` дают правильное чередование `stdout 0 / stderr 0 / stdout 1 …`. Именно `PYTHONUNBUFFERED=1` ставят в Dockerfile — это стандартная строка в образах с Python, и теперь понятно, зачем она там.

> **Версия имеет значение.** До Python 3.9 неинтерактивный `stderr` был буферизован **полностью**, а не построчно — на старых версиях терялись и сообщения об ошибках. Дока фиксирует это как «Changed in version 3.9».

## Кодировка

У текстового потока есть кодировка, и она задаётся при старте интерпретатора, а не берётся из файла:

```python
sys.stdout.encoding      # → 'utf-8'
```

На Windows это исторический источник боли: если кодировка потока не UTF-8, кириллица в выводе превращается в `UnicodeEncodeError` или мусор — при том что сам исходник в UTF-8. Лечится тремя способами:

```python
sys.stdout.reconfigure(encoding="utf-8")   # из кода
```

```bash
python -X utf8 script.py            # ключ интерпретатора
PYTHONIOENCODING=utf-8 python script.py    # переменная окружения
```

Тот же приём нужен, когда вывод уходит в файл через перенаправление: кодировка потока может отличаться от кодировки консоли.

## Куда на самом деле идёт вывод: `isatty()`

Программа может **спросить**, терминал на другом конце или нет:

```python
sys.stdout.isatty()      # True — терминал, False — файл/конвейер
```

Так работают приличные консольные утилиты: при выводе в терминал раскрашивают текст и рисуют прогресс-бар, а при перенаправлении в файл отдают чистый текст без управляющих последовательностей. Без этой проверки в файле оказывается мусор вида `\x1b[31m`.

## Перенаправление: снаружи и изнутри

Развилка, которую стоит держать в голове.

**Снаружи, оболочкой** — программа ничего не знает и не меняется (Перенаправление потоков):

```bash
python task.py < вход.txt > выход.txt 2> ошибки.txt
```

Именно так устроены системы автоматической проверки решений: вход подставляется файлом, вывод собирается файлом, программа при этом написана под обычные `input()` и `print()`.

**Изнутри, кодом** — временно подменить поток на время блока:

```python
import io, contextlib

буфер = io.StringIO()
with contextlib.redirect_stdout(буфер):
    print("это не попадёт на экран")

буфер.getvalue()        # → 'это не попадёт на экран\n'
```

Так ловят вывод чужой функции в тестах ([contextlib](../Библиотеки/Модули/Отладка%20и%20утилиты/contextlib.md), [io](../Библиотеки/Модули/Работа%20с%20файлами/io.md)). Оригиналы потоков всегда доступны в `sys.__stdout__`, `sys.__stdin__`, `sys.__stderr__` — на случай, если подменённый поток надо вернуть.

> ⚠️ `redirect_stdout` подменяет **объект Python**, а не дескриптор ОС. Вывод дочернего процесса, запущенного через subprocess, и вывод из C-расширений он **не перехватит** — они пишут в дескриптор `1` напрямую. Для них нужен `subprocess.PIPE` или подмена на уровне дескрипторов (`os.dup2`).

## Ловушки

- **`readline()` вместо `input()` без `rstrip()`.** Остаётся `\n`, сравнения ломаются молча.
- **Диагностика в stdout.** Прогресс и предупреждения в стандартном выводе портят результат при перенаправлении в файл. Всё, что не результат, — в stderr.
- **Ждать вывод в реальном времени из конвейера.** Без `flush`/`-u` stdout копится блоками по 8 КБ. Не баг, а буферизация.
- **`sys.stdout.write(число)`.** `write` принимает только `str`: `write(5)` — `TypeError`. `print` приводит сам.
- **Считать `redirect_stdout` полным перехватом.** Дочерние процессы и C-код пишут мимо него.
- **`2>&1` не в том месте.** Порядок важен: `команда > файл 2>&1` направит в файл оба потока, а `команда 2>&1 > файл` — только stdout, потому что stderr скопировал ещё **прежнее** назначение stdout (экран).
