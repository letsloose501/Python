# Модули и пакеты Python

> **Модуль** — это просто `.py`-файл, а **пакет** — папка с модулями. Они разбивают программу на части, которые можно переиспользовать и импортировать друг в друга, вместо одного гигантского файла.

---

Когда кода становится много, держать его в одном файле невозможно — его делят по смыслу: расчёт зарплаты отдельно, работа с базой отдельно. Каждый файл — **модуль**, папки модулей — **пакеты**. Механизм `import` связывает их: один файл берёт функции и классы из другого. Множество пакетов, собранных под круг задач, — **библиотека** (иерархия модуль → пакет → библиотека → фреймворк — в Абстракции).

## Модуль — файл .py

Любой `.py`-файл — модуль. Его имя — имя файла без расширения. Другой файл подключает его через `import`:

```python
# файл salary.py
def calculate_salary():
    print("Рассчитываю зарплату")
```
```python
# другой файл
import salary                 # подключить весь модуль
salary.calculate_salary()     # обращение через имя модуля
```

## Формы import

```python
import math                   # весь модуль → math.sqrt(9)
import datetime as dt         # с псевдонимом → dt.date(...)
from math import sqrt, pi     # только нужные имена → sqrt(9)
from math import sqrt as √    # имя с псевдонимом
from math import *            # ВСЁ в текущее пространство — не рекомендуется
```

> `from module import *` тянет все имена и легко создаёт конфликты (перекрывает существующие). Импортируй явно то, что нужно.

## Где делать импорты

По **[PEP 8](../Ядро%20языка/Стиль%20кода%20Python%20—%20PEP%208%20и%20Google%20Style%20Guide.md)** — **вверху файла**, после докстринга и до кода, тремя группами через пустую строку:

```python
import os                   # 1. стандартная библиотека
import sys

import requests             # 2. сторонние пакеты (из пакетного менеджера)

from application import db  # 3. свои модули
```

**Локальный импорт внутри функции** тоже легален и уместен, когда: нужно разорвать циклический импорт; зависимость тяжёлая или опциональная (грузить лениво, при вызове); ускорить старт. Имя тогда видно **только внутри функции**.

```python
def построить_график(data):
    import matplotlib.pyplot as plt   # тяжёлый импорт — только когда реально нужен
    plt.plot(data)
```

> Внутри функции нельзя `from module import *` — это **SyntaxError** (см. [Ловушки](#ловушки)). Точечный импорт (`from math import floor`) — можно.

## Пакет — папка с модулями

**Пакет** — папка, которую Python считает единым «супермодулем». Внутри — модули и, по традиции, файл **`__init__.py`** (может быть пустым): он помечает папку как пакет и выполняется при импорте пакета. Пакеты вкладываются друг в друга:

```
application/
├── __init__.py
├── salary.py           # application.salary
└── db/
    ├── __init__.py
    └── people.py       # application.db.people
```

Доступ к вложенным модулям — через точку, повторяющую структуру папок:

```python
from application.salary import calculate_salary
from application.db.people import get_employees
```

## Абсолютный и относительный импорт

**Абсолютный** — полный путь от корня проекта. Понятен и не ломается при перемещении файла — **предпочтителен** (PEP 8):

```python
from application.db.people import get_employees
```

**Относительный** — от **текущего пакета**, точками: `.` — этот пакет, `..` — на уровень выше. Короче при рефакторинге внутри пакета:

```python
# файл application/salary.py
from . import db                     # соседний подпакет application.db
from .db.people import get_employees # из application/db/people.py
from ..config import settings        # на уровень выше
```

> Относительный импорт работает **только внутри пакета** (файл импортируется как его часть). В скрипте, запущенном напрямую (`python salary.py`), он даст `ImportError: attempted relative import with no known parent package` — запускай через пакет (`python -m application.salary`) или бери абсолютный импорт.

## Как Python находит модуль

При `import x` Python ищет `x` по списку путей **`sys.path`**: сначала папка запускаемого скрипта, затем пути из `PYTHONPATH`, затем стандартная библиотека и установленные пакеты. Поэтому импорт работает относительно того, **откуда запущен** проект (обычно — корень с `main.py`).

```python
import sys
print(sys.path)     # список директорий, где Python ищет модули
```

## Область видимости и конфликты импортов

Импортированное имя попадает в то **пространство имён**, где стоит `import`: на уровне модуля — видно во всём файле; внутри функции — только в ней.

**Конфликт имён** — когда два импорта приносят одно имя. При явном импорте это видно и решаемо; при `import *` перекрытие происходит **молча**:

```python
from math import *      # sqrt отсюда
from numpy import *     # sqrt ТЕПЕРЬ отсюда — math.sqrt затенён незаметно
```

Поэтому `import *` опасен именно скрытыми конфликтами. С `import math` и `import numpy` оба живут раздельно: `math.sqrt` и `numpy.sqrt` не сталкиваются.

> Ещё конфликт — **затенение stdlib своим файлом**: назовёшь файл `math.py` или `random.py` — свой файл перекроет стандартный модуль, и `import math` возьмёт твой. Не называй файлы именами модулей стандартной библиотеки.

## Пакетный менеджер и установка пакетов

Стандартная библиотека идёт с Python, а сторонние пакеты ставят из репозитория **PyPI** (Python Package Index) **пакетным менеджером** — он же тянет их зависимости и следит за версиями.

```bash
pip install requests             # поставить пакет с PyPI
pip install "django==5.0"        # конкретная версия
pip freeze > requirements.txt    # зафиксировать версии проекта
pip install -r requirements.txt  # воспроизвести окружение на другой машине
```

- **`pip`** — стандартный менеджер (идёт с Python);
- **poetry**, **uv** — ещё и управляют зависимостями и окружением заодно (uv — очень быстрый);
- **conda** — научный стек, ставит и не-Python зависимости.

Ставить пакеты лучше в изолированное [виртуальное окружение](../Библиотеки/Модули/Система%20и%20окружение/venv.md) проекта — чтобы версии разных проектов не конфликтовали.

### Poetry — зависимости и окружение вместе

`pip` + `requirements.txt` + `venv` — три отдельных инструмента. **Poetry** объединяет их: одно описание проекта в `pyproject.toml`, автоматическое виртуальное окружение и **лок-файл** с точными версиями.

```bash
poetry new myproj               # создать проект со структурой
poetry add requests             # поставить пакет + записать в pyproject.toml
poetry add --group dev pytest   # dev-зависимость (тесты/линтеры) — в отдельную группу
poetry install                  # поставить всё из lock в окружение проекта
poetry run python main.py       # запустить в окружении проекта
```

- **`pyproject.toml`** — единый стандарт (PEP 518) описания проекта: зависимости, версии, метаданные. Заменяет связку `requirements.txt` + `setup.py`.
- **`poetry.lock`** — фиксирует **точные** версии всех зависимостей (включая транзитивные), чтобы у всех в команде и на сервере окружение было идентичным. Коммитится в гит.
- **Диапазоны версий** — `^1.2`: получать патчи и минорные обновления, но не ломающие мажорные.

> `pip` + `requirements.txt` проще и достаточно для небольших скриптов. Poetry (или очень быстрый **uv**) — для проектов, где важны воспроизводимость и разделение зависимостей на группы (prod/dev).

## if __name__ == "__main__"

У каждого модуля есть переменная **`__name__`**. Когда файл **запускают напрямую** (`python main.py`), `__name__` равно `"__main__"`. Когда его **импортируют** — `__name__` равно имени модуля. Отсюда идиома «код, который выполняется только при прямом запуске, а не при импорте»:

```python
def main():
    print("работаю")

if __name__ == "__main__":     # только при `python main.py`
    main()                     # при импорте этот блок пропускается
```

Проверка на практике:

```
python main.py     → __name__ == "__main__"   → блок выполняется
import main        → __name__ == "main"        → блок пропущен
```

Это позволяет файлу быть **и** запускаемым скриптом, **и** импортируемым модулем без побочных эффектов при импорте.

## Сквозной пример — структура проекта

Разложим программу по пакетам: главный скрипт `main.py` собирает части из пакета `application`.

```
проект/
├── main.py
└── application/
    ├── __init__.py
    ├── salary.py           # def calculate_salary()
    └── db/
        ├── __init__.py
        └── people.py       # def get_employees()
```

```python
# main.py — точка входа
from application.salary import calculate_salary
from application.db.people import get_employees
import datetime as dt

day = dt.date(2026, 2, 4)

if __name__ == "__main__":
    print(f"Сегодня {day}")
    calculate_salary()       # из application/salary.py
    get_employees()          # из application/db/people.py
```

Как читать: `main.py` лежит в корне и импортирует функции из пакета `application` и подпакета `application.db`. Запуск — из корня проекта (`python main.py`), тогда `application` виден в `sys.path`. Блок `if __name__ == "__main__"` делает `main.py` точкой входа: при импорте его код не сработает.

## Ловушки

```python
# Циклический импорт: a.py импортирует b, b.py импортирует a → ImportError.
# Фикс: вынести общее в третий модуль, либо импортировать внутри функции.

# Запуск из неправильной папки:
#   python application/main.py   ← 'application' может не найтись в sys.path
#   python main.py               ← из корня проекта — правильно
#
# import * внутри функции — SyntaxError: import * only allowed at module level.
# Звёздочка создаёт неизвестный заранее набор имён и мешает оптимизации локальных
# переменных. Внутри функции можно только точечно: def f(): from math import floor
```

> Модуль импортируется **один раз** за запуск: результат кэшируется в `sys.modules`, повторный `import` берёт готовый объект, а не выполняет файл заново.
