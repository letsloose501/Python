# Декоратор с состоянием

> **Декоратор с состоянием** — декоратор, который помнит что-то между вызовами обёрнутой функции: сколько раз её звали, когда звали в последний раз, что она вернула. Состояние живёт в замыкании, а чтобы его *менять*, обёртке нужно ключевое слово `nonlocal`.

---

Счётчик вызовов, лимит «не чаще N раз», retry с нарастающей паузой, кэш — всё это декораторы, которым мало обернуть один вызов: им нужно помнить прошлые. Вопрос только в том, где хранить память так, чтобы она не была общей на всю программу и не исчезала между вызовами.

## Где живёт состояние

Обёртка создаётся внутри декоратора и потому видит его локальные переменные — и продолжает видеть их после того, как декоратор давно отработал. Это и есть [замыкание](../Ядро%20языка/Функции%20Python.md#вложенные-функции-и-замыкания): переменная переживает функцию, в которой родилась.

```python
import functools

def counted(func):
    calls = 0                              # 1. создаётся ОДИН раз — при декорировании
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        nonlocal calls                     # 2. без этой строки будет ошибка, см. ниже
        calls += 1
        print(f"вызов №{calls}")
        return func(*args, **kwargs)
    return wrapper

@counted
def ping(): return "pong"

ping(); ping()      # → вызов №1, вызов №2
```

Ключевое — **когда что создаётся**: `calls = 0` выполняется один раз, в момент `@counted`; тело `wrapper` — на каждом вызове. Поэтому счётчик и не обнуляется.

## Зачем `nonlocal`

Уберём одну строку — и код упадёт, но не там, где ждёшь:

```python
def counted(func):
    calls = 0
    def wrapper(*args, **kwargs):
        calls += 1                 # ⚠️ без nonlocal
        return func(*args, **kwargs)
    return wrapper

@counted
def ping(): return "pong"
# при @counted — ошибки нет, функция создалась

ping()
# UnboundLocalError: cannot access local variable 'calls'
#                    where it is not associated with a value
```

Причина — правило области видимости: **любое присваивание делает имя локальным для всей функции**, на этапе компиляции и целиком, а не с той строки, где оно встретилось. `calls += 1` — это присваивание, значит `calls` объявлена локальной в `wrapper`; но значения ей ещё не дали, поэтому чтение в правой части падает. Внешняя `calls` при этом просто перестаёт быть видна.

Видно это прямо в скомпилированном коде:

```python
# без nonlocal:
wrapper.__code__.co_varnames    # → ('calls',)   ← локальная переменная
wrapper.__code__.co_freevars    # → ()           ← замыкания нет вовсе
wrapper.__closure__             # → None

# с nonlocal:
wrapper.__code__.co_varnames    # → ()
wrapper.__code__.co_freevars    # → ('calls',)   ← переменная внешней функции
wrapper.__closure__             # → (<cell at ...: int object>,)
```

`nonlocal` переводит имя из локальных в **свободные** — и обёртка начинает работать с той же ячейкой (`cell`), что и декоратор.

> Отсюда частый вопрос на собеседовании: **почему читать внешнюю переменную можно без `nonlocal`, а менять — нельзя?** Потому что чтение не создаёт локального имени, а присваивание создаёт. `if calls == 0: ...` работает и без объявления; `calls += 1` — уже нет.

## Четыре способа хранить состояние

`nonlocal` — не единственный вариант, и не всегда лучший.

```python
# 1. nonlocal — прямой способ для простого счётчика
def counted(func):
    calls = 0
    @functools.wraps(func)
    def wrapper(*a, **kw):
        nonlocal calls
        calls += 1
        return func(*a, **kw)
    return wrapper

# 2. Изменяемый объект — nonlocal не нужен: мы не присваиваем имя, а меняем объект
def counted(func):
    stats = {"calls": 0}
    @functools.wraps(func)
    def wrapper(*a, **kw):
        stats["calls"] += 1        # присваивания имени нет → имя остаётся внешним
        return func(*a, **kw)
    return wrapper

# 3. Атрибут обёртки — состояние видно и снаружи
def counted(func):
    @functools.wraps(func)
    def wrapper(*a, **kw):
        wrapper.calls += 1
        return func(*a, **kw)
    wrapper.calls = 0
    return wrapper

@counted
def work(): ...
work(); work(); work()
work.calls        # → 3   ← можно прочитать и сбросить из теста

# 4. Класс с __call__ — когда состояния много и нужны методы
class Counted:
    def __init__(self, func):
        functools.update_wrapper(self, func)   # аналог @wraps для класса
        self.func, self.calls = func, 0
    def __call__(self, *a, **kw):
        self.calls += 1
        return self.func(*a, **kw)
    def reset(self):
        self.calls = 0
```

| Способ | `nonlocal` | Состояние снаружи | Когда брать |
|---|---|---|---|
| `nonlocal` | нужен | скрыто | одно-два числа, ничего наружу не надо |
| Изменяемый объект | не нужен | скрыто | несколько полей разом |
| Атрибут обёртки | не нужен | **читается и сбрасывается** | нужны метрики и тесты |
| Класс с `__call__` | не нужен | через методы | много состояния, нужен `reset`/`stats` |

> Способ 2 — не хитрость, а следствие того же правила: `stats["calls"] += 1` меняет **объект**, а имени `stats` ничего не присваивает. Присваивания нет — значит, имя не становится локальным.

## Ловушка: на методе состояние общее для всех объектов

Самая дорогая ошибка темы. Декоратор применяется к **функции в теле класса** — один раз, до того как появится хоть один экземпляр. Значит, замыкание тоже одно на всех:

```python
def limit_calls(limit):
    def decorator(func):
        remaining = limit                  # ← создаётся при разборе класса, один раз
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            nonlocal remaining
            if remaining == 0:
                return "ЛИМИТ ИСЧЕРПАН"
            remaining -= 1
            return func(*args, **kwargs)
        return wrapper
    return decorator

class Client:
    @limit_calls(2)
    def send(self, msg): return f"отправлено: {msg}"

a, b = Client(), Client()
a.send("раз")     # → отправлено: раз
a.send("два")     # → отправлено: два
b.send("три")     # → ЛИМИТ ИСЧЕРПАН   ⚠️ другой объект, а лимит уже кончился
```

Новый клиент не получил свои два вызова: счётчик у метода общий на весь класс. Если лимит должен быть **на объект**, состояние надо хранить в самом объекте:

```python
@functools.wraps(func)
def wrapper(self, *args, **kwargs):
    счётчики = self.__dict__.setdefault("_limits", {})
    осталось = счётчики.get(func.__name__, limit)
    if осталось == 0:
        return "ЛИМИТ ИСЧЕРПАН"
    счётчики[func.__name__] = осталось - 1
    return func(self, *args, **kwargs)
```

> Та же природа у ловушки [`lru_cache` на методе](../Библиотеки/Модули/Функциональные%20инструменты/functools.md#три-ловушки-на-которых-lru_cache-ломается): кэш общий на класс, а `self` лежит в ключе и не даёт объекту умереть.

## Ловушка: состояние живёт до конца процесса

Замыкание создаётся при импорте модуля и не исчезает никогда. Для счётчика это неважно, для кэша — утечка памяти, для тестов — источник ложных падений: второй тест видит состояние, оставшееся от первого.

Лечится тем же, чем и всё остальное: способом 3 или 4, где есть чем сбросить — `wrapper.calls = 0` или `.reset()`. Именно поэтому у `lru_cache` есть `cache_clear()`.

## Практический пример: не чаще одного раза в N секунд

Декоратор из семейства «ограничить частоту» — хранит время последнего вызова:

```python
import time, functools

def throttle(interval: float):
    """Пропускает вызов не чаще одного раза в interval секунд."""
    def decorator(func):
        last = 0.0
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            nonlocal last
            прошло = time.monotonic() - last
            if прошло < interval:
                return None                     # слишком рано — пропускаем
            last = time.monotonic()
            return func(*args, **kwargs)
        return wrapper
    return decorator

@throttle(1.0)
def send_metric(value): print(f"отправлено {value}")

for i in range(5):
    send_metric(i)
    time.sleep(0.3)
# → отправлено 0 (t=0), отправлено 4 (t=1,2 с)
# вызовы 1, 2 и 3 пропущены: на них прошло 0,3 / 0,6 / 0,9 с — меньше секунды
```

Здесь `time.monotonic()` вместо `time.time()` намеренно: монотонные часы не прыгают назад при синхронизации системного времени.

> Это ограничение **на процесс**. Как только приложение поднято в нескольких экземплярах, счётчик у каждого свой, и общий лимит превышается кратно числу инстансов — тогда состояние выносят в [Redis](../Библиотеки/Сторонние/Redis.md) (подробнее про rate limiting).

## Состояние и асинхронность

В [асинхронной обёртке](../Ядро%20языка/Декораторы%20для%20асинхронных%20функций.md) состояние получает вторую проблему — гонку. Между чтением и записью может встрять `await`, и другая задача увидит устаревшее значение:

```python
async def wrapper(*args, **kwargs):
    nonlocal remaining
    if remaining == 0:                    # ← проверили
        return "ЛИМИТ ИСЧЕРПАН"
    result = await func(*args, **kwargs)  # ← здесь управление ушло другой задаче,
    remaining -= 1                        #   она тоже прошла проверку
    return result
```

Замер: при лимите 2 и пяти задачах, запущенных через `asyncio.gather`, выполняются **все пять**. Все успевают пройти проверку `remaining == 0` до того, как хоть одна дойдёт до `remaining -= 1`.

Лечится либо уменьшением счётчика **до** `await` (тогда между проверкой и изменением нет точки переключения), либо `asyncio.Lock` вокруг всей критической секции.

> Общее правило: в асинхронном коде опасен не сам `await`, а **проверка и изменение состояния, разделённые `await`**. То же самое, что «прочитал — записал» в многопоточном коде, только точки переключения видны глазами.
