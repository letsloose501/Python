# Управление памятью в Python

> _Ты не вызываешь `free()` — но память кто-то всё равно освобождает. Понять, кто и когда, — значит перестать удивляться утечкам._

---

**Управление памятью** — то, как интерпретатор выделяет память под объекты и забирает её обратно, когда объект больше не нужен. В C это делает программист вручную (`malloc`/`free`), в Python — сам рантайм, автоматически. Знать механизм нужно не ради теории: без него не объяснить, почему процесс «течёт», почему `del` не всегда освобождает память и почему циклы ссылок опасны.

Речь про **CPython** — стандартную реализацию. У неё два механизма, работающих вместе: основной — **подсчёт ссылок**, дополнительный — **сборщик мусора** для циклов.

## Всё — объект, у каждого объекта есть счётчик

В CPython любое значение — это структура **`PyObject`** в куче. У неё два обязательных поля:

- **`ob_refcnt`** — счётчик ссылок: сколько имён/контейнеров сейчас ссылаются на объект;
- **`ob_type`** — указатель на тип объекта.

```
x = []          PyObject списка:  ┌─────────────┐
                                  │ ob_refcnt=1 │  ← на него ссылается x
                                  │ ob_type=list│
                                  └─────────────┘
```

Переменная в Python — не «коробка со значением», а **имя-ссылка** на объект в куче. Присваивание `y = x` не копирует список — оно добавляет второе имя на тот же объект и увеличивает `ob_refcnt` до 2. Это прямое следствие модели «имя → объект» (см. [Операторы Python](../Ядро%20языка/Операторы%20Python.md#---присваивание)).

## Подсчёт ссылок (reference counting)

**Подсчёт ссылок** — основной механизм. Правило простое: как только `ob_refcnt` объекта падает до нуля, объект **немедленно** уничтожается, а его память освобождается.

Счётчик растёт и падает автоматически:

- **+1** — новая ссылка: присваивание, добавление в список/словарь, передача в функцию как аргумент;
- **−1** — ссылка исчезла: `del`, выход имени из области видимости, переприсваивание, удаление из контейнера.

```python
import sys

x = []
sys.getrefcount(x)   # → 2, а не 1: временную ссылку создаёт сам вызов getrefcount(x)
y = x
sys.getrefcount(x)   # → 3  (x, y и аргумент функции)
del y
sys.getrefcount(x)   # → 2
```

> `sys.getrefcount(obj)` всегда показывает **на 1 больше**, чем ты ожидаешь: аргумент функции — это ещё одна временная ссылка на объект.

**Плюс** подсчёта ссылок — детерминизм: память освобождается ровно в тот момент, когда объект стал не нужен, без пауз на «уборку». Именно поэтому в Python работает идиома `with` — файл закрывается сразу, как только объект теряет последнюю ссылку.

**Минус** — накладные расходы (каждая операция с объектом трогает счётчик) и **неспособность освободить циклы**.

## Проблема циклических ссылок

Подсчёт ссылок бессилен, когда объекты ссылаются **друг на друга**. Даже если снаружи на них никто не смотрит, их взаимные ссылки держат счётчики выше нуля — и память не освобождается.

```python
a = {}
b = {}
a["b"] = b       # a ссылается на b
b["a"] = a       # b ссылается на a  → цикл

del a, b         # внешних имён больше нет...
# ...но ob_refcnt каждого словаря = 1 из-за взаимной ссылки → refcounting их не тронет
```

```
    ┌───────┐        ┌───────┐
    │   a   │───────▶│   b   │
    │refcnt1│◀───────│refcnt1│
    └───────┘        └───────┘
     недостижимы снаружи, но счётчики не нули
```

Это классическая утечка. Ловит её второй механизм.

## Сборщик мусора (cyclic garbage collector)

**Сборщик мусора** (GC) — дополнение к подсчёту ссылок, которое находит и уничтожает **недостижимые циклы**. Он не заменяет refcounting, а подчищает то, что тот пропустил. Работает только с объектами, которые *могут* содержать ссылки (контейнеры: списки, словари, экземпляры классов); числа и строки цикл образовать не могут и GC их не отслеживает.

Идея: пройти по объектам, временно «вычесть» внутренние ссылки и посмотреть, у кого счётчик обнулился — те недостижимы снаружи, их можно удалить.

**GC поколенческий (generational).** Наблюдение: большинство объектов умирает молодыми (гипотеза о поколениях). Поэтому объекты делятся на **три поколения** (0 — молодое, 1, 2 — старое):

- новые объекты попадают в поколение 0;
- переживший сборку объект **повышается** в следующее поколение;
- младшие поколения проверяются часто и дёшево, старшие — редко.

Сборка запускается **по порогам** (не по таймеру): когда число «новых минус удалённых» объектов превышает лимит.

```python
import gc

gc.get_threshold()   # → (700, 10, 10)  пороги поколений 0, 1, 2
gc.get_count()        # → (N0, N1, N2)  текущие счётчики
gc.collect()          # принудительно собрать всё сейчас → число найденного мусора
gc.disable()          # выключить сборщик циклов (refcounting продолжит работать)
```

- поколение 0 собирается, когда счётчик аллокаций превысит **700**;
- поколение 1 — после **10** сборок поколения 0; поколение 2 — после 10 сборок поколения 1.

> **Версии.** До 3.13 GC поколенческий с тремя поколениями. В 3.14.0–3.14.4 его заменили на **инкрементальный** (короче паузы на больших кучах, два поколения), но из-за роста потребления памяти в проде откатили в **3.14.5** (май 2026) обратно к поколенческому из 3.13. Инкрементальный планируют вернуть в 3.16 через PEP. Актуально (3.13, 3.14.5+): **поколенческий, 3 поколения**.

### Финализаторы в циклах

Раньше объект с методом `__del__` внутри цикла GC собрать **не мог** (неясен порядок вызова финализаторов) — такой мусор оседал в `gc.garbage`. С Python 3.4 ([PEP 442](https://peps.python.org/pep-0442/)) это исправлено: циклы с `__del__` собираются. Но полагаться на порядок вызова `__del__` в цикле всё равно нельзя.

## Бессмертные объекты (immortal)

Некоторые объекты живут всё время работы программы: `None`, `True`, `False`, малые целые (−5…256), интернированные строки. С Python 3.12 ([PEP 683](https://peps.python.org/pep-0683/)) они **бессмертны** — их `ob_refcnt` зафиксирован специальным значением, и операции `+1/−1` их не трогают. Смысл: не гонять счётчик у объектов, которые всё равно никогда не удалятся, и дать потокам безопасно делить их без блокировок (задел под сборку без GIL, см. GIL).

## Куда уходит освобождённая память

Даже когда объект удалён, память **не всегда возвращается операционной системе**. Под мелкие объекты (≤ 512 байт) CPython использует свой аллокатор **pymalloc** с трёхуровневой иерархией:

```
арена (256 КБ у ОС) ─▶ пул (4 КБ, объекты одного размера) ─▶ блок (один объект)
```

Освобождённый блок возвращается в пул для повторного использования, но **арену** система забирает обратно, только когда та полностью пуста. Поэтому после обработки большого объёма данных RSS процесса может остаться высоким, хотя объекты удалены — память «осела» в аренах под будущие аллокации. Это не утечка, а стратегия переиспользования.

> Практический вывод: если пиковая нагрузка раздула процесс, память из арен вернётся не сразу. Для гарантированного возврата тяжёлую разовую обработку выносят в **отдельный процесс** ([multiprocessing](../Библиотеки/Модули/Параллелизм/multiprocessing.md)) — когда он завершится, ОС заберёт всю его память разом.

## Диагностика утечек

«Утечка» в Python — это обычно не потерянный указатель (как в C), а объект, который **случайно продолжают удерживать**: глобальный кэш, растущий список, замыкание, незакрытый ресурс. Инструменты — в заметке [Профилирование и отладка](../Библиотеки/Модули/Отладка%20и%20утилиты/Профилирование%20и%20отладка.md):

- **`tracemalloc`** (stdlib) — снимки распределения памяти, diff между двумя точками: где и сколько выделено;
- **`gc`** — `gc.get_objects()` (все живые объекты), `gc.get_referrers(obj)` (кто держит ссылку на объект);
- **`objgraph`** (сторонний) — рисует граф ссылок: наглядно видно, *что* не отпускает объект;
- **`sys.getsizeof(obj)`** — размер одного объекта в байтах (без вложенных).

```python
import tracemalloc

tracemalloc.start()
snap1 = tracemalloc.take_snapshot()
# ... подозрительный код ...
snap2 = tracemalloc.take_snapshot()
for stat in snap2.compare_to(snap1, "lineno")[:5]:
    print(stat)      # топ-5 строк по приросту памяти
```

### Слабые ссылки

**Слабая ссылка** (`weakref`) — ссылка, которая **не увеличивает** `ob_refcnt`. Объект удалится, как только исчезнут все *обычные* ссылки, даже если слабые ещё есть. Нужна для кэшей и наблюдателей, которые не должны продлевать жизнь объекту:

```python
import weakref

class Node: ...
n = Node()
r = weakref.ref(n)   # r не держит n живым
r()                  # → объект n (пока жив) или None (если уже удалён)
del n
r()                  # → None
```

## Ловушки

```python
# НЕПРАВИЛЬНО — глобальный кэш растёт без границ = утечка
_cache = {}
def get_user(uid):
    if uid not in _cache:
        _cache[uid] = load_from_db(uid)   # объекты копятся вечно, никто не чистит
    return _cache[uid]

# ПРАВИЛЬНО — ограниченный кэш, старое вытесняется
from functools import lru_cache
@lru_cache(maxsize=1024)                   # держит максимум 1024 записи
def get_user(uid):
    return load_from_db(uid)
```

> **`lru_cache` сам может держать объекты живыми.** Кэш хранит и аргументы, и результаты по сильным ссылкам — на методах экземпляра это удерживает `self` и живёт дольше объекта. Для таких случаев — `maxsize`, ручная чистка `.cache_clear()` или `weakref`.

Другие частые причины «роста памяти»: обработчики/колбэки, которые никто не отписал; замыкание, случайно захватившее большой объект; `list`, в который только добавляют.

## Сравнение: подсчёт ссылок vs трассирующий GC

|                       | Подсчёт ссылок                  | Трассирующий GC (циклы)     |
| --------------------- | ------------------------------- | --------------------------- |
| **Когда освобождает** | сразу при `ob_refcnt = 0`       | периодически, по порогам    |
| **Циклы**             | не видит                        | находит и собирает          |
| **Паузы**             | нет (размазан по коду)          | есть (стоп на время сборки) |
| **Накладные расходы** | на каждой операции со счётчиком | на обход объектов           |
| **В CPython**         | основной механизм               | дополнительный              |

CPython берёт лучшее от обоих: детерминизм подсчёта ссылок для 99% случаев плюс сборщик циклов как страховка. В Java/Go, наоборот, только трассирующий GC — отсюда паузы, но нет расходов на счётчики.
