# WSGI и ASGI — интерфейс сервера и приложения

> _Что происходит между nginx и твоим кодом._

---

**WSGI** и **ASGI** — договорённости о том, как веб-сервер передаёт запрос Python-программе и забирает ответ. Это не библиотеки и не сервер, а **соглашение о форме функции**: сервер обещает вызвать твою функцию определённым образом, ты обещаешь вернуть ответ в определённом виде. Благодаря этому любой сервер работает с любым фреймворком: gunicorn не знает про Django, Django не знает про gunicorn — оба знают WSGI.

## Проблема, которую это решает

Раньше каждый фреймворк дружил со своим способом запуска, и связка «сервер + фреймворк» была жёсткой: сменить сервер значило переписать приложение. В 2003 году **PEP 333** зафиксировал единый интерфейс (в 2010-м переписан под Python 3 как **PEP 3333**), и рынок разделился надвое:

- **сервер** умеет сеть, процессы, воркеров и не знает ничего о твоей бизнес-логике;
- **приложение** умеет бизнес-логику и не знает ничего о сокетах.

> Отсюда практический вывод: `gunicorn`, `uvicorn`, `waitress`, `mod_wsgi` взаимозаменяемы. Меняешь сервер — код приложения не трогаешь.

## Цепочка запроса

Где именно живёт интерфейс:

```
браузер ──HTTP──▶ nginx ──────▶ gunicorn ──[WSGI]──▶ Django/Flask ──▶ твоя view
                (reverse       (сервер        ↑
                 proxy,        приложений,    интерфейс: словарь + вызов функции
                 статика,      воркеры)
                 TLS)
```

[nginx](DevOps/nginx.md) отдаёт статику и терминирует TLS, **сервер приложений** держит пул процессов-воркеров, а **интерфейс** — это буквально момент вызова твоей функции. Твой код начинается там, где кончается стрелка.

## WSGI — синхронный интерфейс

**WSGI-приложение** — любой вызываемый объект двух аргументов, возвращающий итерируемое из байтов:

```python
def application(environ, start_response):
    статус = '200 OK'
    заголовки = [('Content-Type', 'text/plain; charset=utf-8')]
    start_response(статус, заголовки)              # отдать статус и заголовки
    return ['Привет'.encode('utf-8')]              # тело — только байты, только итерируемое
```

Три части контракта:

- **`environ`** — обычный словарь, в котором лежит **весь запрос**;
- **`start_response(status, headers)`** — функция сервера: ею отдают статус и заголовки;
- **возврат** — итерируемое из `bytes` (список, генератор). Не строка: строка тоже итерируемая, и сервер отправит её посимвольно.

### environ — весь запрос одним словарём

Ключи унаследованы от CGI, поэтому выглядят непривычно:

| Ключ | Что внутри |
|---|---|
| `REQUEST_METHOD` | `'GET'`, `'POST'` — метод |
| `PATH_INFO` | `'/users/42'` — путь |
| `QUERY_STRING` | `'page=2&sort=name'` — строка после `?` |
| `SERVER_NAME` / `SERVER_PORT` | хост и порт сервера |
| `SERVER_PROTOCOL` | `'HTTP/1.1'` |
| `HTTP_*` | заголовки запроса: `Authorization` → `HTTP_AUTHORIZATION` |
| `CONTENT_TYPE` / `CONTENT_LENGTH` | два заголовка-исключения — **без** префикса `HTTP_` |
| `wsgi.input` | поток тела запроса, читается `.read(n)` |
| `wsgi.url_scheme` | `'http'` или `'https'` |
| `wsgi.errors` | поток, куда писать ошибки (уходит в лог сервера) |

Заголовок превращается в ключ так: верхний регистр, дефисы в подчёркивания, спереди `HTTP_`. Отсюда `X-Request-Id` → `HTTP_X_REQUEST_ID`.

### Запустить без фреймворка

В стандартной библиотеке есть готовый WSGI-сервер — для отладки и для того, чтобы пощупать интерфейс руками:

```python
from wsgiref.simple_server import make_server

with make_server('', 8000, application) as сервер:
    сервер.serve_forever()          # http://localhost:8000
```

> `wsgiref` однопоточный и медленный — он для учёбы и тестов, в продакшн ставят gunicorn или uWSGI.

## Почему WSGI упёрся в потолок

Контракт синхронный: сервер вызвал функцию — воркер занят до `return`. Пока приложение ждёт ответа базы, процесс простаивает целиком. Отсюда три вещи, которых WSGI не умеет **в принципе**, а не «плохо умеет»:

- **WebSocket** — соединение живёт минутами, а WSGI знает только «один запрос → один ответ»;
- **долгие соединения** (Server-Sent Events, стриминг) — та же причина;
- **события жизненного цикла** — нет стандартного места «выполнить при старте и при остановке» (открыть пул соединений к БД, закрыть его).

## ASGI — асинхронный интерфейс

**ASGI-приложение** — корутина трёх аргументов. Вместо «дай ответ разом» здесь **обмен сообщениями**:

```python
async def application(scope, receive, send):
    assert scope['type'] == 'http'

    тело = b''                                  # 1. собрать тело запроса из событий
    while True:
        событие = await receive()
        тело += событие.get('body', b'')
        if not событие.get('more_body', False):
            break

    await send({                                 # 2. сначала статус и заголовки
        'type': 'http.response.start',
        'status': 200,
        'headers': [(b'content-type', b'text/plain; charset=utf-8')],
    })
    await send({                                 # 3. потом тело — можно частями
        'type': 'http.response.body',
        'body': 'Привет!'.encode('utf-8'),
    })
```

**Как это читать.** `scope` — постоянные данные соединения (метод, путь, заголовки). `receive` — «дай следующее входящее событие», `send` — «отправь исходящее». Ответ разбит на два сообщения не из вредности: заголовки уходят сразу, а тело можно слать кусками сколько угодно — так работает стриминг.

Запуск: `uvicorn app:application`.

### scope и события

| Поле `scope` (для http) | Что внутри |
|---|---|
| `type` | `'http'`, `'websocket'` или `'lifespan'` — какой это разговор |
| `method` | `'GET'` |
| `path` | `'/users/42'` |
| `query_string` | `b'page=2'` — **байты**, не строка |
| `headers` | список пар байтов, имена в нижнем регистре: `[(b'host', b'example.com')]` |
| `client` / `server` | `(ip, порт)` |

| Событие | Направление | Когда |
|---|---|---|
| `http.request` | `receive` | пришла часть тела запроса |
| `http.disconnect` | `receive` | клиент отвалился |
| `http.response.start` | `send` | отдаём статус и заголовки |
| `http.response.body` | `send` | отдаём тело (флаг `more_body` — «будет ещё») |

`type: 'lifespan'` — тот самый недостающий крючок старта и остановки: на нём построен `lifespan` в [FastAPI](Фреймворки/FastAPI.md).

## Сравнение

| | WSGI | ASGI |
|---|---|---|
| **Расшифровка** | Web Server Gateway Interface | Asynchronous Server Gateway Interface |
| **Стандарт** | PEP 3333 | спецификация проекта Django |
| **Приложение** | `def app(environ, start_response)` | `async def app(scope, receive, send)` |
| **Модель** | запрос за запросом, воркер занят до конца | конкурентно, воркер переключается на `await` |
| **Запрос лежит в** | словарь `environ` (CGI-имена) | словарь `scope` + события `receive` |
| **Ответ** | `return [b'...']` | `await send({...})` дважды и больше |
| **WebSocket, SSE, lifespan** | нет | да |
| **Точка входа** | `project/wsgi.py` | `project/asgi.py` |
| **Серверы** | gunicorn, uWSGI, waitress, mod_wsgi | uvicorn, hypercorn, daphne |
| **Фреймворки** | [Flask](Фреймворки/FLASK.md), [Django](Фреймворки/DJANGO/Django.md) (по умолчанию) | [FastAPI](Фреймворки/FastAPI.md), Starlette, Django Channels |

> ASGI **не быстрее сам по себе**. Он выигрывает там, где воркер простаивал бы в ожидании сети или базы. На чистом счёте (CPU-bound) разницы нет: [блокирующая работа](Библиотеки/Модули/Параллелизм/CPU-bound%20против%20IO-bound.md) держит процесс одинаково в обоих случаях.

## Middleware — почему интерфейс так удобен

Приложение — просто функция известной формы. Значит, её можно **обернуть другой функцией той же формы** — это [декоратор](Ядро%20языка/Декораторы%20Python.md) в чистом виде. Так устроены все middleware: логирование, авторизация, CORS, метрики.

```python
def логирующее(app):                                  # принимает WSGI-приложение
    def обёртка(environ, start_response):             # и возвращает WSGI-приложение
        print(environ['REQUEST_METHOD'], environ['PATH_INFO'])
        return app(environ, start_response)           # зовём оригинал
    return обёртка

application = логирующее(application)                 # цепочка собирается наложением
```

Обёртки складываются стопкой: `метрики(авторизация(логирующее(app)))` — запрос идёт сверху вниз, ответ поднимается обратно. Ровно поэтому в Django middleware настраиваются списком, а порядок в нём важен.

## Сквозной пример: мини-фреймворк на WSGI

Роутер с декоратором — примерно так устроен Flask внутри. Ни одной зависимости, только стандартная библиотека.

```python
# app.py
from wsgiref.simple_server import make_server

маршруты = {}                                   # (метод, путь) → обработчик

def route(метод: str, путь: str):               # 1. декоратор-регистратор
    def декоратор(обработчик):
        маршруты[(метод, путь)] = обработчик
        return обработчик                       # функцию не меняем, только запоминаем
    return декоратор

@route('GET', '/hello')                         # 2. регистрация происходит при импорте
def hello(environ):
    return '200 OK', 'Привет!'

@route('GET', '/health')
def health(environ):
    return '200 OK', 'ok'

def application(environ, start_response):       # 3. точка входа WSGI
    обработчик = маршруты.get((environ['REQUEST_METHOD'], environ['PATH_INFO']))

    if обработчик is None:                      # 4. маршрут не найден — 404
        статус, текст = '404 Not Found', 'Не найдено'
    else:
        статус, текст = обработчик(environ)

    тело = текст.encode('utf-8')                # 5. наружу уходят только байты
    start_response(статус, [
        ('Content-Type', 'text/plain; charset=utf-8'),
        ('Content-Length', str(len(тело))),
    ])
    return [тело]

if __name__ == '__main__':
    with make_server('', 8000, application) as сервер:
        сервер.serve_forever()
```

**Как это читать.** `@route` ничего не оборачивает — он **регистрирует** функцию в словаре в момент импорта модуля (декоратор выполняется сразу, не при вызове). `application` при каждом запросе достаёт обработчик по паре «метод + путь», а если не нашёл — отдаёт 404. Всё, что делает большой фреймворк сверху, — добавляет к этому парсинг параметров, шаблоны, сессии и ORM.

## Ловушки

```python
# НЕПРАВИЛЬНО — строка вместо списка байтов:
return 'Привет'          # сервер пройдётся по символам и отправит их по одному
# ПРАВИЛЬНО:
return ['Привет'.encode('utf-8')]

# НЕПРАВИЛЬНО — async def под WSGI-сервером:
async def application(environ, start_response):
    ...                  # gunicorn получит корутину вместо тела и упадёт
# ПРАВИЛЬНО: async-приложение запускают ASGI-сервером (uvicorn)
```

> **Заголовки после тела отправить нельзя.** `start_response` обязан быть вызван до того, как отдано первое тело — в ASGI то же самое выражено порядком сообщений (`http.response.start` строго перед `http.response.body`). Это не каприз интерфейса, а свойство HTTP: заголовки идут по проводу первыми.
