# Аутентификация — методы и протоколы

> _Половина путаницы в теме — оттого, что в один список кладут вещи разного уровня: способ передать пароль, формат токена и протокол доверия между компаниями._

---

**Аутентификация** — проверка, что запрос пришёл от того, за кого он себя выдаёт. Способов много, и они постоянно смешиваются в кучу: Basic и JWT ставят рядом с OAuth 2.0 и SSO, хотя это сущности трёх разных уровней.

Эта заметка раскладывает их по слоям: сначала три этапа проверки, затем методы передачи учётных данных, затем токены и, наконец, протоколы, которые вообще решают другую задачу.

---

## Три этапа: кто, докажи, что можно

```
идентификация  ──▶  аутентификация  ──▶  авторизация
   «кто ты?»        «докажи, что это ты»   «что тебе можно?»
   логин, id         пароль, токен          роли, права
                          ↓ не прошёл            ↓ прошёл, но не хватает прав
                        401 Unauthorized       403 Forbidden
```

Разница кодов ответа — самая частая ошибка в API: **401 означает «мы не знаем, кто ты»** (отсюда исторически неудачное название `Unauthorized`), **403 — «знаем, но нельзя»**.

> Авторизация — не продолжение аутентификации, а отдельная задача. Систему можно построить с аутентификацией без ролей (все равны) и с авторизацией без аутентификации (доступ по признаку сети или ключа, без личности).

## HTTP-схема: challenge — response

В HTTP есть **штатный механизм аутентификации** ([RFC 7235](https://datatracker.ietf.org/doc/html/rfc7235)), и он объясняет, почему одни методы «стандартные», а другие — нет.

```
клиент ── GET /users ─────────────────────────▶ сервер
       ◀─ 401 + WWW-Authenticate: Basic ───────┤   «нет данных — пришли по этой схеме»
       ── GET /users + Authorization: Basic … ─▶
       ◀─ 200 OK ─────────────────────────────┤
```

Сервер отвечает `401` и в заголовке `WWW-Authenticate` называет **схему**; клиент повторяет запрос с заголовком `Authorization: <схема> <данные>`. Меняется только содержимое — сам механизм один.

| Схема | Что передаёт клиент | Спецификация |
|---|---|---|
| **Basic** | логин и пароль в base64 | [RFC 7617](https://datatracker.ietf.org/doc/html/rfc7617) |
| **Digest** | хеш от пароля и параметров сервера | [RFC 7616](https://datatracker.ietf.org/doc/html/rfc7616) |
| **Bearer** | токен, факт владения которым и есть доказательство | [RFC 6750](https://datatracker.ietf.org/doc/html/rfc6750) |

**API-ключи и сессии в эту схему не попадают** — и именно поэтому их некорректно ставить в один список с Basic и Bearer. Ключ передают где угодно (`X-API-Key`, тело, cookie), а сессия вообще опирается на механизм cookie, а не на `Authorization`.

---

## Basic — логин и пароль в каждом запросе

```
Authorization: Basic YWxpY2U6c2VjcmV0      # base64("alice:secret")
```

**Base64 — не шифрование.** Перехватчик раскодирует строку одной командой и получит пароль в открытом виде. Поэтому Basic допустим **только поверх TLS** и только там, где нечего терять при утечке.

> Утверждение «Basic на практике не встречается» — преувеличение. Он жив в служебных API, интеграциях между сервисами, health-ручках и CI: настраивается в одну строку, а поверх TLS и с отдельной технической учёткой риск управляем. Не годится он для пользовательских сессий: пароль летит в каждом запросе и хранится у клиента постоянно.

---

## Digest — хеш вместо пароля

Сервер присылает разовый параметр (`nonce`), клиент считает от него и пароля хеш и отправляет результат. Пароль по сети не идёт.

Слабость не в самой идее, а в реализации и окружении:

- исходная версия ([RFC 2617](https://datatracker.ietf.org/doc/html/rfc2617)) построена на **MD5**; RFC 7616 добавил SHA-256, но поддержка в клиентах неровная;
- сервер обязан хранить пароль в виде, из которого можно посчитать тот же хеш, — то есть **обратимо или почти**;
- **атака понижения**: посредник подменяет `WWW-Authenticate: Digest` на `Basic`, и клиент послушно отправляет пароль открытым текстом.

Вывод простой: без TLS не спасает ни одна схема, а с TLS смысл Digest теряется — проще Bearer. В новых системах его не берут.

---

## Bearer — «предъявитель сего»

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIs…
```

Схема **предъявительская**: сервер не спрашивает, откуда токен, — сам факт владения считается доказательством. Отсюда единственный, но принципиальный риск: **утёкший токен работает у любого**, пока не истечёт.

> **Bearer ≠ JWT, и это главная путаница темы.** Bearer — *способ передать* токен (заголовок `Authorization`, слово `Bearer`, дальше строка). [JWT](JWT%20—%20подпись%20и%20проверка%20токенов.md) — *формат самого токена*. В Bearer можно положить что угодно: случайную строку на 32 байта, JWT, зашифрованный blob. Postman, где `Bearer Token` и `JWT Bearer` стоят двумя пунктами одного списка, ровно эту путаницу и закрепляет.

Отличие форматов практическое:

| | Случайная строка (opaque) | JWT |
|---|---|---|
| Проверка | поход в хранилище на каждый запрос | подпись проверяется локально |
| Отзыв | мгновенный — удалили запись | нельзя без списка отозванных |
| Нагрузка | запрос к БД или кэшу | ноль обращений |
| Данные о клиенте | лежат на сервере | лежат в самом токене |

## Access и refresh: зачем два токена

Из свойств Bearer следует конфликт: короткий срок жизни токена безопаснее, но заставляет пользователя логиниться каждый час. Решение — разделить обязанности.

- **Access-токен** — короткоживущий (минуты, до часа), ходит в каждом запросе, даёт доступ.
- **Refresh-токен** — долгоживущий (дни, недели), ходит **только** в ручку обновления и меняется на новую пару.

```
запрос с истёкшим access ──▶ 401
запрос с refresh ─────────▶ новый access + новый refresh
```

Три правила, без которых схема бессмысленна:

1. **Refresh хранится на сервере** (БД или [Redis](Библиотеки/Сторонние/Redis.md)) — иначе его нельзя отозвать. Это сознательный возврат к состоянию: короткие access-токены остаются stateless, длинный refresh — под контролем.
2. **В браузере refresh кладут только в `HttpOnly`-cookie.** В `localStorage` его прочитает любой скрипт, попавший на страницу через [XSS](Веб-безопасность.md#xss-cross-site-scripting). Cookie с `HttpOnly` из JavaScript не видна, а браузер сам приложит её к запросу на обновление. _Cookie при этом требует защиты от [CSRF](Веб-безопасность.md#csrf-cross-site-request-forgery) — флаг `SameSite`._
3. **Ротация с обнаружением повторного использования** — приём, которого в большинстве разборов нет: при каждом обновлении старый refresh инвалидируется, и если он приходит второй раз, значит его копия у кого-то ещё — вся цепочка сессий пользователя отзывается.

## API-ключи

Строка, выданная заранее и не связанная с логином: клиент не проходит вход, а просто предъявляет ключ.

```
X-API-Key: sk_live_51H8...
```

Похоже на Bearer, но отличия существенные:

- **выдаётся заранее** и обычно **не истекает** — живёт, пока его не отозвали;
- **не самодостаточен**: это случайная строка, и сервер обязан идти в хранилище, чтобы понять, чей он;
- **утечка не обнаруживается** — ключ работает, пока кто-то не заметит и не перевыпустит.

Отсюда обязательная гигиена: срок жизни и плановая ротация (их приходится вводить самим), область действия (scope) вместо «ключ на всё», отдельный ключ на каждую интеграцию, хранение только **хеша** ключа на сервере — как пароля.

Берут его за простоту: интеграция с внешним сервисом настраивается за минуту.

## Сессии

Классика веба: после входа сервер создаёт запись о сессии в хранилище и отдаёт клиенту только её идентификатор в cookie.

```
вход ──▶ сервер создаёт сессию ──▶ Set-Cookie: sid=a1b2c3; HttpOnly; Secure; SameSite=Lax
                 │
          [ Redis / БД ]  ← при каждом запросе сервер сверяет sid
```

Где хранят: [Redis](Библиотеки/Сторонние/Redis.md) — типовой выбор (быстро, есть TTL и вытеснение), реляционная БД — когда нужна история, память процесса — только для одного инстанса, файлы — legacy.

| | Сессии | Токены (JWT) |
|---|---|---|
| Состояние | на сервере (stateful) | в токене (stateless) |
| Отзыв | мгновенный | сложный |
| Цена запроса | обращение к хранилищу | локальная проверка подписи |
| Масштабирование | общее хранилище на все инстансы | ничего общего не нужно |
| Где уместно | классические веб-приложения | распределённые системы, мобильные клиенты, межсервисные вызовы |

> Ключевой размен формулируется одной фразой: **сессии платят обращением к хранилищу за возможность отозвать доступ, JWT платят невозможностью отзыва за скорость.** Гибрид «короткий access + серверный refresh» и есть попытка получить и то и другое.

## Слоем выше: OAuth 2.0, OIDC, SSO, SAML

Здесь и живёт самая грубая ошибка — назвать OAuth «методом аутентификации».

- **[OAuth 2.0](Библиотеки/Сторонние/Работа%20с%20WEB/Oauth%202.0.md)** — фреймворк **делегирования доступа**: приложение получает право работать с вашими данными в чужом сервисе. Токен отвечает на вопрос «что этому приложению разрешено», а **не** «кто пользователь». Личности в нём нет вовсе.
- **OpenID Connect (OIDC)** — тонкая надстройка над OAuth 2.0, которая добавляет ровно то, чего не хватало: **`id_token`** в формате JWT с данными о пользователе. Именно OIDC стоит за кнопкой «Войти через Google».
- **SSO (Single Sign-On)** — не протокол, а **свойство системы**: вошёл один раз — получил доступ ко всем связанным сервисам. Реализуется сессией у провайдера личности (Identity Provider), который подтверждает вход остальным.
- **SAML** — старший протокол обмена утверждениями о личности, на XML. Живёт в корпоративной среде (Active Directory, внутренние порталы); в новых внешних интеграциях его вытеснил OIDC.

```
OAuth 2.0  →  «что можно делать»          (авторизация)
   + OIDC  →  «кто это»                    (аутентификация)
   → SSO   →  «войти один раз на всё»      (сценарий поверх)
SAML / OIDC → протоколы, которыми провайдер подтверждает вход
```

## Чего в разборах обычно не хватает

Три темы, без которых картина неполная, — они относятся к аутентификации не меньше перечисленного.

- **Хранение паролей.** Любой метод, где пароль вообще существует, упирается в вопрос, как он лежит в базе: только медленная хеш-функция с солью ([Пароли — хранение и проверка](Пароли%20—%20хранение%20и%20проверка.md)).
- **Второй фактор.** Пароль — фактор знания; телефон с кодом (TOTP, [RFC 6238](https://datatracker.ietf.org/doc/html/rfc6238)) — фактор владения; отпечаток — фактор свойства. MFA требует факторов **разных категорий**: пароль плюс контрольный вопрос — это по-прежнему один фактор.
- **Passkeys (WebAuthn/FIDO2).** Современная замена паролю: устройство хранит закрытый ключ, сервер — открытый, и подписывается вызов сервера. Пароля не существует, поэтому его нельзя ни украсть из базы, ни выманить фишингом — подпись привязана к домену. Это направление, куда движется индустрия, и в разборах «7 методов» его обычно нет.

## Ловушки

- **Считать base64 защитой.** Ни в Basic, ни внутри JWT, ни в курсоре пагинации кодирование ничего не скрывает.
- **Ставить OAuth и JWT в один список с Basic.** Разные уровни: способ передачи, формат токена, фреймворк делегирования.
- **JWT в localStorage.** Любой XSS уносит и токен, и сессию целиком.
- **Отсутствие ротации refresh-токенов.** Один украденный refresh даёт бессрочный доступ.
- **API-ключ без области действия и срока.** Утечка навсегда, и обнаружить её нечем.
- **`401` вместо `403` и наоборот.** Ломает клиентов: на `401` они пытаются обновить токен, на `403` — нет.
- **Аутентификация без ограничения частоты.** Форма входа без лимита попыток — приглашение к перебору паролей.
